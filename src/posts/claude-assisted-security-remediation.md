공공 시스템의 SAST와 웹 취약점 점검에 대응하면서 Claude를 활용했다. 검출 건수가 많았고, JSP 출력부터 Java 예외 처리까지 서로 다른 코드의 맥락을 확인해야 했다.

내가 선택한 방식은 **검출 결과를 유형별로 나누고, 필요한 코드를 발췌해 Claude와 분석·조치안을 검토한 뒤 그룹별로 수정하는 것**이었다. 여러 세션을 활용했지만, 세션끼리 자동으로 작업을 전달하는 시스템을 구축한 것은 아니다. 코드와 분석 내용을 전달하고 조치 방향을 정하는 일은 내가 맡았다.

## 시작점은 프롬프트가 아니라 CodeRay 결과 분류였다

CodeRay는 정적 분석 도구다. 결과에 표시된 파일과 코드 위치를 출발점으로 삼되, 같은 CWE 번호라도 실제로 어떤 흐름에서 사용되는지 확인해야 했다.

예를 들어 JSP에서는 EL로 값을 출력하면서 적절한 출력 이스케이프가 적용되지 않은 부분들이 있었다. 같은 출력처럼 보여도 일반 문자열을 표시하는 곳과 에디터 HTML의 서식을 유지해야 하는 곳은 같은 방식으로 처리할 수 없었다.

예외 처리도 마찬가지였다. 광범위한 catch, 예외를 삼키는 코드, 의미 없이 다시 던지는 코드처럼 유형이 나뉘었다. 그래서 개별 검출 위치만 순서대로 고치기보다 **원인과 수정 방향이 비슷한 항목을 묶었다.**

| 분류 예시 | 검토할 맥락 | 관련 조치 기록 |
| --- | --- | --- |
| JSP 출력의 XSS 위험 | 출력 위치, 값의 출처, HTML 서식 유지 필요 여부 | [CWE-79 JSP 출력 개선](/blog/cwe-79-xss-remediation) |
| 부적절한 예외 처리 | catch의 책임, 실패 전달 방식, 호출자의 기대 동작 | [CWE-754 예외 처리 정비](/blog/cwe-754-exception-handling) |
| 공통 null 처리 | 공통 유틸과 호출부의 반환값 사용 방식 | [CWE-476 공통 원인 수정](/blog/cwe-476-null-dereference) |
| 미사용·샘플 코드 | 실제 진입점과 참조 관계 | [미사용 코드 정리](/blog/cwe-330-489-dead-code-removal) |

표는 기존 글의 조치 대상을 정리한 것이다. 모든 유형에 동일한 프롬프트나 동일한 수정 방식을 적용했다는 뜻은 아니다.

## 세션을 나눠 관련 코드와 분석 내용을 전달했다

취약점과 관련된 코드 부분을 발췌해 Claude에 전달했다. 한 세션에 모든 검출 결과를 계속 쌓기보다, 유형과 작업 맥락을 나눠 다뤘다. 분석, 조치안 검토·재설계, 구현, 디버깅에 AI를 활용하되 **분석 결과를 검토하면서 다음 수정으로 이어 갔다.**

작업 흐름을 정리하면 다음과 같다.

```text
CodeRay 결과 확인
  → 취약점 유형과 코드 패턴별 분류
  → 관련 코드 발췌·Claude 세션에 전달
  → 분석 결과 검토·조치 방향 정리
  → 그룹별 코드 수정·디버깅
  → 브라우저에서 동작을 함께 확인
  → 직접 재테스트·AS-IS 데이터와 대조
  → 이상 여부 확인 후 반영
```

세션을 나눴다는 사실보다 중요한 것은 **AI의 분석을 다음 단계의 확정된 사실로 바로 받아들이지 않았다는 점**이다. 분석 결과를 검토하고, 실제 화면과 데이터에서 기존 동작을 유지하는지 확인하는 과정까지 연결했다.

## 브라우저에서 함께 확인한 뒤, 다시 직접 테스트했다

Claude의 Chrome 브라우저 확장 기능을 활용해 화면을 함께 보면서 이동하고, 테스트 동작을 시각적으로 확인했다. 코드만 읽을 때 놓칠 수 있는 화면의 변화와 기능 흐름을 확인하는 과정이었다.

하지만 그 확인으로 검증을 끝내지는 않았다. **이후 내가 다시 테스트하고, DB에 누락된 데이터가 없는지 AS-IS 데이터와 대조했다.** 화면이 정상적으로 보이는 것과 데이터가 빠짐없이 처리되는 것은 별도로 확인해야 했기 때문이다.

| 검증 단계 | 실제로 확인한 내용 |
| --- | --- |
| Claude와 브라우저 확인 | 화면을 이동하며 기능 동작을 시각적으로 확인 |
| 직접 재테스트 | 수정한 기능을 다시 사용하며 이상 여부 확인 |
| 데이터 대조 | AS-IS 데이터와 비교해 DB에 누락된 데이터가 없는지 확인 |
| 반영 판단 | 위 확인에서 이상이 없을 때 반영 |

이 과정은 브라우저 테스트 전체를 자동화했다는 의미는 아니다. AI와 함께 확인한 과정에 **개발자의 재확인과 데이터 비교를 더한 방식**이었다.

## 내가 맡은 판단과 AI의 역할

AI는 코드의 문제를 분석하고 조치안을 검토하며 구현·디버깅을 진행하는 데 활용했다. 반면 작업을 어떤 단위로 묶을지, 어떤 맥락을 전달할지, 수정 결과를 반영할지는 내가 판단했다.

| 구분 | 역할 |
| --- | --- |
| Claude 활용 | 관련 코드 분석, 조치안 검토, 구현·디버깅, 브라우저 동작 확인 |
| 직접 수행 | 검출 결과 분류, 관련 코드 발췌·전달, 분석 결과 검토, 그룹별 수정 진행, 재테스트·데이터 대조, 반영 여부 판단 |

AI가 제안한 코드를 적용했다는 것만으로 내 역할을 설명하기는 어렵다. **실제 시스템의 맥락을 제공하고, 변경 결과를 검토하고, 기존 기능과 데이터가 유지되는지 확인하는 일**까지가 이 경험에서 강조하고 싶은 부분이다.

## 결과는 전체 조치의 성과로 설명한다

포트폴리오에 기록한 결과는 다음과 같다.

- CodeRay SAST 검출 건수 **358건 → 4건** 감소
- 별도 웹 취약점 **16건**, SQL Injection **14건** 조치
- 4개 환경 계정 설정 **17건** 암호화

이 수치는 AI만의 효과를 측정한 결과가 아니라, 코드 분석·구조 개선·미사용 코드 정리·반복 검증을 포함한 **전체 보안 조치의 결과**다. 서로 다른 점검 항목의 수치를 단순 합산하지 않으며, 정적 분석 검출 감소를 모든 보안 문제의 해소로 설명하지 않는다.

## 배운 점과 다음에 보완할 점

**작업을 나누는 기준이 AI 활용의 출발점이었다.** 건수가 많다는 이유로 결과 전체를 한꺼번에 전달하기보다, 같은 원인과 수정 방향을 가진 항목으로 묶었을 때 검토의 초점이 분명해졌다.

**세션 분리와 검증은 함께 가야 했다.** 분석·구현에 AI를 활용해도 화면 확인과 직접 재테스트, 데이터 대조는 별도로 필요했다. 실제로 어떤 검사를 통과했는지 설명할 수 있어야 변경 결과를 신뢰할 수 있었다.

다시 같은 작업을 한다면, 유형별로 확인한 원인·선택한 조치·재검사 결과를 짧은 공통 양식으로 남기겠다. 세션 사이에서 전달해야 할 맥락이 빠지지 않도록 하고, 직접 반복했던 검증 중 자동화할 수 있는 부분도 검토하겠다. 이는 당시 모두 구현한 체계가 아니라, 이번 경험에서 정리한 후속 개선 방향이다.
