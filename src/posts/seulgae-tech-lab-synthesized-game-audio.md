픽셀 연구소에 음악과 환경음을 붙이면서 외부 음원의 사용 조건을 관리하는 대신 직접 합성하는 방법을 선택했다. PR #39의 `d881492`는 파형을 만드는 코드와 게임에서 재생하는 코드를 분리한 사운드 시스템이다.

작업 기록에는 배경음악 6곡, 환경음 7종, 효과음 29종을 22,050Hz 모노로 생성했다고 남아 있다. 오디오 파일 다운로드는 없지만 합성 코드의 전송과 브라우저의 계산 비용까지 없어지는 것은 아니다.

## 샘플 배열을 기존 사운드 시스템에 연결하기

`synth.ts`는 파형과 배음을 합성해 Float32Array를 만든다. 음악의 루프 꼬리와 잡음의 경계를 처리해 반복 시 단절을 줄인다. 직접 만든 음원도 Phaser의 재생 기능을 재사용할 수 있었다.

현재 `frontend/src/audio/AudioManager.ts`의 캐시 등록 부분이다.

```ts
    const data = render()
    const buffer = this.game.sound.context!.createBuffer(1, data.length, SAMPLE_RATE)
    buffer.copyToChannel(data, 0)
    this.game.cache.audio.add(key, buffer)
```

합성 결과를 AudioBuffer로 넣고 이후에는 키로 재생한다. 같은 음원을 매번 다시 합성하지 않도록 캐시 확인을 앞에 둔다. 게임마다 매니저 하나가 채널과 재생 수명을 관리하고 방을 나가면 이전 소리를 페이드아웃한 뒤 정리한다.

## 같은 곡으로 방을 옮겼을 때 끊지 않기

사무실과 연구실처럼 같은 음악을 공유하는 공간도 있다. 같은 곡인데 이동할 때마다 처음부터 재생하면 반복 구간이 더 눈에 띈다. 같은 파일의 교차 전환 함수는 먼저 키를 비교한다.

```ts
    if (channel.key === key) { channel.base = base; this.applyVolumes(); return }
```

곡이 같으면 재생을 이어 가고 음량만 반영한다. 곡이 달라지면 기존 페이드 타이머를 정리하고 새 소리를 겹쳐 전환한다. 효과음에도 동시 재생 한도를 둬 입력이나 원격 이동이 몰릴 때 소리가 무한히 쌓이지 않게 했다.

## 키가 아니라 실제 이동 거리에 발걸음을 붙이기

방향키를 눌렀다는 이유만으로 소리를 내면 벽 앞에서도 걷는 소리가 난다. 현재 `frontend/src/audio/soundRules.ts`의 거리 검사다.

```ts
    const distance = Math.hypot(x - last.x, y - last.y)
    if (distance > this.teleport) { this.travelled = 0; return false }
    if (distance < 0.05) { this.travelled = 0; return false }
```

움직임이 없거나 순간이동에 가까운 변화는 발걸음으로 세지 않는다. 원격 캐릭터는 보간된 위치를 기준으로 거리 감쇠와 좌우 위치를 적용한다. 화면의 움직임과 소리가 같은 위치를 바라보도록 한 것이다.

설정은 전체·음악·효과·환경 카테고리로 나누고 localStorage에 저장한다. 음량 변경은 재생 중인 소리에도 바로 적용한다. 순수 규칙과 좁은 사운드 인터페이스 덕분에 가짜 매니저와 수동 타이머로 전환·중복·한도를 검사할 수 있었다.

## 재생 상태와 듣기 좋은 소리는 다르다

당시 개발 도구에서는 AudioContext 실행 상태와 곡 전환, 음소거·설정 저장을 확인했다. 그러나 실제 청각 품질은 확인하지 못했고 자동 재생 잠금도 내장 브라우저에서 재현하지 못했다. 잠금 흐름은 테스트 대역으로만 검증했다. 이번 글에서도 음질과 운영 브라우저의 자동 재생은 **확인하지 못함**이다.

## 배운 점

합성 데이터도 기존 오디오 캐시에 연결하면 재생 기능을 재사용할 수 있었다.
발걸음은 입력보다 실제 좌표 변화에 연결해야 자연스러웠다.
재생 상태 검증과 사람이 듣는 품질 평가는 별개의 확인이었다.
