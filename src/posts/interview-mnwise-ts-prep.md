## 1. 기업 및 직무 분석

엠앤와이즈(M&WISE)는 자체 메시징 솔루션 WiseU를 금융, 통신, 공공기관 등에 공급하는 B2B 기업이다. 주요 사업은 UMS, 대량 이메일, 클라우드 메시징, 카카오 비즈메시지, 모바일 전자문서 등이다.

UMS(Unified Messaging System)는 SMS, LMS, 이메일, PUSH, 알림톡 등 여러 메시징 채널을 통합 관리하는 시스템이다. 고객사로부터 발송 요청을 받아 메시지를 발송하고 결과 이력을 관리한다.

### TS팀 경력직 주요 업무

- 자사 솔루션 고객사 대응 개발
- 고객사에서 발생하는 솔루션 문제 해결
- Java 및 Spring 개발 경력 3년 이상, Linux 및 DB 이해 요구
- SI 및 고객 기술지원 경험, 커뮤니케이션과 침착한 상황 대응 능력 우대

채용공고를 기준으로 고객사 대응 개발과 트러블슈팅이 핵심인 직무로 판단했다. 실제 개발·기술지원 비중 및 내부 기술 스택은 면접에서 확인할 예정이다. 기업 정보와 공개 사례는 원문 대조 전이다.

## 3. 실무 경험 — 빌링 GW 연동 오류 개선

### 문제 및 조치

Kafka 기반 빌링 GW 연동 시스템에서 누적되는 오류를 분석했다. 모니터링 도구를 활용해 실패 패턴을 확인하고 오류 유형별 대응 절차를 문서화했다. 파트별 오류를 일일 단위로 집계하고 메일로 공유하는 보고 체계를 구축하여 담당 파트가 당일 오류를 확인할 수 있도록 개선했다.

### 성과

- 주간 연동 오류 약 70건 → 5건 수준(약 93% 감소)
- 파트별 오류 확인 및 대응 체계 개선

수치는 당시 주간 오류 규모의 어림값이다. Kafka 전체 구조를 단독 설계하거나 Exactly-once 처리를 구현한 경험은 아니다.

## 4. 실무 경험 — NURI2 메시지 자동 발송 배치

### 문제 및 조치

전세사기 피해자 심사 지연으로 의결기한을 초과한 대상자가 발생하고 심사 진행 상태에 관한 민원 문의가 증가했다. 대상자에게 안내 메시지를 자동 발송하고, 운영자가 발송 결과를 확인할 수 있는 기능을 구현했다.

### 발송 처리 구조

```text
새벽 배치 실행
  → 의결기한 도과 대상자 조회
  → 자체 발송 대상 관리 테이블 적재
  → Enum 템플릿 및 Builder 기반 발송 객체 생성
  → NURI2 DATA 테이블 적재
  → 오전 10시 예약 발송
  → 알림톡 실패 시 SMS/LMS 대체 발송
  → NURI2 LOG 테이블에 발송 이력 기록
  → 메시지 ID 기반 JOIN 및 운영자 화면 조회
```

| 구분 | 역할 |
| --- | --- |
| 자체 관리 테이블 | 발송 대상 및 Y/N 상태 관리, 미발송 대상 재처리 |
| NURI2 DATA 테이블 | 발송 대기 데이터 관리(DB 기반 큐) |
| NURI2 LOG 테이블 | 발송 결과 및 이력 관리 |

직접 개발한 영역은 대상 조회, 배치, 템플릿 관리, 발송 데이터 적재, 상태 관리, 미발송 재처리, 운영자 이력 조회 화면이다. 예약 발송과 채널별 실제 발송, 대체 발송은 NURI2가 제공한 기능이다.

운영 당시 실제 발송 실패 사례는 없었던 것으로 기억한다. 재처리는 실제 장애 해결 사례가 아니라 발송 실패 가능성을 고려한 설계 경험이다.

### 성과

- 일평균 30건의 안내 메시지 자동 발송
- 민원 문의 44건 → 31건(약 30% 감소)
- 운영자 발송 이력 조회 기능 구축
- 심사 결과를 기다리는 민원인의 불안감 완화에 기여

민원 문의 집계 기간과 측정 기준은 추가 확인이 필요하다. 감소 수치는 전후 비교 결과이며 배치 개발만의 효과로 단정하지 않는다.

## 5. 기술 면접 및 꼬리 질문 대비

| 학습 주제 | 확인할 내용 |
| --- | --- |
| Kafka 및 시스템 연동 | 연동 구조, 오류 발생 원인, 모니터링 및 대응 절차 |
| DB Queue | DATA/LOG 테이블 역할과 비동기 발송 방식 |
| Batch 및 Scheduling | 대상자 조회, 적재, 예약 발송 시점 분리 |
| Enum 및 Builder | 템플릿 관리 및 발송 객체 생성 |
| Transaction | DB 적재의 원자성, 커밋과 롤백의 범위 |
| Retry / Fallback | 미발송 재처리와 채널 대체 발송의 차이 |
| Idempotency | 중복 발송 방지 및 결과 미확인 시 처리 |

발송 여부가 N이라고 해서 반드시 실패한 것은 아니다. 발송 대기, 처리 중, 결과 미확인, 최종 실패를 구분해야 중복 발송을 방지할 수 있다. 트랜잭션 적용 범위와 재처리 세부 조건은 추가 복습 대상으로 남겨 둔다.
