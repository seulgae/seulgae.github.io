모든 방을 멀티플레이로 열어 두면 방 이동에도 서버 왕복이 필요했다. 혼자 책을 읽거나 사무실을 둘러보는 동안까지 연결 지연과 복구 상태를 겪게 됐다. PR #50의 `8f09b17`에서는 함께 있다는 의미가 큰 회의실만 실시간 공간으로 남겼다.

개발 로그의 시각은 대략값이어서 실제 커밋 시각으로 기록했다. 이번 변경은 보간 숫자를 다시 조절하는 작업보다 서버와 합의해야 할 행동 자체를 줄이는 선택이었다.

## 연결을 유지할 필요가 있는 순간을 좁히기

현재 `frontend/src/features/multiplayer/MultiplayerClient.ts`는 회의실 목적지일 때만 연결을 시작한다.

```ts
      this.online = true; this.joining = true; this.attempts = 0
      this.updateStatus({ travelling: true, roomError: undefined, phase: 'connecting', message: '회의실에 연결하는 중…' })
      this.connect()
```

처음 로비에서는 소켓을 열지 않는다. 혼자 이동하는 방은 기존 클라이언트 이동·충돌 로직을 사용하고, 회의실에 들어가면 서버 상태와 다른 참가자를 받는다. 채팅창도 회의실에서만 보인다. 연구 기록 같은 HTTP 기능은 소켓 연결 여부와 분리된다.

회의실을 나갈 때는 자동 재접속까지 멈추고 플레이어·입력 대기열·채팅 기록을 정리한다. 연결이 끊긴 것과 더 이상 연결을 원하지 않는 것을 다른 상태로 다룬다.

## 즉시 이동에도 다음 틱이 필요한 이유

서버를 기다리지 않는 이동은 빨라졌지만 같은 호출 안에서 방 변경을 알리면 Scene이 문 열림을 시작하기도 전에 전환할 수 있었다. 같은 파일의 로컬 이동이다.

```ts
    setTimeout(() => {
      if (this.disposed) return
      this.travelling = false
      this.enterLocal(target)
    }, 0)
```

네트워크 지연을 흉내 내는 목적이 아니라 문 연출과 Scene 전환의 실행 순서를 보장하기 위한 한 틱이다.

반대로 회의실 입장은 최대 15초 동안 기다린다. 연결이 잠깐 끊겼다는 이유만으로 이동 완료나 실패로 즉시 판단하지 않고 대기 상태를 유지한다. 정원 초과나 시간 초과라면 원래 문 앞에 남는다.

## 소켓이 사라진 방의 아이템은 어떻게 할까

기존 버리기·줍기는 서버가 아는 좌표와 소켓을 사용했다. 회의실 밖에서도 가방을 사용하려면 REST로 옮겨야 했다. 서버는 전달받은 방·좌표와 줍기 거리를 확인하지만, 혼자 있는 방의 실제 플레이어 위치를 계속 추적하지는 않는다. 통신 비용을 줄인 대신 좌표 신뢰의 제약이 생긴 것이다.

퇴장 시에는 다음과 같이 정상 종료한다.

```ts
      try { socket.close(1000, 'Left meeting room') } catch { }
```

당시 관제실의 참가자 목록도 REST 조회로 전환됐지만 이후 관리자실 변경에서 제거됐다. 현재 코드를 설명할 때는 이 후속 변화를 구분해야 한다.

기록에는 백엔드 81개·프런트 115개 테스트와 타입 검사, 로컬 방 이동 때 소켓이 없고 회의실 입장·퇴장 때만 연결되는 화면 확인이 남아 있다. 실제 두 기기의 만남과 운영 중계 경로 대기는 당시 확인하지 못했다. 이번 작성에서도 운영 검증은 **확인하지 못함**이다.

## 배운 점

모든 기능을 실시간으로 만들기보다 공유가 필요한 범위를 먼저 정해야 했다.
연결 종료에는 장애 복구와 의도된 퇴장이라는 서로 다른 의미가 있었다.
통신 방식을 바꾸면 기존 기능이 의존한 좌표 신뢰도 함께 다시 봐야 했다.
