현재 포트폴리오 사이트([`seulgae.github.io`](https://seulgae.github.io))의 **데이터 소스(`profile.js`, `projects.js`)**, **화면(`HomePage.jsx`, `ResumePage.jsx`)**, 그리고 **개별 기술 블로그 포스팅(`src/posts/*.md`)**을 시니어 테크 면접관 및 테크니컬 라이터 관점에서 교차 점검한 결과다.

이 문서는 코드를 바로 고치기 전에 **"어디가 왜 부족한지, 면접관이 어떤 지점을 파고들 수 있는지, 어떻게 고쳐야 하는지"**를 한눈에 보고 결정하기 위한 작업 지시서다.

## 2. 영역별 상세 분석 및 AS-IS → TO-BE 수정안

### 2-1. 프로필 및 자기소개 (`src/data/profile.js`)

- **현재(AS-IS)**:
  - `badge: "SI / SM Developer"`
  - `intro`: `"... SI / SM 중심의 백엔드 개발자입니다."`
- **부족한 점**:
  - 채용 담당자(특히 자체 서비스 기업·플랫폼 기업) 입장에서 `SI / SM`이라는 단어를 전면에 내세우면, 지원자가 가진 **쿼리 튜닝·데이터 정합성·아키텍처 리팩토링 역량**보다 '단순 유지보수 인력'이라는 선입견이 먼저 작동할 수 있다.
- **개선안(TO-BE)**:
  - `badge`를 **`"Backend · Operations & Performance"`** 등으로 변경하고, `intro`에서는 `"SI / SM 중심의"`라는 수식어 대신 **"엔터프라이즈 운영 환경의 병목과 불안정성을 데이터·실행계획·아키텍처 개선으로 해결해 온 백엔드 개발자"**로 정의한다.

#### ② `intro`와 `strengths`의 중복 제거 및 MECE 재구성
- **현재(AS-IS)**:
  ```text
  [intro] 운영 환경에서 발생하는 문제를 빠르게 수습하는 데서 끝내지 않고, 재발을 줄이는 구조 개선과 자동화까지 연결해온...
  ```

  - `strengths` 3줄이 각각 **성능(DB/Cache)**, **정합성(Kafka/DML)**, **보안·품질(SAST/자동화)**을 대표하도록 구체화한다.
  ```text

  [strengths 3] SAST 취약점 358건→4건 감축, 망간 동기화 정적 SQL 전환, SSH 기반 인프라 점검 자동화 등 레거시의 잠재 리스크를 구조적으로 제거합니다.
  ```

### 2-2. 프로젝트 경력 데이터 (`src/data/projects.js`)

`projects.js`는 **메인 화면(`/`), 프로젝트 상세(`/projects/:slug`), 출력용 이력서(`/resume`) 세 곳 모두의 단일 출처(SSOT)**다. 여기서 표현이 모호하거나 과장되면 모든 화면과 이력서가 함께 영향을 받는다.

#### ① CloudXper — `parallelStream` 서술의 정밀화 (면접 방어용)
- **현재(AS-IS)**:
  - `detail`: `"Java Parallel Stream 기반 병렬 처리 구조를 소스 전역 집계 로직에 적용하여 대용량 데이터 처리 성능 개선"`
- **왜 고쳐야 하는가**:
  - 실제로는 화면별로 복사돼 있던 `Map` 기반의 "목록 + 연관 리스트(N+1)" 조회 로직을 `ServiceImpl`로 모으고 거기에 `parallelStream`을 적용해 DB 대기 시간을 겹친 것이다. `"소스 전역 집계 로직에 적용"`이라고 쓰면 면접관이 *"DB I/O에 parallelStream을 전역으로 쓰면 공용 ForkJoinPool이 막히지 않나요?"*라고 바로 압박한다.
- **개선안(TO-BE)**:
  - `detail`: `"화면별로 파편화된 Map 기반 N+1 연관 조회 로직을 DTO·Model·ServiceImpl 계층으로 통합하고, 병렬 스트림을 적용해 순차 DB 왕복 대기 시간을 단축 (이후 쿼리 횟수 자체를 줄이는 집합 조회 방식으로 한계 복기)"`

#### ② LG U+ 빌링 GW — 누락된 핵심 기술 성과(Oracle 튜닝 · POI) 반영
- **현재(AS-IS)**:
  - 성과 3개: ① Kafka 오류 70건→5건 미만 ② 이기종 DB 인코딩(`SUBSTRB`) 95% 감소 ③ 청구 도메인 요금·위약금 조회 API 신규 개발.
  - 정작 블로그에서 가장 깊이 있게 다룬 **[Oracle 스칼라 서브쿼리 묵시적 형변환(`TO_NUMBER`) 실행계획 튜닝](/blog/oracle-hint-subquery-fullscan)**과 **[POI `XSSF` vs `SXSSF` 대용량 엑셀 다운로드 구현](/blog/sxssf-vs-xssf-excel-download)**이 `projects.js`에는 빠져 있다.
- **개선안(TO-BE)**:
  - 세 번째 성과를 보강하거나 네 번째 성과로 분리해, **종이 이력서(`/resume`)에도 Oracle 실행계획 튜닝과 대용량 스트리밍 엑셀 처리 경험이 명시**되도록 해야 한다.

#### ③ 전세사기 피해자 지원관리 — AI 유지보수 자동화 항목의 구체화
- **현재(AS-IS)**:
  - `detail`: `"전세사기 도메인 업무를 Markdown 기반 템플릿으로 정형화하고 AI 활용 개발 프로세스를 적용하여 기능 개발 속도 및 업무 처리 효율 개선"`
- **개선안(TO-BE)**:
  - `"복잡한 전세사기 접수·심사 상태 흐름, 테이블 관계, 망간 동기화 규칙을 Markdown 컨텍스트 문서로 구조화하여, AI 기반 영향도 분석 및 오류 재현 시간을 30~40% 단축"`처럼 **무엇을 구조화했는지**를 명시한다.

### 2-3. 개별 기술 블로그 포스팅 (`src/posts/*.md`) 보완 포인트

현재 19편의 블로그 원문은 솔직한 회고와 문제 해결 흐름이 매우 훌륭하지만, **이력서(`projects.js`)와 대조했을 때 숫자나 디테일이 살짝 비어 있는 5개 포스트**를 보강하면 완성도가 완벽해진다.

#### ① [`csql-nohup-mass-patch.md`](/blog/csql-nohup-mass-patch)
- **부족한 부분**:
  - 이력서(`projects.js`)에는 **"행안부 연계 CI값 14만 건 · 개인정보 이력 로그 370만 건, 총 384만 건 암호화, Damo 솔루션"**이라고 구체적인 수치가 적혀 있는데, 정작 블로그 본문에는 `"수백만 건"`, `"암호화 솔루션 함수"`라고만 추상적으로 적혀 있다.
- **보완할 내용**:
  - 도입부와 결과 섹션에 **CI값 14만 건 + 개인정보 이력 로그 370만 건(총 384만 건)** 규모의 실체와, 왜 두 테이블의 성격(마스터성 테이블 vs 대량 이력 테이블)에 따라 분할 커밋이 더 중요했는지 한 문단만 보강하면 이력서와 완벽히 아귀가 맞는다.

#### ② [`redis-permission-cache-ttl.md`](/blog/redis-permission-cache-ttl)
- **부족한 부분**:
  - 이력서에는 **"페이지 전환 및 렌더링 응답 속도 개선(10초 → 0.10초 이내), OAuth 인증·권한 정보"**라고 적혀 있으나, 블로그 본문에는 `"밀리초 미만으로 바뀌면서 화면 체감 렌더링이 눈에 띄게 빨라졌다"`라고만 되어 있고 **10초 → 0.10초**라는 정량 수치가 빠져 있다.
- **보완할 내용**:
  - 결과 섹션에 개선 전후 측정 수치(**10초 → 0.10초 이내**)를 명시하고, 추가로 면접 단골 질문인 **"로컬 캐시(Caffeine/Ehcache) 대신 왜 Redis 분산 캐시를 선택했는가(다중 인스턴스 환경에서 권한 변경 시 일관된 즉시 Evict 보장)"**를 2~3줄 덧붙이면 좋다.

#### ③ [`dynamic-to-static-sync-query.md`](/blog/dynamic-to-static-sync-query)
- **부족한 부분**:
  - 이력서에는 **"9개 테이블·97개 컬럼 정적 SQL 분기 재설계, SQL Injection 14건 해소"**라고 되어 있는데, 블로그 본문에는 대상 규모(`9개 테이블·97개 컬럼`, `14건 해소`) 숫자가 빠져 있다.
- **보완할 내용**:
  - 본문의 정적 쿼리 전환 섹션에 **"연계 대상 9개 테이블(총 97개 컬럼)을 전수 조사해 정적 statement로 재작성했고, 국자원 웹 취약점 점검 기준 SQL Injection 14건을 모두 해소했다"**는 문장을 넣어 이력서 성과와 1:1로 일치시킨다.

#### ④ [`kafka-gw-data-integrity.md`](/blog/kafka-gw-data-integrity)
- **부족한 부분**:
  - 이력서의 핵심 성과인 **"WhaTap 히트맵 기반 모니터링 및 대응 시나리오 매뉴얼화로 주간 Kafka 오류 70건 → 5건 미만(93% 감소)"**과 **"Oracle ↔ MySQL 인코딩 바이트 차이(`SUBSTRB`) 해결로 인코딩 오류 95% 감소"** 내용이 블로그 원문에서는 빠져 있거나 약하게 다뤄져 있다.
- **보완할 내용**:
  - 운영 대사(DI) 섹션에 **① WhaTap과 대사로 분류한 오류 4대 패턴(발행 누락, 순서 역전, 인코딩 `SUBSTRB` 길이 초과, 신규 컬럼 누락)**과 **② 이를 표준화해 주간 70건이던 오류를 5건 미만으로 줄인 결과**를 명시하면 블로그 글의 설득력이 배가된다.

### 2-4. 블로그 목록 노출 관리 (`interview-*` 포스트 분리 여부)

- 현재 `src/posts/` 안에 면접 대비용으로 만든 3개의 요약 포스트(`interview-jeonse-support-system.md`, `interview-cloudxper-billing.md`, `interview-lgu-billing-gw.md`)가 들어 있다.
- `src/lib/posts.js`는 `src/posts/*.md`의 모든 파일을 읽어 `/blog` 목록 최상단에 노출하므로, 만약 **인사담당자가 `/blog` 탭을 눌렀을 때 `'면접 정리 1·2·3'`이라는 제목이 보이는 것을 원치 않는다면**:
  1. `posts.js`에서 `hidden: true` 프론트매터 옵션을 추가해 일반 `/blog` 목록에서는 숨기고, 본인이 직접 주소(`/blog/interview-...`)로 들어갈 때만 보이게 처리하거나,
  2. 파일 제목을 `[면접 정리]` 대신 **`[프로젝트 회고] 전세사기 피해자 지원관리시스템 — 아키텍처 의사결정과 트러블슈팅 총정리`**처럼 인사담당자가 읽어도 자연스러운 **프로젝트 종합 회고록(Case Study)** 톤으로 바꾸는 방법 중 하나를 선택하면 된다.
