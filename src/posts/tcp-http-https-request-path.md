# TCP/IP부터 HTTP·HTTPS까지 요청이 지나가는 경로

## 1. 학습 배경

외부 솔루션 연동을 설명할 때 연결이 됐다는 말과 업무가 끝났다는 말을 분리하려 한다. HTTPS 홈서버 학습과 고객사 업무 경험은 구분하며 특정 고객사 네트워크를 재현하지 않는다.

## 2. 핵심 개념

IP는 패킷 주소와 전달 경로를, TCP는 연결 위의 순서 있는 바이트 스트림을 제공한다. HTTP는 요청·응답의 메서드·상태·헤더·표현 의미를 정의한다. HTTPS는 TLS로 보호한 HTTP 통신이다. 계층마다 해결하는 문제가 다르다.

TCP는 애플리케이션 메시지 한 건의 경계를 보존하지 않는다. 한 번 쓴 데이터가 한 번의 read로 그대로 반환된다고 가정하면 안 된다. [TCP 명세](https://www.rfc-editor.org/rfc/rfc9293.html)가 설명하는 바이트 스트림의 성질이다.

## 3. 동작 원리

```text
HTTPS 요청(일반적인 HTTP/1.1·HTTP/2 over TCP)
  → 이름 해석 → TCP 연결 → TLS 핸드셰이크
  → HTTP 요청 → 프록시·앱 → HTTP 응답
```

TLS는 인증서와 키 교환 등을 통해 상대 인증과 암호화·무결성 보호를 제공한다. 보통 서버 인증을 하며 클라이언트 인증은 별도 설정이다. [TLS 1.3 명세](https://www.rfc-editor.org/rfc/rfc8446.html)를 참고하되 프로토콜 세대별 핸드셰이크 차이는 남겨 둔다.

HTTP/3는 QUIC 기반이어서 모든 HTTP를 TCP 위라고 일반화하지 않는다. HTTP의 상태 없는 의미는 서버가 세션·DB 상태를 전혀 저장할 수 없다는 뜻도 아니다. 의미 체계는 [HTTP 명세](https://www.rfc-editor.org/rfc/rfc9110.html)를 기준으로 한다.

## 4. 실무 활용

**학습용 연동 상황:** 타임아웃 후 서버가 실제 처리를 마쳤을 수 있다. TCP 재전송은 전송 계층의 복구이고, 애플리케이션 요청을 새로 보내는 재시도는 업무 효과를 다시 만들 수 있다. 요청 식별자와 멱등성을 함께 설계한다.

프록시에서 TLS를 종료하면 이후 내부 통신이 HTTP인지 HTTPS인지 별도다. 클라이언트↔프록시의 보호를 프록시↔앱까지 무조건 확장해서 설명하지 않는다. 연결·TLS·응답 타임아웃도 나눠 관측한다.

## 5. 주의사항 및 오개념

HTTPS는 SQL Injection·권한 오류·XSS를 자동으로 막지 않는다. TCP ACK는 상대 애플리케이션의 DB 커밋 확인이 아니다. 연결 재사용은 요청마다 TCP·TLS를 반드시 새로 맺는다는 모델과 다르다. 인증서 검증은 암호화만큼 중요하며 이름·체인·유효기간을 확인한다.

| 질문·의도 | 핵심을 담은 구어체 답변 | 꼬리 질문 |

| TCP와 HTTP 차이는? 계층 이해 | “TCP는 순서 있는 바이트 전달이고 HTTP는 그 위의 요청·응답 의미예요. 전달 성공과 업무 성공은 다르게 보겠습니다.” | 메시지 경계는 누가 정하나? |

## 7. 핵심 요약

전달·암호화·HTTP 응답·업무 효과의 보장을 분리한다. 장애를 프로토콜 한 단어로 설명하기보다 실패 경계를 찾는다.
