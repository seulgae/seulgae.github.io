테이블 이름을 바꾸는 작업은 [호환 뷰를 이용해 단계적으로 전환](/blog/seulgae-tech-lab-table-rename-compatibility-views)하도록 설계했다. 하지만 PR #93과 #94가 연이어 병합될 당시 운영 DB는 아직 V16이었다. 개발 로그와 #95·#96의 기록을 따라, 안전장치가 각각 동작했음에도 다음 단계로 갈 수 없었던 이유를 복기했다.

## 배포와 마이그레이션이 서로 다른 이유로 막혔다

#94의 새 릴리스는 DB V17~V18을 지원한다. 배포 도구는 호환되는 과거 릴리스를 찾지 않고 최신 main 릴리스를 선택했기 때문에 V16 DB에 해당 릴리스를 배포하지 못했다.

동시에 서버 체크아웃의 마이그레이션 도구는 최신 목표인 V18을 기준으로 동작했다. 당시 실행 중인 앱은 V18을 지원하지 않아 마이그레이션도 거부됐다. 각 검사는 호환되지 않는 조합을 막았지만, 결과적으로 V17을 적용할 수 있는 중간 릴리스가 선택되지 않는 상태가 됐다.

개발 로그와 PR에는 **기존 서비스와 DB는 유지됐고 배포·마이그레이션 경로가 막혔다**고 기록돼 있다. 데이터가 손상됐다고 확대하지 않는다.

## 되돌린 뒤 중간 단계를 거친다

#95에서 #94의 변경을 일시적으로 되돌려 최신 릴리스의 호환 범위와 목표를 V17까지로 되돌렸다. 그 릴리스를 배포하고 V17을 적용한 뒤, #96에서 원래 변경을 다시 반영했다. 이후 V18에서 호환 뷰를 제거하고 릴리스 범위를 좁히는 순서다.

개발 로그와 #98 본문에는 운영 V18 적용이 기록돼 있다. #98의 18..18 릴리스 고정은 이후 main에 병합됐다. 이 글 작성 과정에서 운영 DB를 직접 조회하지는 않았다.

이번 경험에서 확장 PR의 병합과 실제 마이그레이션은 서로 다른 단계였다. 사용 코드의 PR을 준비해 두더라도 운영 스키마 적용 확인 전 병합하면 중간 호환 릴리스가 최신 선택 대상에서 밀릴 수 있다. 다음에는 적용 확인까지 사용 PR을 Draft로 두는 절차를 기록했다.
