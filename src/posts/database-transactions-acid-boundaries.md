## 1. 학습 배경

NURI2 복기의 대상 등록과 발송 DATA 적재를 설명하려면 무엇이 함께 성공해야 하는지부터 정해야 한다. 이 글은 일반 트랜잭션 원리이며 당시 적용 범위는 소스·DB 설정 확인이 필요한 사실로 남긴다.

## 2. 핵심 개념

트랜잭션은 여러 DB 작업을 하나의 완료 단위로 다루는 경계다. ACID는 다음 성질을 설명한다.

| 성질 | 의미와 한계 |
| --- | --- |
| 원자성 | 단위 안의 변경이 함께 완료되거나 취소됨 |
| 일관성 | 제약과 올바른 업무 로직을 통해 유효한 상태를 유지함 |
| 격리성 | 동시 작업의 간섭을 정해진 수준으로 제어함 |
| 지속성 | 성공적으로 완료된 변경을 장애 뒤에도 보존함. 구체 보장은 설정·장애 범위에 따름 |

일관성은 DB가 모든 업무 규칙을 알아서 판단한다는 뜻이 아니다. 업무 검증과 제약 조건 설계가 필요하다.

## 3. 동작 원리

```text
트랜잭션 시작 → 검증·조회 → 여러 변경
  ├─ 성공: COMMIT
  └─ 실패: ROLLBACK
```

DB는 로그·동시성 제어 등의 기법으로 성질을 구현한다. PostgreSQL은 WAL과 복구를 사용하지만 commit 지속성은 동기화 관련 설정까지 확인해야 한다. 일반 원리는 [트랜잭션 안내](https://www.postgresql.org/docs/17/tutorial-transactions.html), 동시 실행은 [격리 수준 안내](https://www.postgresql.org/docs/17/transaction-iso.html)와 연결한다.

## 4. 실무 활용

**학습용 예제:** 같은 DB와 같은 트랜잭션에서 관리 행과 발송 대기 행을 기록하면 한쪽 실패 시 함께 취소하는 설계가 가능하다. 단, 별도 연결·별도 DB·별도 트랜잭션이면 애너테이션 하나로 그 원자성이 생기지 않는다.

DB 커밋 후 외부 발송에 실패하거나, 발송은 됐는데 결과 응답이 유실되는 문제는 로컬 DB 롤백만으로 해결할 수 없다. 대기 작업과 처리 결과를 추적하고 재시도·멱등성 같은 별도 설계가 필요하다. 이것이 당시 outbox 패턴을 구현했다는 주장은 아니다.

## 5. 주의사항 및 오개념

긴 트랜잭션 안에서 외부 HTTP 응답을 기다리면 연결·잠금 보유 시간이 늘어날 수 있다. 짧게 나누기만 해도 원자성이 깨질 수 있어 실패 시나리오를 함께 설계한다. autocommit 환경의 개별 문장 성공과 업무 전체의 commit을 혼동하지 않는다.

## 6. 기술 면접 예상 질문

| 질문·의도 | 핵심을 담은 구어체 답변 | 꼬리 질문 |
| --- | --- | --- |
| ACID를 설명해 달라면? 의미 | “여러 변경의 원자적 완료, 유효 상태 유지, 동시성 제어, 완료 데이터 보존으로 설명하겠습니다. 각 보장은 경계와 설정을 확인해야 해요.” | 업무 일관성은 누가 보장하나? |
| DB 롤백으로 문자도 취소되나? 자원 경계 | “이미 외부에 전달된 발송은 로컬 DB 롤백으로 취소되지 않아요. 발송 상태와 결과 확인·재처리를 따로 설계해야 해요.” | 응답만 유실되면? |
| 트랜잭션을 짧게 하는 이유는? 자원 | “연결과 잠금 유지 시간을 줄이기 위해서예요. 다만 분리 후 부분 성공을 어떻게 처리할지도 같이 정하겠습니다.” | 같은 DB라도 연결이 다르면? |
