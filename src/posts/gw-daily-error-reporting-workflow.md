GW 연동을 운영하면서 모니터링 화면에 남은 실패 내역을 매일 확인했다. 이벤트 처리 순서가 맞지 않거나, 문자열이 대상 컬럼의 바이트 길이를 넘거나, 발행된 데이터의 정합성이 맞지 않아 연동에 실패하는 경우가 있었다.

그런데 원인을 알아도 처리가 끝나지 않는 일이 있었다. 실패 내역은 연동 파트에서 보고 있지만, 실제로 어떤 값이 맞는지 판단하고 조치해야 하는 사람은 해당 업무 데이터를 다루는 파트의 운영자였다. 이 사이에서 보정 요청이 연동 파트로 다시 돌아오고, 오류는 미처리 상태로 남았다.

**내가 바꾼 것은 미처리 오류를 정리하고 전달하는 방식이었다.** 파트별 오류와 조치가 남은 내역을 표로 만들고, 담당 운영자들에게 매일 메일로 공유했다. PL과 PM도 참조에 포함해 같은 현황을 볼 수 있게 했다.

## 실패 건수만으로는 다음 행동이 정해지지 않았다

모니터링에 연동 실패가 10건 남아 있다고 하자. 건수만 전달하면 담당자는 그중 어느 건을 자신이 봐야 하는지, 무엇을 확인해야 하는지 다시 찾아야 한다. 다음 날에도 같은 건이 남아 있다면 새로 발생한 오류와 미처리 오류를 구분하는 일부터 반복하게 된다.

당시 확인했던 오류 유형은 다음과 같았다. 아래 표는 원인별 확인 관점을 정리한 것이다.

| 오류 유형 | 확인할 내용 |
| --- | --- |
| 이벤트 처리 순서 문제 | 현재 이벤트를 처리하는 데 필요한 선행 데이터가 준비되어 있는지 |
| 이기종 DB의 인코딩·컬럼 바이트 초과 | 원천 값과 대상 컬럼의 길이·문자셋 조건이 맞는지 |
| 신규 컬럼·매핑 누락 | 발행 데이터와 대상 테이블을 연결하는 규칙이 반영되어 있는지 |
| 발행 누락·원천 데이터 불일치 | 필요한 데이터가 발행되었는지, 발행 값이 실제 업무 데이터와 맞는지 |

WhaTap 히트맵과 로그는 실패 패턴을 분석하는 데 활용했고, 메시지 저장 내역과 GW 모니터링 화면에서 오류 건수와 세부 데이터를 확인했다. GW의 변환·매핑 구조는 [Kafka 데이터 정합성 글](/blog/kafka-gw-data-integrity)에 정리해 두었다.

내가 운영 업무에서 해결해야 했던 문제는 그다음이었다. **확인한 원인을 누가 판단하고, 어떤 조치로 이어갈 것인가.**

## 보정 도구가 있어도 업무 데이터의 판단은 필요했다

MySQL과 Oracle에서 데이터를 조회하고, 결과값을 연동에 필요한 매핑값으로 변환해 맞춰 주는 별도의 보정 프로그램이 있었다. 이 도구를 이용해 실패 데이터를 맞출 수 있었지만, 도구의 존재만으로 모든 조치를 연동 파트에서 결정할 수 있는 것은 아니었다.

예를 들어 발행 측에서 정합성이 맞지 않는 값을 보냈다면, 우선 해당 파트에서 실제 운영 데이터와 업무 기준을 확인해야 했다. 기술적으로 대상 테이블에 넣을 수 있는 값과 업무상 올바른 값은 함께 확인해야 했다.

각 파트의 운영자들은 그 데이터로 실제 업무를 처리하고 있었다. 따라서 값의 의미와 수정 영향을 판단할 수 있는 담당자가 확인해야 한다고 생각했다. 연동을 성공시키기 위해 내가 임의로 운영 데이터를 수정하는 방식은 선택하기 어려웠다.

당시에는 이런 보정 요청이 연동 파트로 몰리기도 했다. 나는 연동 실패 원인과 확인에 필요한 정보를 정리하되, 업무 데이터의 판단과 조치는 담당 파트에서 진행하도록 연결하고자 했다.

## 담당 배분과 미처리 현황 공유를 연결했다

청구·과금 파트의 PM들이 실패 데이터별 담당 운영자를 배분해 관리했다. 나는 그중 **실패로 남아 있으면서 아직 조치되지 않은 내역을 빠뜨리지 않고 공유하는 역할**에 집중했다.

업무 흐름은 다음과 같았다.

```text
메시지 저장 내역·GW 화면에서 실패 데이터 확인
  → 로그와 데이터로 원인 확인
  → 담당 파트와 조치가 남은 내역을 표로 정리
  → 각 파트 운영자에게 일일 메일 공유 · PL/PM 참조
  → 담당 파트에서 업무 데이터 확인·조치
  → GW 모니터링과 대사로 반영 결과 재확인
```

메일에는 실패가 발생했다는 사실과 함께 어느 파트에서 확인해야 하는지, 무엇이 아직 처리되지 않았는지를 담았다. 운영자는 자신이 확인할 건을 찾을 수 있고, PL·PM은 파트별로 남은 일을 함께 검토할 수 있도록 했다.

참조에 관리자를 포함한 목적은 동일한 미처리 현황을 기준으로 대응하기 위해서였다. 담당자에게 전달한 요청과 관리자가 보는 현황이 같아야 후속 확인도 이어갈 수 있었다.

## 표에는 담당자가 다음에 할 일을 담았다

보고 자료는 엑셀로 정리했다. 오류 목록을 길게 전달하는 데서 끝내지 않고, 담당 파트가 확인할 내용을 읽을 수 있도록 정리하는 것이 중요했다.

아래는 당시 공유 방식의 취지를 설명하기 위한 예시다. 실제 메일의 원본 양식이나 운영 데이터는 아니다.

| 확인 대상 | 원인·현재 상태 | 담당 파트에 요청할 내용 |
| --- | --- | --- |
| 선행 데이터가 없는 연동 실패 | 현재 이벤트 처리에 필요한 데이터 확인 필요 | 선행 데이터의 존재·발행 여부 확인 |
| 대상 컬럼 길이를 초과한 값 | 원천 값과 대상의 바이트 길이 조건 불일치 | 업무상 유지할 값과 보정 가능 범위 확인 |
| 원천·대상 데이터 불일치 | 발행 값과 업무 데이터의 정합성 확인 필요 | 올바른 값 판단 후 보정 프로그램을 통한 조치 검토 |

실무에서는 여기에 해당 오류를 찾을 수 있는 식별 정보와 담당 파트가 연결되어야 한다. 메일을 받은 사람이 오류를 다시 찾고 원인을 처음부터 파악하는 부담을 줄이려는 관점이다.

이상하거나 특이한 데이터는 바로 처리하기 어려웠다. 이런 건도 남아 있는 이유와 확인할 내용을 함께 공유해, 미처리 목록에서 사라지지 않도록 했다.

## 잔여 오류는 발행 파트의 수정과 재발행으로 맞췄다

오류가 5건 수준으로 줄어든 뒤에도, 발행 데이터 자체를 수정해야 하는 건이 남았다. 모델명에 연동 처리가 받아들이지 못하는 특수기호가 포함되거나, 대상 테이블의 `NOT NULL` 컬럼에 대응하는 값이 `null`로 발행된 경우가 있었다. 이런 건은 발행 측에서 전달한 값과 연동 대상의 조건을 함께 확인해야 했다.

나는 해당 건을 발행 파트에 직접 메일로 전달하고, 문제가 되는 값을 수정한 뒤 다시 발행해 달라고 요청했다. 어떤 데이터와 항목에서 실패했는지, 어떤 조건에 맞지 않았는지를 전달해 발행 담당자가 확인할 수 있도록 했다.

```text
잔여 실패 데이터 확인
  → 특수기호·필수값 누락 등 원천 값의 문제 확인
  → 발행 파트에 직접 메일로 수정·재발행 요청
  → 발행 파트에서 데이터 수정 후 재발행
  → 재연동 결과를 확인하며 원천·대상 데이터 정합성 맞춤
```

모델명의 특수기호는 해당 데이터와 연동 조건에서 문제가 된 사례다. 어떤 값이 올바른지는 발행 파트의 업무 기준과 함께 판단해야 했다. 필수값이 빠진 경우에도 연동 파트에서 임의의 값을 채우기보다, 발행 파트가 원천 데이터를 수정하고 다시 전달하도록 요청했다.

**일일 보고로 잔여 오류를 드러내고, 원천 수정이 필요한 건은 발행 담당자에게 직접 연결해 재발행까지 이어가는 것**이 당시의 후속 대응이었다.

## 결과는 각 파트의 조치가 이어지면서 나왔다

이 보고 체계를 통해 운영자가 오류를 바로 확인하고, PL·PM도 처리 상황을 검토할 수 있게 했다. 실패 패턴 분석, 대응 절차와 보정 스크립트 정비, 일일 공유 및 각 파트의 조치가 함께 이루어지면서 **주간 약 70건 수준으로 파악하던 연동 오류가 5건 수준으로 줄었다.**

약 70건은 당시 운영 중 파악한 주간 오류 수준을 어림잡아 표현한 값이다. 일별 발생량에는 편차가 있었다. 메일 보고만의 효과를 따로 측정한 수치는 아니며, 원인 분석과 담당 파트의 실제 조치를 함께 연결한 결과로 정리한다.

내 기여는 보고 체계를 직접 만들고, 미처리 오류를 담당자의 후속 조치로 이어지게 한 데 있었다. 업무 데이터를 판단하고 보정하는 각 운영자의 역할이 함께 있었기에 가능한 결과였다.

### 청구·과금 운영 일정까지 생각하며 오류를 처리했다

연동 데이터는 각 파트의 청구 배치인 **요금 생성 작업과 과금 작업**에 이어지는 데이터였다. 오류가 쌓이면 뒤에서 해당 데이터를 사용하는 작업에도 영향을 줄 수 있었다. 그래서 미처리 내역을 매일 공유하고, 담당 파트의 보정이나 발행 파트의 수정·재발행으로 이어지도록 챙겼다.

이때 내가 신경 쓴 것은 **월초·월중·월말에 진행되는 운영 작업에 차질이 없도록 하는 것**이었다. 실패 건수를 확인하는 데서 끝내지 않고, 각 파트가 필요한 데이터를 받아 정해진 업무를 진행할 수 있도록 오류를 쌓아 두지 않고 조치하려고 노력했다.

## 잘되지 않았던 점과 보완한 과정

### 원인을 알아도 조치가 끝나지 않았다

초기에 잘 풀리지 않았던 부분은 **연동 실패를 확인하고 원인을 파악하는 일과, 실제 데이터를 바로잡는 일 사이의 간격**이었다. 실패는 GW 화면에 보였지만 업무 데이터의 확인은 다른 파트에서 필요했다. 보정 요청이 연동 파트로 돌아오면서 담당자의 판단과 조치가 이어지지 않고, 오류가 미처리 상태로 남았다.

보정 프로그램도 있었지만, 그것만으로 업무상 올바른 값을 판단할 수는 없었다. 내가 운영 데이터를 임의로 수정하지 않는다는 원칙을 지키면서도, 해당 건이 처리될 수 있는 다음 행동을 연결해야 했다.

또한 일일 공유 체계를 만든 뒤에도 원천 데이터가 잘못된 건은 담당 파트의 보정만으로 끝나지 않았다. 모델명의 특수기호나 필수값 누락처럼 발행 측의 수정이 필요한 사례는 별도의 요청과 재발행 확인이 필요했다.

### 담당자의 판단으로 이어지도록 전달 방식을 바꿨다

이 간격을 줄이기 위해 **미처리 내역을 파트별로 정리하고, 각 운영자와 PL·PM이 같은 표를 보도록 일일 메일 보고 체계를 만들었다.** PM들이 배분한 담당 파트와 남은 조치가 연결되도록 정보를 모아 전달했다.

원천 값의 문제가 확인된 건은 발행 파트에 직접 수정·재발행을 요청했다. 이후 GW 화면과 대사로 결과를 다시 확인하며 대응을 이어갔다. 연동 파트에서 조사할 내용, 업무 운영자가 판단할 내용, 발행 파트가 수정할 내용을 구분해 각 담당자에게 연결한 것이다.

## 배운 점

### 운영의 완료 기준은 후속 업무까지 이어진다

실패 원인을 알아내면 기술적인 분석은 한 단계 진행된 것이다. 하지만 해당 데이터가 필요한 청구 요금 생성 배치나 과금 작업을 앞두고 있다면, 담당자의 조치와 정상 연동 확인까지 이어져야 한다. 이 경험을 통해 오류를 조사할 때부터 **이 데이터가 어디에 쓰이고, 어떤 운영 일정과 연결되는지** 함께 생각하게 됐다.

### 책임 범위와 후속 대응을 함께 챙겨야 한다

업무 데이터의 의미를 확인할 수 있는 담당자가 수정 여부를 판단하는 것은 중요하다. 그 원칙을 지키면서도 내가 조사한 정보와 확인이 필요한 사항을 충분히 전달하고, 조치 여부를 다시 살펴야 일이 멈추지 않는다.

**내가 확인할 수 있는 정보는 조사하고, 담당자가 판단할 부분은 구체적인 요청으로 바꾸며, 반영 결과를 다시 확인하는 것.** 이 과정이 내가 익힌 운영 업무 방식이다.

### 공유 자료는 다음 행동을 정할 수 있어야 한다

오류 건수는 현황을 보여 주지만, 담당자가 무엇을 해야 하는지까지 설명하지는 못한다. 실패 데이터와 원인, 확인이 필요한 부분을 묶어 전달해야 받은 사람이 조치를 시작할 수 있다. 일일 보고를 만들면서 보고 자료의 역할을 **현황 전달과 후속 행동의 연결**로 이해하게 됐다.

## 지금 다시 운영한다면 보완할 점

당시의 엑셀·메일 공유를 바탕으로 다음 항목을 더 명확히 관리하고 싶다. 아래는 회고에서 정리한 후속 개선안이다.

- **미처리 사유와 마지막 확인 내역 기록** — 업무 판단 대기, 원천 수정 대기, 재발행 대기 등을 나눠 기록하면 같은 내용을 매일 다시 확인하는 부담을 줄일 수 있다.
- **후속 운영 일정에 따른 우선순위** — 월초·월중·월말의 요금 생성·과금 작업과 연결되는 건을 구분해 먼저 확인할 대상을 정하고 싶다.
- **조치 진행을 보여 주는 지표 추가** — 오류 건수와 함께 미처리 기간, 재발행 요청 후 처리까지 걸린 시간, 같은 원인으로 다시 발생한 건을 기록하면 보고 체계의 효과와 남은 병목을 더 구체적으로 확인할 수 있다.
