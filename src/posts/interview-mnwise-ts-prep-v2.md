> **이 글의 범위:** 엠앤와이즈 TS팀 경력직 면접을 준비하며, 공개 자료로 이해한 직무와 내 경험 두 가지를 정리했다. 회사의 내부 구조와 기술 스택은 **확인되지 않았다.** 경험별 상세 내용은 [빌링 GW 복기](/blog/billing-gw-integration-error-interview-review)와 [NURI2 복기](/blog/nuri2-message-batch-interview-review)에 있다.

## 1. 기업과 직무 이해

엠앤와이즈는 WiseU 제품군(통합 메시징 솔루션 UMS, 대량 이메일, 클라우드 메시징 등)을 자체 개발해 금융·통신·공공 고객사에 공급하는 B2B 기업이다.

**UMS(Unified Messaging System)** 는 일반적으로 문자, 이메일, 푸시, 알림톡 같은 여러 발송 채널을 하나의 시스템에서 받아, 알맞은 채널로 내보내고 결과를 기록하는 솔루션을 말한다. 엠앤와이즈 UMS의 내부 구조는 확인되지 않았으므로, 여기서는 이 일반 개념으로만 이해한다.

### TS팀 경력직 공고

| 구분 | 내용 |
| --- | --- |
| 주요 업무 | 자사 솔루션 고객사 대응 개발, 고객사 문제 해결 |
| 필수 | Java·Spring 3년 이상, Linux·DB 이해, 문제 해결에 대한 호기심 |
| 우대 | SI 경험, 고객 기술지원 경험 |

공고를 보면 **솔루션과 고객사 시스템 사이에서 생기는 문제를 확인하고 해결하는 일**이 중심이다. 내 경험 중 두 시스템 사이의 연동 오류를 다룬 일, 메시징 솔루션에 업무 시스템을 연동한 일이 이 지점과 맞닿아 있다고 판단했다.

## 2. 1분 자기소개

> 안녕하세요. 이번에 엠앤와이즈 TS 직무에 지원한 길태형입니다.
>
> 저는 안정적인 서비스 운영을 위해 데이터 불일치로 발생한 연동 오류를 일일 단위로 집계하고, 파트별 보고 체계를 구축해 주간 연동 오류를 약 93% 줄이는 데 기여한 경험이 있습니다.
>
> 또한 전세사기 피해자 심사 지연으로 발생한 민원 문제를 해결하기 위해 메시징 솔루션을 활용하여 알림톡 자동 발송 기능을 개발하고, 민원 문의를 약 30% 줄인 경험이 있습니다.
>
> 이러한 저의 경험들이 엠앤와이즈 UMS 솔루션 사업에 도움이 될 수 있을 것 같아 지원하게 되었습니다.
>
> 감사합니다.

### 자기소개를 이렇게 구성한 이유

- **모든 구현을 나열하지 않았다.** 면접관이 "어떻게 집계했나요?", "어떤 솔루션이었나요?"처럼 다음 질문을 할 여지를 남겼다.
- **근거를 설명할 수 있는 성과만 넣었다.** 93%와 30%는 아래에서 기준과 함께 설명할 수 있는 수치다.
- **직접 한 일과 솔루션이 제공한 기능을 구분했다.** "메시징 솔루션을 활용하여"라고 말해 발송 엔진을 만든 것처럼 들리지 않게 했다.

## 3. 지원 동기

> 저는 서비스 안정화를 위해 실무 담당자들과 소통하고, 파트별 보고 체계를 만들어 문제를 개선한 경험이 있습니다. 또 민원인들의 고충을 해결하며 신속한 문제 해결의 중요성을 경험했습니다. 이런 경험이 고객사와의 소통과 트러블슈팅이 중요한 엠앤와이즈 TS팀과 맞닿아 있다고 생각해 지원했습니다.

### 각 문장의 근거

| 문장 | 근거가 되는 경험 |
| --- | --- |
| 실무 담당자들과 소통하고, 파트별 보고 체계를 만들어 문제를 개선 | 경험 1: 실패 유형·가이드를 담당 파트에 메일로 보내고 답변을 종합한 보고 체계 |
| 민원인들의 고충을 해결하며 신속한 문제 해결의 중요성을 경험 | 경험 2: 의결기한을 넘긴 대상자에게 안내 메시지를 자동 발송한 배치 |
| 고객사와의 소통과 트러블슈팅이 중요한 TS팀 | 공고의 주요 업무: 고객사 대응 개발, 고객사 문제 해결 |

자기소개에서 수치를 이미 말했으므로, 지원 동기에서는 수치를 반복하지 않고 **일하는 방식**이 직무와 맞닿는 점을 말한다.

## 4. 경험 1 — 빌링 GW 연동 오류 대응

(주)애버커스 빌링시스템팀에서 LG U+ 빌링·GW 연계를 유지보수하며 맡은 일이다.

### 문제

원천(이력) 파트가 Kafka 토픽을 발행하고 응용 파트가 구독하는 구조였다. 그 사이에서 도메인 데이터를 변환해 반영하는 계층이 GW다. 두 파트가 따로 고도화되면서 데이터 구조가 달랐고, 다음과 같은 오류가 났다.

- DB 인코딩이 달라 컬럼 사이즈가 맞지 않는 오류
- 업무 중심 키가 달라, 다른 컬럼 값을 조합해 쓰다 생기는 PK 중복 오류

인계 시점에 연동 오류 테이블에는 **1,000건 이상**이 쌓여 있었다. 운영자가 모니터링 화면에서 데이터를 맞춘 뒤 **조치 완료 처리**까지 해야 정리되는 구조라, 이미 맞춘 건과 조치가 필요한 건이 섞여 있었다.

오류는 화면에 있었지만, 알려 주는 장치가 없어 화면에 들어가야만 알 수 있었다. 원인이 시스템 문제인지 원천 데이터 문제인지도 구분되지 않았다. 그래서 문제를 **"누가 무엇을 확인해야 하는지 보이지 않는다"** 로 정의했다.

### 한 일

1. 메일 이력을 확인해 이미 조치된 건은 이벤트 단위로 완료 처리하고, 조치가 필요한 건은 운영자와 확인했다.
2. 실패 유형, 키워드, 해결 방법(가이드)을 엑셀로 정리해 담당 파트에 메일로 보내고 답변을 종합하는 **보고 체계**를 만들었다.
3. 오류 잔량이 하루 10건 안팎이 되어 하루 안에 처리할 수 있게 된 뒤부터 **매일** 보냈다. PL·PM은 참조로 넣어 처리 상황을 함께 볼 수 있게 했다.
4. 운영 데이터는 직접 고치지 않고, 데이터를 가장 잘 아는 담당 파트가 고치도록 알림과 가이드를 제공했다.

**대량 오류 사례:** 원천 파트의 테이블 이관으로 한 번에 10만 건까지 오류가 난 적이 있다. 원천 파트에 원인과 이벤트 형식 특이사항을 확인하고 재발행을 요청했다. 긴 트랜잭션으로 락이 오래 잡히는 것을 예방하려고 **2만 건씩 나눠** 받았고, 나눠 받을 때마다 일괄 조치 후 재검증했다.

### 결과

- 대규모 이관이 없는 **평소 주간 기준**, 오류가 약 70건 안팎(**어림값**)에서 5건 수준으로 감소했다. 약 93%는 70 → 5로 계산한 값이다.
- 남은 5건 수준은 GW 쪽에서 고칠 수 없어 원천 파트에 재발행을 요청해야 하는 건이다.

### 구분할 점

| 내가 한 일 | 내가 하지 않은 일 |
| --- | --- |
| 누적 오류 정리, 유형·가이드 정리, 보고 체계 구축, 대량 오류 분할 처리와 재검증 | 운영 데이터 직접 수정, Kafka 전체 구조 설계, exactly-once 구현 |

**TS 직무와의 연결:** 문제를 분석하는 데서 끝내지 않고 누가 무엇을 해야 하는지 정리해 전달하고, 처리 후 결과를 재검증했다. 고객사 문제를 솔루션 담당자와 고객사 담당자에게 연결하는 일에도 같은 방식을 쓸 수 있다고 생각한다.

## 5. 경험 2 — 안내 메시지 자동 발송 배치

(주)마이크로 서비스 SI본부에서 전세사기 피해자 지원관리시스템을 개발하며 맡은 일이다. 심의 지연으로 의결기한을 넘긴 대상자가 생겨 민원이 늘었고, 이 대상자에게 안내 메시지를 자동으로 보내는 기능을 만들었다.

### 처리 흐름

```text
[직접 개발] 새벽 배치 → 의결기한 도과 대상자 조회
              (발송 대상 관리 테이블 기준 NOT EXISTS로 이미 적재된 대상 제외)
[직접 개발] → 발송 대상 관리 테이블 적재
[직접 개발] → Enum 템플릿 + Builder로 발송 객체 생성
[직접 개발] → NURI2 DATA 테이블 적재 (같은 CUBRID DB, 하나의 트랜잭션)
[NURI2]     → 오전 10시 예약 발송, 알림톡 실패 시 SMS/LMS 대체 발송
[NURI2]     → 발송 후 DATA에서 빠지고 LOG에 이력 기록
[직접 개발] → LOG와 메시지 ID로 JOIN → send_yn Y/N 관리
[직접 개발] → 운영자 발송 이력 화면, 미발송 건 선택 재발송
```

### 직접 개발한 영역과 솔루션이 제공한 영역

| 직접 개발 | NURI2 솔루션 제공 |
| --- | --- |
| 대상 조회, 배치, 발송 대상 관리 테이블 | 발송 대기열 |
| Enum 템플릿, Builder 기반 발송 객체 | 예약 발송 |
| NURI2 DATA 테이블 적재, `send_yn` 관리 | SMS·LMS·알림톡 발송 |
| 미발송 재처리, JOIN 기반 이력 조회 | 대체 발송 |
| 운영자 화면 | 발송 결과·이력 저장 |

발송 엔진은 직접 만들지 않았다. 대상 관리 적재와 `send_yn` 갱신을 하나의 트랜잭션으로 묶었고, NURI2 DATA도 같은 DB라 함께 롤백된다. 다만 이미 솔루션이 발송한 메시지는 롤백할 수 없다.

### 성과와 한계

- 일평균 30건의 안내 메시지를 자동 발송했다. 규모는 작았다.
- 관련 민원 문의가 **44건에서 31건으로 감소**했다(약 29.5%). 집계 기간과 측정 기준은 확인 필요이며, 전후 비교일 뿐 이 기능만의 효과로 단정하지 않는다.
- 운영 중 실제 발송 실패는 없었다. 이 경험은 **장애를 해결한 경험이 아니라 장애 가능성을 고려해 설계한 경험**이다.
- 한계: `send_yn`의 N은 "발송 전"과 "발송 후 결과 미수신"을 구분하지 못한다. 지금 다시 한다면 상태 컬럼이나 적재 시각을 추가해 구분하겠다. (당시 구현이 아닌 개선안)
- 하루 단위로 도는 구조라 당일 발송 원칙이 완벽히 보장되지는 않을 수 있다. 운영자가 당일 확인하고 선택 재발송할 수 있었다.

**TS 직무와의 연결:** 메시징 솔루션에 업무 시스템을 연동하는 쪽, 즉 고객사 개발자의 자리에서 일해 봤다. 발송 요청을 넣는 부분과 결과를 확인하는 부분이 어디서 어긋날 수 있는지 알고 있어, 고객사 문의를 이해하는 데 도움이 된다고 생각한다.

## 6. 이어지는 질문 대비

답변은 외우는 문장이 아니라 **확인된 것 / 모르는 것 / 보완할 것**을 나눠 말하는 틀로 준비한다.

| 질문 | 확인된 것 | 모르는 것 | 보완할 것 |
| --- | --- | --- | --- |
| NURI2는 어떤 솔루션이고, 직접 발송했나요? | DATA 테이블에 적재하면 솔루션의 별도 모듈이 발송, 결과는 LOG에서 확인 | 솔루션 내부 동작 | 직접 개발과 솔루션 영역을 나눠 말하기 |
| 중복 발송은 어떻게 막았나요? | 1차 조회 쿼리의 NOT EXISTS, 2차 `send_yn`과 LOG 대조 | 재발송 실행 조건·횟수 제한 | 결과 미수신 N은 재발송 전 LOG를 먼저 확인해 Y로 보정하고, 그래도 모르면 사람이 확인 |
| 트랜잭션으로 발송까지 되돌릴 수 있나요? | DB 롤백은 DB 안의 작업만 되돌린다 | 격리 수준 등 설정 | 이미 나간 메시지는 되돌릴 수 없다는 전제로 결과 확인을 따로 설계 |
| 93%의 근거는? | 평소 주간 약 70건 안팎(어림값) → 5건 수준 | 정확한 집계 기준과 기간 | 정확한 평균이 아님을 먼저 말하기 |
| 10만 건은 어떻게 처리했나요? | 원인 확인, 재발행 요청, 2만 건씩 분할, 일괄 조치와 재검증 | 분할 단위 결정 주체, 순차·병렬 여부, 락 종류 | 예방 목적으로 나눴다고 말하기 |
| 락은 왜 신경 썼나요? | 트랜잭션이 길면 락이 오래 잡혀 대기·타임아웃이 날 수 있다(일반 원리) | 당시 실제 락 종류와 대기 경험 | 병렬 처리는 락을 없애지 않으며, 겹치지 않는 범위를 나눠 맡겨야 한다 |
| 민원 30% 감소의 근거는? | 44건 → 31건 | 집계 기간과 기준 | 다른 요인을 분리해 측정하지 못했다고 말하기 |

### 다른 경험을 물으면 (한두 줄)

- **SQL 성능:** 운영 화면의 53초 조회를 CUBRID 실행계획 분석과 복합 인덱스로 1초 미만으로 단축했다. 측정 구간은 DB 조회 기준이다.
- **보안 조치:** CodeRay SAST 검출 358건을 CWE 유형별로 조치했고, 검출 건수가 4건으로 감소했다. 정적 검출 수의 감소이며 보안 문제 전체의 해소를 뜻하지 않는다.
- **병렬 조회:** CloudXper에서 DB 테스트 데이터 100만 건 환경의 API 응답이 약 480초에서 10초 이내로 단축됐다. SQL 호출 수는 줄지 않았고, 렌더링 시간이 아니다.
