기능별 폴더 안에 HTTP 처리, 업무 로직, SQL과 데이터 객체가 함께 놓여 있으면 기능을 찾은 뒤에도 책임을 파악하기 어렵다. PR #97은 기존 기능을 유지하면서 각 기능 내부의 계층을 정리한 작업이다. 해당 PR은 확인 시점에 main에 병합됐다.

## 기능을 먼저, 계층을 그 안에 둔다

소지품 기능을 예로 들면 컨트롤러, 요청·응답 DTO, 데이터 행을 표현하는 객체, 저장소 인터페이스와 JDBC 구현, 서비스 인터페이스와 구현을 하위 패키지로 나눴다. 컨트롤러는 서비스 인터페이스에 의존하고 서비스는 저장소 인터페이스를 사용한다. 구현체는 Spring 주입으로 연결한다.

이 프로젝트의 `entity`는 JPA 엔티티가 아니라 JDBC로 읽은 테이블 행을 담는 record다. 계층 이름만 보고 ORM이 도입됐다고 판단하면 실제 구현과 달라진다. WebSocket 멀티플레이는 동일한 틀에 억지로 맞추지 않고 설정·소켓·도메인 중심 구조를 유지했다.

## 인터페이스 분리의 목적과 비용

기존 `Store`를 저장소 인터페이스와 JDBC 구현으로 정리하고, 일부 클래스형 저장소도 인터페이스와 구현으로 나눴다. 서비스 역시 인터페이스와 구현을 분리했다. 호출자가 구체 클래스보다 기능 계약을 따라가도록 한 선택이다.

반면 모든 서비스에 인터페이스와 구현이 생기면서 파일과 이동 경로가 늘어난다. 작은 기능에서는 추상화가 변경의 이해를 돕는지, 단순히 파일만 늘리는지 지속적으로 살펴봐야 한다.

## 대량 이동 후 무엇을 확인했나

개발 로그에는 파일 이동·이름 변경·내부 record 분리를 매핑한 스크립트로 수행하고 컴파일 오류를 단계적으로 해결한 과정이 기록돼 있다. 컴파일 성공은 참조가 연결됐다는 근거지만 API 동작의 완전한 보장은 아니다.

PR은 백엔드 테스트 102개 통과·1개 건너뜀과 로컬 Spring 기동 테스트를 기록한다. API 계약은 CI에서 확인하도록 했다고 명시돼 있다. 이 글에서 테스트를 다시 실행하거나 운영 동작을 별도로 검증한 것은 아니다.
