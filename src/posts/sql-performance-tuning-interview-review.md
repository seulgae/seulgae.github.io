### 수치를 말하기 전에 확인할 점

다른 프로젝트의 기록과 섞이지 않도록 두 수치를 따로 확인한다.

- **약 75초(1분 15초):** 이 숫자는 CloudXper MyBatis 병렬화 글의 **예전 개선 결과 기록**에도 같은 값으로 남아 있었다. 그 기록은 이후 약 480,000ms → 10,000ms 이내로 정정됐다. CUBRID 화면의 개선 전 시간으로 기억하는 75초가 그 기록과 섞인 것은 아닌지 확인하기 전에는 **면접에서 숫자로 말하지 않고 "1분이 넘는 화면도 있었다" 정도로만 설명**한다.
- **약 98%:** CUBRID 원문에는 감소율이 적혀 있지 않다. 포트폴리오에서 '약 98% 단축'으로 쓰는 성과는 **CloudXper의 API 응답 시간** 지표다. CUBRID 사례에는 "53초 → 1초 미만"이라는 원래 표현을 그대로 쓴다.

### 감소율을 묻는다면

- 53초에서 **정확히 1초**로 줄었다면 감소율은 `(53 - 1) / 53 × 100 ≈ 98.1%`다.
- 개선 후가 **1초 미만**이었다면 감소율은 이보다 크다.
- 계산상으로는 98% 이상이지만, 53초는 과거에 기억한 수치를 블로그에 기록한 것이다. 측정 조건이 같았는지, 반복 횟수와 캐시 영향은 확인되지 않았다. 따라서 면접에서는 **"53초에서 1초 미만으로 줄었다"**를 기본 표현으로 쓰고, 퍼센트는 질문을 받았을 때 계산 근거와 함께 말한다.

## 2. 업무 배경 — 이 화면은 무슨 일을 했나

지자체에서 국토교통부로 전달된 피해자 관련 건을 대상으로, 국토교통부가 심사·의결에 활용하는 **의결 명단·의결 목록부**를 조회하고 작성하는 업무가 있었다. 피해자 결정과 1호, 2호, 3~4호, 부결 등의 판단을 위해 안건을 상정하고 회의를 진행할 때 참고하는 목록이다.

이 화면이 느리면 담당자의 심사·의결 준비가 늦어진다. 다만 실제 상태 코드, DB 스키마, 화면별 조회 대상은 확인되지 않았다.

**유의:** 기존 블로그의 '접수 목록 약 7만 건, 53초' 사례와 이번에 떠올린 '의결 명단·의결 목록부'가 같은 화면이라고 확정하지 않는다. **성능을 개선한 화면이 여러 개였다**는 점까지만 확정한다.

## 3. 실제 수행한 작업 — 복기한 순서

1. **느린 화면 확인:** 일부 목록 조회가 수십 초에서 1분 이상 걸리는 현상을 인지했다.
2. **SQL 구조 파악:** 여러 목록 조회 SQL이 `include`로 재사용되는 구조를 보고, JOIN·서브쿼리·조회 조건·`ORDER BY`와 불필요한 관리자 영역의 조회 요소를 살펴봤다. 특정 구문이 실제 병목이었다는 확정 근거는 따로 없다.
3. **실행계획 확인:** CUBRID Manager에서 플랜을 열어 테이블 접근 방식 등 문제 후보를 살폈다. 빨간색으로 표시된 부분을 병목 후보로 봤던 것으로 기억하지만, 그 UI 표시의 정확한 의미는 미확인이다.
4. **개선안 검토:** 당시에는 실행계획을 혼자 충분히 해석할 수준이 아니었다. Claude에 'DBA 역할'을 주고 SQL·인덱스 개선 제안을 받아 검토했다. **실제 DBA가 직접 튜닝해 준 것은 아니다.**
5. **개발환경 적용:** 개선안을 바탕으로 인덱스를 추가하고, 필요한 경우 Mapper SQL을 수정했다. 인덱스 정의와 변경 SQL 원본은 현재 없다.
6. **조회 결과 검증:** AS-IS/TO-BE의 건수, 조회 기간, 엑셀로 추출한 일부 데이터가 일치하는지 대조했던 것으로 기억한다. 약 100건을 조건별로 추출했는지는 확정하지 않는다.
7. **운영 DB 검증:** 운영 DBeaver에서 SQL을 실행해 조회 속도가 개선된 것을 확인했다.
8. **실제 화면 검증:** Mapper XML을 배포하고 실제 운영 화면의 조회 속도가 줄었는지 확인했다. **정확한 화면 응답 시간 수치는 미확인이다.**

```text
느린 화면 인지
  → Mapper SQL 구조 파악 (include · JOIN · 서브쿼리 · 정렬)
  → CUBRID Manager 실행계획 확인
  → AI(DBA 역할)에 분석 요청 → 제안 검토
  → 개발환경에 인덱스·SQL 적용
  → AS-IS/TO-BE 건수·데이터 대조
  → 운영 DBeaver 실행 시간 확인
  → Mapper XML 배포 후 실제 화면 확인
```

### AI 도구 활용을 어떻게 설명할까

AI의 분석 도움을 받았다는 사실을 숨기지 않는다. 처음부터 혼자 인덱스 설계의 최적성을 입증했다고 과장하지도 않는다. 대신 **문제를 발견하고, 제안을 적용하고, 결과 데이터가 달라지지 않는지 검증하고, 운영 DB와 실제 화면에서 확인한 실무 역할**을 분명하게 설명한다.

AI의 제안은 정답이 아니라 **검증할 가설**로 다뤘다는 점이 핵심이다. 실제로 쓴 판단 기준은 개발환경의 실행 시간, 결과 데이터 일치, 운영 DB와 화면의 재확인이었다.

## 4. 성과 검증 — 무엇을 측정했나

### 4-1. SQL 실행 시간과 화면 응답 시간

- **SQL 실행 시간:** DB 도구에서 쿼리를 직접 실행했을 때 표시되는 시간이다. CUBRID Manager의 조회 결과 하단에 나오는 실행 시간(초 또는 ms)을 확인한 것으로 기억한다.
- **실행계획:** DB가 어떤 접근 경로와 연산을 선택했는지 보여 주는 정보다. 예상 비용은 실제 경과 시간과 같지 않다.
- **운영 DB 재확인:** DBeaver에서 개선 SQL을 실행해 운영환경에서도 빨라진 것을 확인했다.
- **화면 응답 시간:** HTTP 요청, 서버 로직, DB 작업, 네트워크, 렌더링이 모두 포함될 수 있다. 운영 화면이 빨라진 것은 확인했지만 **수치화된 화면 응답 개선율은 없다.**

**면접 표현:** "기록해 둔 대표 사례에서 SQL 실행 시간이 약 53초에서 1초 미만으로 줄었고, 운영 DB와 실제 화면에서도 속도 개선을 확인했습니다."

### 4-2. AS-IS / TO-BE 데이터 비교

기억하는 검증 방식은 다음과 같다.

- 같은 조회 기간 등 조건을 맞춰 기존 SQL과 개선 SQL을 각각 실행했다.
- 조회 건수를 확인했다.
- 일부 결과를 엑셀로 추출해 값이 같은지 대조했다.
- 특정 기간에서 약 100건 정도를 비교한 것 같지만 정확한 표본 크기는 불확실하다.

**사후 학습 — 더 엄밀하게 검증하려면:**

- 건수가 같아도 결과가 같다고 보장할 수 없다. 업무 키를 기준으로 누락·중복과 컬럼 값 차이를 확인해야 한다.
- 정렬이나 페이징에 영향을 주는 수정이라면 행의 순서와 페이지 경계도 확인해야 한다.
- 기간·상태·지역·빈 결과·같은 키의 중복 등 여러 조건을 따로 시험해야 한다.
- 표본 100건의 일치는 **그 표본에 대한 검증**이지 전체 데이터의 완전 일치가 아니다.

두 결과를 SQL로 직접 비교하는 방법도 있다. 아래는 학습용 예시다.

```sql
-- 학습용 예시: AS-IS에만 있는 행 찾기 (반대 방향도 같은 방식으로 확인)
SELECT rcpt_no, rcpt_status, reg_dt FROM ( /* AS-IS SQL */ ) a
DIFFERENCE
SELECT rcpt_no, rcpt_status, reg_dt FROM ( /* TO-BE SQL */ ) b;
```

CUBRID는 집합 연산자로 `DIFFERENCE`(표준 SQL의 `EXCEPT`에 해당)를 제공한다. 양방향 모두 0건이면 비교한 컬럼 기준으로 두 결과의 집합이 같다는 뜻이다. 다만 중복 행 개수와 정렬 순서는 별도로 확인해야 한다.

## 5. 사후 학습 — 실행계획과 인덱스 핵심 원리

> 아래 개념은 면접 준비 중 공부한 내용이다. 당시 각 기술을 독립적으로 진단·판단했다고 주장하지 않는다.

### 5-1. 순차 스캔(`sscan`)과 인덱스 스캔(`iscan`)

- `sscan`: 테이블의 행을 순서대로 읽으면서 조회 조건을 검사하는 접근 방식이다.
- `iscan`: 인덱스 키로 조건에 맞는 키나 범위를 찾고, 필요하면 실제 테이블 행을 추가로 읽는 접근 방식이다.
- **"Full Scan은 무조건 비효율적이다"는 틀린 설명이다.** 작은 테이블이나 많은 행을 읽는 쿼리에서는 순차 스캔이 유리할 수 있다.
- **"인덱스가 있으면 반드시 쓴다"도 아니다.** 옵티마이저는 통계·데이터 분포·예상 비용으로 접근 방법을 고른다.
- 조회에 필요한 컬럼이 모두 인덱스에 있으면 테이블을 추가로 읽지 않는 **커버링** 처리가 가능할 수 있다.

### 5-2. 인덱스가 있어도 쓰이지 않거나 비효율적인 경우

- 조건을 만족하는 행이 너무 많아 인덱스를 거쳐 테이블을 읽는 비용이 커지는 경우
- 테이블이 작아 전체를 읽는 편이 더 싼 경우
- 조회 조건이 복합 인덱스의 선두 컬럼과 맞지 않는 경우
- 인덱스 컬럼을 함수로 가공하거나, 자료형이 맞지 않거나, `LIKE '%값'`처럼 앞에 `%`가 붙어 범위 탐색에 불리한 경우
- 통계 정보가 오래됐거나 데이터 분포가 바뀐 경우

이유를 하나로 단정하지 말고 **실제 플랜과 실행 시간**을 비교해야 한다. 함수 기반 인덱스, Index Skip Scan처럼 DBMS별 예외도 있다.

### 5-3. 복합 인덱스 — 백과사전 목차 비유

```sql
-- 학습용 예시. 실제 운영 인덱스가 아님
CREATE INDEX ix_decision_region_status_date
ON decision_list (region_cd, status_cd, reg_dt);
```

백과사전의 **대분류 → 중분류 → 날짜**처럼, 복합 인덱스의 키는 지정한 컬럼 순서대로 정렬되어 있다고 이해한다.

- `WHERE region_cd = '11'`: **선두 컬럼만** 있어도 해당 인덱스 구간을 찾을 수 있다.
- `WHERE region_cd = '11' AND status_cd = '01'`: 앞의 두 등치 조건으로 더 좁은 구간을 탐색할 수 있다.
- `WHERE region_cd = '11' AND status_cd = '01' AND reg_dt >= ...`: 앞의 두 컬럼 값을 고정한 뒤 날짜의 연속 구간을 읽을 수 있어 유리할 수 있다.
- `WHERE reg_dt >= ...`**만** 있다면 이 인덱스의 일반적인 선두 키 범위 탐색에는 불리하다. 그렇다고 인덱스를 절대 못 쓰는 것은 아니며, Index Skip Scan 같은 최적화와 비용 판단이 있을 수 있다.

**정리:** 많은 경우 '등치 조건 → 범위 조건' 순서가 합리적인 출발점이지만 고정 공식은 아니다. 실제 선택은 **조회 패턴, 분포, 선택도, 정렬, 쓰기 비용, 실행계획**으로 결정한다.

### 5-4. `ORDER BY`와 인덱스

조회 조건과 정렬 순서에 맞는 인덱스를 쓰면 별도 정렬 작업을 줄일 수 있는 경우가 있다. 단, 인덱스가 있다고 해서 정렬이 항상 생략되는 것은 아니므로 실행계획으로 확인해야 한다.

### 5-5. 인덱스를 추가할 때의 비용

인덱스는 조회를 빠르게 할 수 있지만 공짜가 아니다.

- `INSERT`·`UPDATE`·`DELETE` 때마다 인덱스도 함께 갱신해야 하므로 **쓰기 비용**이 늘어난다.
- 인덱스만큼 **저장 공간**이 더 필요하다.
- 비슷한 인덱스가 여러 개 있으면 옵티마이저의 선택이 복잡해지고 관리 부담이 커진다.
- 큰 테이블에 운영 중 인덱스를 만들면 생성 시간 동안 부하나 잠금이 생길 수 있다. 동작 방식은 DBMS 버전과 옵션에 따라 다르므로 실제 반영 방법은 확인이 필요하다.

### 5-6. 개발환경과 운영환경의 차이

개발환경에서 빨라졌다고 운영환경에서도 똑같이 빨라지는 것은 아니다. 데이터 건수와 분포, 통계, 캐시, 동시 사용자, DB 설정과 자원이 다를 수 있기 때문이다.

**실제 경험:** 개발환경에서 검증한 뒤 **운영 DBeaver로 다시 실행**하고, **Mapper XML 반영 후 실제 화면을 점검**했다. 정확한 운영 측정 수치와 반복 횟수는 미확인이다.

## 6. 사후 학습용 예제 SQL과 플랜 (원본 아님)

다음은 [기존 블로그](/blog/cubrid-query-plan-index-tuning)의 재구성 예제를 참고한 개념 학습용 SQL이다. **실제 운영 테이블·컬럼·실행계획과 다르다.**

```sql
-- 재구성 학습 예제 (운영 원본 아님)
SELECT rcpt_no, rcpt_status, apply_nm, area_cd, reg_dt
  FROM rcpt_list
 WHERE del_yn = 'N'
   AND area_cd = ?
   AND rcpt_status = ?
   AND reg_dt BETWEEN ? AND ?
 ORDER BY reg_dt DESC, rcpt_no DESC;
```

예제에서 순차 스캔과 별도 정렬이 나타난 상황을 단순화하면 다음과 같다.

```text
[재구성 개념도 — 원본 플랜 아님]
 temp(order by)        ← 전체를 읽은 뒤 별도 정렬
   sscan (rcpt_list)   ← 테이블 순차 스캔
```

조회 패턴과 컬럼 분포에 맞는 인덱스를 적용하면 인덱스 탐색과 정렬 생략을 기대해 볼 수 있다. 그러나 플랜 변화와 성능 향상은 실제 환경에서 검증해야 한다.

```sql
-- 블로그 학습용 예시 인덱스 (실제 운영 DDL 아님)
CREATE INDEX ix_rcpt_list_01
ON rcpt_list (area_cd, rcpt_status, reg_dt DESC, rcpt_no DESC, del_yn);
```

**주의:** 예제는 `apply_nm`을 인덱스에 포함하지 않으므로 SELECT 전체가 커버링 인덱스만으로 처리된다고 단정할 수 없다. 예시의 컬럼 순서가 실제 업무의 정답이라는 뜻도 아니다.

## 7. 면접 답변 (구어체)

### 질문: SQL 성능 개선 경험을 설명해 주세요. (약 1분)

> 전세사기 피해자 관련 행정망 내부 시스템에서 의결 명단과 목록부처럼 조회가 오래 걸리는 화면들이 있었습니다. 일부 화면은 조회에 1분 가까이, 또는 그 이상 걸렸습니다.
>
> CUBRID Manager에서 실행계획을 확인했고, 당시에는 플랜을 혼자 깊게 분석하기 어려워 AI 도구의 도움을 받아 SQL과 인덱스 개선 방향을 검토했습니다. 개발환경에서 인덱스를 적용하고 필요한 SQL을 수정한 뒤, 기존 쿼리와 개선 쿼리의 건수와 데이터를 비교해 결과가 달라지지 않는지 확인했습니다.
>
> 이후 운영 DB에서도 쿼리를 실행해 속도 개선을 확인했고, Mapper XML을 반영한 뒤 실제 화면에서도 조회가 빨라졌는지 확인했습니다. 기록해 둔 대표 사례에서는 SQL 실행 시간이 53초에서 1초 미만으로 줄었습니다.

### 20초 압축 답변

> CUBRID 기반 행정망 시스템에서 1분 가까이 걸리던 목록 조회를 실행계획 확인과 인덱스 적용으로 개선했습니다. AI 도구의 분석을 참고하되, 개발환경에서 결과 데이터가 같은지 대조하고 운영 DB와 실제 화면에서 다시 확인했습니다. 대표 사례는 53초에서 1초 미만으로 줄었습니다.

### 질문: 직접 SQL 튜닝을 하신 건가요?

> 문제 화면의 SQL 구조와 실행계획을 살펴봤고, 당시에는 인덱스 설계 원리가 충분히 익숙하지 않아서 AI를 분석 보조 도구로 활용했습니다. 개발환경에 개선안을 적용하고 AS-IS/TO-BE 데이터를 비교하는 일, 운영 DB와 실제 화면에서 동작과 성능을 확인하는 일은 직접 수행했습니다. 이후 실행계획과 복합 인덱스 원리는 따로 공부했습니다.

### 질문: AI가 제안한 내용을 어떻게 믿을 수 있었나요?

> 그대로 믿지 않고 검증할 가설로 다뤘습니다. 개발환경에 적용해 실행 시간이 실제로 줄었는지 보고, 기존 쿼리와 결과 건수와 데이터가 같은지 대조했습니다. 운영 DB에서 다시 실행해 보고, 배포 후 실제 화면에서도 확인한 다음에 개선됐다고 판단했습니다.

### 질문: 무엇이 가장 큰 원인이었나요?

> 정확히 어떤 구문이 병목이었는지는 지금 원본 플랜이 없어 단정하기 어렵습니다. 기록해 둔 사례에서는 테이블 전체를 순차로 읽은 뒤 별도로 정렬하는 구조가 문제 후보였고, 조회 조건과 정렬에 맞춘 인덱스를 적용해 읽는 범위를 줄이는 방향으로 개선했습니다.

### 질문: 왜 복합 인덱스가 유리할 수 있나요?

> 복합 인덱스는 지정한 컬럼 순서로 키가 정렬되기 때문에, 조회 조건이 선두 컬럼부터 맞으면 탐색 범위를 효율적으로 좁힐 수 있습니다. 등치 조건으로 앞부분을 고정한 뒤 날짜 같은 범위 조건으로 필요한 구간만 읽도록 설계할 수 있습니다. 다만 실제 효율은 데이터 분포와 실행계획으로 확인해야 한다고 이해하고 있습니다.

### 질문: 인덱스가 있는데 왜 Full Scan을 할 수 있나요?

> 인덱스가 항상 빠른 것은 아닙니다. 조회 대상이 테이블의 대부분이거나 테이블이 작으면 인덱스를 거치는 것보다 순차적으로 읽는 비용이 더 낮을 수 있습니다. 그래서 인덱스가 있는지만 보지 않고 실제 접근 경로와 실행 시간을 함께 확인해야 합니다.

### 질문: 인덱스를 추가하면 단점은 없나요?

> 데이터를 등록하거나 수정할 때마다 인덱스도 갱신해야 해서 쓰기 비용이 늘고, 저장 공간도 더 필요합니다. 그래서 조회 패턴에 꼭 필요한 인덱스인지, 비슷한 인덱스가 이미 있는지 확인하는 것이 중요하다고 생각합니다. 당시 대상 테이블의 쓰기 빈도까지 측정해 비교하지는 못했습니다.

### 질문: 개선 후 데이터가 달라지지 않았는지 어떻게 확인했나요?

> 기억하기로는 같은 기간 조건에서 AS-IS와 TO-BE 결과 건수를 비교하고, 일부 결과를 엑셀로 추출해 값이 달라지지 않았는지 대조했습니다. 지금 다시 한다면 건수뿐 아니라 업무 키 기준의 누락·중복과 정렬 순서까지 확인하겠습니다.

### 질문: Oracle 튜닝 경험과는 어떻게 다른가요?

> Oracle은 다른 프로젝트의 청구 목록 사례로, 묵시적 형변환과 힌트, 서브쿼리 구조를 다뤘습니다. CUBRID 사례는 실행계획과 인덱스 적용이 중심이었습니다. 두 사례 모두 실행계획을 근거로 원인을 좁히고 결과를 검증했다는 점은 같지만, 프로젝트와 성과는 구분해서 말씀드립니다.

※ **면접 주의:** 표본 수, 전체 데이터의 완전 일치, 특정 인덱스의 독자적 설계, 운영 배포 후 정확한 응답 시간, 다른 프로젝트의 98%·75초 같은 수치를 확언하지 않는다.
