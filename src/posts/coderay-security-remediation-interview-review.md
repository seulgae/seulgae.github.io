### 수치를 말할 때 주의할 점

- **"358건 → 4건"** 은 그대로 말한다. 감소율을 묻는다면 "건수 기준으로 약 98.9%"라고 계산 근거를 함께 말한다. 다른 프로젝트의 '약 98% 단축'(CloudXper API 응답 시간)과 섞이지 않게 한다.
- 유형별 건수는 기존 글에 **"여 건" 단위**로 남아 있다(CWE-79 200여 건, CWE-209 25여 건, CWE-754 15여 건, CWE-476 20여 건). 대략적인 기록이므로 더해서 358건을 맞추려 하지 않는다.
- 최초·최종 점검의 **검사 규칙과 소스 범위가 같았는지**는 기록으로 확인하지 못했다. 미사용 파일 삭제처럼 검사 대상 자체가 줄어든 조치도 포함되어 있다.

## 2. 문제와 접근

### 문제 상황

- CodeRay 최초 점검에서 358건이 검출됐다. 엑셀 보고서에는 취약점 유형과 소스 위치가 정리되어 있었다.
- 유형이 다양했고 JSP 출력부터 Java 예외 처리까지 맥락이 달랐다. **같은 CWE 번호라도 실제 코드에서는 여러 패턴으로 나타났다.**
- 한꺼번에 일괄 수정하면 기존 화면이나 업무 기능이 깨질 위험이 있었다.

### 작업 흐름

```text
CodeRay 엑셀 결과 확인 (1회차)
  → 유형·코드 패턴별 분류, 조치 관리 문서 작성
  → 시큐어코딩 가이드 정리, 관련 코드 발췌 → Claude 세션별 분석·조치안 검토
  → 유형별·기능별로 범위를 나눠 수정
       ├─ 공통 원인 수정 (공통 유틸, API 계약)
       ├─ 표준 조치 일괄 적용 (c:out, 고정 문구 로깅)
       └─ 미사용 증명 후 삭제 / 서드파티는 조치불가 사유 기록
  → 1차 확인: Claude + 브라우저
  → 2차 확인: 직접 재테스트, 전후 스크린샷, AS-IS 데이터 대조
  → CodeRay 재점검 (총 4회) → 완료·미조치·재검출 갱신
  → 잔여 4건: 영향 검토 → 보류 사유·소명 자료 보고
```

### 조치를 고르는 기준

검출 하나하나를 "어떻게 고칠까"보다 먼저 **"이 검출은 어떤 종류인가"** 를 판단했다. 기존 글에 남긴 판단을 한 표로 정리하면 다음과 같다.

| 판단 | 조치 | 대표 사례 |
| --- | --- | --- |
| 여러 검출이 한 근원을 가리킴 | 근원 한 곳 수정 | 공통 치환 유틸 null 가드로 CWE-476 **15건** 해소 |
| 같은 패턴이 반복됨 | 표준 조치를 정해 일괄 적용 | JSP 출력 `c:out`, 오류 로깅 "고정 문구 + throwable" |
| 실행 경로가 없는 코드 | 미사용 증명 후 삭제 | 벤더 샘플·테스트 JSP **40여 건** 삭제 |
| 고칠 수 없는 서드파티 산출물 | 조치불가 + 사유 기록 | 난독화된 서드파티 JS의 `eval` |
| 변경 영향이 큰 외부 라이브러리 | 영향 검토 후 보류 사유 보고 | 최종 잔여 4건 |

## 3. 주요 유형과 조치 원리

### 3-1. CWE-754 — 부적절한 예외 처리

기존 글에서는 15여 건이 네 가지 안티패턴으로 나타났다고 기록했다.

| 안티패턴 | 조치 |
| --- | --- |
| 광범위한 `catch (Exception e)` | try 블록이 실제로 던지는 예외로 좁힘. DB 접근이 섞이면 `DataAccessException`을 앞에 둔 2단 구성 |
| 잡아서 그대로 다시 던지기 | 의미 없는 catch 제거, try/finally만 남김 (같은 클래스에 4곳 반복) |
| 예외 삼키기 (`printStackTrace()` 후 진행) | 로깅 후 실패를 전파하거나 명시적 실패 응답 반환 |
| 실패 조건 미검사 | null 반환 확인 추가 (근본 원인은 CWE-476에서 다시 다룸) |

```java
// 재구성 예시 — 원인을 남기고 호출자에게 실패를 알린다
try {
    processFile();
} catch (IOException e) {
    LOGGER.error("파일 처리 중 오류가 발생했습니다.", e);
    throw new IOException("파일 처리 중 오류가 발생했습니다.", e);
}
```

- `LOGGER.error(..., e)`: 원인 분석에 필요한 예외와 스택트레이스를 로그에 남긴다.
- `throw new IOException("...", e)`: 원인 예외(cause)를 보존하는 **예외 체이닝**이다.
- `throw` 뒤에 있는 같은 블록의 문장은 실행되지 않는다. 로그를 먼저 남긴 순서가 이 때문이다.
- AJAX 응답 컨트롤러는 예외를 다시 던지지 않고 `result=false` 실패 JSON을 반환하게 바꿨다. **전파할지 응답할지는 호출자가 누구냐에 따라 갈린다.**
- 최상위 공통 예외 처리기처럼 마지막 경계에서는 `catch (Exception)`이 적절할 수 있다. **모든 광범위한 catch가 취약한 것은 아니다.**

### 3-2. CWE-209 — 오류 메시지에 의한 정보 노출

기존 글에서는 25여 건을 원칙 하나로 통일했다고 기록했다.

> **사람에게 보이는 메시지는 고정 문구, 예외 상세는 throwable 인자로만.**

```java
// Before — 예외 원문을 문자열로 조립
LOGGER.error("오류: " + e.getMessage());
e.printStackTrace();
saveHistory("실패 [에러: " + ex.getMessage() + "]");
throw new SQLException(ie.getMessage());

// After — 고정 문구 + 원인 전달
LOGGER.error("데이터 처리 중 오류가 발생했습니다.", e);
saveHistory("작업 실행 오류");
throw new SQLException("데이터 읽기 중 오류가 발생했습니다.", ie);
```

- 오류 메시지·스택트레이스에는 파일 경로, 클래스 구조, DB·호스트 단서가 담길 수 있다.
- `printStackTrace()`는 기본적으로 표준 오류(`System.err`)에 쓴다. **그 자체가 사용자 HTTP 응답으로 전송된다는 뜻은 아니다.**
- `throw new IOException("...")`도 HTTP 응답을 직접 만들지 않는다. 응답은 Spring 예외 처리기나 에러 페이지 같은 상위 계층이 정한다.
- `LOGGER.error("...", e)`도 예외 상세를 로그에 남긴다. 고정 문구로 바꿨다고 로그 유출 위험이 사라지지 않으므로 **로그 접근 권한·보관 기간·마스킹을 따로 확인**해야 한다.
- 함정: `LOGGER.error("오류: {}", e.getMessage(), e)`처럼 메시지 원문을 플레이스홀더로 넣는 코드도 원문이 한 줄에 그대로 남아 함께 정리했다.

### 3-3. CWE-476 — Null Pointer 역참조

검출은 20건이 넘었지만, 상당수가 **같은 공통 치환 메서드**를 가리켰다. 정적 분석이 호출 지점마다 결함을 하나씩 찍은 것이다.

```java
// 근원 메서드 입구에서 한 번 가드
private static String replace(String target, String from, String to) {
    if (target == null || from == null || to == null) {
        return target;
    }
    ...
}
```

- 호출부 15곳 대신 **근원 메서드 한 곳**을 고쳐 검출 15건을 해소했다.
- `||`는 단락 평가라서 앞 조건이 참이면 뒤 조건을 평가하지 않는다.
- null을 반환하던 내부 메서드를 **예외를 던지는 계약으로 바꿔** 호출부 4곳의 검출을 함께 없앤 사례도 있다.
- `System.getProperty("line.separator")`는 non-null이 보장되는 `System.lineSeparator()`로 교체했다.
- 사후 보완: 빈 `from` 문자열이면 반복이 끝나지 않을 수 있다. 그 처리가 당시 적용됐는지는 **미확인**이다. 잘못된 인자를 조용히 원본으로 반환할지 예외로 알릴지도 메서드 계약으로 판단해야 한다. 당시 실제 변경과 이 사후 개선안을 섞어 말하지 않는다.

### 3-4. CWE-79 — JSP 출력부 XSS

200여 건으로 가장 많았다. 이 시스템은 서블릿 필터가 입력값의 특수문자를 HTML 엔티티로 바꿔 저장하는 **입력 측 방어**가 있었지만, 출력부에서는 EL을 그대로 찍는 곳이 많았다.

| 패턴 | 조치 |
| --- | --- |
| HTML 본문의 raw EL | `<c:out value="${...}"/>`로 감쌈. 마스킹 함수 출력도 포함 |
| 입력 필터가 인코딩해 저장한 값 | **디코딩 후 `c:out`으로 다시 이스케이프** |
| HTML을 반환하는 서버 함수 | 전용 rawHtml 커스텀 태그로 raw 출력 통로를 한 곳에 모음 |
| 에러 페이지의 `${exception.message}` | `c:out` 적용 (메시지 원문 노출 문제는 CWE-209로 별도) |
| 미사용 샘플·테스트 JSP | 진입 경로 없음을 확인하고 삭제 |
| 에디터 본문처럼 HTML 서식을 유지해야 하는 값 | 서버의 Jsoup 기반 Java 필터로 HTML을 걸러내고, 출력은 rawHtml 통로로 정리 |

**이중 이스케이프 문제:** 저장된 `&lt;서울&gt;`에 `c:out`만 씌우면 화면에 `&lt;서울&gt;`라는 글자가 그대로 보인다. 그래서 입력 인코딩 값은 디코딩한 뒤 출력 시점에 다시 이스케이프했고, 화면에서 특수문자 표시·값 누락·레이아웃 변화를 직접 확인했다.

**rawHtml 태그의 한계:** raw 출력 지점을 한 곳으로 모으면 검색과 리뷰가 쉬워지지만, **태그로 옮겼다는 사실만으로 XSS가 해결되지는 않는다.** EL에서 커스텀 태그로 옮기면 SAST 검출에서 빠질 수 있으므로, 실제 안전성은 Jsoup 필터가 무엇을 허용하는지와 태그에 사용자 입력이 들어가지 않는지에 달려 있다. Jsoup 허용 목록의 세부 설정은 **미확인**이다.

사후 학습: `c:out`은 HTML 텍스트 문맥의 이스케이프다. JavaScript 문자열, URL, HTML 속성 같은 다른 출력 문맥에는 각각 맞는 인코딩이 필요하다.

### 3-5. 미사용 코드 삭제와 조치불가 판정

CWE-330·489·497 검출의 상당수는 쓰지 않는 벤더 모듈과 테스트 화면에서 나왔다. 고치기보다 **쓰지 않음을 증명하고 지웠다.**

1. 진입점 역추적: 컨트롤러 매핑, 화면 흐름, include·script 로드 관계 확인
2. 참조 전수검색: 활성 화면에서 참조가 0건인지 확인
3. 실사용 대체재 확인: 예를 들어 실서비스 인증코드는 `SecureRandom`을 쓰는지 확인
4. 삭제 + 미사용 근거 기록

반대로 난독화된 서드파티 산출물 안의 `eval`은 직접 수정이 라이선스·유지보수 면에서 맞지 않다고 보고 **"조치불가 + 사유 기록"** 으로 종결했다. 고치지 못하는 이유를 남기는 것도 조치 과정의 일부였다.

## 4. 테스트와 검증

### CodeRay 재점검

- 회차별 엑셀 결과로 **조치 완료 / 미조치 / 재검출**을 구분했다.
- 총 4회 점검 끝에 4건이 남았다. 회차별 건수는 기록으로 확인하지 못했다.

### 두 단계 기능 확인

| 단계 | 실제로 확인한 내용 | 근거 |
| --- | --- | --- |
| 1차: Claude + 브라우저 | Chrome 확장 기능으로 화면을 이동하며 기능 동작을 함께 확인 | 기존 블로그 기록 |
| 2차: 직접 재테스트 | 사용자 관점에서 수정 기능을 다시 사용, 값 누락·특수문자 표시 확인 | 기존 블로그 기록 + 실제 경험(기억) |
| 화면 비교 | 수정 전후 스크린샷 비교 | 실제 경험(기억) |
| 데이터 대조 | AS-IS 데이터와 비교해 DB에 누락된 데이터가 없는지 확인 | 기존 블로그 기록 |
| 반영 판단 | 위 확인에서 이상이 없을 때 반영 | 기존 블로그 기록 |

당시 환경에서는 JSP 수정이 비교적 빨리 반영되어 화면 중심으로 반복 확인할 수 있었다. **화면이 정상으로 보이는 것과 데이터가 빠짐없이 처리되는 것은 따로 확인해야 했다.**

**검증 범위:** 위 작업은 기능 회귀 확인과 SAST 재점검이다. 공격 시나리오 기반 침투 테스트나 동적 분석(DAST)을 이 작업에서 수행했는지는 **미확인**이다. 스크린샷 비교로 XSS 공격 가능성이 사라졌다고 말하지 않는다.

## 5. 잔여 4건의 판단과 보고

- 외부 첨부파일(업로드) 컴포넌트의 버전·함수와 관련된 검출이 남았다. 공개 글에서는 제품명을 생략한다.
- 버전 업그레이드만으로 끝나지 않고 기존 첨부파일 기능 전반의 수정과 회귀 검증이 필요할 것으로 판단했다.
- 그래서 즉시 수정하지 않고 **조치 보류 사유와 소명 자료를 작성해 보고**했다.
- 서드파티 `eval`을 "조치불가 + 사유 기록"으로 남긴 판단과 같은 방향이다. 다만 잔여 4건이 그 `eval` 건과 같은 항목인지는 **미확인**이다.
- 보고는 위험의 해결이나 승인과 다르다. 면접에서는 **"영향을 검토해 보류 사유를 문서화하고 보고했다"** 까지만 말한다.

## 7. 예상 꼬리 질문

**Q1. `catch(Exception)`을 구체적인 예외로 바꾼 이유는?**
예상하지 못한 예외, 예를 들어 버그로 생긴 NPE까지 잡아서 원인을 숨기지 않기 위해서입니다. 다만 최상위 공통 예외 처리기처럼 마지막 경계에서는 넓게 잡는 것이 맞을 수 있습니다.

**Q2. `LOGGER.error(..., e)`로 바꿔도 내부 정보가 로그에 남지 않나요?**
남습니다. 그래서 사용자 응답에는 고정 문구만 보여 주고, 로그는 접근 권한과 보관·마스킹 정책으로 따로 보호해야 합니다. 로깅 방식만으로 해결된다고 보지 않습니다.

**Q3. `throw`와 `return`은 무엇이 다른가요?**
`return`은 정상 결과를 돌려주고, `throw`는 정상 흐름을 멈추고 실패를 호출자에게 알립니다. 실제로 AJAX 컨트롤러는 예외를 던지는 대신 실패 JSON을 반환하게 했습니다. 호출자가 실패를 어떤 형태로 받아야 하는지에 따라 정했습니다.

**Q4. `finally`는 무조건 실행되나요?**
보통 예외나 `return`과 관계없이 실행되지만, JVM 종료처럼 실행되지 않는 경우가 있습니다. 자원 정리는 가능하면 `try-with-resources`를 씁니다.

**Q5. AI가 만든 코드를 어떻게 검증했나요?**
유형별로 범위를 나눠 적용하고, Claude와 브라우저에서 1차로 확인한 뒤 제가 직접 다시 테스트했습니다. 전후 스크린샷과 AS-IS 데이터를 대조했고, CodeRay 재점검으로 검출 상태도 확인했습니다.

**Q6. Claude 세션은 왜 나눴나요? 역할은 어떻게 나눴나요?**
한 세션에 모든 검출을 쌓으면 맥락이 섞이기 때문에 유형과 작업 맥락별로 나눴습니다. 세션끼리 자동으로 일을 넘기는 구조는 아니었고, 코드를 발췌해 전달하고 결과를 검토하는 일은 제가 했습니다. *(네 세션의 정확한 역할 분담은 답하기 전에 다시 확인한다.)*

**Q7. 358건이 4건이 됐다면 안전해진 건가요?**
아닙니다. 특정 정적 분석 도구의 검출 수가 줄어든 것입니다. 도구가 못 찾는 문제나 실행 환경의 위험까지 없어졌다는 뜻은 아닙니다. 에디터 HTML처럼 출력 통로만 정리한 부분은 필터 설정까지 봐야 합니다.

**Q8. 공통 유틸 하나를 고쳐 15건이 사라졌다는 건 무슨 뜻인가요?**
여러 화면이 같은 치환 메서드를 호출했고, 도구가 호출 지점마다 결함을 찍었습니다. 근원 메서드에 null 가드를 넣어 15곳에 같은 방어 코드를 복제하지 않고 해결했습니다.

**Q9. 코드를 삭제하는 건 위험하지 않나요?**
그래서 근거 없이 지우지 않았습니다. 진입점 역추적, 참조 전수검색, 실사용 대체재 확인을 거쳐 미사용을 확인했고 삭제 사유를 기록했습니다.

**Q10. `c:out`을 붙이자 화면에 `&lt;`가 보였다면 어떻게 하나요?**
입력 필터가 이미 엔티티로 저장한 값을 한 번 더 이스케이프한 것입니다. 디코딩해서 원문으로 돌린 뒤 출력할 때 다시 이스케이프했습니다. 입력 인코딩과 출력 이스케이프가 각자 역할을 지켜야 합니다.

**Q11. 에디터 본문은 이스케이프하면 서식이 깨지는데 어떻게 했나요?**
서버에서 Jsoup 기반 Java 필터로 HTML을 걸러내고, 출력은 전용 rawHtml 태그 한 곳으로 모았습니다. 필터는 위험한 HTML을 거르는 역할이고, 태그는 raw 출력 지점을 관리하는 역할로 구분했습니다.

**Q12. 왜 최종 4건은 수정하지 않았나요?**
외부 첨부파일 라이브러리 업데이트가 첨부 기능 전반에 영향을 줄 수 있었습니다. 변경 영향과 검증 범위를 검토해 즉시 수정 대신 보류 사유를 문서로 정리해 보고했습니다. 공식 위험 수용 승인까지 받았는지는 확인이 필요합니다.

**Q13. 최초와 최종 점검 결과를 그대로 비교해도 되나요?**
회차별 엑셀로 항목 상태를 추적했습니다. 다만 검사 규칙과 소스 범위가 같았는지는 확인해야 더 정확하게 말할 수 있고, 미사용 파일 삭제로 검사 대상이 줄어든 효과도 들어 있습니다.

**Q14. 정적 분석(SAST)과 동적 분석(DAST)은 어떻게 다른가요?**
SAST는 실행하지 않고 소스 코드 패턴을 검사하고, DAST는 실행 중인 애플리케이션에 요청을 보내 동작을 검사합니다. 이번 작업은 SAST 결과를 줄인 경험이고, 별도 웹 취약점 점검 16건과 SQL Injection 14건 조치는 다른 점검 결과입니다.

**Q15. 지금 다시 한다면 무엇을 바꾸겠나요?**
유형별 원인·조치·재검사 결과를 짧은 공통 양식으로 남겨 세션 사이에 맥락이 빠지지 않게 하겠습니다. 직접 반복했던 화면 확인 중 자동화할 수 있는 부분도 검토하겠습니다. 당시 모두 구현한 체계가 아니라 이번 경험에서 정리한 개선 방향입니다.
