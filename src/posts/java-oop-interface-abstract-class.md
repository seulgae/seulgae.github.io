# 객체지향 설계에서 인터페이스와 추상 클래스를 선택하는 기준

## 1. 학습 배경

기존 객체지향 학습 기록을 바탕으로 문법보다 설계 선택의 이유를 복습한다. 아래 메시지 발송기는 **학습용 예제**이며 실제 NURI2 연동 코드를 옮긴 것이 아니다.

## 2. 핵심 개념

캡슐화는 상태 변경의 규칙을 객체 안에 모으는 것이고 추상화는 사용자에게 필요한 역할을 드러내는 것이다. 상속은 타입·구현 관계를 만들고 다형성은 같은 계약을 통해 서로 다른 동작을 사용할 수 있게 한다. 필드를 private으로 바꾸거나 상속을 사용했다는 사실만으로 좋은 설계가 되지는 않는다.

인터페이스는 여러 구현이 지켜야 할 계약을 정의한다. 추상 클래스는 인스턴스 상태와 공통 구현을 함께 제공할 수 있다. Java 17에서 클래스 상속은 하나지만 인터페이스는 여러 개를 구현할 수 있다.

## 3. 동작 원리

```text
발송 업무 → MessageSender 계약
                ├─ SMS 구현
                └─ 이메일 구현
```

호출 측은 계약에 의존하고 런타임 객체의 구현이 동작을 결정한다. 상속 계층에서는 하위 타입이 상위 타입을 기대한 코드의 약속을 깨지 않아야 한다. 다른 역할을 재사용하려면 상속 대신 협력 객체를 필드로 갖는 조합을 검토한다.

공통 발송 순서를 고정하고 일부 단계만 바꾸는 템플릿이 필요하면 추상 클래스가 후보가 된다. 단지 메서드 몇 개가 같다는 이유로 도메인이 다른 객체를 한 부모에 묶지는 않는다. [추상 클래스 안내](https://docs.oracle.com/javase/tutorial/java/IandI/abstract.html)의 기본 구분을 참고하되 해당 튜토리얼은 JDK 8 문서다.

## 4. 실무 활용

학습 예제에서 발송 수단을 교체하거나 외부 호출을 테스트 대역으로 바꾸려면 인터페이스가 유용하다. 반면 구현이 하나이고 바뀔 경계도 없다면 모든 클래스에 인터페이스를 추가할 필요는 없다. 적용 전에는 “무엇이 달라질 때 호출 측을 보호하려는가”를 먼저 묻는다.

## 5. 주의사항 및 오개념

인터페이스에 구현이 전혀 없다는 답은 부정확하다. Java 17은 default·static·private 메서드를 지원하지만 인스턴스 상태를 가진 추상 클래스와 같지는 않다. 구버전 튜토리얼의 접근 제어 설명을 최신 문법 전체로 일반화하지 않는다.

## 7. 핵심 요약

역할의 계약, 공통 상태, 변경 방향을 기준으로 선택한다. 기존 [상속과 조합 학습](/blog/java-oop-05-inheritance-and-composition)과 연결해 설명하되 새 설계를 실무 경험으로 꾸미지 않는다.
