## Case 1. 망간 데이터 동기화 쿼리 정적 전환과 테이블 누락 사고 복구

- **원문**: [MyBatis를 JPA처럼 쓰던 연계 로직 — 범용 동적 쿼리를 정적 쿼리로 되돌리기](/blog/dynamic-to-static-sync-query)

### 1. [문제 정의 및 배경]
내부망(업무망)과 외부망(인터넷망)에 각각 CUBRID DB를 두고 게시물·첨부파일을 양방향 동기화하는 연계 로직이 있었다. 기존 코드는 어떤 테이블이든 처리할 수 있도록 `${targetTable}`과 `<foreach>${item.columnName} = #{item.columnValue}</foreach>` 문자열 치환을 사용한 **단 2개의 범용 statement(`selectSyncInfo`, `updateSyncInfoReg`)**로 구현되어 있었다.
- MyBatis에서 `${}`는 `PreparedStatement` 바인딩이 아닌 런타임 문자열 치환이므로 외부 입력과 닿는 순간 SQL Injection에 그대로 노출된다.
- 소스 코드 어디에도 완성된 SQL이 존재하지 않아 정적분석 스캐너나 코드 리뷰어가 실제 실행 쿼리를 검증할 수 없었다.
- 원본 조회 결과가 `null`일 때도 `MERGE`가 실행되어 반대편 망의 정상 데이터를 전부 `NULL`로 덮어쓸 수 있는 잠재 버그가 있었다.

### 2. [기술적 의사결정 및 대안 비교]
- **대안 A (기존 유지 + 애플리케이션 화이트리스트 검증)**: 범용 동적 쿼리 2개를 유지하고 Java 단에서 허용 테이블·컬럼 문자열만 검사하는 방식. 코드는 짧지만 SAST 도구에서는 여전히 `${}` 구문을 SQL Injection 취약점으로 검출하며, `SELECT *`와 동적 컬럼 조립이 스키마 변경에 취약하다는 근본 한계가 남는다.
- **대안 B (채택 — 테이블별 명시적 정적 Statement 분리 + Statement ID 라우팅)**:
  - JDBC `PreparedStatement` 표준상 테이블명·컬럼명 같은 식별자 자리에는 `?`(`#{}`) 바인딩을 쓸 수 없다. 따라서 "범용 1개"의 편의성을 버리고 연계 대상 **9개 테이블·97개 컬럼**을 테이블별 정적 `SELECT` / `MERGE` statement로 모두 풀어 썼다.
  - 이때 상위 `Service` 인터페이스와 스케줄러 호출부는 건드리지 않고, DAO에서만 `selectOne("SyncDAO.select_" + tableName)`처럼 **statement ID를 선택**하도록 변경했다. 매퍼 XML에 정의되지 않은 테이블명이 들어오면 SQL이 조립·실행되는 대신 "존재하지 않는 statement ID" 예외로 즉시 차단되어 자연스러운 화이트리스트가 완성됐다.

### 3. [해결 과정 및 트러블슈팅 (Fail-Recovery)]
- **원본 미존재 가드 추가**: 원본 조회 결과가 없을 때는 `MERGE`를 건너뛰고(skip) 경고 로그를 남기도록 방어 로직을 추가해 `NULL` 덮어쓰기 위험을 제거했다.
- **[실패와 수습] 코드 상수만 믿었다가 발생한 '조용한 연계 누락'**:
  - 정적 statement를 작성할 대상 테이블 목록을 **소스 코드에 하드코딩되어 있던 테이블 목록**에서 뽑았다.
  - 그러나 운영 DB의 **동기화 이력(`hist`) 테이블**에는 실제로 연계가 돌고 있었지만 Java 상수 목록에는 빠져 있던 테이블이 1개 존재했다.
  - 배포 직후 해당 테이블의 정적 statement가 없다 보니 그 테이블의 변경분만 반대편 DB로 넘어가지 않았고, 동기화 호출 자체가 누락되니 에러 로그조차 찍히지 않는 장애가 발생했다.
  - 양쪽 DB 데이터가 어긋난 것을 확인한 즉시 이력 테이블(`hist`)을 전수 조회해 누락된 테이블의 정적 statement를 추가 배포하고, 누락 기간 동안 쌓인 변경 이력의 PK를 추출해 데이터를 보정한 뒤 **양쪽 DB 건수 및 PK 대사(Reconciliation)**로 정합성 복구를 완료했다.

### 4. [정량적/정성적 성과 및 배운 점]
- **성과**: 국자원 웹 취약점 점검 사전 대응으로 **SQL Injection 14건 해소**(이후 CodeRay 정적분석에서 SQL 삽입 검출 0건), 보안 취약점 16건 개선 및 Jasypt 공통 유틸 기반 4개 환경 계정정보 17건 암호화 완료.
- **배운 점**: **"운영 시스템의 진실은 코드가 아니라 운영 데이터(이력 테이블)에 있다."** 리팩토링 범위를 잡을 때 코드 상수만 믿지 않고 반드시 운영 이력 테이블의 `DISTINCT` 집계와 교차 검증해야 하며, 에러 로그가 안 찍히는 '조용한 누락'을 잡기 위해 배포 후에는 반드시 **데이터 대사 쿼리**로 검증하는 원칙을 세웠다.

### 5. [면접관 예상 꼬리 질문 (3가지)]
1. **Q. MyBatis에서 `#{}`와 `${}`의 내부 동작 원리 차이는 무엇이며, 왜 테이블명에는 `#{}`를 쓸 수 없나요?**
   - **답변 포인트**: `#{}`는 JDBC `PreparedStatement`의 `?` 파라미터로 컴파일되어 DB가 값을 리터럴로만 취급하므로 SQL 구조가 변조되지 않고 실행계획도 캐싱됩니다. 반면 DB 옵티마이저는 실행계획을 세울 때 테이블과 컬럼 식별자를 먼저 확정해야 하므로 표준 SQL 문법상 식별자 자리에는 `?` 바인딩을 허용하지 않습니다. 그래서 `${}` 문자열 치환을 쓰게 되는데, 이를 제거하기 위해 매퍼 XML에 테이블별 정적 쿼리를 선언하고 Java에서는 실행할 statement ID만 매핑하도록 구조를 바꿨습니다.
2. **Q. 테이블 1개가 누락됐을 때 에러 로그도 안 남았다고 했는데, 어떻게 인지했고 누락된 데이터는 어떤 절차로 복구했나요?**
   - **답변 포인트**: 업무망과 인터넷망 게시물 건수가 어긋난다는 현업/운영 확인 과정에서 발견했습니다. 즉시 동기화 이력(`hist`) 테이블을 기준으로 코드의 대상 목록과 `MINUS` 비교를 수행해 빠져 있던 테이블 1개를 특정했습니다. statement를 추가 배포한 뒤에는, 배포 시점부터 복구 시점까지 이력 테이블에 기록된 해당 테이블의 변경 `row_id` 목록을 뽑아 원본 행을 조회하고 대상 망에 `MERGE` 보정을 실행한 뒤 양쪽 `COUNT`와 PK 대사로 일치 여부를 최종 확인했습니다.
3. **Q. 테이블마다 정적 쿼리를 다 만들면 향후 테이블이나 컬럼이 추가될 때 유지보수가 번거롭지 않나요?**
   - **답변 포인트**: 맞습니다. 범용 동적 쿼리 대비 새 컬럼 추가 시 매퍼 XML을 함께 수정해야 하는 번거로움은 늘어납니다. 하지만 공공 망분리 시스템에서는 '스키마 변경 시 코드 한 줄 덜 고치는 편의성'보다 '외부 점검 기준 충족(SQL Injection 원천 차단)과 실행 SQL의 가시성 확보, 의도치 않은 신규 컬럼 자동 동기화 방지'가 훨씬 중요한 가치였기 때문에 명시적 관리 비용을 감수하는 트레이드오프를 선택했습니다.

## Case 2. 운영 행정망 53초 Slow Query 분석 및 복합 인덱스 설계

- **원문**: [53초짜리 목록 조회 — CUBRID 쿼리 플랜의 빨간 구간을 지우는 인덱스 설계](/blog/cubrid-query-plan-index-tuning)

### 1. [문제 정의 및 배경]
운영 행정망에서 약 **7만 건** 규모의 접수 목록을 조회할 때 응답에 **53초**가 걸렸다. 7만 건은 RDBMS 기준 대용량도 아닌데 1분 가까이 걸리다 보니, 운영자는 화면이 멈춘 줄 알고 새로고침을 반복했고 동일한 무거운 쿼리가 DB에 중첩으로 쌓였다.

### 2. [기술적 의사결정 및 대안 비교]
- **CUBRID Manager 쿼리 플랜 진단**:
  - 실행계획을 열어본 결과 비용이 큰 빨간색 노드가 두 곳이었다: ① `sscan`(유효한 인덱스가 없어 7만 건 테이블 전체 순차 스캔) ② `temp(order by)`(필터링 결과를 임시 공간에서 별도 정렬).
- **단일 인덱스 추가 vs WHERE + ORDER BY 통합 복합 인덱스 설계**:
  - 후보 컬럼은 `WHERE`절 4개(`del_yn`, `area_cd`, `rcpt_status`, `reg_dt`)와 `ORDER BY`절 2개(`reg_dt DESC`, `rcpt_no DESC`)였다.
  - 단순히 조건 컬럼 하나에만 인덱스를 걸면 `sscan`은 피해도 `temp(order by)` 정렬 부하가 남는다. 따라서 **탐색(Range Scan)과 정렬 생략, 커버링 필터까지 인덱스 1개로 끝내는 복합 인덱스 순서**를 설계하기로 결정했다.
  - **순서 결정 근거**:
    1. **등치(`=`) 조건 선두 배치 (`area_cd, rcpt_status`)**: 탐색 범위를 가장 먼저 점으로 좁힌다.
    2. **범위(`BETWEEN`) + 정렬 조건 연결 (`reg_dt DESC, rcpt_no DESC`)**: B-Tree 특성상 범위 조건 뒤에 오는 컬럼은 인덱스 탐색 범위를 좁히는 데 쓰이지 못하므로 등치 조건 뒤에 `reg_dt`를 두고, 이어서 `rcpt_no DESC`를 붙여 두 컬럼 모두 `DESC` 방향을 일치시킴으로써 별도 정렬(`temp`) 없이 인덱스 읽는 순서 그대로 결과를 반환하게 했다.
    3. **저카디널리티 컬럼 후미 배치 (`del_yn`)**: `'Y'/'N'` 두 값뿐이고 대부분이 `'N'`인 `del_yn`을 선두에 두면 거의 전 구간을 스캔한다. 맨 뒤에 포함시켜 테이블 접근 전 인덱스 단에서 걸러내는 커버링 효과를 택했다.

### 3. [해결 과정 및 트러블슈팅]
- **복합 인덱스 생성**: `CREATE INDEX ix_rcpt_list_01 ON rcpt_list (area_cd, rcpt_status, reg_dt DESC, rcpt_no DESC, del_yn);`
- **인덱스를 무력화하던 조건절(Non-SARGable) 교정**:
  - 같은 화면의 다른 조회 조건들에 인덱스를 못 타게 막는 패턴이 섞여 있어 함께 수정했다.
  - **좌변 컬럼 가공 제거**: `WHERE TO_CHAR(reg_dt, 'YYYYMMDD') = ?`처럼 인덱스 컬럼을 함수로 감싸 정렬 기준을 깨뜨리던 조건을 `WHERE reg_dt >= ? AND reg_dt < ?` 범위 비교로 변경했다.
  - **선행 와일드카드 협의 변경**: `WHERE apply_nm LIKE '%' || ? || '%'`는 시작점을 알 수 없어 풀스캔을 유발한다. 이름 검색은 앞자리 입력이 자연스럽다는 점을 현업과 협의해 `LIKE ? || '%'` 전방 일치로 전환했다.
- **통계 정보 갱신**: 인덱스를 생성해도 통계가 낡으면 옵티마이저가 기존 풀스캔을 고집할 수 있어 `UPDATE STATISTICS ON rcpt_list;`까지 실행해 마무리했다.

### 4. [정량적/정성적 성과 및 배운 점]
- **성과**: 실행계획이 `iscan`(인덱스 스캔) 단일 경로로 바뀌고 `temp(order by)` 노드가 완전히 제거됐다. 조회 응답 시간은 **53초 → 1초 미만**으로 단축됐고, 이후 월간 운영 점검에서 해당 화면의 Slow Query 특이사항 0건을 유지했다.
- **배운 점**: 인덱스는 공짜가 아니며 `INSERT/UPDATE`마다 갱신 비용을 치른다. 접수 목록 테이블은 쓰기보다 운영자의 반복 조회가 압도적인 읽기 위주 테이블이어서 5개 컬럼 복합 인덱스가 남는 장사였지만, 이력 로그처럼 쓰기가 집중되는 테이블이었다면 같은 결정을 내리지 않았을 것이다.

### 5. [면접관 예상 꼬리 질문 (3가지)]
1. **Q. 만약 `ORDER BY reg_dt DESC, rcpt_no ASC`처럼 두 정렬 컬럼의 방향이 서로 달랐다면 인덱스를 어떻게 타게 되나요?**
   - **답변 포인트**: 기본 ASC 인덱스를 역순(Backward)으로 읽으면 전체 방향이 뒤집히므로 `DESC, DESC`는 해결되지만, `DESC, ASC`처럼 방향이 섞여 있으면 인덱스를 읽는 순서만으로 정렬을 끝낼 수 없어 다시 `temp(order by)` 정렬 노드가 생깁니다. 이를 피하려면 인덱스 생성 시점부터 쿼리의 정렬 방향과 동일하게 `(..., reg_dt DESC, rcpt_no ASC)`로 내림차순/오름차순을 명시해서 생성해야 합니다.
2. **Q. `del_yn`을 아예 인덱스에서 빼는 것과 맨 뒤에 넣는 것을 둘 다 비교해 봤다고 했는데, 어떤 차이가 있었나요?**
   - **답변 포인트**: `del_yn`을 인덱스에서 빼면 인덱스로 `area_cd, rcpt_status, reg_dt` 조건을 만족하는 행들의 OID/데이터 페이지를 찾아간 뒤에야 테이블을 읽고 `del_yn = 'N'`인지 확인합니다. 반면 맨 뒤에라도 인덱스에 넣어두면 테이블 데이터 페이지로 랜덤 액세스하기 전에 인덱스 리프 노드 안에서 `del_yn = 'N'`이 아닌 행을 먼저 걸러낼 수 있어 테이블 접근 횟수가 근소하게 줄어드는 것을 플랜으로 확인하고 포함시켰습니다.
3. **Q. 이름 검색을 `%키워드%`에서 `키워드%`로 바꿀 때 현업(운영자)의 반대는 없었나요?**
   - **답변 포인트**: 무작정 기능부터 바꾸지 않고, 먼저 운영자가 실제로 이름을 어떻게 검색하는지 패턴과 53초 지연의 원인을 함께 설명드렸습니다. 신청자 성명 검색은 대부분 성씨를 포함한 전체 이름이나 앞 글자부터 입력하고 있었고, 중간 글자 검색 기능을 유지하느라 매번 수십 초를 기다리는 것보다 전방 일치로 바꿔 1초 안에 조회하는 편이 업무 효율에 훨씬 유리하다는 공감대를 얻어 변경했습니다.

## Case 3. 개인정보 384만 건 무중단 암호화 패치 (`csql + nohup`)

- **원문**: [csql과 nohup — 운영 중인 DB에 수백만 건 패치를 조용히 밀어 넣는 법](/blog/csql-nohup-mass-patch)

### 1. [문제 정의 및 배경]
외부 OTT 서비스의 본인확인 값(CI) 유출 사건 보도를 계기로 자체 점검을 수행한 결과, 가입·인증 과정에서 수집된 행안부 연계 CI값(**14만 건**)과 개인정보 이력 로그(**370만 건**) 총 **384만 건**이 평문으로 저장된 테이블을 확인했다. 유출 사고 예방을 위해 DB 암호화 솔루션(Damo) 함수로 즉시 암호화 패치를 수행해야 했으나, **운영 중인 대민/업무 서비스를 중단할 수 없다**는 제약이 있었다.

### 2. [기술적 의사결정 및 대안 비교]
- **애플리케이션 배치 개발·배포 vs DB 서버 CLI(`csql`) 스크립트 직접 실행**:
  - 일회성 마이그레이션을 위해 WAS 애플리케이션에 배치 코드를 작성해 빌드·배포하면 불필요한 배포 리스크와 형상 관리 부담이 생긴다. DB 서버 내부에서 Damo 암호화 함수를 직접 호출하는 SQL 스크립트를 `csql` CLI로 실행하는 편이 네트워크 왕복도 없고 영향 범위도 최소였다.
- **포그라운드 실행 vs `nohup` 백그라운드 + 단일 트랜잭션 vs 범위 분할 커밋**:
  - 수백만 건 UPDATE 도중 작업자 PC의 VPN이 끊기거나 터미널 세션이 닫히면 `SIGHUP` 시그널로 프로세스가 죽고 어디까지 반영됐는지조차 알기 어렵다. 따라서 `nohup ... > encrypt_patch.log 2>&1 &`로 세션 생명줄을 분리했다.
  - 또한 384만 건을 단일 트랜잭션으로 UPDATE하면 커밋 전까지 전체 행의 배타 락(X-Lock)이 잡혀 실사용자 거래가 마비되므로, **PK 범위 분할(예: 1만 건 단위) + 블록마다 `COMMIT` + 미처리 조건(`enc_yn = 'N'`)** 구조를 채택했다.

### 3. [해결 과정 및 트러블슈팅]
- **사전 검증**: 대상 테이블 백업 및 전체 `COUNT` 확정 후, 샘플 row를 대상으로 Damo 암·복호화 왕복 테스트를 먼저 수행해 함수 오적용으로 인한 데이터 훼손 가능성을 차단했다.
- **실행 및 모니터링**: 저부하 시간대에 백그라운드 작업을 띄운 뒤 `jobs -l`, `ps -ef | grep csql`, `tail -f encrypt_patch.log`로 진행 상황을 추적하면서 동시에 실제 운영 화면의 조회·인증 응답 속도에 지연이 없는지 체감 모니터링을 병행했다.
- **사후 대사**: 패치 완료 후 사전 확정 건수와 암호화 반영 건수(384만 건)를 대사하고, 애플리케이션 화면에서 복호화 조회가 정상 동작하는지 확인해 무중단으로 작업을 마쳤다.

### 4. [정량적/정성적 성과 및 배운 점]
- **성과**: 서비스 중단 및 사용자 지연 0건으로 **총 384만 건(CI 14만 건 + 이력 로그 370만 건) 암호화 완료**. 이 절차(`nohup` 백그라운드 + 범위 분할 커밋 + 멱등 조건 + 전후 대사)는 이후 연계 데이터 보정 등 다른 대량 DB 작업의 표준 절차로 재사용됐다.
- **배운 점**: 대량 DML의 핵심은 `nohup` 명령어 한 줄이 아니라 **"중간에 죽어도 같은 스크립트를 그대로 다시 돌릴 수 있는가(Idempotency)"**와 **"실사용자 트랜잭션이 블록 사이에 끼어들 수 있게 락 보유 시간을 쪼갰는가"**에 있다.

## Case 4. 인프라 용량 모니터링 자동화 (`JSch` → `Apache MINA SSHD`) & SAST 358건 → 4건 개선

- **원문**: [JSch가 WEB 서버 앞에서 멈춘 날 — Apache MINA SSHD로 서버 용량 모니터링 만들기](/blog/jsch-to-mina-sshd) / CWE 보안 시리즈 8편

### 1. [문제 정의 및 배경]
- **수기 서버 점검**: 매월 말 인터넷망·업무망의 WEB/WAS 서버마다 터미널로 접속해 `free -h`, `df -h`를 치고 표로 옮겨 적는 반복 수작업이 있었고, 공공 인프라 특성상 각 서버에 별도 모니터링 에이전트를 설치하기엔 보안 승인 비용이 컸다.
- **SAST 358건 검출**: CodeRay 정적분석에서 XSS(200여 건), NPE 역참조(20여 건), 오류 메시지 노출(25여 건), 자원 미해제 등 총 **358건**의 보안 약점이 검출됐다.

### 2. [기술적 의사결정 및 트러블슈팅]
- **[Troubleshooting] JSch 암호화 알고리즘 협상 실패와 MINA SSHD 전환**:
  - 에이전트 설치 대신 대표 WAS 1대가 Quartz(4시간 주기)로 각 서버에 SSH 접속해 명령 결과를 수집하는 구조를 설계했다.
  - 초기 적용한 `JSch`가 로컬/개발 서버에서는 잘 붙었으나 **운영 WEB 서버 앞에서 인증 단계조차 가지 못하고 실패**했다. `/etc/ssh/sshd_config`와 `ssh -vvv` 협상 로그를 비교한 결과, 운영 서버는 보안 정책상 `ssh-rsa`(SHA-1) 등 구형 알고리즘이 비활성화돼 있었고 오래된 JSch와 알고리즘 교집합이 없었다.
  - 보안 점검을 받는 시스템에서 서버 보안 설정을 낮추는(구형 알고리즘 허용) 대신, 최신 키 교환(kex)·호스트키 알고리즘을 지원하는 **Apache MINA SSHD 2.16.0**으로 클라이언트를 교체해 해결했다.
- **[Edge Cases] 비동기 타임아웃 격리와 예외 마스킹 방지**:
  - 모니터링 대상 서버 1대가 죽거나 방화벽에 막혔을 때 전체 수집 스레드가 무한 대기하지 않도록, MINA SSHD의 연결·인증·채널 오픈·종료 대기 모든 Future 단계에 `verify(10, TimeUnit.SECONDS)` 타임아웃을 걸었다.
  - 프롬프트 파싱이 불필요하고 종료 이벤트(`CLOSED`)가 명확한 `CHANNEL_EXEC`를 사용하며 `stdout`/`stderr`를 분리 수집했다. 특히 `finally`에서 채널→세션→클라이언트 역순 종료 시 `close()` 예외가 `try` 블록의 원본 예외를 덮어쓰지 않도록 원본 예외 보존 분기를 구현했다.
- **[SAST 전략] 데드 코드 제거 + 공통 뿌리 수정**:
  - 358건을 줄 단위로 고치지 않고, 먼저 검출 파일의 URL·메뉴 진입점을 역추적해 **실제 운영에서 쓰지 않는 벤더 샘플과 테스트 화면을 통째 삭제**(CWE-330·489·497)해 공격 표면과 작업량을 대폭 줄였다.
  - NPE 검출 20여 건(CWE-476)은 호출 사슬을 역추적해 **공통 유틸 메서드 1곳을 수정함으로써 15건을 일괄 해소**했고, 예외 정보 노출(CWE-209)은 `"고정 안내 문구 + 로거 throwable 전달"` 원칙으로 통일했다.

## 기본기를 다지기 위한 사이드 프로젝트 아이디어 (이 프로젝트 기반)

### Idea 1. B-Tree 복합 인덱스 & 실행계획 벤치마크 샌드박스
- **목적**: "등치 → 범위 → 정렬"과 "카디널리티(선택도)", "커버링 인덱스"가 실제 디스크 페이지 I/O와 실행 시간에 미치는 영향을 눈으로 증명하는 실습.
- **구현 내용**: Docker MySQL에 100만 건 더미 데이터(지역 17종, 상태 5종, `del_yn` 99:1, 등록일시)를 적재하고 ① 인덱스 없음 ② `del_yn` 선두 인덱스 ③ `reg_dt` 선두 인덱스 ④ 최적 복합 인덱스 4가지 케이스의 `EXPLAIN ANALYZE` 결과와 k6 부하 테스트 TPS 차이를 리포트로 정리.

### Idea 2. 무중단 대량 마이그레이션 시뮬레이터 (Lock 경합 & Zero-Offset Paging)
- **목적**: `csql + nohup`으로 수행한 384만 건 분할 커밋 패치를 애플리케이션 레벨에서 재구현하며 **Lock 경합과 페이징 성능** 비교하기.
- **구현 내용**: 실사용자 조회/수정 트래픽(초당 50건)이 도는 상태에서 ① 단일 트랜잭션 일괄 UPDATE ② `OFFSET` 페이징 분할 업데이트 ③ PK 커서(`WHERE id > :lastId LIMIT 5000`) 기반 Zero-Offset 분할 커밋 3가지를 실행해 실사용자 API의 p99 지연(Lock Wait)과 실패 지점 자동 재개(Resume) 체크포인트를 검증.

### Idea 3. 경량 SSH 리소스 수집기 & 다중 서버 분산 스케줄러 (`ShedLock` 실습)
- **목적**: 대표 WAS 1대 고정 플래그로 풀었던 Quartz 스케줄러를 **다중 인스턴스 자동 Failover 구조**와 **타임아웃 격리(Bulkhead)**로 고도화하기.
- **구현 내용**: 수집 서버 2대에 `ShedLock`을 적용해 1대 강제 종료 시 나머지 1대가 다음 주기에 자동 인계받는지 검증하고, 대상 컨테이너 1대에 `tc netem delay 15s` 네트워크 지연을 걸어 `verify(10s)` 타임아웃으로 정상 서버 수집이 보호되는지 테스트.
