> **이 글의 범위:** (주)마이크로 서비스 SI본부에서 전세사기 피해자 지원관리시스템의 안내 메시지 자동 발송 배치를 개발한 경험을 정리했다. **내가 개발한 영역**과 **메시징 솔루션 NURI2가 제공한 영역**을 나눠 적고, 확인하지 못한 내용은 **확인 필요**로 남겼다.

## 1. 한눈에 보기

| 구분 | 내용 |
| --- | --- |
| 배경 | 심의 지연으로 의결기한을 넘긴 대상자가 생겨 진행 상태 관련 민원 문의가 늘었다 |
| 만든 것 | 의결기한 도과 대상자에게 안내 메시지를 자동으로 보내는 배치, 발송 이력 화면, 미발송 건 선택 재발송 |
| 연동 방식 | 같은 CUBRID DB 안에 있는 NURI2의 DATA 테이블(큐 형태)에 적재하면, 솔루션 모듈이 가져가 발송 |
| 실행 시각 | 새벽 1시 대상자 추출·적재, 오전 10시 예약 발송 |
| 규모 | 일평균 30건. 규모는 작았다 |
| 업무 요건 | 대상자 한 명에게 **1회 발송** |
| 결과 | 관련 민원 문의 44건 → 31건 (약 29.5%). 콜센터 직원에게 직접 확인한 문의 건수 기준이며, 집계 기간은 확인 필요 |
| 운영 중 실패 | 실제 발송 실패는 없었다. **장애 해결 경험이 아니라 장애 가능성을 고려한 설계 경험**이다 |

## 2. 배경

심의·의결이 지연되면서 의결기한(60일 이내로 안내)을 넘긴 대상자가 생겼고, 진행 상태와 결정문에 관한 민원 문의가 늘었다. 그래서 의결기한이 지난 대상자에게 **안내 메시지를 자동으로 보내는 기능**을 만들었다.

## 3. 처리 흐름

```text
[직접 개발] 새벽 1시 배치 실행
[직접 개발]   → ① 신규: 의결기한 도과 대상자 조회
                 (발송 대상 관리 테이블 기준 NOT EXISTS로 이미 적재된 대상 제외)
                 → 발송 대상 관리 테이블에 적재
[직접 개발]   → ② 재발송: 발송 대상 관리 테이블에서 send_yn = N 대상 조회
[직접 개발]   → ①·② 대상을 Enum 템플릿 + Builder로 발송 객체 생성 (순차 처리)
[직접 개발]   → NURI2 DATA 테이블에 적재
                 (대상 관리 테이블 적재와 함께 하나의 트랜잭션)
[NURI2]       → 오전 10시 예약 발송
[NURI2]       → 알림톡 발송, 실패 시 SMS/LMS 대체 발송
[NURI2]       → 발송 후 DATA에서 빠지고 LOG 테이블에 이력 기록
[직접 개발]   → LOG와 대상 관리 테이블을 메시지 ID로 JOIN → send_yn Y/N 관리
[직접 개발]   → 운영자 발송 이력 화면, 미발송 건 선택(수동) 재발송
```

### 직접 개발한 영역과 솔루션이 제공한 영역

| 직접 개발 | NURI2 솔루션 제공 |
| --- | --- |
| 대상 조회 쿼리와 배치 | 발송 대기열(DATA 테이블) |
| 발송 대상 관리 테이블 | 예약 발송 |
| Enum 템플릿, Builder 기반 발송 객체 | 알림톡·SMS·LMS 발송 |
| NURI2 DATA 테이블 적재 | 알림톡 실패 시 대체 발송 |
| `send_yn` 관리, 미발송 재처리 | 발송 결과·이력 저장(LOG 테이블) |
| LOG JOIN 기반 이력 조회, 운영자 화면 | |

발송 엔진은 직접 만들지 않았다. 내가 만든 것은 **발송 엔진 앞뒤의 업무 연동**이다. 무엇을 누구에게 보낼지 정해 큐에 넣고, 보낸 결과를 업무 데이터와 맞춰 보는 부분이다.

## 4. 설계에서 나눈 것

### 4-1. 대상 관리와 발송 큐를 분리

NURI2의 DATA 테이블은 발송이 끝나면 비워지는 **대기열**이다. 그래서 "누구에게 보냈는가"를 업무 기준으로 남길 곳이 따로 필요했다. 이 역할을 내가 만든 **발송 대상 관리 테이블**이 맡았다.

| 테이블 | 역할 | 데이터 수명 |
| --- | --- | --- |
| 발송 대상 관리 테이블 (직접 개발) | 업무 기준 대상, `send_yn` | 계속 남음 |
| NURI2 DATA | 발송 대기열 | 발송되면 빠짐 |
| NURI2 LOG | 발송 결과와 이력 | 계속 남음 |

### 4-2. 신규 적재와 미발송 재발송을 나눔

배치는 매일 두 가지 일을 한다.

| 구분 | 대상 | 방식 |
| --- | --- | --- |
| 신규 적재 | 의결기한 도과 대상자 | **발송 대상 관리 테이블에 이미 있는 대상은 NOT EXISTS로 제외**하고 새로 적재 |
| 미발송 재발송 | 발송 대상 관리 테이블의 `send_yn = N` 대상 | 다음날 배치가 다시 뽑아 **순차 재발송** |

재적재 방지는 로그 테이블이 아니라 내가 관리하는 테이블을 기준으로 삼았다. 같은 대상이 관리 테이블에 두 번 쌓이지 않게 하는 1차 장치다. 한 번 적재된 대상은 신규 추출에서는 빠지고, 아직 N이면 재발송 쪽에서 다시 처리된다.

자동 재발송과 별도로, 운영자가 이력 화면에서 대상을 골라 보내는 **수동 재발송 기능**도 만들었다.

| 화면 | 수동 재발송 용도 |
| --- | --- |
| 미발송(N) 목록 | 다음날 자동 재발송을 기다리지 않고 당일 보내기 |
| 발송 완료(Y) 목록 | 예외 상황에 대비해 운영자 판단으로 다시 보내기 |

업무 요건은 **대상자당 1회 발송**이다. 자동 처리(신규 적재 제외, N만 재발송)는 이 요건을 따르고, 발송 완료 건의 재발송은 운영자가 판단하는 예외 통로로 열어 두었다.

### 4-3. 트랜잭션 범위

대상 관리 테이블 적재와 `send_yn` 갱신을 **하나의 트랜잭션**으로 묶어, 중간에 실패하면 함께 롤백되게 했다. NURI2 DATA 테이블이 같은 CUBRID DB에 있어서 DATA 적재도 함께 롤백된다.

다만 **이미 솔루션이 발송한 메시지는 롤백할 수 없다.** DB 롤백은 DB 안의 작업만 되돌리기 때문이다.

트랜잭션의 세부 설정(어노테이션 속성, 격리 수준 등)은 지금 근거를 들어 설명할 수 있을 만큼 정리되어 있지 않다. 그래서 면접에서는 **"무엇을 하나로 묶었는지"까지만 확정해서 말하고**, 세부 설정은 6장의 일반 원리로 보완한다.

### 4-4. 템플릿과 발송 객체

메시지 템플릿은 Enum으로 관리하고, 발송 객체는 Builder 패턴으로 만들었다. 템플릿 문구가 코드 여러 곳에 흩어지지 않고, 발송 객체를 만들 때 필요한 값을 이름으로 채울 수 있다.

## 5. 성과와 한계

### 성과

| 항목 | 내용과 단서 |
| --- | --- |
| 자동 발송 | 일평균 30건의 안내 메시지를 자동 발송했다. 규모는 작았다 |
| 민원 문의 | 44건 → 31건으로 감소 (`(44 - 31) / 44 ≈ 29.5%`). 콜센터 직원에게 직접 확인한 문의 건수 기준이며, 집계 기간은 확인 필요. 전후 비교이며 이 기능만의 효과로 단정하지 않는다 |
| 운영 확인 | 운영자가 발송 이력과 미발송 대상을 화면에서 보고, 미발송 건을 골라 다시 보낼 수 있게 했다 |

### 한계

- **`send_yn`의 N이 두 가지 상태를 구분하지 못한다.** "아직 발송 전"과 "발송은 됐지만 결과를 아직 못 받은 상태"가 모두 N이다. 다음날 배치가 N 대상을 자동으로 재발송하므로, 결과만 늦게 온 건이 다시 보내져 중복 발송이 될 수 있는 구조다.
- **당일 발송 원칙이 완벽히 보장되지 않을 수 있다.** 하루 단위로 도는 구조라 자동 재발송은 다음날 이뤄진다. 다만 운영자가 당일 확인하고 수동 재발송할 수 있었다.
- **운영 중에는 미발송이 남지 않았다.** 모니터링에서 발송되지 않은 건은 확인되지 않았다. 남았더라도 설계상 다음날 배치가 다시 보내고, 운영자도 수동으로 재발송할 수 있었다.

### 지금 다시 한다면 (당시 구현이 아니라 개선안)

| 한계 | 개선 방향 |
| --- | --- |
| N이 "발송 전"과 "결과 미수신"을 구분 못 함 | 상태 컬럼이나 적재 시각을 추가해 구분 |
| 결과 미수신 건의 재발송 위험 | 재발송 전에 LOG를 먼저 확인해 Y로 보정하고, 그래도 모르면 사람이 확인 |
| 1회 발송 요건을 코드 흐름으로만 지킴 | 업무 키 유일 제약이나 상태 전이로 DB가 1회를 보장하게 함 (당시 제약 여부는 확인 필요) |
| 발송 완료 건 재발송이 운영자 판단에만 맡겨짐 | 재발송 사유와 실행자를 이력으로 남김 |

## 6. 기술 원리 정리

아래는 경험을 설명할 때 필요한 **일반 원리**다. 당시 구현과 구분한다.

### 중복 발송 방지

| 단계 | 당시 구현 | 남은 위험 |
| --- | --- | --- |
| 1차 | 조회 쿼리에서 대상 관리 테이블 기준 NOT EXISTS | — |
| 2차 | `send_yn`과 LOG 대조 | 발송 후 결과를 받지 못한 N을 다시 보내는 경우 |
| 재발송 | 다음날 배치의 N 대상 순차 재발송, 운영자 수동 재발송 | 결과 미수신 N도 재발송 대상이 됨 |

더 견고하게 하려면 일반적으로 다음 방법을 함께 쓴다. 당시 적용 여부는 확인 필요다.

- 업무 키(대상자 + 회차 등)에 **유일 제약**을 걸어 DB가 중복 적재를 거부하게 한다.
- 배치를 여러 서버에서 돌린다면 **한 곳에서만 실행되도록** 잠금을 둔다.

**당시 서버 구조:** WAS 1번과 2번이 **모두 기동 중**이고, 1번이 내려가면 2번으로 넘어가는 구조였다. 두 WAS는 같은 WAR와 같은 DB를 바라본다. 운영 중 중복 발송 문제는 확인되지 않았다.

다만 이 구조에서는 짚어 볼 점이 있다. 장애 전환은 보통 **요청이 가는 서버**를 바꾸는 것이고, WAR 안의 스케줄러는 서버가 떠 있기만 하면 돈다. 같은 WAR가 두 서버에 모두 떠 있다면 새벽 1시 배치가 **두 곳에서 동시에** 돌 수 있다. 그 경우 NOT EXISTS는 두 배치가 같은 순간에 조회한 대상을 함께 적재하는 것을 막지 못한다.

당시에는 **인프라 설정으로 한 곳만 동작하도록** 되어 있었다. 쉘로 WAS를 기동하면, 1번이 구동 중일 때 2번 로그에 "1번을 바라보고 있다"는 내용이 남았다. 이 로그로 보아 2번은 1번이 살아 있는 동안 대기 상태로 있었던 것으로 **추정**한다.

이 설정은 인프라 영역이라 정확한 방식은 확인하지 못했다. 그래서 면접에서는 이렇게 나눠 말한다.

| 구분 | 내용 |
| --- | --- |
| 확인된 것 | 인프라 설정으로 한 곳만 동작, 2번 기동 로그에 1번을 바라본다는 메시지, 운영 중 중복 발송은 확인되지 않음 |
| 모르는 것 | 그 설정의 정확한 방식, 대기 중인 2번에서 애플리케이션 스케줄러가 어떤 상태였는지 |
| 지금이라면 | 인프라 설정에만 기대지 않고, 애플리케이션에서도 ShedLock 같은 실행 잠금이나 업무 키 유일 제약으로 한 번 더 막겠다 |
- 재발송은 "실패"로 확정된 건만 대상으로 하고, "결과 미확인"은 먼저 확인한다.

### 트랜잭션의 한계

트랜잭션은 같은 DB 안의 작업을 함께 커밋하거나 함께 롤백한다. 이번 구조는 NURI2 DATA가 같은 DB에 있어서 적재까지는 하나로 묶을 수 있었다. 하지만 **솔루션이 가져가 외부로 보낸 메시지는 되돌릴 수 없다.** 그래서 "적재까지의 원자성"과 "발송 결과의 확인"을 따로 설계해야 한다.

### Spring `@Transactional` 기본

당시 세부 설정을 설명할 수 없는 부분을 보완하려고 정리한 일반 원리다. 아래 코드는 **학습용 예시이며 실제 소스가 아니다.**

```java
@Service
public class NoticeEnqueueService {

    // 대상 관리 테이블 적재와 NURI2 DATA 적재를 하나의 트랜잭션으로 묶는 예
    @Transactional(rollbackFor = Exception.class)
    public void enqueue(NoticeTarget target) {
        targetMapper.insertTarget(target);           // 발송 대상 관리 테이블
        nuriMapper.insertData(target.toMessage());   // NURI2 DATA (같은 DB)
    }
}
```

**동작 방식:** Spring은 `@Transactional`이 붙은 빈을 프록시로 감싼다. 바깥에서 이 메서드를 호출하면 프록시가 트랜잭션을 시작하고, 정상 종료 시 커밋, 예외 시 롤백한다. MyBatis도 Spring이 관리하는 트랜잭션에 참여하므로 두 매퍼의 INSERT가 같은 트랜잭션에 묶인다.

| 알아 둘 점 | 내용 |
| --- | --- |
| 기본 롤백 대상 | `RuntimeException`과 `Error`. 체크 예외는 기본으로 롤백하지 않으므로 필요하면 `rollbackFor`를 지정한다 |
| 예외를 삼키면 | 메서드 안에서 `catch`하고 다시 던지지 않으면 정상 종료로 보고 **커밋**된다 |
| 자기 호출 | 같은 클래스 안에서 `this.enqueue()`처럼 부르면 프록시를 거치지 않아 트랜잭션이 적용되지 않는다 |
| 전파(propagation) | 기본값 `REQUIRED`는 진행 중인 트랜잭션이 있으면 참여하고 없으면 새로 만든다. `REQUIRES_NEW`는 항상 새 트랜잭션을 연다 |
| 격리 수준(isolation) | 기본값 `DEFAULT`는 DB의 기본 격리 수준을 따른다 |
| 범위 정하기 | 배치 전체를 하나로 묶으면 한 건 실패에 전체가 롤백된다. 대상 한 건 단위로 묶으면 실패 영향이 그 건으로 줄어든다 |

**면접에서 말하는 법:** "대상 관리 적재와 DATA 적재를 하나의 트랜잭션으로 묶었다"까지는 확정해서 말한다. 어노테이션 속성 같은 세부 설정은 모른다고 말하고, 위 원리로 "이렇게 동작한다고 이해하고 있다"고 설명한다.

### DB 테이블을 큐로 쓰는 방식

업무 시스템은 DATA 테이블에 넣기만 하고, 발송은 솔루션 모듈이 따로 가져가 처리한다. 업무 시스템이 발송 완료를 기다리지 않아도 되는 **비동기 구조**다. 대신 결과는 LOG를 따로 조회해야 알 수 있다.

## 7. 이어지는 질문 대비

답변은 외우는 문장이 아니라 **확인된 것 / 모르는 것 / 보완할 것**을 나눠 말하는 틀로 준비한다.

| 질문 | 확인된 것 | 모르는 것 | 보완할 것 |
| --- | --- | --- | --- |
| NURI2는 어떤 솔루션이고, 직접 발송했나요? | DATA 테이블에 적재하면 솔루션의 별도 모듈이 발송, 결과는 LOG에서 확인 | 솔루션 내부 동작 | 직접 개발 영역과 솔루션 영역을 나눠 말하기 |
| 중복 발송은 어떻게 막았나요? | 업무 요건은 1회 발송. 1차 NOT EXISTS, 2차 `send_yn`과 LOG 대조, 자동 재발송은 N만 | 업무 키 유일 제약 여부 | 결과 미수신 N의 한계와 개선안을 함께 말하기 |
| 트랜잭션은 어떻게 잡았나요? | 대상 관리 적재와 `send_yn` 갱신을 하나로 묶음. NURI2 DATA도 같은 DB라 함께 롤백 | 세부 설정(어노테이션 속성, 격리 수준) | 세부 설정은 모른다고 말하고 6장 원리로 설명. 이미 발송된 메시지는 롤백할 수 없다는 점 |
| 발송 실패는 어떻게 처리했나요? | 운영 중 실제 실패는 없었다. 대체 발송은 솔루션 기능 | — | 장애 해결이 아니라 설계 경험으로 말하기 |
| 민원 30% 감소의 근거는? | 44건 → 31건. 콜센터 직원에게 직접 확인한 문의 건수 | 집계 기간 | 다른 요인을 분리해 측정하지 못했다고 말하기 |
| 미발송 건은 어떻게 다시 보냈나요? | 다음날 배치가 대상 관리 테이블의 N 대상을 뽑아 순차 재발송. 운영자 수동 재발송(미발송 목록, 발송 완료 목록 모두)도 구현. 운영 중 미발송이 남은 건은 확인되지 않음 | — | 결과 미수신 N도 재발송될 수 있다는 한계와 개선안을 함께 말하기 |
| WAS가 두 대인데 배치가 두 번 돌지 않나요? | WAS 1·2번 모두 기동, 1번 장애 시 2번으로 전환. 같은 WAR·DB. 인프라 설정으로 한 곳만 동작했고 2번 기동 로그에 1번을 바라본다는 메시지가 남음. 운영 중 중복 발송은 확인되지 않음 | 인프라 설정의 정확한 방식 | 모르는 부분은 인정하고, 지금이라면 ShedLock 같은 실행 잠금이나 업무 키 유일 제약으로 막겠다고 말하기 |

### 고정 답변: "메시지가 일부만 안 갔다"는 항의

**질문:** 고객사가 "메시지가 일부만 안 갔다"고 항의했을 때, 실제로 어떤 순서로 처리했는지 1분 안에 설명해 주세요.

> **로그에서 누락을 확인하고 소스와 커밋 이력으로 시점의 장애를 확인한 뒤, 그 사실을 담당자에게 전달했습니다.**

이 한 문장 뒤에 순서를 물으면 아래 흐름으로 풀어 말한다.

```text
1. LOG 테이블에서 해당 대상의 발송 이력이 있는지 확인
2. 이력이 없으면(누락) 그 시점의 소스와 커밋 이력을 확인해 장애 여부 파악
3. 확인한 사실을 담당자에게 전달
```

**말할 때 주의할 점**

- 이 답변은 **원인을 확인해 전달한 경험**이다. 솔루션의 발송 장애를 직접 고친 경험으로 넓혀 말하지 않는다.
- 운영 중 실제 발송 실패는 없었다는 점과 어긋나지 않게, "장애를 해결했다"가 아니라 **"장애 여부를 확인했다"** 로 말한다.
- 확인 결과가 무엇이었는지, 전달받은 담당자가 누구였는지는 **확인 필요**다. 묻기 전에 먼저 말하지 않는다.

## 8. 지원 직무와 연결 — 엠앤와이즈 TS팀

엠앤와이즈는 UMS 같은 메시징 솔루션을 고객사에 공급한다. 이 경험은 **메시징 솔루션에 업무 시스템을 연동하는 쪽, 즉 고객사 개발자의 자리**에서 일해 본 경험이다.

> 기존 메시징 솔루션을 이해해 업무 시스템에 연계하고, 발송 요청과 처리 이력을 분리해 운영자가 확인할 수 있는 기능을 만든 경험입니다. 고객사 시스템이 발송 요청을 넣고 결과 이력을 확인하는 구조에서, 요청을 넣는 부분과 결과를 확인하는 부분이 어디서 어긋날 수 있는지 알고 있어 고객사 문의를 이해하는 데 도움이 될 것이라고 생각합니다.

**TS 면접에서 특히 나올 수 있는 주제**

| 주제 | 이 글에서 볼 곳 |
| --- | --- |
| DB 테이블을 큐로 쓰는 연동 방식 | 3장 처리 흐름, 6장 "DB 테이블을 큐로 쓰는 방식" |
| 발송 요청과 결과 이력의 분리 | 4-1 대상 관리와 발송 큐 분리 |
| 중복 발송과 결과 미확인 | 5장 한계, 6장 중복 발송 방지 |
| 트랜잭션 범위와 한계 | 4-3, 6장 트랜잭션의 한계 |
| 일부 미발송 문의 대응 | 7장 고정 답변 |

**말할 때 주의할 점:** 발송 엔진은 직접 만들지 않았다. 엠앤와이즈 UMS의 내부 구조는 확인되지 않았으므로, NURI2와 같은 구조라고 단정하지 않는다.
