### 확정해서 말할 수 있는 문장

- 심사 지연 대상에게 안내 알림톡을 보내는 **자동 발송 배치와 운영자 이력 조회 화면**을 개발했다.
- 메시징 엔진은 **기존 NURI2 솔루션**을 썼고, 나는 업무 시스템 쪽 연계를 맡았다.
- `SEND_YN = Y`는 **발송 요청을 적재했다는 뜻**이지, 수신자에게 전달됐다는 뜻이 아니다.
- 도입 후 민원 문의가 **약 30% 줄었다**. 배치만의 효과로 단정하지 않는다.

## 2. 업무 배경

피해자 신청 후 지자체 조사와 국토교통부 심의·의결을 거쳐 인정 여부가 결정된다. 업무에서는 **지자체 30일, 국토교통부 30일 등 통상 60일 기준**으로 안내했지만, 실제로는 더 오래 걸리는 사례가 생겼다.

결정문은 여러 지원 제도를 신청할 때 쓰는 중요한 증빙이다. 그래서 심사가 늦어지면 신청자의 불안이 커지고 진행 상황 문의가 늘었다.

> **면접용 배경 한 줄:** “전세사기 피해자 인정 심사가 지연되는 동안 신청자 문의가 늘어서, 지연 대상에게 안내 메시지를 자동으로 보내 민원 부담을 줄이고자 했습니다.”

**주의:** ‘지원금이 자동 지급된다’, ‘반드시 60일 이내 결정된다’, ‘개인별 지원금 지급을 직접 처리했다’고 말하지 않는다.

## 3. 연동 구조와 내가 맡은 범위

```text
[업무 시스템 · 일일 배치]          ← 직접 개발
  └─ 심사 지연 대상 조회
        ▼
[발송 대상 관리 테이블]            ← 직접 개발
  └─ 대상 정보 · 메시지 키 · SEND_YN
        │  기존 NURI2 연동 모듈 참조
        │  Enum 템플릿 → 개인별 문구 생성
        ▼
[MyBatis INSERT → NURI2 DATA 테이블] ← 직접 개발 (적재 시 SEND_YN N → Y)
        ▼
[NURI2 메시징 엔진]                ← 기존 솔루션
  └─ 요청 처리 · 채널 발송 · 결과 기록
        ▼
[NURI2 LOG 테이블]
        │  메시지 키로 JOIN
        ▼
[발송 이력 조회 화면]              ← 직접 개발
  └─ 이력 확인 · 미확인 건 파악 · 재처리 대상 선택
```

※ 기억에 따른 논리적 흐름이다. 실제 클래스명·테이블명, LOG 기록 조건, 배치 시각, 트랜잭션 범위는 원본 소스로 확인해야 한다.

### DATA 테이블을 큐처럼 쓰는 구조

업무 시스템은 발송 요청 행을 DATA 테이블에 넣고, 메시징 엔진이 그 행을 읽어 처리한 뒤 결과를 LOG에 남긴다. 업무 시스템은 엔진의 내부 API를 직접 부르지 않고 **테이블이라는 약속된 경계**로만 연동한다.

그래서 업무 쪽 책임은 두 가지로 나뉜다.

1. **올바른 요청을 정확히 한 번 적재하는 것**
2. **결과를 LOG로 확인하는 것**

### 직접 수행한 일

| 순서 | 한 일 |
| --- | --- |
| 1 | 다른 기능에 이미 구현된 **NURI2 연동 모듈을 분석·참조** |
| 2 | 심사 지연 대상을 조회해 별도 **발송 대상 관리 테이블**로 관리 |
| 3 | 메시지 유형(SMS/LMS/MMS 등)은 공통 코드·Enum 상수로, 안내 문구는 **Enum 템플릿**으로 관리 |
| 4 | 이름·날짜 등을 템플릿에 넣어 **완성된 문자열**로 문구 구성 |
| 5 | Builder 형태로 발송 정보를 설정하고 **MyBatis INSERT**로 DATA 테이블에 적재 |
| 6 | 적재 시 `SEND_YN`을 **N → Y**로 갱신 |
| 7 | 대상 테이블과 LOG 테이블을 **메시지 키로 JOIN**한 운영자 이력 조회 화면 개발 |
| 8 | 이력 확인 후 대상을 골라 재발송하거나 일일 배치로 다시 처리하는 기능 마련 (**자동 재처리 조건과 중복 방지 상세는 미확인**) |

**면접에서는 ‘메시징 엔진을 개발했다’가 아니라 ‘기존 메시징 솔루션과 연계한 업무 배치와 운영 관리 기능을 개발했다’고 말한다.**

## 4. 발송 상태와 결과 이력의 차이

| 상태 | 의미 | 주의 |
| --- | --- | --- |
| `SEND_YN = N` | 아직 발송 요청 적재가 끝나지 않음 | 재처리 조건은 원본 로직 확인 필요 |
| `SEND_YN = Y` | DATA 테이블 적재 완료 | **최종 발송 성공 표시가 아님** |
| DATA 테이블의 요청 행 | 엔진이 처리할 발송 요청 | 적재 성공 ≠ 수신자에게 발송 성공 |
| LOG에 메시지 키 있음 | 그 키의 처리 이력 확인됨 | 결과값의 구체적 의미는 추가 판독 필요 |
| LOG에 메시지 키 없음 | 조회 시점에 이력이 확인되지 않음 | **실패 확정이 아님**. 처리 대기·반영 지연 가능 |

기억상 **발송되지 않은 건은 LOG 이력이 남지 않았던 것 같지만**, 이것이 NURI2의 공식 동작인지는 확인하지 못했다. `1001`, `1002`도 **결과 코드 관련 상수로 기억하는 정도**라서 의미를 확정하지 않는다.

## 5. 실제로 있었던 문의·사례

### “알림톡을 받지 못했다”는 문의

1. 휴대전화 번호로 발송 이력을 조회했다.
2. 해당 시점의 **Git 커밋 이력**을 확인했다.
3. 그때는 **발송 기능이 아직 구현되기 전**이어서 보내지지 않은 것으로 확인했다.

→ 발송 장애를 복구한 사례가 아니라, **이력과 개발 시점을 대조해 원인을 확인한 사례**다.

### 수신 대상이 잘못 선정된 사례

지자체 담당자에게 가야 할 메시지가 **국토교통부 담당자에게 발송된 사례**를 본 적이 있다. 전송 실패가 아니라 **대상 선정 조건의 문제**다. 직접 수행한 후속 조치는 확인되지 않았으므로, 이 사례에서 느낀 점으로만 말한다.

> **교훈:** "발송이 성공했다"와 "맞는 사람에게 맞는 내용이 갔다"는 다른 문제다. 메시징 연동에서는 결과 코드만큼 **대상 추출 조건과 수신자 구분**이 중요하다.

솔루션 쪽 발송 실패를 직접 처리한 사례는 기억나지 않는다. "실패 사례가 없었다"가 아니라 **"엔진 발송 장애를 직접 처리한 경험은 없다"** 로 말한다.

## 6. 성과 수치와 설명 범위

| 항목 | 내용 |
| --- | --- |
| 개선 전 → 후 | 민원 문의 44건 → 31건 |
| 계산 | `(44 - 31) / 44 × 100 ≈ 29.5%` → 약 30% |
| 수치 성격 | 실무 기억에 근거한 전후 비교 |
| 아직 확인할 점 | 비교 기간, 같은 조건 비교 여부, 다른 요인(심사 진행 속도 변화 등) |

**말하는 기준:** “안내 기능을 도입한 뒤 당시 집계 기준으로 민원 문의가 약 30% 줄었습니다.” 정밀한 인과 검증 결과라고 말하지 않는다.

## 7. 면접 답변

### 약 1분 답변

> 전세사기 피해자 인정 심사가 지연되면서 결과를 기다리는 신청자들의 문의가 늘어나는 문제가 있었습니다.
>
> 이를 줄이기 위해 기존 기능에 구현된 NURI2 연동 모듈을 참고해 알림톡 자동 발송 배치를 개발했습니다.
>
> 심사 지연 대상자를 별도 테이블에서 관리하고, 메시지 템플릿과 발송 정보를 구성해 MyBatis로 NURI2 DATA 테이블에 적재하도록 했습니다.
>
> 또 발송 대상 테이블과 LOG 테이블을 메시지 키로 연결한 이력 조회 화면을 만들어, 운영자가 발송 내역을 확인하고 재처리 대상을 관리할 수 있게 했습니다.
>
> 도입 후 민원 문의는 당시 집계 기준으로 약 30% 줄었습니다.

### 20초 압축 답변

> 심사 지연으로 문의가 늘어서, 지연 대상에게 안내 알림톡을 보내는 배치를 만들었습니다. 발송 엔진은 기존 NURI2 솔루션을 쓰고, 저는 대상 관리·DATA 테이블 적재·LOG 연계 이력 조회 화면을 개발했습니다. 도입 후 민원 문의가 약 30% 줄었습니다.

## 8. 예상 꼬리 질문

### 역할과 구조

**Q1. 본인이 개발한 영역과 솔루션 기능은 어떻게 다른가요?**
저는 심사 지연 대상 조회, 발송 데이터 구성과 적재, 발송 상태 관리, 운영자 이력 조회와 재처리 기능을 개발했습니다. 실제 발송 엔진과 채널 처리 로직은 기존 NURI2 솔루션을 활용했습니다.

**Q2. DATA 테이블에 적재하는 방식의 장단점은 무엇인가요?**
업무 시스템은 정해진 테이블에 요청을 넣기만 하면 되므로 엔진과 결합도가 낮고, 엔진이 잠시 멈춰도 요청이 테이블에 남습니다. 반면 결과가 비동기로 LOG에 남기 때문에 적재 성공과 발송 성공을 구분해야 하고, 결과는 따로 조회해야 합니다. 그래서 `SEND_YN`과 LOG 조회 화면을 분리했습니다.

### 상태와 실패 처리

**Q3. `SEND_YN`은 발송 성공 여부인가요?**
아니요. 요청이 NURI2 DATA 테이블에 적재되었는지 관리하는 값입니다. 적재 시 `N`에서 `Y`로 바꾸고, 실제 처리 결과는 메시지 키로 LOG 테이블과 연결해 따로 확인했습니다.

**Q4. 메시지가 발송되지 않았을 때 어떻게 확인했나요?**
이력 조회 화면에서 휴대전화 번호로 확인했습니다. 실제 문의 사례에서는 Git 커밋 이력까지 대조해, 문의 시점에 기능이 아직 구현되지 않았다는 것을 확인했습니다. 엔진 쪽 발송 장애를 직접 처리한 경험은 없습니다.

**Q5. 결과 코드 `1001`, `1002`는 무슨 의미인가요?**
결과 코드 관련 상수와 이력 테이블을 참고해 개발한 것은 기억하지만, 코드별 정확한 의미는 지금 확정해서 말씀드리기 어렵습니다. 적재 상태와 결과 이력은 분리해 관리했습니다.

**Q6. 발송 결과가 없으면 자동으로 재발송했나요?**
미발송·이력 미확인 건을 확인하고 재처리할 수 있게 했습니다. 다만 LOG 반영 지연을 어떻게 구분했는지, 자동 재처리의 상세 조건은 원본 로직을 확인해야 정확히 말씀드릴 수 있습니다.

**Q7. 같은 대상에게 중복 발송되지 않도록 어떻게 했나요?**
`SEND_YN`으로 이미 적재한 대상과 아직 적재하지 않은 대상을 구분했습니다. 동시 실행이나 재처리까지 막는 유일 제약·멱등 처리가 있었는지는 원본 코드를 확인해야 합니다. 지금 다시 설계한다면 대상과 발송 회차를 묶은 유일 키를 최종 방어선으로 두고, 조건부 UPDATE로 한 건씩 선점하고, 배치가 한 서버에서만 돌게 하겠습니다. 재발송은 LOG 반영 대기 시간이 지난 뒤 결과를 다시 확인하고 하겠습니다. *(방어층 정리: 11-1)*

**Q7-1. 배치가 두 서버에서 동시에 돌면 어떻게 되나요?**
`SEND_YN`만 보고 처리하면 두 실행이 같은 `N` 건을 동시에 읽어 둘 다 적재할 수 있습니다. 그래서 일반적으로는 ShedLock 같은 DB 락으로 한 서버만 실행하게 하고, 조건부 UPDATE로 선점하고, 유일 제약으로 마지막에 한 번 더 막습니다. 당시 서버 구성과 실행 제어 방식은 확인이 필요합니다.

### 데이터와 성과

**Q8. 휴대전화 번호 같은 개인정보는 어떻게 다뤘나요?**
발송에는 수신자 번호가 필요해서 업무 시스템의 대상 정보로 발송 데이터를 구성했습니다. 이력 조회 화면의 접근 권한, 표시 마스킹, 저장 암호화 여부는 정확히 기억나지 않아 확인이 필요합니다.

**Q9. 대상자 선정이 잘못되어 다른 사람에게 메시지가 간 경우는 없었나요?**
지자체 담당자에게 가야 할 안내가 국토교통부 담당자에게 간 사례를 본 적이 있습니다. 전송 장애가 아니라 대상 선정 조건의 문제였습니다. 그래서 발송 결과뿐 아니라 대상 추출 조건과 수신자 구분을 검증하는 것이 중요하다고 느꼈습니다.

**Q10. 성과는 어떻게 확인했나요?**
민원 문의가 44건에서 31건 정도로 줄어든 것으로 기억합니다. 약 30% 수준인데, 정확한 집계 기간과 같은 조건 비교 여부는 확인되지 않아 당시 관찰한 운영 성과로 설명합니다.

### 회고

**Q11. 지금 다시 한다면 무엇을 바꾸겠나요?**
`SEND_YN` 두 값 대신 적재·결과 확인 단계를 나눈 상태로 관리하고, 대상과 발송 회차로 유일 키를 두겠습니다. 발송 전에 대상 추출 결과를 건수와 수신자 구분으로 점검하는 단계도 넣겠습니다.

**Q12. 이 경험으로 무엇을 배웠나요?**
외부 솔루션과 연동할 때는 **"요청을 넣었다"와 "결과가 나왔다"를 분리해서 봐야 한다**는 것을 배웠습니다. 그리고 발송이 성공해도 대상이 틀리면 의미가 없기 때문에, 기술적인 성공과 업무적인 정확성을 함께 확인해야 한다고 생각하게 됐습니다.

**Q13. 이 경험이 지원 직무와 어떻게 연결되나요?**
기존 솔루션 모듈을 분석해 업무 시스템에 연계하고, 요청과 처리 이력을 나눠 운영자가 확인할 수 있게 만든 경험입니다. 솔루션 연동, 이력 기반 원인 확인, 운영 관점의 기능 설계가 함께 들어 있어 연동 개발과 운영 지원 업무에 연결된다고 생각합니다.
*(회사별로 맞춘 답은 해당 회사 준비 글에 둔다. 예: [엠앤와이즈 TS팀 면접 준비](/blog/interview-mnwise-ts-prep))*

## 10. 지금 다시 설계한다면

실제로 구현한 내용이 아니라 복기하면서 정리한 개선안이다. "보완할 점"을 물으면 **당시 구현과 구분해서** 말한다.

| 당시 구조 | 보완 방향 |
| --- | --- |
| `SEND_YN` Y/N으로 적재 여부만 관리 | `READY → QUEUED → DONE / FAIL`처럼 적재·결과 확인 단계를 나눠 관리 |
| LOG 미확인 건을 운영자가 보고 재처리 | LOG 반영 대기 시간을 정하고, 지나도 이력이 없는 건만 재처리 대상으로 분류 |
| 중복 방지 수단 미확인 | 대상 + 발송 회차(또는 기준일)로 유일 키를 두어 재실행 시에도 한 번만 적재 |
| 메시지 키 생성 방식 미확인 | 업무 키(대상·회차)로 메시지 키를 만들어 같은 요청은 같은 키가 되게 함 |
| 배치 단일 실행 여부 미확인 | DB 락(ShedLock 등)이나 Job 파라미터로 한 번에 하나만 실행 |
| 수동 재발송 | 배치와 같은 선점·제약 조건을 거치게 하고, 직전 발송 이력을 화면에 표시 |
| 중복 여부를 사후에 확인하지 않음 | 수신자·회차별 중복 탐지 쿼리로 주기 점검 |
| 대상 선정 오류를 발송 후 발견 | 발송 전에 추출 결과를 건수·수신자 구분으로 점검 |
| 성과를 민원 건수 전후로만 기억 | 집계 기간과 기준을 고정해 발송 건수·민원 건수를 같은 기간으로 비교 |

## 11. 이론 보충 — 기술 질문 대비

> 아래는 면접 준비 중 공부한 일반 원리와 학습용 예시다. 실제 NURI2 연동 소스가 아니다.

### 11-1. 중복 발송을 막는 방어층

> 당시 구현은 `SEND_YN`으로 적재 여부를 구분한 것까지다. 아래는 **일반적인 모범 방식**을 공부한 내용이며 당시 적용했다는 뜻이 아니다.

**중복은 어디서 생기나**

| 상황 | 예 |
| --- | --- |
| 배치가 두 번 실행됨 | WAS 이중화로 두 서버에서 같은 스케줄이 동시에 실행 |
| 적재 도중 실패 후 재실행 | DATA INSERT는 됐는데 `SEND_YN` 갱신 전에 오류 → 다음 실행에서 다시 적재 |
| 결과 미확인 상태에서 재발송 | LOG 반영이 늦을 뿐인데 실패로 보고 다시 보냄 |
| 수동 재발송 | 운영자가 이력 화면에서 같은 건을 다시 보냄 |

한 가지 장치로는 네 상황을 다 막기 어렵다. 그래서 **여러 층으로 방어**하고, 마지막 방어선은 DB 제약으로 둔다.

| 층 | 방어 수단 | 막는 상황 |
| --- | --- | --- |
| ① 추출 | 이미 적재한 대상을 추출 쿼리에서 제외 | 재실행 |
| ② 실행 | 배치를 한 번에 하나만 실행 | 동시 실행 |
| ③ 선점 | 조건부 UPDATE로 한 건씩 선점 | 동시 실행, 재실행 |
| ④ 원자성 | DATA 적재와 상태 변경을 한 트랜잭션으로 | 적재 도중 실패 |
| ⑤ 제약 | 업무 키 유일 제약 + 결정적인 메시지 키 | 모든 상황의 최종 방어선 |
| ⑥ 재발송 | 결과 미확인과 실패를 구분한 뒤에만 재발송 | 결과 미확인 재발송, 수동 재발송 |
| ⑦ 점검 | 중복 탐지 쿼리로 사후 확인 | 놓친 경우 발견 |

#### ① 추출 단계에서 이미 보낸 대상 제외

```sql
-- 학습용 예시: 같은 회차에 이미 적재한 대상은 뽑지 않는다
SELECT a.applicant_id, a.receiver
  FROM applicant a
 WHERE a.decision_due_dt < CURRENT_DATE
   AND NOT EXISTS (
         SELECT 1 FROM notice_target t
          WHERE t.applicant_id = a.applicant_id
            AND t.notice_round = #{noticeRound}
       );
```

#### ② 배치를 한 번에 하나만 실행

WAS가 두 대면 같은 `@Scheduled` 작업이 두 서버에서 동시에 돌 수 있다. DB 락 테이블로 한 서버만 실행하게 하는 방법이 흔하다.

```java
// 학습용 예시: ShedLock — 락을 얻은 서버 한 대만 실행
@Scheduled(cron = "0 0 5 * * *")
@SchedulerLock(name = "reviewDelayNotice", lockAtMostFor = "PT30M")
public void sendReviewDelayNotice() {
    noticeService.enqueueTargets();
}
```

Spring Batch를 쓴다면 같은 Job 파라미터(예: 기준일)로 이미 완료된 JobInstance는 다시 실행되지 않는다.

#### ③ 조건부 UPDATE로 선점

`SEND_YN`처럼 두 값만 있으면 "적재 중에 죽은 건"과 "아직 시작 안 한 건"을 구분하기 어렵다. 상태를 `READY → QUEUED → DONE / FAIL`로 나누고 **조건부 UPDATE로 한 건을 선점**하면, 두 배치가 동시에 돌아도 한쪽만 처리한다.

```sql
-- 학습용 예시: READY인 건만 QUEUED로 바꾼다. 영향받은 행이 1이면 내가 선점한 것
UPDATE notice_target
   SET status = 'QUEUED', queued_at = CURRENT_TIMESTAMP
 WHERE target_id = #{targetId}
   AND status = 'READY';
```

#### ④ 적재와 상태 변경을 한 트랜잭션으로

```java
// 학습용 예시: 선점·적재가 함께 커밋되거나 함께 롤백된다
@Transactional(rollbackFor = Exception.class)
public void enqueue(NoticeTarget target) {
    if (targetMapper.markQueued(target.getId()) != 1) {
        return;                                   // 다른 실행이 이미 선점
    }
    nuriMapper.insertMessage(toMessage(target));  // DATA 적재
}
```

두 테이블이 **다른 DB**에 있으면 이 방식으로 원자성이 보장되지 않는다(11-2, 11-3 참고).

#### ⑤ 업무 키 유일 제약과 결정적인 메시지 키

"이 사람에게 이 회차 안내는 한 번"을 DB가 강제하게 한다. 코드에 실수가 있어도 두 번째 적재는 제약 위반으로 거부된다.

```sql
-- 학습용 예시
ALTER TABLE notice_target
  ADD CONSTRAINT uk_notice_target UNIQUE (applicant_id, notice_round);
```

메시지 키도 무작위 값 대신 **업무 키로 만들면** 같은 요청은 항상 같은 키가 된다. DATA 테이블의 키 컬럼에 유일 제약을 둘 수 있다면 그 단계에서도 중복이 바로 드러난다.

```java
// 학습용 예시: 같은 대상·회차면 항상 같은 메시지 키
String msgKey = "RD-" + noticeRound + "-" + applicantId;
```

솔루션 테이블(NURI2 DATA)에 제약을 추가할 수 있는지는 솔루션 정책에 따라 다르므로, 보통은 **업무 쪽 대상 테이블**에 먼저 둔다.

#### ⑥ 결과 미확인과 실패를 구분한 뒤에만 재발송

| 상태 | 판단 | 재발송 |
| --- | --- | --- |
| 적재 후 대기 시간 이내, LOG 없음 | 결과 미확인 | 하지 않음 |
| 대기 시간이 지나도 LOG 없음 | 확인 필요 | 솔루션 쪽 확인 후 결정 |
| LOG에 실패 결과 | 실패 | 새 회차(또는 재발송 순번)로 보냄 |
| LOG에 성공 결과 | 완료 | 하지 않음 |

재발송 직전에 LOG를 **한 번 더 조회**한다. 운영자 화면의 수동 재발송도 같은 조건(③·⑤)을 거치게 하고, 화면에 직전 발송 이력을 함께 보여 준다.

#### ⑦ 중복 탐지 쿼리로 사후 점검

```sql
-- 학습용 예시: 같은 수신자·회차로 두 번 이상 적재된 건
SELECT receiver, notice_round, COUNT(*) AS cnt
  FROM msg_data
 GROUP BY receiver, notice_round
HAVING COUNT(*) > 1;
```

막는 장치가 있어도 실제로 0건인지 주기적으로 확인한다.

**면접용 한 문장:** “중복 발송은 코드 조건만으로 막기 어려워서, **DB 유일 키로 최종 방어선을 두고 상태 선점, 단일 실행, 결과 확인 후 재발송**을 함께 쓰는 것이 일반적입니다. 당시에는 `SEND_YN`으로 적재 여부를 구분했고, 지금 다시 한다면 대상과 회차로 유일 키부터 두겠습니다.”

### 11-2. `@Transactional` 기본 규칙

```java
// 학습용 예시
@Service
public class NoticeService {

    @Transactional(rollbackFor = Exception.class)   // 체크 예외도 롤백하려면 지정
    public void enqueue(NoticeTarget target) {
        nuriMapper.insertMessage(toMessage(target)); // DATA 적재
        targetMapper.markSent(target.getId());       // SEND_YN = 'Y'
    }
}
```

| 규칙 | 설명 |
| --- | --- |
| 기본 롤백 대상 | `RuntimeException`과 `Error`. 체크 예외는 `rollbackFor`가 없으면 커밋된다 |
| 자기 호출 | 같은 클래스 안에서 `this.enqueue()`처럼 부르면 프록시를 거치지 않아 트랜잭션이 적용되지 않을 수 있다 |
| 서로 다른 DB | 대상 테이블과 DATA 테이블이 **다른 DataSource**면 `@Transactional` 하나로 원자성이 보장되지 않는다 |
| 컴파일 오류 | `try-catch` 대상이 아니다. 예외 처리는 실행 중 오류에만 적용된다 |

실제 코드에서 어떤 방식을 썼는지는 **미확인**이므로 일반 원리로만 설명한다.

### 11-3. DB 큐와 Transactional Outbox

"업무 데이터를 바꾸면서 같은 DB 트랜잭션 안에서 발송 요청 행도 함께 쓰고, 별도 프로세스가 그 행을 읽어 내보내는" 구조를 **Transactional Outbox 패턴**이라고 부른다. NURI2 DATA 테이블 연동도 업무 시스템 입장에서는 비슷한 모양이다. 같은 DB에 있다면 업무 변경과 발송 요청이 함께 커밋되거나 함께 롤백된다는 장점이 있다. 실제 두 테이블이 같은 DB에 있었는지는 **미확인**이다.

### 11-4. Enum 템플릿과 `String.format`

```java
// 학습용 예시
public enum MessageTemplate {
    REVIEW_DELAY("%s님, 피해자 결정 심사가 지연되고 있습니다. 접수일: %s");

    private final String content;

    MessageTemplate(String content) { this.content = content; }

    public String format(Object... args) {
        return String.format(content, args);
    }
}

String text = MessageTemplate.REVIEW_DELAY.format("홍길동", "2026-11-19");
```

| 상황 | 결과 |
| --- | --- |
| 인자가 부족함 | 실행 중 `MissingFormatArgumentException` (컴파일 오류 아님) |
| 인자가 남음 | 예외 없이 무시됨 → **틀린 문구가 조용히 발송될 수 있음** |
| 대책 | 템플릿별 결과 문자열을 단위 테스트로 확인 |

Java 15 이상에서는 `"...".formatted(args)`도 쓸 수 있다. 실제 업무에서 `String.format()`을 썼는지, 저장 형식이 완성 문자열이었는지는 **확인 필요**다. 예전에는 JSON으로 기억했지만 이후 복기에서는 완성 문자열 쪽 기억이 더 강하다.

### 11-5. Builder 패턴

```java
// 학습용 예시
Message message = Message.builder()
        .receiver("01012345678")
        .messageType("ALIMTALK")
        .content(text)
        .build();
```

필드 이름이 드러나서 생성자보다 읽기 쉽고, 선택 필드를 다루기 편하다. 각 설정 메서드가 `return this`를 반환해서 **메서드 체이닝**이 된다. 기존 코드에서 Builder 호출 사이에 MyBatis INSERT가 있었던 것 같지만, `build()` 안에서 INSERT가 일어났는지는 **미확인**이다.

### 11-6. MyBatis `#{}`와 `${}`

```xml
<!-- 학습용 예시 -->
<insert id="insertMessage" parameterType="Message">
    INSERT INTO MSG_DATA (MSG_KEY, RECEIVER, MSG_TYPE, CONTENT)
    VALUES (#{msgKey}, #{receiver}, #{messageType}, #{content})
</insert>
```

- `#{}`: PreparedStatement 바인딩 파라미터. 값이 SQL 문법으로 해석되지 않는다.
- `${}`: 문자열을 SQL에 그대로 끼워 넣는다. 외부 입력에 쓰면 **SQL 인젝션 위험**이 있다.
- `sqlSession.insert("message.insertMessage", message)`의 첫 인자는 SQL 본문이 아니라 **namespace + id**다. 반환값은 영향받은 행 수다.
