> **이 글의 범위:** (주)마이크로 서비스 SI본부에서 전세사기 피해자 지원관리시스템의 안내 메시지 자동 발송 배치를 개발한 경험을 정리했다. **내가 개발한 영역**과 **메시징 솔루션 NURI2가 제공한 영역**을 나눠 적고, 확인하지 못한 내용은 **확인 필요**로 남겼다.

> **2026-11-22 정정 — [실무 경험: 본인 확인]:** `send_yn=Y`는 **NURI2 DATA에 요청 적재가 성공한 뒤** 바꾼 값이다. 최종 발송 성공 표시는 아니다. 기존의 “LOG 성공 확인 뒤 Y 갱신”처럼 읽히는 흐름과 그에 따른 재처리 위험 설명을 수정했다. 당시 원본 코드는 없으며, 이 확인은 본인의 구현 기억이지 소스 검증 완료를 뜻하지 않는다. 면접 연습 Q6의 이전 답변은 글 아래에 원문 그대로 보존했다.

## 2. 배경

심의·의결이 지연되면서 의결기한(60일 이내로 안내)을 넘긴 대상자가 생겼고, 진행 상태와 결정문에 관한 민원 문의가 늘었다. 그래서 의결기한이 지난 대상자에게 **안내 메시지를 자동으로 보내는 기능**을 만들었다.

## 3. 처리 흐름

```text
[직접 개발] 새벽 1시 배치 실행
[직접 개발]   → ① 신규: 의결기한 도과 대상자 조회
                 (발송 대상 관리 테이블 기준 NOT EXISTS로 이미 적재된 대상 제외)
                 → 발송 대상 관리 테이블에 적재
[직접 개발]   → ② 재발송: 발송 대상 관리 테이블에서 send_yn = N 대상 조회
[직접 개발]   → ①·② 대상을 Enum 템플릿 + Builder로 발송 객체 생성 (순차 처리)
[직접 개발]   → NURI2 DATA 테이블에 적재 → 적재 성공 후 send_yn = Y
                 (대상 관리 적재·상태 갱신과 함께 하나의 트랜잭션)
[NURI2]       → 오전 10시 예약 발송
[NURI2]       → 알림톡 발송, 실패 시 SMS/LMS 대체 발송
[NURI2]       → 발송 후 DATA에서 빠지고 LOG 테이블에 이력 기록
[직접 개발]   → LOG와 대상 관리 테이블을 메시지 ID로 JOIN → 실제 발송 결과 조회
[직접 개발]   → 운영자 발송 이력 화면, 미발송 건 선택(수동) 재발송
```

### 직접 개발한 영역과 솔루션이 제공한 영역

| 직접 개발 | NURI2 솔루션 제공 |
| --- | --- |
| 대상 조회 쿼리와 배치 | 발송 대기열(DATA 테이블) |
| 발송 대상 관리 테이블 | 예약 발송 |
| Enum 템플릿, Builder 기반 발송 객체 | 알림톡·SMS·LMS 발송 |
| NURI2 DATA 테이블 적재 | 알림톡 실패 시 대체 발송 |
| `send_yn` 관리, 미발송 재처리 | 발송 결과·이력 저장(LOG 테이블) |
| LOG JOIN 기반 이력 조회, 운영자 화면 | |

발송 엔진은 직접 만들지 않았다. 내가 만든 것은 **발송 엔진 앞뒤의 업무 연동**이다. 무엇을 누구에게 보낼지 정해 큐에 넣고, 보낸 결과를 업무 데이터와 맞춰 보는 부분이다.

## 4. 설계에서 나눈 것

### 4-1. 대상 관리와 발송 큐를 분리

NURI2의 DATA 테이블은 발송이 끝나면 비워지는 **대기열**이다. 그래서 "누구에게 보냈는가"를 업무 기준으로 남길 곳이 따로 필요했다. 이 역할을 내가 만든 **발송 대상 관리 테이블**이 맡았다.

| 테이블 | 역할 | 데이터 수명 |
| --- | --- | --- |
| 발송 대상 관리 테이블 (직접 개발) | 업무 기준 대상, DATA 요청 적재 여부 `send_yn` | 계속 남음 |
| NURI2 DATA | 발송 대기열 | 발송되면 빠짐 |
| NURI2 LOG | 발송 결과와 이력 | 계속 남음 |

### 4-2. 신규 적재와 요청 적재 재시도를 나눔

| 구분 | 대상 | 방식 |
| --- | --- | --- |
| 신규 적재 | 의결기한 도과 대상자 | 대상 관리 테이블에 이미 있는 대상은 NOT EXISTS로 제외 |
| 요청 적재 재시도 | 대상 관리 테이블의 `send_yn=N` | 다음날 배치에서 다시 조회해 순차적으로 DATA 적재 시도 |

**[실무 경험: 본인 확인]** DATA 적재가 성공하면 Y로 바꿨다. 따라서 N은 “DATA 적재 완료로 표시되지 않은 상태”이며, LOG에서 확인한 최종 발송 실패를 모두 대표하는 값으로 쓰면 안 된다. N의 상세 원인과 실패 뒤 상태 재설정 조건은 원본 코드 확인이 필요하다.

기존 기록에는 운영자가 N 목록과 Y 목록에서 수동으로 다시 보내는 기능도 있다. 여기서 당시 화면의 “발송 완료”가 Y 분류를 뜻하더라도 실제 전달 성공과 같은 의미는 아니다. Y 대상 재요청은 중복 발송 가능성이 있어 LOG 확인과 운영자 판단을 분리해야 한다.

업무 요건은 대상자당 1회 발송이었다. 신규 제외 조건과 재시도 경로가 그 요건을 겨냥한 것은 맞지만, 업무 키 유일 제약·동시 실행·외부 발송까지 포함한 정확히 한 번 처리가 증명된 것은 아니다.

### 4-3. 트랜잭션 범위

**[실무 경험: 기존 기록]** 대상 관리 테이블 적재·DATA 적재·`send_yn` 갱신을 하나의 트랜잭션 단위로 묶어 실패 시 함께 롤백되도록 설계했다. DATA는 같은 CUBRID DB에 있었다. 다만 같은 DB라는 사실만으로 모든 작업의 원자성이 입증되는 것은 아니다. 실제 연결·트랜잭션 관리자와 메서드 경계는 원본 코드로 재확인해야 한다.

다만 **이미 솔루션이 발송한 메시지는 롤백할 수 없다.** DB 롤백은 DB 안의 작업만 되돌리기 때문이다.

트랜잭션의 세부 설정(어노테이션 속성, 격리 수준 등)은 지금 근거를 들어 설명할 수 있을 만큼 정리되어 있지 않다. 그래서 면접에서는 **"무엇을 하나로 묶었는지"까지만 확정해서 말하고**, 세부 설정은 6장의 일반 원리로 보완한다.

### 4-4. 템플릿과 발송 객체

메시지 템플릿은 Enum으로 관리하고, 발송 객체는 Builder 패턴으로 만들었다. 템플릿 문구가 코드 여러 곳에 흩어지지 않고, 발송 객체를 만들 때 필요한 값을 이름으로 채울 수 있다.

## 5. 성과와 한계

### 성과

| 항목 | 내용과 단서 |
| --- | --- |
| 자동 발송 | 일평균 30건의 안내 메시지를 자동 발송했다. 규모는 작았다 |
| 민원 문의 | 44건 → 31건으로 감소 (`(44 - 31) / 44 ≈ 29.5%`). 콜센터 직원에게 직접 확인한 문의 건수 기준이며, 집계 기간은 확인 필요. 전후 비교이며 이 기능만의 효과로 단정하지 않는다 |
| 운영 확인 | 운영자가 발송 이력과 미발송 대상을 화면에서 보고, 미발송 건을 골라 다시 보낼 수 있게 했다 |

### 한계

- **적재 상태와 최종 발송 결과가 분리돼 있다.** Y인데도 발송 대기·실패·결과 미확인일 수 있으므로 LOG를 별도로 조회해야 한다. “Y니까 실제 발송 성공”이라는 판정은 틀리다.
- **LOG 실패의 자동 복구 범위는 확인 필요다.** N 재조회 경로가 있다고 해서 Y 적재 뒤 발생한 모든 전송 실패까지 다음날 자동 재발송된다고 결론 낼 수 없다. LOG 결과에 따른 Y→N 변경 여부는 자료가 없다.
- **재시도 중복 방지는 별도 문제다.** 응답 유실·중복 배치·수동 재요청과 업무 키 제약의 적용 여부를 확인해야 한다. 이 위험이 실제 운영 사고로 발생했다고 말하지 않는다.
- **운영에서 확인한 범위와 설계를 나눈다.** 기존 기록에는 실제 발송 실패나 미발송 잔량이 확인되지 않았다고 남아 있다. 따라서 실패 복구 성공 사례가 아니라 실패 가능성을 고려한 설계 경험으로 설명한다.

### 지금 다시 한다면 (당시 구현이 아니라 개선안)

| 한계 | 개선 방향 |
| --- | --- |
| Y/N은 요청 적재 상태만 표시 | 요청 상태와 전송 결과·확인 시각을 별도 관리 |
| LOG 결과 미확인·최종 실패 구분 부족 | 실제 결과 코드 명세와 대기 시간·재조회 정책 정의 |
| 1회 발송 요건의 동시성 근거 부족 | 업무 키 유일 제약·조건부 상태 변경·실행 잠금 검증 |
| 운영자 재발송의 중복 위험 | 기존 요청·LOG 확인 뒤 사유와 실행자 기록 |

## 6. 기술 원리 정리

아래는 경험을 설명할 때 필요한 **일반 원리**다. 당시 구현과 구분한다.

### 중복 발송 방지

| 단계 | 기존 기록과 이번 확인 | 남은 검증 |
| --- | --- | --- |
| 신규 추출 | 대상 관리 테이블 기준 NOT EXISTS | 동시 추출을 막는 업무 키 제약 여부 |
| 요청 적재 | DATA 적재 성공 후 send_yn=Y | 실제 메서드·commit·롤백 경계 |
| 결과 조회 | 메시지 ID로 LOG와 JOIN | 결과 코드·최종 결과 선택·LOG 누락 처리 |
| 재시도 | 다음날 N 대상 적재 재시도, 운영자 수동 재요청 | LOG 실패 뒤 상태 재설정 및 중복 방지 범위 |

더 견고하게 하려면 일반적으로 다음 방법을 함께 쓴다. 당시 적용 여부는 확인 필요다.

- 업무 키(대상자 + 회차 등)에 **유일 제약**을 걸어 DB가 중복 적재를 거부하게 한다.
- 배치를 여러 서버에서 돌린다면 **한 곳에서만 실행되도록** 잠금을 둔다.

**당시 서버 구조:** WAS 1번과 2번이 **모두 기동 중**이고, 1번이 내려가면 2번으로 넘어가는 구조였다. 두 WAS는 같은 WAR와 같은 DB를 바라본다. 운영 중 중복 발송 문제는 확인되지 않았다.

다만 이 구조에서는 짚어 볼 점이 있다. 장애 전환은 보통 **요청이 가는 서버**를 바꾸는 것이고, WAR 안의 스케줄러는 서버가 떠 있기만 하면 돈다. 같은 WAR가 두 서버에 모두 떠 있다면 새벽 1시 배치가 **두 곳에서 동시에** 돌 수 있다. 그 경우 NOT EXISTS는 두 배치가 같은 순간에 조회한 대상을 함께 적재하는 것을 막지 못한다.

당시에는 **인프라 설정으로 한 곳만 동작하도록** 되어 있었다. 쉘로 WAS를 기동하면, 1번이 구동 중일 때 2번 로그에 "1번을 바라보고 있다"는 내용이 남았다. 이 로그로 보아 2번은 1번이 살아 있는 동안 대기 상태로 있었던 것으로 **추정**한다.

이 설정은 인프라 영역이라 정확한 방식은 확인하지 못했다. 그래서 면접에서는 이렇게 나눠 말한다.

| 구분 | 내용 |
| --- | --- |
| 확인된 것 | 인프라 설정으로 한 곳만 동작, 2번 기동 로그에 1번을 바라본다는 메시지, 운영 중 중복 발송은 확인되지 않음 |
| 모르는 것 | 그 설정의 정확한 방식, 대기 중인 2번에서 애플리케이션 스케줄러가 어떤 상태였는지 |
| 지금이라면 | 인프라 설정에만 기대지 않고, 애플리케이션에서도 ShedLock 같은 실행 잠금이나 업무 키 유일 제약으로 한 번 더 막겠다 |
- 재발송은 "실패"로 확정된 건만 대상으로 하고, "결과 미확인"은 먼저 확인한다.

### 트랜잭션의 한계

트랜잭션은 같은 DB 안의 작업을 함께 커밋하거나 함께 롤백한다. 이번 구조는 NURI2 DATA가 같은 DB에 있어서 적재까지는 하나로 묶을 수 있었다. 하지만 **솔루션이 가져가 외부로 보낸 메시지는 되돌릴 수 없다.** 그래서 "적재까지의 원자성"과 "발송 결과의 확인"을 따로 설계해야 한다.

### Spring `@Transactional` 기본

당시 세부 설정을 설명할 수 없는 부분을 보완하려고 정리한 일반 원리다. 아래 코드는 **학습용 예시이며 실제 소스가 아니다.**

```java
@Service
public class NoticeEnqueueService {

    // 대상 관리 테이블 적재와 NURI2 DATA 적재를 하나의 트랜잭션으로 묶는 예
    @Transactional(rollbackFor = Exception.class)
    public void enqueue(NoticeTarget target) {
        targetMapper.insertTarget(target);           // 발송 대상 관리 테이블
        nuriMapper.insertData(target.toMessage());   // NURI2 DATA (같은 DB)
    }
}
```

**동작 방식:** Spring은 `@Transactional`이 붙은 빈을 프록시로 감싼다. 바깥에서 이 메서드를 호출하면 프록시가 트랜잭션을 시작하고, 정상 종료 시 커밋, 예외 시 롤백한다. MyBatis도 Spring이 관리하는 트랜잭션에 참여하므로 두 매퍼의 INSERT가 같은 트랜잭션에 묶인다.

| 알아 둘 점 | 내용 |
| --- | --- |
| 기본 롤백 대상 | `RuntimeException`과 `Error`. 체크 예외는 기본으로 롤백하지 않으므로 필요하면 `rollbackFor`를 지정한다 |
| 예외를 삼키면 | 프록시가 예외를 직접 관측하지 못한다. 단, 이미 rollback-only면 정상 반환 후에도 커밋 실패할 수 있다 |
| 자기 호출 | 일반 프록시 방식에서 호출된 메서드의 별도 속성이 적용되지 않는다. 이미 외부 트랜잭션이 있으면 그 안에서 실행될 수 있다 |
| 전파(propagation) | 기본값 `REQUIRED`는 진행 중인 트랜잭션이 있으면 참여하고 없으면 새로 만든다. `REQUIRES_NEW`는 항상 새 트랜잭션을 연다 |
| 격리 수준(isolation) | 기본값 `DEFAULT`는 DB의 기본 격리 수준을 따른다 |
| 범위 정하기 | 배치 전체를 하나로 묶으면 한 건 실패에 전체가 롤백된다. 대상 한 건 단위로 묶으면 실패 영향이 그 건으로 줄어든다 |

**면접에서 말하는 법:** "대상 관리 적재와 DATA 적재를 하나의 트랜잭션으로 묶었다"까지는 확정해서 말한다. 어노테이션 속성 같은 세부 설정은 모른다고 말하고, 위 원리로 "이렇게 동작한다고 이해하고 있다"고 설명한다.

### DB 테이블을 큐로 쓰는 방식

업무 시스템은 DATA 테이블에 넣기만 하고, 발송은 솔루션 모듈이 따로 가져가 처리한다. 업무 시스템이 발송 완료를 기다리지 않아도 되는 **비동기 구조**다. 대신 결과는 LOG를 따로 조회해야 알 수 있다.

## 7. 이어지는 질문 대비

답변은 외우는 문장이 아니라 **확인된 것 / 모르는 것 / 보완할 것**을 나눠 말하는 틀로 준비한다.

| 질문 | 확인된 것 | 모르는 것 | 보완할 것 |
| --- | --- | --- | --- |
| NURI2는 어떤 솔루션이고, 직접 발송했나요? | DATA 테이블에 적재하면 솔루션의 별도 모듈이 발송, 결과는 LOG에서 확인 | 솔루션 내부 동작 | 직접 개발 영역과 솔루션 영역을 나눠 말하기 |
| 중복 발송은 어떻게 막았나요? | 업무 요건은 1회. NOT EXISTS 신규 제외와 N 적재 재시도 경로 | 업무 키 제약·동시 실행·재요청의 중복 방지 범위 | Y는 적재 성공이며 최종 발송은 LOG로 별도 확인 |
| 트랜잭션은 어떻게 잡았나요? | 대상 관리 적재와 `send_yn` 갱신을 하나로 묶음. NURI2 DATA도 같은 DB라 함께 롤백 | 세부 설정(어노테이션 속성, 격리 수준) | 세부 설정은 모른다고 말하고 6장 원리로 설명. 이미 발송된 메시지는 롤백할 수 없다는 점 |
| 발송 실패는 어떻게 처리했나요? | 운영 중 실제 실패는 없었다. 대체 발송은 솔루션 기능 | — | 장애 해결이 아니라 설계 경험으로 말하기 |
| 민원 30% 감소의 근거는? | 44건 → 31건. 콜센터 직원에게 직접 확인한 문의 건수 | 집계 기간 | 다른 요인을 분리해 측정하지 못했다고 말하기 |
| 미발송 건은 어떻게 다시 보냈나요? | 다음날 N 대상의 DATA 적재 재시도와 운영자 수동 재요청 경로 | 적재 Y 이후 LOG상 실패를 자동 재요청했는지 | 적재 미완료와 최종 전송 실패를 나눠 설명 |
| WAS가 두 대인데 배치가 두 번 돌지 않나요? | WAS 1·2번 모두 기동, 1번 장애 시 2번으로 전환. 같은 WAR·DB. 인프라 설정으로 한 곳만 동작했고 2번 기동 로그에 1번을 바라본다는 메시지가 남음. 운영 중 중복 발송은 확인되지 않음 | 인프라 설정의 정확한 방식 | 모르는 부분은 인정하고, 지금이라면 ShedLock 같은 실행 잠금이나 업무 키 유일 제약으로 막겠다고 말하기 |

### 고정 답변: "메시지가 일부만 안 갔다"는 항의

**질문:** 고객사가 "메시지가 일부만 안 갔다"고 항의했을 때, 실제로 어떤 순서로 처리했는지 1분 안에 설명해 주세요.

> **로그에서 누락을 확인하고 소스와 커밋 이력으로 시점의 장애를 확인한 뒤, 그 사실을 담당자에게 전달했습니다.**

이 한 문장 뒤에 순서를 물으면 아래 흐름으로 풀어 말한다.

```text
1. LOG 테이블에서 해당 대상의 발송 이력이 있는지 확인
2. 이력이 없으면(누락) 그 시점의 소스와 커밋 이력을 확인해 장애 여부 파악
3. 확인한 사실을 담당자에게 전달
```

**말할 때 주의할 점**

- 이 답변은 **원인을 확인해 전달한 경험**이다. 솔루션의 발송 장애를 직접 고친 경험으로 넓혀 말하지 않는다.
- 운영 중 실제 발송 실패는 없었다는 점과 어긋나지 않게, "장애를 해결했다"가 아니라 **"장애 여부를 확인했다"** 로 말한다.
- 확인 결과가 무엇이었는지, 전달받은 담당자가 누구였는지는 **확인 필요**다. 묻기 전에 먼저 말하지 않는다.

## 8. 지원 직무와 연결 — 엠앤와이즈 TS팀

엠앤와이즈는 UMS 같은 메시징 솔루션을 고객사에 공급한다. 이 경험은 **메시징 솔루션에 업무 시스템을 연동하는 쪽, 즉 고객사 개발자의 자리**에서 일해 본 경험이다.

> 기존 메시징 솔루션을 이해해 업무 시스템에 연계하고, 발송 요청과 처리 이력을 분리해 운영자가 확인할 수 있는 기능을 만든 경험입니다. 고객사 시스템이 발송 요청을 넣고 결과 이력을 확인하는 구조에서, 요청을 넣는 부분과 결과를 확인하는 부분이 어디서 어긋날 수 있는지 알고 있어 고객사 문의를 이해하는 데 도움이 될 것이라고 생각합니다.

**TS 면접에서 특히 나올 수 있는 주제**

| 주제 | 이 글에서 볼 곳 |
| --- | --- |
| DB 테이블을 큐로 쓰는 연동 방식 | 3장 처리 흐름, 6장 "DB 테이블을 큐로 쓰는 방식" |
| 발송 요청과 결과 이력의 분리 | 4-1 대상 관리와 발송 큐 분리 |
| 중복 발송과 결과 미확인 | 5장 한계, 6장 중복 발송 방지 |
| 트랜잭션 범위와 한계 | 4-3, 6장 트랜잭션의 한계 |
| 일부 미발송 문의 대응 | 7장 고정 답변 |

**말할 때 주의할 점:** 발송 엔진은 직접 만들지 않았다. 엠앤와이즈 UMS의 내부 구조는 확인되지 않았으므로, NURI2와 같은 구조라고 단정하지 않는다.

## 면접 연습 Q5·Q6 — 원문과 정정된 상태 의미

### Q5. 어떤 메시징 솔루션을 사용했고, 어떻게 개발하여 성과를 냈나요?

#### 현재 준비한 답변 — 원문 보존

> 네, 당시 사용했던 메시징 솔루션은 NURI2였습니다.
>
> 국토교통부 전세사기 피해자 지원 시스템에서 심의와 의결이 지연되면서, 처리 결과를 기다리는 민원인들의 문의가 지속적으로 발생하고 있었습니다.
>
> 이 문제를 개선하기 위해 심사가 지연되고 있는 대상자에게 진행 상황을 자동으로 안내하는 메시지 발송 배치를 개발했습니다.
>
> 먼저 Java 기반으로 새벽 시간에 안내 대상자를 조회하는 배치를 구현하고, 조회된 데이터를 별도의 발송 대상 관리 테이블에 저장했습니다.
>
> 이후 Enum으로 관리하는 메시지 템플릿을 활용하여 발송 데이터를 구성하고, MyBatis를 통해 NURI2 솔루션의 DATA 테이블에 적재했습니다.
>
> 실제 메시지는 솔루션의 예약 발송 기능을 이용하여 오전 10시에 발송되도록 설정했습니다.
>
> 1차로 카카오 알림톡을 발송하고, 실패할 경우 SMS나 LMS로 대체 발송하도록 솔루션 기능을 활용했습니다.
>
> 또한 DATA 테이블은 발송 요청, LOG 테이블은 발송 이력 관리에 활용했습니다.
>
> 메시지 ID를 기준으로 발송 대상과 이력을 연결하여 운영자가 발송 결과를 확인할 수 있는 화면도 개발했습니다.
>
> 그 결과 일평균 약 30건의 안내 메시지를 안정적으로 발송할 수 있었고, 당시 집계 기준으로 관련 민원 문의가 44건에서 31건으로 약 30% 감소했습니다.
>
> 제가 직접 메시징 엔진을 개발한 것은 아니지만, 기존 NURI2 솔루션을 업무 시스템에 연동하고 대상자 추출부터 발송 요청, 이력 관리까지 자동화하여 실제 업무 개선 성과를 낸 경험입니다.

#### 기술적 검증과 실제 개발 경계

| 구분 | 내용 |
| --- | --- |
| [실무 경험] | 새벽 대상 조회·별도 관리 테이블·Enum/Builder·MyBatis DATA 적재·이력 조회·재처리 경로 |
| [실무 경험] | 10시 예약과 알림톡→SMS/LMS 대체는 NURI2 제공 기능. 발송 엔진을 직접 만든 것이 아님 |
| [실무 경험: 이번 확인] | send_yn=Y는 DATA 적재 성공 후 변경. 최종 전송 결과는 LOG와 별도 대조 |
| [검증 완료: 산술] | `(44-31)/44 × 100 ≈ 29.55%`. 준비 답변의 약 30%·일평균 약 30건은 그대로 유지 |
| [확인 필요] | 문의 집계 기간·다른 요인, 당시 SQL·Mapper·템플릿 소스, 솔루션 결과 코드와 설정 원문 |

전후 문의 건수와 배치 개발의 인과관계를 따로 측정하지 못했다. “안정적으로”라는 표현을 전송 성공률 100%의 측정 결과로 확대하지 않는다. 실제 코드가 없어 아래 예제를 당시 원본 소스나 실행한 재현 구현으로 표시하지 않는다.

#### 트랜잭션 흐름 — 학습용 의사 코드, 미실행

```text
같은 DB·같은 트랜잭션 자원에 참여한다는 전제:
  대상 관리 데이터 준비
  → NURI2 DATA에 발송 요청 적재
  → 적재 성공 상태 send_yn=Y 기록
  → COMMIT (실패하면 참여한 DB 변경 ROLLBACK)
별도 시간의 솔루션 발송 → LOG 결과 기록 → 운영자 조회
```

**[사후 학습]** 테이블이 같은 DB에 있다는 조건만으로 서로 다른 연결·autocommit 작업이 자동으로 함께 롤백되지는 않는다. MyBatis-Spring의 SqlSessionFactory와 트랜잭션 관리자가 같은 DataSource를 사용하는지 등 실제 자원 참여를 확인해야 한다. [MyBatis-Spring 트랜잭션 문서](https://mybatis.org/spring/transactions.html)의 일반 계약과 당시 구성의 미확인을 구별한다. 외부 채널에서 이미 발생한 발송 효과는 이 DB 롤백의 대상이 아니다.

#### 최종 면접 답변

> NURI2를 업무 시스템에 연동했습니다. 심의·의결 지연 대상자를 새벽 배치로 조회해 별도 관리 테이블에 저장하고, Enum 템플릿과 Builder로 발송 데이터를 구성해 MyBatis로 DATA 테이블에 적재했습니다. 요청 적재가 성공하면 send_yn을 Y로 바꿨고, 실제 발송 결과는 메시지 ID로 LOG와 연결해 따로 확인했습니다. 오전 10시 예약 발송과 알림톡 실패 시 SMS·LMS 대체는 NURI2 기능을 이용했습니다. 제가 개발한 것은 대상 관리·요청 적재·이력 조회·재처리 경로입니다. 일평균 약 30건을 자동 발송했고 문의는 44건에서 31건으로 약 30% 감소했지만, 집계 기간과 다른 요인의 영향은 분리해 확인하지 못했습니다.

#### 예상 꼬리 질문과 답변

- **배치 프레임워크와 스케줄러는 무엇이었나요?** “Java 배치를 구현한 경험은 설명할 수 있지만 이번 자료만으로 정확한 등록·실행 설정을 특정하지 않겠습니다.”
- **Enum·Builder가 어떤 장점이 있었나요?** “템플릿을 한곳에 관리하고 발송 객체의 값을 이름으로 채우기 좋았습니다. 원본 클래스·필드명은 자료 확인이 필요합니다.”
- **같은 DB면 모두 함께 롤백되나요?** “실제 같은 트랜잭션 자원에 참여해야 합니다. 당시 하나로 묶은 의도와 세부 연결·설정 검증은 구분해서 답하겠습니다.”
- **30% 감소를 어떻게 증명하나요?** “44건과 31건의 전후 비교로 계산했습니다. 집계 기간과 다른 요인의 영향은 분리해 확인하지 못했습니다.”

### Q6. 메시지 발송 실패에 대한 이력 관리는 어떻게 했나요?

#### 현재 준비한 답변 — 원문 보존, 아래 정정과 함께 읽기

> 네, 발송 실패 이력은 NURI2 솔루션의 LOG 테이블과 별도로 만든 발송 대상 관리 테이블을 활용하여 관리했습니다.
>
> 먼저 메시지를 발송할 때 발송 대상 관리 테이블에 대상자 정보와 메시지 ID를 저장했습니다.
>
> 이후 NURI2의 LOG 테이블에 기록된 발송 결과를 메시지 ID 기준으로 연결하여 성공 여부를 확인했습니다.
>
> 발송에 성공한 경우에는 관리 테이블의 발송 상태를 Y로 변경하고, 실패한 경우에는 N으로 유지하도록 구현했습니다.
>
> 특히 실패한 건은 다음 날 배치에서 다시 조회될 수 있도록 하여, 일시적인 장애로 발송에 실패하더라도 대상자가 누락되지 않도록 관리했습니다.
>
> 또한 운영자가 발송 실패 여부를 확인할 수 있도록 발송 대상 관리 테이블과 LOG 테이블을 연결한 조회 화면도 제공했습니다.
>
> 여기서 중요한 점은 발송 요청이 정상적으로 적재된 것과 실제 메시지 발송에 성공한 것은 구분해서 관리했다는 것입니다.
>
> DATA 테이블에 데이터가 들어갔다고 해서 무조건 발송에 성공한 것은 아니기 때문에 최종 발송 결과는 LOG 테이블을 기준으로 판단했습니다.

#### 원문에서 수정할 부분과 이유

| 원문 표현 | 검증 결과와 최종 답변에 반영할 내용 |
| --- | --- |
| 실제 발송 성공이면 Y로 변경 | **[실무 경험: 2026-11-22 본인 확인] DATA 적재 성공 후 Y로 변경**. 최종 성공 의미로 사용하면 안 됨 |
| 실패한 건은 N으로 유지해 다음날 처리 | N 조회 경로는 적재 완료로 표시되지 않은 대상의 재시도다. LOG상 실패가 모두 N으로 바뀌었는지는 **[확인 필요]** |
| 최종 결과는 LOG로 판단 | 요청 상태와 구분하는 원칙은 맞다. 실제 결과 코드 값·최종 로그 선택은 **[확인 필요]** |
| 실패 누락을 자동으로 방지 | 경로를 구현했다는 경험과 실제 장애 복구 성공은 다르다. 운영 중 실패 복구 실적으로 확대하지 않음 |

원문은 연습 과정의 이전 답변으로 보존한다. **현재 설명의 기준은 DATA 적재 성공이라는 이번 확인**이다. 같은 사실이 [전세사기 피해자 시스템 복기](/blog/interview-jeonse-support-system)에도 기록돼 있어 문서 간 의미를 맞췄다. 다만 당시 실제 코드·DB 로그를 이번에 열어 검증한 것은 아니다.

#### 요청 상태와 결과를 대조하는 SQL — 가상 예제, 미실행

테이블·컬럼명은 설명용이며 실제 NURI2 제품 스키마가 아니다. 성공·실패 코드 값을 임의로 넣지 않았다.

```sql
SELECT m.request_id, m.send_yn,
       l.result_code, l.result_at
FROM example_send_target m
LEFT JOIN example_send_log l
  ON l.request_id = m.request_id;
```

LOG가 없으면 “최종 실패”가 아니라 대기·처리 중·이력 미확인의 가능성을 남긴다. 요청 하나에 채널별·시도별 LOG가 여러 건이면 JOIN 결과도 여러 행이다. 최종 결과 선택은 실제 제품 명세와 시도·채널·시각 기준을 확인해야 한다. 메시지 ID의 생성 주체·고유 범위도 자료 없이 UUID·sequence 등으로 확정하지 않는다.

**[사후 학습]** NOT EXISTS만으로 동시 적재를 막을 수는 없다. 업무 키 제약, 상태 전이, 요청 식별자와 외부 결과 대사를 검토한다. 이것들을 당시 모두 구현한 것은 아니므로 [멱등성 학습](/blog/message-delivery-idempotency)과 경험을 구분한다.

#### 최종 면접 답변

> 발송 대상 관리 테이블과 NURI2 LOG를 메시지 ID로 연결해 결과를 조회했습니다. 여기서 send_yn의 Y는 실제 발송 성공이 아니라 DATA에 요청을 적재한 상태였습니다. 실제 성공·실패는 LOG의 결과를 따로 봤습니다. 다음날 배치에서 N 대상을 다시 조회하는 경로와 운영자 수동 재발송은 있었지만, 이를 LOG상 발송 실패가 자동으로 모두 복구되는 구조라고 말할 수는 없습니다. LOG 결과 코드와 실패 뒤 상태 재설정 조건은 추가 확인이 필요하고, 운영 중 실제 발송 실패를 해결한 사례로 설명하지는 않겠습니다.

#### 예상 꼬리 질문과 답변

- **Y인데 LOG가 실패면 어떻게 하나요?** “Y는 요청 적재 상태여서 충돌이 아닙니다. 실제 전송 실패의 재시도 조건은 LOG 코드와 기존 요청 상태를 확인해야 합니다.”
- **LOG가 없으면 다시 보내나요?** “즉시 실패라고 판단하지 않겠습니다. 예약·처리 지연·결과 미확인일 수 있어 기존 요청과 대기 시간을 먼저 확인해야 합니다.”
- **메시지 ID는 어떻게 만들었나요?** “연결 키로 사용한 사실은 설명할 수 있지만 생성 규칙과 고유 범위는 이번 자료로 확인하지 못했습니다.”
- **자동으로 중복 없이 복구됐나요?** “그 범위까지 검증했다고 말할 수 없습니다. N 재조회·수동 재요청 경로와 실제 최종 실패 복구를 나눠 설명하겠습니다.”
- **실패가 실제로 있었나요?** “기존 운영 기록에서 실제 발송 실패를 확인한 사례는 없었습니다. 설계와 미확인 조건을 설명하고 해결 경험을 만들지 않겠습니다.”
