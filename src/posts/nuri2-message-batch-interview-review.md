# NURI2 알림톡 자동 발송 배치 개발 경험 복기

> **작성 목적:** 엠앤와이즈 TS 직무 면접에서 NURI2 연동 개발 경험을 실제 기여 범위에 맞춰 설명하고, 예상 꼬리 질문과 기술 복습을 준비하기 위한 문서.
>
> **작성 기준:** 대화에서 복기한 실무 기억을 우선 기록했다. 실제 프로젝트 소스·DB 스키마·운영 지표 원본과 대조하지 못한 내용은 **확인 필요**로 표시한다. 코드 예시는 교육용으로, 실제 사용한 소스가 아니다.

## 1. 핵심 요약

- **개발 배경:** 전세사기 피해자 결정 절차에서 지자체 조사 및 국토교통부 심의가 지연되면서, 결정문을 기다리는 신청자들의 반복적인 민원 문의가 발생했다.
- **개선 방법:** 심사 지연 대상에게 안내 알림톡을 보내는 **자동 발송 배치 프로그램**을 개발했다.
- **직접 개발한 내용:** 발송 대상 추출·관리, 기존 연동 모듈 참조, 메시지 템플릿·발송 데이터 구성, NURI2 DATA 테이블 적재, `SEND_YN` 관리, LOG 이력 연계 조회 화면, 재처리 대상 관리 및 선택 재발송 기능.
- **기존 솔루션이 제공한 기능:** 적재된 발송 요청을 처리하는 메시징 엔진, 실제 채널 발송, 발송 처리 이력 관리. 알림톡 실패 후 문자 대체 발송은 기존 솔루션에서 제공하는 기능으로 이해하고 있으며, 직접 구현한 엔진 기능으로 말하지 않는다.
- **성과:** 민원 문의가 **44건에서 31건**으로 감소했다는 실무 기억을 바탕으로 **약 30% 감소**라고 설명한다. 정확한 전후 집계 기간과 집계 기준은 확인이 필요하다.
- **중요한 구분:** `SEND_YN = Y`는 발송 요청을 DATA 테이블에 **적재했다는 뜻**이지, 알림톡이 최종적으로 전달되었다는 뜻이 아니다.

## 2. 업무 배경과 해결하려던 문제

전세사기 피해자가 신청한 뒤 지자체 피해 사실 조사와 국토교통부 심의·의결을 거쳐 피해자 인정 여부가 결정되는 과정이 있었다. 당시 업무에서는 지자체 30일, 국토교통부 30일 등 **통상 60일을 기준으로 안내**했지만, 실제 조사·심의 지연으로 더 오래 걸리는 사례가 발생했다.

결정문은 다양한 지원 제도를 신청할 때 활용되는 중요한 인정·증빙 자료이므로, 결과를 기다리는 신청자는 심사가 지연되면 불안감이 커지고 진행 상황을 문의하게 된다.

**개발 목적은 심사 자체를 앞당기는 것이 아니라, 심사가 지연된 대상에게 안내를 제공해 정보 부족과 반복 문의를 줄이는 것**이었다.

> **면접용 배경 설명:** “전세사기 피해자 인정 심사가 지연되는 동안 신청자들의 문의가 증가하는 문제가 있었습니다. 심사 지연 대상에게 안내 메시지를 자동으로 발송해 민원 부담을 줄이고자 했습니다.”

**주의:** ‘지원금이 자동 지급된다’, ‘반드시 60일 이내 결정된다’, ‘개인별 지원금 지급을 직접 처리했다’고 설명하지 않는다.

## 3. 실제 개발 및 연동 구조

```text
[업무 시스템 / 일일 배치]
  └─ 심사 지연 대상 조회
        │
        ▼
[별도 발송 대상 관리 테이블]
  └─ 대상 정보 · 메시지 키 · SEND_YN 관리
        │
        │ 기존 메시징 연동 모듈 참조
        │ 템플릿·발송 유형·개인별 메시지 생성
        ▼
[MyBatis INSERT → NURI2 DATA 테이블]
  └─ 적재 과정에서 SEND_YN: N → Y
        │
        ▼
[기존 NURI2 메시징 처리 모듈]
  └─ 적재된 발송 요청을 처리하고 결과 이력 생성
        │
        ▼
[NURI2 LOG 테이블]
        │
        │ 메시지 키 기반 연결(JOIN)
        ▼
[직접 개발한 발송 이력 조회 화면]
  └─ 이력 확인 · 미확인 건 파악 · 재처리 대상 선택
```

※ 위 그림은 **기억에 따른 논리적 흐름**이다. 실제 클래스명, 테이블명, LOG에 기록되는 조건, 배치 시각, 트랜잭션 범위는 원본 소스로 확인해야 한다.

### 본인이 직접 수행한 내용

1. 다른 기능부에 이미 구현되어 있던 **NURI2 연동 모듈을 분석하고 참조**했다.
2. 심사가 지연된 대상자를 조회하여 별도 **발송 대상 관리 테이블**로 관리했다.
3. 메시지 유형(SMS/LMS/MMS 등)은 공통 코드·Enum 상수를 활용했고, 안내 문구도 **Enum 템플릿**으로 관리했다.
4. 이름·날짜·안내 내용 등의 값을 템플릿에 넣어 **완성된 문자열** 형태의 안내 문구를 구성했다.
5. Builder 형태의 코드를 활용해 발송 정보를 설정하고, **MyBatis Mapper의 INSERT**를 호출해 NURI2 DATA 테이블에 요청을 적재했다.
6. DATA 적재 시 `SEND_YN`을 **N → Y**로 갱신하도록 구성했다.
7. 대상 관리 테이블과 LOG 이력 테이블을 **메시지 키로 JOIN**하여 발송 이력을 조회하는 운영자 화면을 개발했다.
8. 이력 확인 후 대상을 선택해 재발송하거나 일일 배치로 다시 처리할 수 있는 기능을 마련했다. **다만 실제 자동 재처리 조건과 중복 방지 절차의 상세 구현은 미확인**이다.

### 기존 솔루션 또는 공통 모듈의 역할

- 발송 요청 데이터를 처리하고 알림톡·문자 채널에 실제 전달하는 로직
- 발송 결과를 생성·관리하는 내부 처리
- 알림톡 실패 시 문자 대체 발송과 같은 메시징 솔루션 제공 기능(당시 기억 기준)

**면접에서는 ‘메시징 엔진을 개발했다’가 아니라 ‘기존 메시징 솔루션과 연계한 업무 배치 및 운영 관리 기능을 개발했다’고 설명한다.**

## 4. 발송 상태와 결과 이력의 차이

| 항목 | 의미 | 주의할 점 |
|---|---|---|
| 발송 대상 테이블 `SEND_YN = N` | 아직 발송 요청 적재가 완료되지 않은 상태 | 정확한 재처리 조건은 원본 로직 확인 필요 |
| 발송 대상 테이블 `SEND_YN = Y` | NURI2 DATA 테이블 적재 처리 완료 | **최종 발송 성공 표시가 아님** |
| DATA 테이블의 요청 행 | 메시징 솔루션이 처리할 발송 요청 | 적재 성공 ≠ 수신자에게 발송 성공 |
| LOG 테이블에 해당 메시지 키가 있음 | 해당 키에 대한 처리 이력이 확인됨 | 이력의 구체적 결과값은 추가 판독 필요 |
| LOG 테이블에 해당 메시지 키가 없음 | 조회 시점에 해당 이력이 확인되지 않음 | **실패 확정이 아님**. 처리 대기·이력 반영 지연 등 가능 |

당시 기억상 **발송되지 않은 건은 LOG 이력이 남지 않았던 것 같지만**, 이 규칙이 NURI2의 공식 동작인지 확인된 것은 아니다. `1001`, `1002` 같은 숫자도 **결과 코드 관련 상수로 기억하는 정도**이며, 의미와 위치는 확정하지 않는다.

### 트랜잭션 및 예외 처리 주의

- 컴파일 오류는 Java `try-catch`로 처리할 수 없다. 예외 처리는 **실행 중 발생하는 오류**에 적용한다.
- DATA `INSERT`와 `SEND_YN` `UPDATE`가 **한 트랜잭션으로 묶였는지**는 아직 확인되지 않았다. ‘트랜잭션을 보장했다’고 단정하지 않는다.
- 설계상 적재 실패 시 `SEND_YN`이 `N`으로 남도록 의도했으나, 실제 커밋·롤백 범위는 확인 필요.
- `SEND_YN = Y`인데 LOG가 비어 있다고 **즉시 재발송**하면 이력 반영 지연 등으로 중복 발송 가능성이 있다. 실제 운영에서 어떤 대기 시간·검증 조건을 썼는지는 기억나지 않는다.

## 5. 실제 문의 대응 사례

“알림톡을 받지 못했다”는 문의가 있었을 때:

1. **휴대전화 번호로 발송 이력을 조회**했다.
2. 해당 시점의 **Git 커밋 이력**을 확인했다.
3. 확인 결과, **그 당시에는 해당 발송 기능이 아직 구현되기 전**이어서 발송되지 않은 것으로 파악했다.

이는 **실제 발송 장애를 복구한 사례가 아니라, 문의에 대해 이력과 배포·개발 시점을 대조해 원인을 확인한 사례**이다.

또한 대상자 선정 오류로 **지자체 담당자에게 가야 할 메시지가 국토교통부 담당자에게 발송된 사례**를 본 적이 있다. 이는 전송 실패라기보다 **업무상 수신 대상 선정 오류**이므로 구분해 설명한다. 이 사례에서 직접 수행한 후속 조치는 확인되지 않았다.

## 6. 대표 면접 답변

### Q. NURI2 메시징 솔루션 연동 경험을 설명해 주세요.

> 전세사기 피해자 인정 심사가 지연되면서 민원 문의가 증가하는 문제가 있었습니다.
>
> 이를 개선하기 위해 기존 기능부에 구현된 NURI2 연동 모듈을 참고해 알림톡 자동 발송 배치를 개발했습니다.
>
> 심사 지연 대상자를 별도 테이블에서 관리하고, 메시지 템플릿과 발송 정보를 구성해 MyBatis로 NURI2 DATA 테이블에 적재하도록 했습니다.
>
> 또한 발송 대상 테이블과 LOG 테이블을 메시지 키로 연결한 이력 조회 화면을 개발해 발송 내역을 확인하고 재처리 대상을 관리할 수 있도록 했습니다.
>
> 이러한 안내 기능을 도입한 이후 민원 문의는 당시 집계 기준 약 30% 감소했습니다.

※ 성과 수치의 상세 집계 기간은 확인 전이므로 ‘정밀한 인과 검증 결과’라고 말하지 않는다.

### Q. 본인이 개발한 영역과 솔루션 기능은 어떻게 다른가요?

> 저는 심사 지연 대상 조회, 발송 데이터 구성과 적재, 발송 상태 관리, 운영자 이력 조회 및 재처리 기능을 개발했습니다. 실제 발송 엔진과 메시징 채널 처리 로직은 기존 NURI2 솔루션을 활용했습니다.

### Q. `SEND_YN`은 발송 성공 여부인가요?

> 아니요. 발송 대상의 요청 데이터가 NURI2 DATA 테이블에 적재되었는지 관리하기 위한 값입니다. 적재 시 `N`에서 `Y`로 변경하고, 실제 처리 이력은 메시지 키를 기준으로 LOG 테이블과 연결해 별도로 확인했습니다.

### Q. 메시지가 발송되지 않았을 때 어떻게 확인했나요?

> 이력 조회 화면에서 휴대전화 번호를 기준으로 확인했고, 실제 문의 사례에서는 Git 커밋 이력까지 대조해 문의 시점에 해당 기능이 아직 구현되지 않았다는 점을 확인했습니다. 제가 개발한 기능에서 실제 솔루션 발송 장애를 해결한 사례는 기억나지 않습니다.

### Q. 실패 코드 `1001`, `1002`는 무슨 의미인가요?

> 당시 결과 코드 관련 상수와 이력 테이블을 참고해 개발한 것은 기억하지만, 정확한 코드별 의미는 지금 확정해서 말씀드리기 어렵습니다. 발송 요청 적재 상태와 결과 이력은 분리해 관리했습니다.

### Q. 발송 결과가 없으면 자동으로 재발송했나요?

> 미발송·이력 미확인 건을 확인하고 재처리할 수 있도록 기능을 마련했습니다. 다만 실제로 LOG 기록 지연을 어떻게 구분했는지, 자동 재처리의 상세 조건은 원본 로직을 확인해야 정확하게 설명할 수 있습니다.

### Q. 알림톡 도입 성과는 어떻게 확인했나요?

> 당시 민원 문의가 44건에서 31건 정도로 줄어든 것으로 기억합니다. 약 30% 수준의 전후 감소인데, 현재는 정확한 집계 기간과 동일 조건 비교 여부가 확인되지 않았으므로 당시 관찰한 운영 성과로 설명하고 있습니다.

### Q. 이 경험이 엠앤와이즈 TS 업무와 어떤 관련이 있나요?

> 기존 메시징 모듈을 이해해 업무 시스템에 연계하고, 발송 요청과 처리 이력을 분리해 운영 관점에서 확인 가능한 기능을 개발한 경험입니다. 기술적 연동과 운영 이력 확인, 문제 원인 파악을 함께 수행했다는 점이 고객사 대응 개발 및 솔루션 운영 업무와 연결된다고 생각합니다.

## 7. Java 기술 복습 — 직접 공부한 개념

### Builder 패턴

여러 발송 필드를 **이름이 드러나는 방식으로 설정**할 수 있어 생성자보다 가독성이 좋고 선택 필드 처리도 유연하다. Builder 메서드에서 `return this`를 반환하면 **메서드 체이닝**이 가능하고, `build()`는 일반적으로 최종 객체를 생성한다.

```java
// 학습용 예시: 실제 NURI2 연동 소스가 아님
Message message = Message.builder()
        .receiver("01012345678")
        .messageType("ALIMTALK")
        .content("심사 지연 안내")
        .build();
```

**실무 기억:** 기존 Builder 계열 코드 사이에 MyBatis INSERT 호출이 있었던 것 같지만, 정확히 `build()` 안에서 INSERT가 일어났는지는 미확인. 일반적인 Builder 패턴의 필수 특성으로 설명하지 않는다.

### Enum 템플릿과 문자열 조합

Enum 상수가 생성될 때 생성자로 템플릿 필드를 초기화하고, Getter 등으로 값을 읽어 수신자 이름·기준일을 채워 넣을 수 있다.

```java
// 학습용 예시
public enum MessageTemplate {
    REVIEW_DELAY("%s님, 심사가 지연되고 있습니다. 기준일: %s");

    private final String content;

    MessageTemplate(String content) {
        this.content = content;
    }

    public String getContent() {
        return content;
    }
}

String content = String.format(
        MessageTemplate.REVIEW_DELAY.getContent(),
        "홍길동", "2026-11-19"
);
```

- `String.format()`은 `%s`에 전달한 문자열을 순서대로 배치한다.
- 필요한 인자가 부족하면 **컴파일 오류가 아니라** 실행 중 `MissingFormatArgumentException`이 발생할 수 있다.
- 실제 업무에서 `String.format()`을 사용했는지, 문자열 병합을 다른 방식으로 했는지는 미확인.
- 예전에는 JSON을 쓴 것으로 기억했지만, 이후 복기에서는 **필드별 JSON 객체라기보다 템플릿에 값을 채운 완성 문자열을 저장한 기억이 더 강함**. 정확한 저장 형식은 확인 필요.

### MyBatis Mapper

```java
// 학습용 예시: namespace와 id는 실제 값이 아님
sqlSession.insert("message.insertMessageTable", message);
```

`message.insertMessageTable`은 SQL 본문이 아니라 **Mapper의 namespace와 SQL id를 결합한 식별자**다. `message` 객체는 바인딩할 값들을 전달한다. 실제 SQL은 XML 또는 어노테이션 Mapper에 정의될 수 있다.

### 예외 처리와 발송 실패 구분

| 구분 | 설명 |
|---|---|
| 컴파일 오류 | Java 코드의 문법·타입 검사 단계에서 발생. `try-catch` 대상 아님 |
| Java 런타임 예외 | 실행 중 메시지 생성·DB 적재 등에서 발생 가능. `try-catch`로 처리 가능 |
| 발송 솔루션 처리 결과 | 메시징 엔진이 발송 처리 이후 남기는 상태·결과. Java 예외와 동일하지 않음 |

## 10. 30초 복습 요약

**문제:** 전세사기 피해자 인정 심사 지연으로 민원 문의 증가.

**역할:** 기존 NURI2 연동 모듈을 분석해 대상 조회·메시지 생성·DATA 적재 배치와 발송 이력 조회 화면을 개발.

**구조:** Enum 템플릿 → Builder 형태의 발송 데이터 구성 → MyBatis DATA 적재 → 솔루션 처리 → 메시지 키로 LOG 연계 조회.

**운영 관리:** `SEND_YN = Y`는 요청 적재 완료. 실제 발송 결과는 LOG 이력과 별도 구분. 재처리 기능 제공.

**성과:** 민원 문의 약 30% 감소(44건 → 31건으로 기억, 기간·기준은 확인 필요).

**면접 원칙:** 실제 구현과 기존 솔루션 기능을 구분하고, 기억나지 않는 결과 코드·실패 조건·트랜잭션을 추측하지 않는다.
