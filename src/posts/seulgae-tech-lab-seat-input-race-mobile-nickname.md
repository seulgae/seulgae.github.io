의자에 앉았는데 잠시 뒤 저절로 일어났다. 로컬에서는 잘 보이지 않고 지연이 있는 환경에서 나타나는 증상이었다. PR #41의 `182d448`에서는 표시 시간을 늘리는 데서 멈추지 않고 이동 명령과 앉기 요청의 순서를 추적했다.

## 전송 순서와 처리 완료 순서가 달랐다

이동은 50ms 단위로 묶지만 앉기 요청은 즉시 보낸다. 따라서 E 직전의 걸음이 클라이언트에 남아 앉기보다 늦게 전송될 수 있었다. 먼저 남은 이동을 보내도 서버에는 시간 예산에 따라 아직 처리하지 않은 걸음이 대기한다.

서버가 먼저 앉힌 뒤 옛 걸음을 처리하면 ‘움직였으니 일어나기’가 실행된다. 여기에 클라이언트의 1.5초 확인 제한도 겹쳤다. 기록의 약 2초는 단일 타이머의 문제가 아니라 요청 전송·서버 대기·화면 확인이 만나는 결과였다.

## 앉기 요청에 이동 순번의 경계를 만들기

클라이언트는 앉기 전에 남은 걸음을 보내고 서버는 그때까지 받은 이동 번호를 기억한다. 현재 `backend/src/main/java/kr/seulgae/techlab/multiplayer/lobby/domain/LobbyRoom.java`의 필드다.

```java
        long seatAfter = -1;
        /** 앉기 전에 보낸 걸음이 아직 처리 중이면, 그 걸음을 마친 뒤 앉을 의자 */
        String seatRequest;
```

그 번호 이하의 걸음은 앉기 이전 행동이다. 대기열에 남아 있으면 다 처리한 위치에서 의자 거리와 점유 상태를 다시 검사한 뒤 앉힌다.

같은 파일의 확정 함수 시작이다.

```java
    private void applySeatRequest(Member m) {
        if (m.seatRequest == null || m.pending.stream().anyMatch(command -> command.seq() <= m.seatAfter)) return;
        String seatId = m.seatRequest;
        m.seatRequest = null;
```

앉은 뒤에 보낸 새 이동만 자리에서 일으키게 했다. 확인 제한도 3초로 늘렸지만 이는 정상 지연의 여유이고, 오래된 걸음과 새 걸음을 구별하는 규칙이 근본 수정이다.

## 늦게 끝난 로그인도 게임에 반영하기

모바일에서는 로그인 확인이 게임 시작 대기보다 늦게 끝나 임시 이름이 남는 문제도 있었다. 인증 확인 후 회원 닉네임을 적용하고 이미 연결됐다면 전용 종료 코드로 다시 접속하게 했다.

현재 `frontend/src/features/multiplayer/MultiplayerClient.ts`의 중복 방지 조건이다.

```ts
    if (this.disposed || !validNickname(nickname) || nickname === this.info.nickname || nickname === this.appliedNickname) return false
    this.appliedNickname = nickname
```

서버가 이름 충돌을 피하려고 표시 이름을 바꿔도 같은 회원 이름으로 계속 재접속하지 않도록 시도한 값을 따로 기억한다. 원하는 이름과 서버가 부여한 이름을 같은 상태로만 다루면 반복 연결이 생길 수 있었다.

같은 변경에는 회의 테이블을 세로로 바꾸고 의자와 화분을 재배치한 작업도 포함됐다. 다만 의자의 방향별 외형은 별도 과제로 남았다. 공간 배치 개선과 네트워크 경쟁 수정은 검증 기준이 다르다.

기록에는 서버 테스트로 앉기 이전 걸음의 경쟁을 재현했고 프런트 테스트·타입 검사·빌드를 통과했다고 남아 있다. 실제 운영 지연과 모바일 환경에서는 당시 재확인이 필요했다. 이번 글에서도 운영 재현 결과는 **확인하지 못함**이다.

## 배운 점

명령을 먼저 보냈다는 사실과 서버에서 처리를 마쳤다는 사실은 달랐다.
상태 전환에는 이전 입력과 이후 입력을 나누는 순번 경계가 필요했다.
비동기 인증 결과에는 늦은 반영과 중복 적용 방지를 함께 설계해야 했다.
