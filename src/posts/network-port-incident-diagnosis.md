## 1. 학습 배경

NURI2 다중 WAS 복기에는 한쪽만 동작한 현상과 다른 WAS를 가리키는 기동 로그가 남아 있다. 실제 설정 원문 없이 원인을 특정하기보다, 다음에는 어떤 증거로 접근할지 정리한다. 아래 명령과 장애 분류는 학습용이며 당시 실행한 절차라고 주장하지 않는다.

## 2. 핵심 개념

포트는 호스트 안의 통신 종단을 구분하는 번호다. 리스닝은 특정 주소·포트에서 연결을 기다리는 상태이고 외부 접근 성공은 라우팅·방화벽·프록시·서비스까지 통과한 결과다. 로컬에서 열렸다고 인터넷에서도 열린 것은 아니다.

## 3. 동작 원리

```text
이름 해석 → IP 경로 → 연결 수립 → TLS(HTTPS)
  → HTTP 응답 → 인증·업무 처리 → DB·외부 시스템
```

각 단계 실패는 다음 단계의 성공 여부를 알려 주지 않는다. TCP 연결 성공이 DB 로그인 성공을 뜻하지 않고, HTTP 200도 응답 본문이 오류를 담는 API에서는 업무 성공의 충분조건이 아니다.

## 4. 실무 활용

아래 주소와 서비스는 학습용이다. 명령은 실행하지 않았다.

```bash
ss -lntp
ss -ntp
ip route
curl --show-error --connect-timeout 3 --max-time 10 \
  -o /dev/null -w 'status=%{http_code} connect=%{time_connect} total=%{time_total}\n' \
  http://127.0.0.1:8080/health
```

`ss -lntp`는 수신 대기 TCP 소켓을 숫자 주소와 프로세스 정보로 확인한다. 권한에 따라 프로세스 정보가 제한될 수 있다. [ss 매뉴얼](https://man7.org/linux/man-pages/man8/ss.8.html)을 기준으로 한다.

curl은 [공식 옵션](https://curl.se/docs/manpage.html)에 따라 연결 제한과 전체 제한을 따로 둔다. 위 명령은 기본적으로 HTTP 4xx·5xx만으로 종료 코드를 실패로 만들지는 않으므로 상태 코드도 읽어야 한다. HTTPS 이름 기반 서비스는 올바른 호스트명·SNI·인증서로 검사한다. 로컬 성공 후 프록시와 외부 요청 위치로 넓혀 가며 어느 경계부터 실패하는지 찾는다.

## 5. 주의사항 및 오개념

Connection refused는 도달한 지점의 거부·리스너 부재 등을, timeout은 무응답·차단·지연 등을 의심하게 하지만 오류 한 줄만으로 특정 방화벽 규칙을 확정하지 않는다. ping은 ICMP 검사이므로 실패했다고 TCP도 반드시 실패하는 것은 아니다. 인증서 오류를 `-k`로 숨긴 결과를 정상 HTTPS 검증으로 보고하지 않는다.

## 6. 기술 면접 예상 질문

| 질문·의도 | 핵심을 담은 구어체 답변 | 꼬리 질문 |
| --- | --- | --- |
| 포트가 열렸는데 접속이 안 되면? 경계 분리 | “어느 주소에 리스닝하는지 보고 로컬·프록시·외부에서 차례로 검사하겠습니다. 방화벽과 이름 해석도 따로 봐요.” | 127.0.0.1에만 바인딩했다면? |
| timeout과 refused 차이는? 오류 해석 | “거부 응답이 왔는지 제한 시간 안에 답이 없었는지의 차이예요. 어느 장비에서 생겼는지 추가 증거로 확인하겠습니다.” | 프록시 502와는 어떻게 다른가? |
| HTTP 200이면 정상인가? 업무 계약 | “전송 계층과 HTTP 처리는 통과했지만 본문·업무 상태와 외부 의존성 결과도 확인해야 해요.” | 어느 지연 시간을 측정하나? |

## 7. 핵심 요약

관측 위치·프로토콜 단계·시간 범위를 함께 적는다. 확인한 설정과 로그 기반 추정을 구분한다.
