슬개기술연구소에 WebSocket 멀티플레이어를 붙인 뒤, 연결이 유지돼도 내 캐릭터가 흔들리는 문제가 남았다. 상하좌우와 대각선 모두 움직임이 부자연스러웠고, 앞으로 이동하다가 다시 끌려오는 것처럼 보였다.

이전에 처리하던 `1008 Input rate exceeded`와는 증상이 달랐다. 연결을 오래 유지하는 것과 캐릭터를 부드럽게 움직이는 것은 별도로 검증해야 했다.

이번에는 서버 제한을 더 느슨하게 바꾸기보다 **내 캐릭터의 위치를 누가, 언제, 어떤 기준으로 수정하는지**부터 추적했다. 그 결과, 지연된 서버 좌표와 현재 로컬 좌표를 직접 비교하던 방식에 더해 `body.reset()`의 동작이 현재 발밑 충돌 영역과 맞지 않는 경로를 확인했다.

프로젝트는 React + Vite + TypeScript, Phaser **3.90.0**, Java 17 + Spring Boot 기반이다. 수정 범위는 이동과 위치 동기화로 한정했다. 기존 충돌, 애니메이션, 플레이어 인사, 컴퓨터 상호작용과 연구 기록 패널을 유지하는 것이 조건이었다.

## 연결 종료와 이동 진동을 먼저 구분했다

앞선 작업에서는 다음 오류를 확인했다.

```text
code: 1008
reason: Input rate exceeded
```

이 경우에는 서버가 메시지 수신 빈도 제한으로 연결을 종료했다는 점이 명확했다. 클라이언트의 방향 변경 전송과 정기 전송을 합쳐 제한하고, 서버에서는 짧은 수신 몰림을 흡수하도록 보완했다. 다만 실제 운영 전송 경로에서 버퍼링이 발생했는지까지 확인한 것은 아니었다.

그 뒤에는 다른 종료 사유도 보고됐다. 아래는 실제 전달받은 종료 기록 중 한 건이다.

```text
code: 1008
reason: Invalid input
wasClean: true
sentInputs: 10
connectedMs: 4322
sentLastSecond: 0
```

4.3초 동안 10개를 전송했고 마지막 1초에는 이동 입력을 보내지 않았다는 기록이었다. 이 오류를 다시 입력 횟수 제한으로 설명할 수는 없었다.

백엔드를 재기동한 뒤 정상화됐다는 확인을 받았다. 개발 중 새 프론트엔드 코드가 반영됐지만 실행 중인 백엔드는 이전 코드였을 가능성이 있었다. 그래서 서버가 지원을 알린 경우에만 새 인사 요청을 보내도록 호환성 검사도 추가했다.

하지만 당시 서버가 거부한 원문 메시지는 확보하지 못했다. **재기동 후 정상화된 사실과, 버전 불일치가 원인이었을 것이라는 해석은 구분해서 기록했다.**

이번 이동 진동은 연결 종료 이후의 또 다른 문제였다.

| 증상 | 확인한 내용 | 조사할 기준 |
| --- | --- | --- |
| Input rate exceeded | 서버 수신 빈도 제한으로 종료 | 실제 송수신량과 제한 방식 |
| Invalid input | 입력 검증에서 거부, 재기동 후 정상화 | 메시지 형식·입력 번호·실행 버전 |
| 연결은 유지되지만 이동이 흔들림 | 로컬 이동과 서버 위치 보정 경로 조사 | 좌표의 시점과 Physics Body 갱신 |

## 내 캐릭터의 위치를 바꾸는 경로를 추적했다

로컬 플레이어와 원격 플레이어는 이동 방식이 달랐다.

로컬 플레이어는 `Player.update()`에서 키보드 방향을 읽고 정규화한 뒤 속도를 설정한다. 초당 이동 속도는 200px이며 시간 적분과 벽·가구 충돌은 Arcade Physics가 처리한다. WebSocket 응답을 받아야만 화면에서 움직이는 구조는 아니었다.

```text
키보드 입력
  → 매 Phaser 프레임에서 이동 속도 설정
  → Arcade Physics의 시간 적분·충돌 처리
  → Sprite 위치 반영

이동 입력
  → 별도로 제한된 주기로 WebSocket 전송
  → 서버에서 이동·충돌 계산
  → 서버 상태를 약 20Hz로 전파
```

반면 다른 방문자의 캐릭터는 서버 스냅샷 사이를 보간했다. React는 접속 상태와 연구 기록 패널을 표시했으며, 로컬 캐릭터 좌표를 직접 갱신하지 않았다.

문제는 `LobbyMultiplayer.applySnapshot()`이었다. 서버 상태를 수신한 콜백 안에서 로컬 캐릭터 위치를 수정했다. 다음은 기존 로직의 핵심 부분이다.

```typescript
const distance = Math.hypot(this.player.x - own.x, this.player.y - own.y)
const input = this.player.getInput()

if (this.selfId !== selfId || distance > 96) {
  this.player.body.reset(own.x, own.y)
} else if (
  distance > 24 ||
  !own.moving && input.x === 0 && input.y === 0 && distance > 1
) {
  this.player.body.reset(
    Phaser.Math.Linear(this.player.x, own.x, 0.25),
    Phaser.Math.Linear(this.player.y, own.y, 0.25),
  )
}
```

작은 차이는 일부만 반영하고 큰 차이는 서버 위치로 맞추려는 의도였다. 그러나 비교하는 두 좌표의 시점이 달랐고, 보정할 때 호출하는 API도 단순한 좌표 이동으로 취급하고 있었다.

## 지연된 서버 좌표와 현재 좌표를 바로 비교하고 있었다

서버 상태가 도착할 때 로컬 플레이어는 이미 다음 입력을 처리하고 있다. 이때 지연된 서버 위치를 현재 위치와 그대로 비교하면, 정상적으로 진행한 이동까지 오차로 계산할 수 있다.

예를 들어 다음 값은 원리를 설명하기 위한 예시이며 실제 측정값은 아니다.

| 위치 | X |
| --- | ---: |
| 입력 42번을 보냈을 때의 로컬 예측 위치 | 440 |
| 해당 입력 번호를 응답한 서버 위치 | 442 |
| 응답이 도착한 시점의 로컬 위치 | 470 |

현재 위치와 서버 위치를 비교하면 28px 차이가 난다. 하지만 입력 42번을 보낼 때의 예측 위치와 비교하면 차이는 2px이다. 그 이후 로컬에서 진행한 이동을 전부 되돌릴 이유는 없다.

기존 프로토콜에는 클라이언트 입력의 `seq`와 서버가 마지막으로 수신해 적용한 입력 번호인 `ack`가 있었다. 그러나 로컬 보정은 이 번호에 대응하는 과거 위치를 사용하지 않았다.

여기서 `ack`가 물리 시뮬레이션의 정확한 시각까지 나타내는 것은 아니다. 서버는 자신의 고정 틱으로 이동을 계산한다. 따라서 입력 번호를 맞추더라도 서버 틱과 렌더링 프레임 사이의 작은 차이는 허용해야 했다.

## body.reset은 좌표만 바꾸는 메서드가 아니었다

두 번째 문제는 실제 Phaser 3.90.0의 `Body`로 재현했다.

현재 캐릭터는 16×24 원본 Sprite를 2배로 표시하고, origin을 `(0.5, 1)`로 둔다. 화면상의 외형은 32×48이지만 충돌 영역은 발밑의 **20×16**으로 분리했다.

이 설정에서 `body.reset()`을 호출하자 다음 변화가 발생했다.

- 이동 속도가 `(0, 0)`으로 초기화됐다.
- 기존 `blocked` 충돌 플래그가 지워졌다.
- reset 직후 Body 기준점과 다음 물리 프레임의 발밑 offset 기준점이 달랐다.

실제 Body를 사용해 확인한 좌표는 다음과 같다.

| 단계 | Sprite 좌표 | Body 좌상단 |
| --- | --- | --- |
| 초기 발밑 영역 | (400, 400) | (390, 384) |
| reset(390, 400) 직후 | (390, 400) | (374, 352) |
| 다음 물리 preUpdate, 이동 시간 0으로 확인 | (390, 400) | (380, 384) |

목표 Sprite가 `(390, 400)`일 때 기대한 발밑 Body 좌상단은 `(380, 384)`이다. reset 직후에는 그 기준에서 X 6px, Y 32px 차이가 생겼다.

**이 프로젝트의 Sprite origin·scale·Body offset 조합에서 관찰한 결과다. 모든 Phaser 설정에서 같은 수치가 발생한다는 뜻은 아니다.**

네트워크 상태가 도착할 때마다 속도와 충돌 상태를 지우고 Body 기준점까지 바꿨다면, 보정 계수만 조절해서는 안정적인 이동을 기대하기 어려웠다. 일반적인 네트워크 보정에서 이 초기화 경로를 제거하기로 했다.

## 입력 번호에 맞춘 예측 위치를 기록했다

`MultiplayerClient`가 실제로 이동 입력을 전송하면 로컬 콜백에 그 `seq`를 알리도록 했다. `LocalReconciliation`은 그 순간의 로컬 예측 위치를 저장한다.

```text
입력 seq 전송
  → 해당 시점의 로컬 예측 위치 저장

서버 상태 수신
  → ack에 대응하는 예측 위치 조회
  → 서버 위치와 과거 예측 위치의 오차 계산
  → 이후 로컬에서 진행한 이동은 유지
```

기록은 최대 256개로 제한했다. 오래된 입력 번호는 정리하고, 같은 이동 `ack`나 그보다 오래된 응답은 중복 보정하지 않는다. 재접속과 장면 종료 시에도 기록을 비운다.

클라이언트 좌표를 서버로 보내도록 바꾸지는 않았다. 서버는 여전히 방향과 입력 번호를 받아 자신의 시계로 이동·속도·충돌을 계산한다.

이번 구현은 **ack를 기준으로 보정할 시점을 맞추는 제한적인 예측 보정**이다. 입력별 시간까지 맞춘 결정론적 재시뮬레이션이나 완전한 rollback을 구현한 것은 아니다. 기존 프로토콜을 유지하면서 2~5명 규모에 필요한 범위로 수정했다.

## 위치를 쓰는 시점을 물리 프레임 이후로 모았다

서버 수신 콜백에서는 더 이상 Body 위치를 바꾸지 않는다. 오차와 보정할 양만 기록한다.

실제 위치 수정은 Arcade Physics의 `postUpdate`가 끝난 뒤, Scene의 `POST_UPDATE`에서 한 번 수행한다. 물리 엔진이 Sprite에 이동 결과를 반영한 다음 네트워크 보정을 적용하도록 순서를 정했다.

```text
서버 수신 콜백: 오차 기록
                         ↓
Physics 이동·충돌 → Sprite 반영 → POST_UPDATE에서 보정
```

일반 보정은 Sprite와 Body의 관련 위치를 같은 양만큼 옮긴다. 아래는 실제 구현의 핵심이다.

```typescript
sprite.setPosition(sprite.x + dx, sprite.y + dy)

for (const position of [body.position, body.prev, body.prevFrame]) {
  position.x += dx
  position.y += dy
}

body.updateCenter()
```

이 경로에서는 `body.reset()`을 호출하지 않으므로 이동 속도와 충돌 플래그를 보존한다. 현재 플레이어가 사용하는 일반 Arcade Body 이동 방식을 기준으로 검증했으며, 다른 물리 구성을 위한 범용 이동 API를 만든 것은 아니다.

보정량에도 제한을 뒀다.

| 기준 | 이번 설정과 의도 |
| --- | --- |
| 이동 중 허용 오차 | 16px, 서버 50ms 틱의 최대 10px 이동과 렌더링 차이 허용 |
| 정지 중 허용 오차 | 2px, 남은 작은 차이 수렴 |
| 일반 보정 속도 | 최대 60px/초, 200px/초의 키 이동을 역전시키지 않도록 제한 |
| 큰 오차 | ack 기준 128px 초과 시 검증된 서버 위치로 한 번 동기화 |
| 대응 기록 누락 | 즉시 현재 위치를 덮지 않고, 1초 이상 누락과 큰 오차가 함께 남을 때 재동기화 |

일반 보정이 벽이나 가구를 통과해서도 안 됐다. 공유 맵의 발밑 모양과 장애물을 기준으로 보정 경로를 축별로 제한했다. 서버의 기존 속도·맵 경계·장애물 충돌·입력 번호·메시지 빈도 검증은 그대로 유지했다.

원격 플레이어는 기존처럼 서버 스냅샷을 약 80ms에 걸쳐 보간한다. 로컬의 키 입력 예측과 원격의 스냅샷 보간을 같은 처리로 합치지 않았다.

## 수정 전후를 같은 조건의 자동 테스트로 비교했다

먼저 실제 Phaser Body를 사용한 격리 테스트를 만들었다. 60Hz 고정 스텝에서 초당 200px로 1초 동안 이동하고, 서버 스냅샷에 150ms 지연을 적용했다. 네 방향과 네 대각선을 각각 검사했다.

| 각 방향의 1초 결과 | 기존 알고리즘 | 수정 알고리즘 |
| --- | ---: | ---: |
| 입력과 반대로 움직인 프레임 | 1 | 0 |
| 불필요한 보정 횟수 | 1 | 0 |
| 보정 이동 거리 | 약 6.67px | 0px |
| 실제 이동 거리 | 약 190px | 약 200px |

이 테스트에서는 기존 알고리즘의 보정과 속도 초기화로 이동 거리가 줄고 역방향 프레임이 생기는 것을 확인했다. 수정 알고리즘은 해당 지연을 현재 위치의 오차로 오인하지 않았다.

단, 이 수치는 **가구가 없는 격리된 물리 테스트의 결과**다. 운영 브라우저의 모든 진동을 이 횟수로 설명하거나, 실제 브라우저의 수정 전후 FPS 비교로 해석하지 않았다. 충돌은 별도 경계 테스트와 브라우저에서 확인했다.

수신 콜백에서 위치가 바뀌지 않는지, POST_UPDATE에서만 보정하는지, 장면 종료 후 리스너가 남지 않는지도 회귀 테스트에 포함했다.

## 실제 브라우저 두 개에 지연을 넣어 확인했다

다음에는 실제 로컬 Tomcat과 Vite, 브라우저 두 개를 연결했다. 테스트 전용 TCP 중계기로 각 방향에 75ms씩 지연을 추가해 **추가 왕복 지연 150ms**를 만들었다.

키를 누른 시간을 합쳐 120초 동안 WASD, 방향키, 네 대각선, 빠른 방향 전환을 실행했다. 같은 연결은 약 3분 유지했다. `?netDebug=1`에서 5초마다 출력한 집계 34개를 확인했다.

| 브라우저 측정 항목 | 결과 |
| --- | --- |
| 렌더링 집계 FPS | 60.0~60.4 |
| 같은 방향 입력 중 역방향으로 움직인 프레임 | 0회 |
| 측정 구간의 강제 재동기화 | 0회 |
| ack에 맞춘 위치 오차 최대값 | 32.7px |
| 서버 스냅샷 수신 | 대체로 약 20Hz |
| 이동 입력 전송 | 구간별 약 14~17Hz |
| 정지 상태의 이동 입력 전송 | 0Hz |
| 2분 이동 중 정책 위반·연결 오류 | 없음 |

32.7px는 지연된 서버 좌표와 현재 Sprite 좌표를 그대로 뺀 값이 아니라, 입력 번호에 맞춘 예측 위치와의 오차다. 이 차이는 제한된 프레임별 보정으로 처리했다.

일부 방향 전환 구간에서는 작은 보정이 계속 발생했다. 60Hz 프레임에서는 보정 이동이 최대 약 1px로 제한됐다. **보정 자체를 없앤 것이 아니라, 정상 이동을 역전시키는 반복 초기화를 제거한 것이다.**

역방향 프레임 집계도 측정 기준을 한정했다. 같은 방향 입력이 유지되는 동안 실제 이동의 입력 방향 성분이 음수로 튀는 프레임을 세었다. 이 숫자 하나가 모든 형태의 시각적 진동을 증명하는 지표는 아니다.

수정 전 실제 브라우저 FPS는 측정하지 않았다. 따라서 “FPS가 개선됐다”는 성과로 쓰지 않는다. 격리 테스트의 비교 결과와 수정 후 브라우저의 관찰 결과를 나눠 해석했다.

## 이동 외의 기존 기능도 확인했다

진동이 줄어도 충돌이나 상호작용이 깨지면 수정이 끝난 것이 아니었다.

- 두 브라우저에서 서로의 캐릭터 이동과 방향 표시를 확인했다.
- 의자에 막히는 충돌과 우회 이동을 확인했다.
- 새로고침 후 접속자 상태가 갱신되는 것을 확인했다.
- 2분 이동 검사 이후 중계기를 의도적으로 끊었다가 다시 실행해 자동 복구를 확인했다.
- 복구 후 E 키 인사와 상대 화면의 말풍선 표시를 확인했다.
- 컴퓨터 E 키로 연구 기록을 조회하고 ESC로 패널을 닫는 동작을 확인했다.

로컬 브라우저 검증에는 DB 없는 테스트용 연구 기록 데이터를 사용했다. 운영 PostgreSQL에 접속해 확인한 결과는 아니다.

정상 접속에서 진단 로그가 계속 쌓이지 않도록 상세 이동 집계는 `?netDebug=1`일 때만 출력한다. FPS, 보정 횟수와 거리, 입력·스냅샷 빈도를 5초 단위로 모으며 원문 메시지나 자격 증명은 출력하지 않는다.

## 테스트와 Docker 빌드를 확인한 뒤 병합했다

로컬에서는 다음 검사를 실행했다. 명령은 실제 실행한 목표를 일반적인 프로젝트 루트 기준으로 정리했다.

```bash
npm --prefix frontend test
npm --prefix frontend run lint
npm --prefix frontend run build
mvn -B -f backend/pom.xml verify
```

프론트엔드 테스트는 **24개**, Maven 전체 테스트는 **27회** 통과했다. TypeScript 검사, Vite 프로덕션 빌드, 백엔드 실행 JAR 생성도 성공했다. 기존 큰 번들 크기 경고는 남아 있다.

로컬에는 Docker 실행 도구가 없어 이미지 빌드를 직접 실행하지 못했다. 대신 [PR CI 실행](https://github.com/seulgae/seulgae-tech-lab/actions/runs/43739089998)에서 다음 항목의 성공을 확인했다.

| CI 항목 | 결과 |
| --- | --- |
| 프론트엔드 테스트·린트·빌드 | 성공 |
| Maven 전체 검증 | 성공 |
| 임시 PostgreSQL 마이그레이션 및 실제 HTTP API 회귀 | 성공 |
| 백엔드 Docker 이미지 빌드 | 성공 |
| 프론트엔드 Docker 이미지 빌드 | 성공 |

작업 브랜치 `codex/fix-player-rubber-banding`의 [PR #11](https://github.com/seulgae/seulgae-tech-lab/pull/11)은 CI가 모두 통과하고 병합 가능한 상태인지 확인한 뒤 main에 병합했다.

- 작업 커밋: `39edf0691498a1db031813f65ff9774c4db1e6ce`
- main 병합 커밋: `622180723a9e1972672371d80cc690060ebc42ac`

주요 파일의 책임은 다음과 같이 나눴다.

| 파일 | 역할 |
| --- | --- |
| MultiplayerClient.ts | 실제 입력 전송 번호를 로컬 예측 기록에 전달 |
| LocalReconciliation.ts | ack에 대응하는 과거 위치 조회와 보정량 계산 |
| Player.ts, networkPosition.ts | 물리 프레임 이후 Sprite·Body 동기화와 보정 경로 충돌 제한 |
| LobbyMultiplayer.ts | 수신과 실제 위치 적용 분리, POST_UPDATE 연결·해제 |
| MovementDiagnostics.ts | 선택적으로 활성화하는 이동 집계 로그 |
| reconciliation.test.mjs | 실제 Body·지연 재현·충돌·프레임 순서 회귀 테스트 |

서버 코드나 DB 구조, GitHub Actions와 서버 인프라는 수정하지 않았다. PR CI의 성공과 main 병합은 확인했지만, 이후 자동 배포 완료 여부와 실제 운영 화면의 최종 체감은 이번 검증 범위에 포함하지 않았다.

## 이번에 배운 점

처음에는 연결이 끊기지 않고 캐릭터가 움직이면 멀티플레이어 이동도 어느 정도 검증됐다고 생각하기 쉬웠다. 하지만 입력 전송, 서버 이동, 로컬 Physics, 화면 보정은 서로 다른 시간 축에서 동작한다. 연결이 유지되는 것만으로 이 경계가 안전하다고 볼 수 없었다.

또한 `reset()`처럼 익숙해 보이는 이름도 현재 Body 설정에서 어떤 상태를 초기화하는지 확인해야 했다. 이번에는 실제 Phaser Body를 사용한 작은 재현이 속도·충돌 플래그·offset 문제를 드러냈다.

가장 중요했던 변경은 보정 값을 줄이는 것보다 **비교할 시점과 위치를 쓰는 시점을 명확히 나눈 것**이었다. 입력 번호에 맞는 과거 위치를 비교하고, Physics가 프레임을 마친 뒤 한 곳에서 보정하니 서버 검증을 유지하면서도 로컬 이동을 안정적으로 처리할 수 있었다.
