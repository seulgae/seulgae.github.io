## 1. 학습 배경

Java 개발 경험과 JVM 운영·튜닝 경험은 다르다. 이 글은 Java 17의 실행 구조를 복습하는 학습 문서다. 특정 고객사에서 GC나 JIT를 튜닝했다는 경험을 전제하지 않는다.

## 2. 핵심 개념

JDK는 컴파일러 등 개발 도구와 실행에 필요한 구성 요소를 제공한다. JRE는 Java 프로그램 실행 환경을 가리키는 개념이고, JVM은 클래스 파일을 실행하는 가상 머신이다. JRE를 반드시 별도 설치 패키지로 받아야 하는 것은 아니다. 배포판과 Java 버전에 따라 런타임 제공 방식이 다르다.

바이트코드는 CPU 명령어 자체가 아니다. OS·CPU에 맞는 JVM 구현이 이를 실행하므로 실행 플랫폼 차이를 흡수할 수 있다. 네이티브 라이브러리와 파일 경로까지 자동으로 이식되는 것은 아니다.

## 3. 동작 원리

```text
.java → javac → .class 바이트코드
  → 클래스 로딩 → 연결(검증·준비·해석) → 초기화
  → JVM 실행 엔진 → OS·CPU
```

연결의 해석은 구현에서 지연될 수 있어, 위 흐름을 모든 클래스가 한 번에 통과하는 고정 일정으로 외우지 않는다. 초기화는 클래스의 정적 초기화 등을 수행한다. HotSpot은 인터프리터와 JIT 컴파일을 함께 사용하지만, 특정 JIT 전략은 JVM 명세가 강제하는 단일 실행 방법이 아니다. 로딩·연결·초기화의 구분은 [JVM 명세 5장](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-5.html)을 기준으로 한다.

## 4. 실무 활용

**학습용 진단 예제:** 로컬 빌드는 되는데 서버에서 실행이 실패하면 먼저 `java -version`과 `javac -version`, 빌드의 target/release 설정을 대조한다. 더 새로운 클래스 파일을 오래된 런타임에 올린 문제와 의존 클래스를 찾지 못한 문제는 다르게 조사한다. 여기서는 명령을 실행하거나 장애를 재현하지 않았다.

## 5. 주의사항 및 오개념

JIT와 사전 컴파일, GC는 역할이 다르다. 시작 직후와 충분히 실행한 뒤 성능이 달라질 수 있지만 모든 지연을 JIT 탓으로 결론 내리면 안 된다. JDK 버전과 프로젝트 언어 수준, 실행 JVM은 각각 확인한다.
