슬개기술연구소의 멀티플레이어 이동을 개선하면서 내 캐릭터의 움직임은 많이 자연스러워졌다. 그런데 브라우저 화면을 두 개 띄워 보니 다른 문제가 보였다. 내 화면에서는 바로 움직이는데 상대 화면에는 조금 늦게 나타났고, 상대 캐릭터가 끊기듯 이동했다. 움직이다 보면 WebSocket 연결도 종료됐다.

이번에는 **연결이 끊기는 문제와 상대 캐릭터가 부드럽게 보이지 않는 문제를 나누어 조사했다.** 로컬 예측을 유지하면서 서버의 입력 검증과 원격 표시를 보완하는 것이 목표였다.

프로젝트는 React + Vite + TypeScript, Phaser **3.90.0**, Java 17 + Spring Boot 기반이다. 이번 글은 재현한 문제의 수정과 로컬 검증, PR 병합까지의 기록이다. 수정본을 운영에 반영한 뒤의 결과는 아직 확인하지 않았다.

## 같은 이동 문제처럼 보여도 확인할 기준이 달랐다

앞선 작업에서는 지연된 서버 위치와 현재 로컬 위치를 비교하면서 캐릭터가 뒤로 밀리는 문제를 다뤘다. 허용 오차와 보정량을 조절한 뒤에도 한계가 남아, 서버가 완료한 입력을 기준으로 미확인 이동을 재생하도록 바꿨다.

이번에 다시 확인한 증상은 다음과 같았다.

| 구분 | 관찰한 증상 | 확인할 대상 |
| --- | --- | --- |
| 내 캐릭터 | 내 화면에서는 움직임이 개선됨 | 기존 로컬 예측과 물리 처리가 유지되는지 |
| 상대 캐릭터 | 다른 화면에서 늦게 포착되고 끊기듯 이동 | 스냅샷 수신 간격과 원격 보간 |
| 연결 | 이동 중 1008로 종료 | 서버가 어떤 명령을 어떤 조건에서 거부했는지 |

내 캐릭터는 키보드 입력을 받아 Arcade Physics로 먼저 이동한다. 다른 방문자의 캐릭터는 서버에서 받은 위치를 이용해 표시한다. 두 화면의 움직임은 서로 다른 경로를 거치므로 각각 검증해야 했다.

## 종료 로그에서 확정할 수 있는 범위를 먼저 정했다

제보된 로그의 주요 값은 다음과 같았다.

```json
{
  "code": 1008,
  "connectedMs": 119005,
  "reason": "Invalid movement command",
  "sentInputs": 1504,
  "sentLastSecond": 0,
  "wasClean": true
}
```

이 프로젝트의 서버 핸들러는 이동 명령의 형식, 방향, 시간, 순번, 시간 예산 검증에서 실패하면 같은 `Invalid movement command` 문구로 연결을 닫고 있었다. **이 로그만으로 어느 조건이 실패했는지는 확정할 수 없었다.**

`sentInputs`도 이름을 주의해서 읽어야 했다. 당시 클라이언트 코드는 이 필드에 마지막 물리 스텝의 순번을 기록했다. 여러 스텝을 한 메시지에 묶어 보내므로, 1504를 그대로 WebSocket 메시지 수로 해석할 수는 없다. `sentLastSecond: 0` 역시 종료 직전 1초의 전송 상황을 보여주는 값이다.

운영에 띄워 둔 두 창의 실행 파일과 이동·상대 표시를 확인했지만, 이번 관찰에서는 제보된 종료를 다시 잡지 못했다. 따라서 이후 로컬에서 확인한 거부 경로와 운영 오류의 정확한 원인은 구분해서 기록했다.

## 정상 입력도 지연 뒤에 몰리면 거부될 수 있었다

완료 입력 재생 방식에서는 클라이언트가 실제 `WORLD_STEP`의 방향과 시간을 기록한다. 서버는 이 명령을 검증해 이동과 충돌을 계산하고, 처리 완료 순번을 `ack`로 전달한다.

기존 서버에는 이동 시간 예산이 있었다. 서버의 단조 시계로 예산을 충전하고, 명령의 이동 시간만큼 소비하는 방식이다. 클라이언트가 시간을 과장해 계속 빠르게 이동하는 것을 막기 위한 장치였다.

문제는 **당장 사용할 수 있는 예산이 부족하면 명령을 즉시 거부했다는 점**이었다. 네트워크에서 정상 입력이 잠시 대기했다가 한꺼번에 도착하면, 입력이 만들어진 시간과 서버에서 수신한 간격이 달라질 수 있었다.

이를 확인하기 위해 같은 Java 탐침을 수정 전 `LobbyRoom`과 수정 후 클래스에 각각 실행했다. 60Hz 기준 3초 이동에 해당하는 180개 스텝을 메시지당 8개 이하로 묶어 같은 서버 시각에 전달했다.

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 수신에 성공한 이동 스텝 | 120개 | 180개 |
| 즉시 처리 예산이 부족할 때 | `Movement time exceeded`로 거부 | 남은 명령을 대기 큐에 보관 |
| 이후 처리 | 거부된 명령은 진행하지 못함 | 예산 충전 후 끝까지 완료 |

수정 전 탐침에서는 다음 결과를 얻었다.

```text
accepted=120, rejected=Movement time exceeded
```

수정 후에는 다음과 같이 진행됐다.

```text
accepted=180, initial ack=121
after drain ack=181
```

탐침의 첫 명령은 순번 1의 0ms 정지 명령이었다. 이동 명령 180개는 순번 2부터 181까지다. 초기 `ack=121`은 정지 명령과 이동 120개가 완료됐다는 뜻이며, 나머지 이동 60개가 대기한 뒤 `ack=181`까지 처리됐다.

이 재현으로 **정상 입력 몰림이 기존 서버의 일반 종료 문구로 이어지는 경로 하나를 확인했다.** 제보된 운영 오류도 반드시 이 분기였다고 단정하지는 않았다.

## 수신한 순번과 완료한 순번을 분리했다

예산이 부족한 명령을 기다리게 하려면, 서버가 받은 입력과 실제로 적용한 입력을 구분해야 했다.

```text
명령 수신
  → 형식·방향·시간·연속 순번 검증
  → 제한된 대기 큐에 저장
  → 서버 시간 예산이 허용하는 만큼 이동·충돌 계산
  → 처리 완료 순번을 ack로 전파
```

서버 내부에는 수신 순번을 별도로 보관하고, `ack`는 기존 의미대로 실제 처리가 끝난 번호를 유지했다. 이미 수신한 명령을 다시 보내도 큐에 중복으로 넣지 않는다.

| 제한 | 값과 역할 |
| --- | --- |
| 스텝 시간 | 이동 스텝당 최대 50ms, 정지 명령은 0ms |
| 메시지 묶음 | 한 메시지에 최대 8개 명령 |
| 즉시 처리 예산 | 초기 250ms, 최대 2000ms |
| 서버 대기 큐 | 합계 2000ms 및 240명령 이하 |
| 이동 계산 | 서버에서 초당 200px, 대각선 정규화와 맵 충돌 적용 |

즉시 처리 예산은 지금 적용할 수 있는 이동 시간이고, 대기 큐의 시간 한도는 이후 충전을 기다릴 수 있는 양이다. 예산이 부족한 정상 명령은 기다리되, 계속 시간을 과장해 대기 한도를 넘기는 요청은 거부한다. 기존 메시지 빈도 제한과 잘못된 방향·시간·순번 검증도 유지했다.

예산 갱신에는 동시 실행 상황도 반영했다. 수신 콜백이 시각을 기록한 뒤 잠금을 기다리는 동안 서버 갱신이 먼저 진행될 수 있다. 오래된 콜백의 시각으로 예산 시계를 되돌리면 다음 갱신에서 같은 시간이 중복 충전될 수 있었다.

다음은 예산 갱신의 핵심 부분이다.

```java
now = Math.max(now, member.budgetAt);
member.timeBudget = Math.min(2000,
    member.timeBudget + Math.max(0, now - member.budgetAt) / 1_000_000d);
member.budgetAt = now;
```

대기 큐를 도입한 뒤에도 서버 시계에 따른 속도 제한이 유지되는지, 과거 시각의 콜백이 예산을 추가로 만들지 않는지를 회귀 테스트에 넣었다.

## 상대 캐릭터는 서버 시간의 표본 사이를 보간했다

원격 캐릭터의 기존 로직은 최신 목표 좌표를 계속 따라가는 방식이었다. 프레임마다 현재 위치에서 목표까지 `delta / 80` 비율로 이동했고, 거리가 크면 바로 목표 위치로 옮겼다.

수신 간격이 일정하지 않으면 목표와의 거리가 달라진다. 캐릭터가 목표 근처에서 느려졌다가 새 위치가 도착하면 다시 빨라질 수 있었다. 이동 중 같은 좌표가 반복되는 서버 틱도 잠깐 멈추는 구간처럼 보일 수 있었다.

이번에는 `welcome`과 `state`에 서버 단조 시계의 밀리초 값인 `time`을 추가하고, 원격 위치 표본을 잠깐 보관하도록 바꿨다.

```text
서버 시간과 위치 표본 수신
  → 수신 지터를 반영한 표시 버퍼
  → 일정한 재생 시각에서 앞뒤 표본 선택
  → 두 위치 사이 보간
```

주요 처리는 다음과 같다.

- 위치 표본과 시계 차이 측정값을 각각 최대 120개 보관한다.
- 수신 지터에 따라 100~650ms의 표시 버퍼를 사용한다.
- 이동 중 반복된 같은 위치를 불필요한 정지 구간으로 만들지 않는다.
- 오래 쉬었다가 이동할 때는 첫 이동을 과거 유휴 시간 전체에 걸쳐 보간하지 않는다.
- 백그라운드 복귀나 긴 단절 후에는 재생 시계를 다시 맞춘다.
- 알려진 마지막 위치 너머로 외삽하지 않고, 원격 표시의 따라잡기 속도를 제한한다.

처음에는 버퍼 상한을 400ms로 잡았지만, 실제 가변 지연 시험에서 표본이 부족해 멈추는 구간이 나타났다. 이를 반영해 상한을 650ms로 조정했다.

표시 버퍼는 지연을 조금 더 두고 수신 간격의 흔들림을 흡수하는 선택이다. 전달 시간 자체가 사라지는 것은 아니며, 버퍼 한도를 넘는 지연이나 완전한 전송 정체에서는 일시 정지가 남을 수 있다.

이 변경은 원격 캐릭터의 표시 경로에 적용했다. 본인 캐릭터의 Arcade Physics 이동과 미확인 입력 재생은 유지했다.

## 재현 모델과 실제 브라우저의 결과를 나누어 확인했다

### 일정 이동을 비교한 격리 모델

20Hz 스냅샷에 수신 지터와 중복 이동 틱을 넣고, 일정 이동 구간의 프레임별 속도 표준편차를 비교했다.

| 방식 | 프레임별 속도 표준편차 |
| --- | ---: |
| 기존 최신 목표 추종 | 71.34px/s |
| 서버 시간 기준 버퍼 보간 | 0.37px/s |

같은 모델의 일정 이동 구간에서는 속도 변동이 줄었다. **이 수치는 운영 환경 전체의 개선율이나, 충돌·반전이 섞인 실제 브라우저의 평균 결과가 아니다.**

### 로컬 브라우저 화면 두 개와 가변 지연

로컬 Tomcat과 Vite 사이에 테스트용 TCP 중계기를 두고, 각 방향에 150~650ms의 가변 지연을 적용했다. 두 브라우저 화면으로 본인과 상대 캐릭터를 함께 관찰했다.

| 확인 항목 | 결과 |
| --- | --- |
| 키를 누른 이동 시간 | 합계 120초 |
| 대기를 포함한 세션 관찰 | 약 5분, 5초 집계 56개 |
| 해당 구간의 새 연결 종료 | 없음 |
| 강제 위치 동기화 | 없음 |
| 일반 위치 보정 | 일부 충돌·반전 구간에서 7회 |
| 최대 집계 위치 오차 | 10.5px |

일반 보정이 남아 있으므로 모든 보정이 없어졌다고 기록하지 않았다. 가변 지연과 급반전이 섞인 구간에는 원격 표시가 짧게 멈추는 프레임도 남았다.

별도로 중계기에 3초 전송 정체를 넣고 입력을 풀었을 때에도 연결이 유지됐고, 이후 이동과 정지가 복구됐다. 개발 중 의도적으로 중계기를 재시작하거나 페이지를 갱신한 종료 기록은 정상 이동 관찰 구간과 분리했다.

이 시험은 로컬 화면 두 개와 인위적인 지연을 이용했다. 서로 다른 실제 기기와 회선에서의 최종 체감은 추가 확인이 필요하다. 연구 기록 조회는 운영 DB 대신 기존 로컬 fixture를 사용했고, E로 목록 열기와 ESC 종료도 확인했다.

### 자동 검사와 PR 검증

프런트엔드에서는 다음 명령을 실행했다.

```powershell
cd frontend
npm.cmd test
npm.cmd run lint
npm.cmd run build
```

백엔드는 Maven `verify`를 실행했다. 테스트 JVM에는 `-DargLine=-XX:ActiveProcessorCount=2`를 적용했다.

- 프런트엔드 테스트 31개, lint, TypeScript 및 Vite 빌드 통과.
- 백엔드 테스트 39개, Maven verify 및 실행 JAR 생성 통과.
- 실제 WebSocket에서 입력 몰림 후 연결 유지와 정지 명령의 완료 ack 확인.
- 잘못된 방향·시간·순번과 대기 한도 초과 차단, 재접속 시 입력 순번 초기화 검증.
- PR CI에서 프런트엔드·백엔드 검사, 임시 PostgreSQL API 검증과 Docker 이미지 빌드 통과.

기존 Vite 번들 크기 경고는 남아 있다.

## 재발했을 때 구분할 수 있도록 진단도 바꿨다

앞으로는 이동 검증 실패의 종료 사유를 형식, 방향, 시간, 순번, 대기 한도에 따라 나눈다. 예를 들어 방향 검증 실패는 `Invalid movement: Movement axes`, 대기 한도 초과는 `Invalid movement: Movement backlog exceeded`로 확인할 수 있다.

클라이언트의 `[multiplayer:movement-rejected]`에는 마지막 전송 묶음의 방향·스텝 시간·순번과 대기 개수를 남긴다. 플레이어 좌표, 채팅 원문, 토큰 등은 추가하지 않았다.

`?netDebug=1`에서는 `[multiplayer:remote]`로 원격 표시의 프레임, 표시 중 정지 프레임, 속도 변동과 버퍼 시간을 확인할 수 있다. 충돌과 방향 전환이 섞인 집계는 일정 속도 구간의 수치와 구분해서 읽어야 한다.

## 코드 반영과 남은 운영 확인

수정 커밋은 [`6ee4c80`](https://github.com/seulgae/seulgae-tech-lab/commit/6ee4c805538e5b348b5b34c3afa4fad0a76c393a)이며, [PR #15](https://github.com/seulgae/seulgae-tech-lab/pull/15)의 CI 성공을 확인한 뒤 main에 병합했다.

이번에 확인한 것은 입력 몰림 거부 경로의 재현과 수정, 원격 표시 방식의 변경, 로컬 검증과 코드 병합까지다. **수정본의 운영 배포 후 종료 재발 여부와 실제 체감은 글 작성 시점에 미검증이다.**

운영에서 확인할 때는 두 창을 모두 새로고침하고, 같은 버전에서 이동·정지·반전을 반복해야 한다. 다시 종료되면 새 종료 사유와 마지막 명령 정보를 함께 확인한다. 다른 기기와 회선에서도 원격 표시의 부드러움과 추가 표시 지연을 살펴볼 필요가 있다.

이번 작업에서 가장 크게 배운 점은 연결 유지, 로컬 예측, 원격 표시를 각각 측정해야 한다는 것이었다. 짧은 지연 시험을 통과한 뒤에도 긴 연결과 입력 몰림에서는 다른 문제가 드러났다. 다음 검증에는 일정 지연뿐 아니라 입력 몰림, 긴 유휴 후 재출발, 단절 복구를 처음부터 포함하려고 한다.
