기업별 청구 정보를 관리하는 화면에서는 사용자에게 등록된 권한을 기준으로 조회 가능한 목록을 제공했다. 권한 정보는 **권한 API를 호출해 가져왔고**, 이를 Redis에 저장해 재사용했다.

## 배경 — 반복되는 권한 조회

권한을 확인할 때마다 같은 API를 반복 호출하면 화면·목록 조회에 같은 권한 확인 비용이 쌓인다. 사용자 권한 정보를 Redis에 보관하고, 이후 요청에서 재사용해 반복 호출을 줄였다.

이 서비스가 권한 테이블에 직접 접근해 SQL을 실행한 구조로 설명했던 부분은 정정했다. 업무 목록을 조회하는 MyBatis·MySQL 경로와 권한 API를 호출하는 경로는 구분한다.

## 로그인 시 권한 정보 저장

로그인할 때마다 권한 API로 사용자가 가진 권한을 조회해 Redis에 저장했다. 이후 화면·API 요청에서는 캐시된 권한을 기준으로 조회 가능한 목록을 가져왔다.

```text
매 로그인 → 권한 API 호출 → 사용자 권한 조회 → Redis에 저장
이후 요청 → Redis의 권한 확인 → 권한에 맞는 업무 목록 조회·반환
```

권한 정보를 캐싱한 것이므로 업무 목록 전체를 Redis에 저장했다는 의미는 아니다. 목록을 가져오는 데 필요한 업무 데이터 조회는 별도로 수행한다.

## 재로그인 시 권한 갱신

재로그인할 때도 권한 API에서 사용자 권한을 다시 가져와 Redis에 저장·갱신했다. 이후 요청에서는 저장된 권한을 재사용했다.

```text
로그인 · 재로그인 → 권한 API 호출 → Redis 권한 정보 저장·갱신
이후 요청 → 캐시된 권한 재사용 → 권한에 맞는 업무 목록 제공
```

## 캐시 보관 기간

TTL은 사용자 권한 정보가 Redis에 계속 쌓이지 않도록 보관 기간을 제한하려는 목적으로 사용했다. 시간이 지나면 저장한 정보가 만료되도록 하고, 로그인·재로그인 시 권한 API에서 가져온 정보를 저장했다.

마지막에는 보관 기간을 **12시간 정도로 설정했던 것으로 기억한다.** 정확한 만료 설정 방식까지는 기억이 분명하지 않아 12시간을 검증된 운영 설정값으로 단정하지 않는다.

캐시의 보관 시간과 로그인 세션·토큰의 유효시간은 구분해야 한다. 고정 TTL이라면 저장 시점부터 시간이 흐르며 세션 활동이나 토큰 갱신과 자동으로 연결되지는 않는다. [Spring Data Redis의 TTL 설명](https://docs.spring.io/spring-data/redis/reference/redis/redis-cache.html)

당시 담당 업무에는 권한 수정에 대응하는 요구사항이 없었다. 권한 변경 시 캐시를 무효화하는 처리를 구현 성과로 제시하지 않는다. 로그아웃 시 삭제 방식과 장애 처리는 [AI 검수 기록](/blog/ai-portfolio-review-notes)의 확인 보류 항목이다.

로그인할 때마다 권한 API를 다시 호출해 저장하므로, API가 변경된 권한을 반환하고 해당 사용자 캐시에 반영된다면 재로그인 후에는 새 권한을 사용하게 된다. 이는 처리 흐름에서 예상할 수 있는 동작이며, 당시 권한을 수정한 뒤 재로그인해 검증한 결과까지 기억하는 것은 아니다.

TTL은 데이터가 남는 시간을 제한한다. 순간적인 대량 적재까지 포함한 메모리 사용량 제한은 별도의 maxmemory·축출 정책과 함께 검토할 수 있다. 이를 당시 설정했다고 주장하지 않는다. [Redis 메모리 관리 지침](https://redis.io/docs/latest/develop/reference/eviction/)

## 권한 변경 요구가 생긴다면 — 후속 개선안

만료·무효화·장애 처리의 세부 사항은 기억으로 채우지 않고 [사이드 프로젝트에서 재현·비교 검증할 계획](/blog/redis-permission-cache-side-project)이다. 아래 일반적인 개선 방향도 당시 구현 성과와 구분한다.

아래는 당시 구현한 기능이 아니라 추가 요구가 생길 때 검토할 방향이다.

권한 원본 변경이 성공하면 해당 사용자의 캐시를 무효화하고, 다음 요청에서 권한 API를 다시 호출해 새 권한을 저장하도록 설계할 수 있다. 원본 API와 캐시를 관리하는 서비스가 다르면 변경 알림·이벤트 또는 무효화 API 등 전달 수단부터 합의해야 한다. TTL은 알림 누락 등으로 오래된 정보가 남는 시간을 제한하는 보조 정책으로 사용한다. [Redis 캐시 갱신 지침](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

실제 데이터 접근 권한은 화면에서 목록을 숨기는 것만으로 보장하지 않는다. 서버에서 요청마다 사용자·대상·작업에 대한 권한을 확인해야 하며, 매 요청 권한 확인이 권한 API를 매번 호출해야 한다는 뜻은 아니다. 캐시의 허용 지연과 권한 회수 정책을 함께 정해야 한다. [OWASP 권한 검증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 결과

로그인 시 가져온 권한을 재사용하면서 화면 이동마다 반복되던 권한 API 호출을 줄였다. 적용 후 화면 전환과 로딩이 빨라진 것을 체감했다. 이 결과는 화면 사용 중 관찰한 정성적 개선이며 API 응답 시간이나 화면 로딩 시간을 계측한 수치로 제시하지 않는다.

## 배운 점

- **권한 조회 경로와 업무 데이터 조회 경로를 구분한다.** 권한 API의 응답을 캐싱한 경험을 권한 테이블의 SQL 튜닝으로 설명하지 않는다.
- **자주 재사용하는 결과를 캐싱하면 반복 호출을 줄일 수 있다.** 로그인·재로그인 시 권한을 갱신하고 이후 요청에서 저장된 정보를 재사용했다.
- **조회 최적화와 권한 변경 반영은 함께 고려한다.** 보관 기간과 무효화 정책은 구분하며 실제 수행한 구현과 이후 개선안을 섞지 않는다.
