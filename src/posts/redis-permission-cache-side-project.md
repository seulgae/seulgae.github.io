권한 API에서 가져온 사용자 권한을 Redis에 저장하고, 이후 요청에서 재사용해 반복 호출을 줄인다. 로그인 시 권한 적재와 캐시 미스 시 재조회를 기본 흐름으로 두고, 만료·권한 변경·동시 요청·장애 처리까지 설계한다.

## 목표와 구현 범위

목표는 사용자 권한을 정확한 범위로 재사용하면서 권한 API 호출을 줄이는 것이다. 최적화 여부는 호출 수·응답 시간·변경 반영 지연·오류를 함께 측정해 판단한다.

첫 단계는 Spring 기반 업무 API, Redis 하나, 제어 가능한 테스트용 권한 API로 구성한다. 테스트용 권한 API에는 사용자별 권한 조회·변경과 지연·오류 주입 기능을 둔다. 앱 인스턴스를 두 개로 늘리는 것은 기본 동작 확인 이후다. Spring·Redis 버전은 구현 저장소를 만들 때 고정해 기록한다.

## 과제 진행 순서와 제출물

기본 캐시 흐름부터 완성하고, 각 단계의 동작을 확인한 뒤 다음 과제로 넘어간다. 동시성·다중 인스턴스는 확장 과제로 진행한다.

| 과제 | 구현할 내용 | 확인할 결과·제출물 |
| --- | --- | --- |
| 1. 기본 권한 캐시 | 테스트용 권한 API, 로그인·재로그인 시 Redis 저장, 이후 요청에서 재사용 | 요청 흐름도, Redis 키·값 예시, 원본 API 호출 횟수 |
| 2. 만료와 재조회 | 설정 가능한 TTL, 만료 후 API 재조회 | 만료 전후 요청 결과, TTL별 호출 수 비교 |
| 3. 권한 변경 | 원본 권한 변경 후 캐시 무효화·갱신 확인 | 권한 회수 전후 접근 결과, 변경 반영 시간 |
| 4. 장애 대응 | Redis 중단, 권한 API 오류·지연, 정상 빈 권한 응답 구분 | 상황별 응답·로그와 보호 작업 실행 여부 |
| 5. 성능 비교 | 캐시 없음·기본 캐시·개선형 비교 | 동일 조건의 호출 수·응답 시간·오류율 비교표 |
| 확장. 동시성 | 동시 miss, 변경 중 오래된 응답 재적재, 두 인스턴스 실험 | 재현 절차와 개선 전후 결과 |

최종 결과물은 실행 가능한 Spring 프로젝트, 실행 방법을 적은 README, 재현 가능한 검증 절차, 측정 결과를 정리한 회고 글로 구성한다.

## 1단계 — 로그인 시 적재와 캐시 조회

```text
로그인 성공 → 권한 API 조회 → Redis 저장

인증된 업무 요청
  → Redis 권한 조회
      ├─ hit → 사용자·대상·작업에 대한 인가 판단
      └─ miss → 권한 API 조회 → Redis 저장 → 인가 판단
  → 허용된 경우에만 업무 데이터 조회
```

기본형은 매 로그인마다 원본 API에서 가져온 권한으로 저장하고, 이후 요청에서는 캐시를 우선 읽는다. 캐시가 없으면 API로 돌아가 채운다. Redis가 권한 API를 직접 호출하는 것이 아니라 애플리케이션이 이 흐름을 담당한다. [Redis cache-aside 설명](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

캐시에는 권한 목록과 원본 버전(테스트 API가 제공하는 경우), 조회 시각을 담은 DTO를 JSON으로 저장한다. 원본 API 호출 실패를 빈 권한 목록으로 바꾸어 정상 캐싱하지 않는다. 정상 응답의 빈 권한 목록은 유효한 결과로 구분하고 접근을 거부한다.

### 키와 책임

키 예시는 `permission:v1:{tenantId}:{userId}`다. tenantId가 없는 단일 조직 실험에서는 해당 구간을 생략할 수 있다. 값은 인증된 사용자 정보에서 얻으며 요청 파라미터만 믿고 다른 사용자의 권한을 가져오지 않는다. 권한이 자원·범위에 따라 다르면 그 차이가 키 또는 캐시 값과 인가 판단에 반영되어야 한다.

로그인 유효성 검사와 권한 캐시는 분리한다. Redis에 권한이 남아 있어도 로그아웃·만료된 세션으로 접근을 허용하지 않는다. 사용자 단위 공유 캐시와 세션별 데이터도 구분한다. 한 세션이 로그아웃했다고 다른 세션의 인증까지 해제되는 구조로 만들지 않는다.

서버에서는 매 요청마다 권한을 검사한다. 이는 매 요청마다 원본 API를 호출한다는 뜻이 아니다. 캐시된 권한을 쓸 수 있는지와 해당 요청을 허용할 수 있는지는 각각 판단한다. [OWASP 권한 검증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 2단계 — 보관 기간과 메모리 제한

첫 구현에서는 조회만으로 기간이 늘어나지 않는 고정 TTL을 사용한다. 테스트를 빠르게 반복하기 위해 짧은 만료 시간을 설정 가능하게 두고, 예를 들어 30초·60초·300초에서 비교한다. 이 값들은 실험 조건이며 운영 권장값이 아니다.

허용 가능한 권한 변경 지연이 정해져야 실제 TTL을 선택할 수 있다. 민감한 작업은 캐시를 우회해 원본 API로 확인하는 정책도 별도로 실험한다. 권한 회수를 즉시 반영해야 하는 작업에 긴 TTL만 적용하지 않는다.

TTL은 데이터 보관 시간을 제한한다. 메모리 사용량 상한은 Redis의 `maxmemory`로 별도 설정하고, 캐시 전용 인스턴스에서 축출 정책을 비교한다. `allkeys-lru`는 실험 후보이며, 키가 축출돼도 API 재조회로 복구할 수 있어야 한다. 세션·영구 데이터가 섞인 인스턴스에 같은 정책을 그대로 적용하지 않는다. [Redis 메모리·축출 정책](https://redis.io/docs/latest/develop/reference/eviction/)

Spring Data Redis의 캐시 설정은 TTL·직렬화·캐시별 설정을 지원한다. 다만 로그인 강제 갱신, API 오류와 정상 빈 응답 구분, 장애 정책까지 어노테이션 하나가 해결한다고 가정하지 않는다. 캐시 접근과 권한 API 호출을 분리한 서비스를 먼저 구현하고 실제 선택한 버전의 계약을 확인한다. [Spring Data Redis 캐시 설정](https://docs.spring.io/spring-data/redis/reference/redis/redis-cache.html)

## 3단계 — 권한 변경 처리

제어 가능한 테스트용 권한 API에서 변경이 성공하면 해당 사용자 캐시를 삭제하고 다음 요청에서 다시 가져오는 기본형을 만든다. 원본 변경에 실패했을 때는 성공으로 응답하지 않는다.

```text
원본 권한 변경 성공 → 대상 사용자 캐시 무효화
다음 요청 → 권한 API 재조회 → 변경된 권한 사용
```

하지만 삭제만으로 즉시 일관성을 보장할 수는 없다. 변경 전에 시작한 조회가 늦게 끝나면서 옛 권한을 다시 저장할 수 있다. 두 앱 인스턴스에서 다음 순서를 의도적으로 재현한다.

```text
A: 변경 전 권한 조회 시작 ───────────────→ 옛 응답 도착
B: 권한 변경 성공 → 캐시 삭제
A: 옛 응답을 캐시에 다시 저장하려는 경합
```

기본형은 이 경합과 원본 변경·캐시 삭제 사이의 실패 구간을 측정하는 대상이다. 즉시 회수를 보장하는 완성형으로 설명하지 않는다.

그다음 원본 API의 단조 증가 권한 버전과 변경 알림 재전송을 사용하는 개선형을 실험한다. 오래된 응답의 저장·사용을 어떻게 차단할지, 버전 정보 유실·알림 지연·앱 재시작 상황에서도 정책이 유지되는지 검증해야 한다. Redis Lua나 분산 락을 추가했다는 이유만으로 이 문제가 해결됐다고 판정하지 않는다.

원본 API가 버전이나 변경 이벤트를 제공하지 않는 실제 환경이라면 그 제약부터 합의해야 한다. 엄격한 회수 요구는 원본 재검증 등으로 충족하고, 일반 조회의 TTL 기반 허용 지연과 구분한다.

## 4단계 — 동시 요청과 장애 처리

캐시 miss와 Redis 장애는 다르다. 빈 값과 연결 실패·timeout을 별도로 다룬다.

| 상황 | 계획한 처리·검증 |
| --- | --- |
| 정상 hit | 원본 API 호출 없이 캐시된 권한으로 인가 판단 |
| 정상 miss | API 조회 후 저장. 같은 키에 요청이 몰리는 상황 측정 |
| Redis 연결 실패 | 원본 API를 제한 시간·동시 호출 상한 안에서 직접 호출하는 방안 실험 |
| API가 정상적으로 권한 없음 반환 | 접근 거부. 조회 실패와 구분 |
| API timeout·오류 | 권한을 확인할 수 없으므로 보호된 작업 실행 금지. 의존성 오류로 기록 |
| 캐시 JSON 손상 | 정상 권한으로 취급하지 않고 제거·재조회 시도. 재조회 실패 시 실행 금지 |
| Redis 저장 실패 | API에서 정상 조회한 권한으로 현재 요청을 판단하되 캐시 저장 실패를 관측. 다음 요청의 과도한 재호출 제한 |

기본 정책에서는 원본 API까지 실패했을 때 만료된 허용 권한으로 임의 승인하지 않는다. 권한 부족과 의존성 장애를 응답·로그·지표에서 구분한다. Redis 장애 폴백이 원본 API의 과부하로 이어지지 않도록 호출 상한과 재시도 횟수도 제한한다.

동일 키의 동시 miss는 먼저 단일 앱에서 요청을 합치는 single-flight 방식으로 비교한다. 두 인스턴스에서는 인스턴스별로 한 번씩 원본 호출이 발생할 수 있다. 분산 락은 원본 호출량이 실제 병목일 때 추가 비교하고, 락 만료·실패·대기 시간까지 측정한다. 캐시 stampede 방지와 권한 변경 경합 방지는 다른 과제로 검증한다.

## 비교 방법과 완료 기준

동일한 사용자·권한 데이터, API 지연, 동시 요청 조건에서 아래 세 가지를 비교한다.

| 비교군 | 목적 |
| --- | --- |
| 캐시 없음 | 매번 권한 API 호출하는 기준선 |
| 로그인 선적재 + Redis + 고정 TTL | 기본 캐싱 흐름의 효과 비교 |
| 변경 처리·요청 합치기·제한된 폴백 추가 | 개선 효과와 복잡도·실패 비용 비교 |

cold/warm cache를 분리하고 반복 횟수, 사용자 수, 요청 수, API 지연·오류율, TTL, 앱·Redis 버전과 자원 제한을 기록한다. p50/p95/p99 응답 시간, 권한 API 호출 수, hit/miss, 오류율, Redis 메모리·만료·축출 수, 권한 변경 반영 지연을 함께 측정한다.

- [ ] 로그인 때 원본 권한을 가져와 저장하고, 캐시 miss 후 API 재조회·저장이 동작한다.
- [ ] 사용자·조직이 다른 요청에서 캐시나 데이터 접근이 섞이지 않는다.
- [ ] 만료·축출 뒤 재조회가 가능하고, 캐시가 남아 있어도 만료 세션은 거부한다.
- [ ] 정상 권한 없음과 API 장애를 구분하고, 미확인 권한으로 보호 작업을 실행하지 않는다.
- [ ] 권한 변경 후 정상 반영과 이전 응답 재적재 경합을 각각 재현한다.
- [ ] 개선형이 만족하는 회수 지연·실패 정책을 수치와 테스트로 설명한다. 보장하지 못한 조건은 남긴다.
- [ ] 동시 miss·Redis 중단·API 지연·저장 실패에서 호출 상한과 대기 시간이 유지된다.
- [ ] 비교군의 실행 조건·결과·남은 한계를 정리한 뒤 구현 완료 여부를 판단한다.

## 확장 범위

L1 로컬 캐시는 기본형의 병목이 확인된 뒤 검토한다. L1을 추가하면 노드별 무효화·알림 유실·오래된 권한 관리가 늘어난다. 처음부터 Caffeine과 Redis를 묶어 복잡도를 높이기보다 Redis 하나로 정확한 흐름과 측정 기준을 만드는 것을 우선한다.
