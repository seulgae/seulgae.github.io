## 1. 학습 배경

NURI2 배치 경험을 UMS 연동 직무와 연결하려 한다. 직접 개발한 것은 대상 추출·관리·DATA 적재·조회 화면·재처리 경로다. 예약·실제 발송·채널 대체는 솔루션 제공 기능이었다. 이를 구분한 [기존 실무 복기](/blog/nuri2-message-batch-interview-review)를 경험 근거로 사용한다.

## 2. 핵심 개념

동기 호출에서는 호출자가 해당 작업의 응답·완료를 기다리는 흐름을 갖는다. 비동기 흐름은 요청 제출과 후속 완료 확인을 분리할 수 있다. 블로킹·논블로킹은 호출 동안 스레드가 대기하는가의 관점이어서 동기·비동기와 같은 구분은 아니다.

UMS는 여러 메시징 채널의 발송 요청과 결과 관리를 통합하는 시스템을 가리킨다. 제품마다 접수 API·DB 연동·채널·결과 형식은 다르며, NURI2 구조가 모든 제품의 내부 구조는 아니다.

## 3. 동작 원리

기존 기록의 흐름은 다음과 같다. 내부 솔루션의 polling·잠금 구현까지 확인한 것은 아니다.

```text
배치 대상 추출 → 자체 관리 테이블 → NURI2 DATA 적재
  → 솔루션의 예약·채널 발송 → LOG 기록
  → 메시지 ID로 조회·상태 대조
```

DATA 적재 성공은 DB 작업 완료를 뜻한다. 수신자에게 메시지가 전달됐다는 뜻은 아니다. 접수·발송 시도·채널 결과·업무 완료의 의미를 따로 정의해야 한다. HTTP 연동에서도 202 응답은 처리 완료를 보장하지 않는다. [HTTP 의미 명세](https://www.rfc-editor.org/rfc/rfc9110.html)의 비동기 접수 의미와 연결해 이해한다.

## 4. 실무 활용

요청 처리와 외부 전송의 속도를 분리하면 호출자가 긴 발송 작업을 모두 기다리지 않게 할 수 있다. 대신 대기량·지연·실패·결과 미확인 상태가 생기므로 상태 조회와 운영 추적이 필요하다. Kafka를 쓰지 않아도 DB 대기 테이블과 후속 실행으로 비동기 업무를 구성할 수 있다.

**학습용 확장:** 상태를 접수·처리 중·성공·실패·미확인으로 나누고 업무 키와 메시지 ID를 함께 추적한다. 이 상태 모델을 당시 실제 테이블에 모두 구현했다는 의미는 아니다.

## 5. 주의사항 및 오개념

비동기는 작업을 없애거나 무한 처리량을 만드는 기능이 아니다. 소비 속도가 느리면 큐가 쌓인다. 재처리 전에 기존 요청이 늦게 완료될 가능성을 확인한다. fallback은 같은 요청을 무조건 다시 실행하는 retry와 구분한다. 응답 시간 개선을 최종 전달 시간 개선으로 표현하지 않는다.

## 7. 핵심 요약

접수·처리·결과를 분리하고 책임 주체를 표시한다. 이어서 [배치 재처리와 대체 발송](/blog/batch-retry-fallback-reprocessing)을 연결한다.
