# 빌링 GW 연동 오류 개선 경험 복기

> **작성 목적:** 엠앤와이즈 TS 직무 면접에서 **문제 상황 → 본인 역할 → 협업 및 조치 → 검증 → 성과**를 설명하기 위한 학습 노트.
>
> **기록 기준:** 실제 수행한 업무, 다른 파트가 수행한 조치, 아직 기억나지 않거나 확인되지 않은 사항을 구분한다. 본 문서는 당시 실무 기억을 바탕으로 정리한 것이며 원본 운영 자료 대조 전 단계다.

## 1. 핵심 요약

- **문제:** 서로 다른 시기에 고도화된 원부·이력 시스템과 응용 시스템의 업무 키·컬럼 구조가 맞지 않아 연동 오류가 반복 발생. 모니터링 도구는 있었지만 정기적인 확인과 조치로 연결되는 관리 과정이 부족해 오류가 누적됨.
- **본인 역할:** 연동 실패 이력과 GW 모니터링 시스템으로 오류를 분석하고, 일일 단위로 엑셀에 취합해 유형별 원인·조치 가이드를 정리. 청구·과금 운영자 20명과 PL·PM에게 공유하고 조치를 요청. 조치 후 GW 재검증 결과를 확인해 다음 보고에 반영.
- **다른 파트 역할:** 청구·과금 등 해당 업무 운영자가 데이터를 확인·수정하고, 발행 데이터에 문제가 있는 경우 관련 발행 파트에서 데이터를 확인하거나 재발행함.
- **성과:** 당시 관찰한 **주간 연동 오류 수준이 약 70건에서 약 5건으로 감소**. 계산상 약 **92.86% ≈ 93%**. 주별 편차가 있는 대략적인 운영 성과이며 정확한 비교 기간과 집계 기준은 추가 확인이 필요함.
- **강점:** 개발·연동 문제를 **원인 분석 → 담당자 협업 → 재검증**으로 연결하여 운영 안정화에 기여한 경험.

## 2. 시스템 구조 및 문제 배경

### 업무 시스템 구성

```text
원부·이력 파트 (가입 · 상품 · 단말)
       │
       │ Kafka 토픽 발행
       ▼
   빌링 GW 연동 구간
       │
       │ 메시지 수신·데이터 연동
       ▼
응용 파트 (청구 · 과금 · 수미납 · 정산)
```

※ 실제 메시지 소비 순서, 연동 컴포넌트의 세부 배치 및 내부 아키텍처까지 확정한 그림은 아니다. 이해를 돕기 위한 논리적 흐름이다.

응용 시스템이 먼저 고도화되고 이후 원부·이력 시스템이 고도화되었다. 두 시스템은 업무 중심키와 데이터 구조가 서로 달랐고, 원부에서 발행된 데이터를 응용 시스템에서 처리하는 과정에서 호환성 문제가 생겼다.

당시 Kafka 연동 실패 이력과 **Python 기반 GW 모니터링 사이트**가 있었고, 사이트에서 원부 DB와 응용 DB를 조회해 불일치 항목을 확인할 수 있었다. 다만 해당 정보를 담당 파트의 정기적인 조치로 연결하는 체계가 충분하지 않아 오류가 쌓였고, 데이터 이상이 제기된 뒤에야 개별 건을 찾아 대응하는 일이 있었다.

### 주요 오류 유형

| 구분 | 당시 관찰한 오류 현상 | 확인·조치 방향 |
|---|---|---|
| 업무 중심키·컬럼 불일치 | 시스템별 식별키 구성이나 컬럼 형태가 맞지 않아 연동 실패 | 원부·응용 키 구성과 매핑, 컬럼 정의 비교 |
| PK 중복(DUP) | 이미 발행된 데이터가 수정·재발행되는 과정 등에서 기존 데이터와 키 충돌 | 대상 데이터와 처리 이력 확인, 필요 시 관련 파트 협업 |
| 문자열 길이 초과 | 문자 인코딩·길이 기준 차이가 있는 구간에서 컬럼 길이 초과 | 실제 데이터와 DB 컬럼의 길이·단위·인코딩 정의 확인 |

**기술적 주의:** Kafka 메시지 키와 DB 기본키(PK)는 동일 개념이 아니다. MS949, UTF-16, 컬럼 길이 초과 사이의 정확한 인과관계 역시 당시 DB 컬럼 정의와 변환 로직 확인 전에는 확정하지 않는다.

## 3. 실제 수행 업무 — 오류 관리 개선 흐름

1. **오류 발견:** Kafka 관련 연동 실패 이력과 GW 모니터링 사이트로 오류를 확인했다.
2. **원인 분석:** 사이트에서 원부·응용 DB의 데이터를 쿼리로 조회·비교하고, 오류 유형을 확인했다.
3. **일일 집계:** 오류 항목을 매일 엑셀에 취합하고, 업무 중심키 불일치·DUP·문자열 길이 초과 등으로 분류했다.
4. **파트별 공유:** 오류 현황과 원인, 조치 가이드를 메일 본문·표로 정리해 **청구 운영자 12명, 과금 운영자 8명**, 총 20명에게 공유했다. 관련 **PL·PM에게도 보고 또는 참조**했다.
5. **조치 협의:** PL·PM에게 협조를 요청해 주간 회의나 정규 운영 작업 전에 미조치 항목을 확인하도록 건의했다. 업무 데이터 수정은 담당 운영자가 수행했고, 발행 데이터 관련 오류는 발행 파트에 확인 및 재발행을 요청했다.
6. **재검증:** 담당 파트 조치 이후 **GW 사이트의 재검증 기능**으로 해당 데이터의 불일치 여부를 확인했다.
7. **완료 반영:** 재검증 결과 해당 항목의 **불일치가 0건**이면 조치 완료로 판단해 다음 날 미조치 오류 보고 대상에서 제외했다.

**면접에서 강조할 점:** 모니터링 사이트 자체를 개발했다고 주장하지 않는다. 본인이 개선한 것은 **일일 오류 분석·분류·보고 및 협업, 재검증으로 이어지는 관리 방식**이다.

## 4. 성과 수치와 설명 범위

| 항목 | 내용 |
|---|---|
| 개선 전 | 주간 오류 수준 약 70건 |
| 개선 후 | 주간 오류 수준 약 5건 |
| 감소 건수 | 약 65건 |
| 계산상 감소율 | `(70 - 5) / 70 × 100 = 약 92.86%` → 약 93% |
| 수치 성격 | 당시 운영 과정에서 관찰한 대략적인 평균 수준. 주별 변동 있음 |
| 아직 확인할 점 | 집계 기간, 신규 발생 오류와 미처리 오류 중 어떤 기준인지, 원본 집계 자료 |

> 일부 날에는 10건 이상, 긴급 장애 시에는 훨씬 많은 대량 오류가 발생한 사례도 있었다고 기억한다. 이 **예외적인 대량 오류 건수**와 위의 **평상시 주간 약 70→5건 성과**를 혼동하지 말 것. 면접에서는 질문받지 않으면 100만 건 사례를 굳이 덧붙이지 않는다.

## 5. 대표 면접 답변 (약 1분)

> 당시 빌링 GW 시스템은 원부와 응용 시스템이 서로 다른 시기에 고도화되면서 업무 중심키와 데이터 구조가 맞지 않아 연동 오류가 반복 발생했습니다.
>
> 오류를 확인할 수 있는 모니터링 시스템은 있었지만, 담당 파트의 정기적인 확인과 조치로 연결되지 않아 오류가 누적되는 상황이었습니다.
>
> 저는 매일 오류를 집계하고 원인별로 분류해 조치 가이드와 함께 각 파트 운영자에게 공유했습니다. 또한 PL·PM에게 협조를 요청해 주간 회의나 정규 작업 전에도 오류를 확인하도록 했습니다.
>
> 담당 파트가 조치한 후에는 GW 모니터링 사이트에서 데이터 정합성을 재검증하고, 완료 여부를 다음 날 보고에 반영했습니다.
>
> 이 과정을 지속하면서 주간 연동 오류 수준을 약 70건에서 5건으로 낮추는 데 기여했습니다.

### 20초 핵심 압축 답변

> 연동 오류를 확인할 수 있는 도구는 있었지만, 담당 파트의 조치로 이어지는 관리 체계가 부족했습니다. 그래서 매일 오류를 유형별로 정리해 담당자와 PL·PM에게 공유하고, 조치 후에는 GW 사이트에서 재검증했습니다. 그 결과 주간 오류 수준을 약 70건에서 5건으로 낮추는 데 기여했습니다.

## 6. 예상 꼬리 질문과 답변

### Q1. 연동 오류의 근본 원인은 무엇이었나요?

응용 시스템과 원부·이력 시스템의 고도화 시점이 달라 업무 중심키와 컬럼 구조가 맞지 않는 문제가 있었습니다. 그 과정에서 키 매핑 불일치, DB PK 중복, 문자열 길이 초과 등 여러 형태의 오류가 발생했습니다.

### Q2. 모니터링 시스템이 이미 있었는데 왜 별도 보고 체계가 필요했나요?

오류를 확인하는 도구는 있었지만, 발생 항목이 담당 파트의 정기적인 확인과 후속 조치까지 이어지는 관리가 충분하지 않았습니다. 그래서 매일 오류를 취합하고 원인·조치 방법을 함께 공유해 누락을 줄이려 했습니다.

### Q3. 메일 공유만으로 오류가 93%나 감소할 수 있었나요?

메일 자체보다 **정기적인 확인과 실제 조치, 조치 후 재검증을 연결한 것**이 중요했습니다. 일일 오류 현황을 공유하고 PL·PM의 협조를 받아 담당자들이 작업 전에 확인하도록 했습니다. 이후 데이터 수정이나 재발행 조치를 재검증하며 누적 오류를 점차 줄였습니다.

### Q4. 오류를 어떻게 분석했나요?

Kafka 관련 연동 실패 이력과 Python 기반 GW 모니터링 사이트를 활용했습니다. 사이트에서 원부 DB와 응용 DB를 조회해 데이터 차이를 확인하고, 업무 중심키 불일치·PK 중복·문자열 길이 초과 등으로 분류했습니다.

### Q5. 오류를 직접 수정한 건가요?

제가 주로 수행한 업무는 오류 분석과 분류, 조치 가이드 공유, 담당 파트 협업 및 재검증이었습니다. 실제 청구·과금 데이터 수정은 해당 업무 운영자가 수행했고, 발행 데이터에 문제가 있으면 발행 파트에 확인과 재발행을 요청했습니다.

### Q6. 조치 완료 여부는 어떻게 검증했나요?

담당 파트가 조치한 후 GW 사이트의 재검증 기능을 사용했습니다. 해당 항목에서 원부와 응용 데이터의 불일치가 0건으로 확인되면 완료로 판단하고 다음 날 미조치 보고 대상에서 제외했습니다.

### Q7. 93%는 어떻게 계산한 수치인가요?

당시 일일 집계와 운영 현황을 바탕으로 관찰한 대략적인 주간 오류 수준을 비교한 값입니다. 개선 전 약 70건, 개선 후 약 5건이어서 계산상 약 93%입니다. 주별 편차가 있었고, 정확한 비교 기간과 집계 기준은 원본 자료 확인이 필요합니다.

### Q8. 이 경험으로 무엇을 배웠나요?

기술적인 오류를 찾아내는 것뿐 아니라, 담당자들이 실제로 조치할 수 있도록 원인과 해결 방향을 전달하고 결과까지 검증하는 과정이 중요하다고 배웠습니다. 운영 안정화는 분석과 협업, 후속 확인이 함께 이루어져야 가능하다고 생각합니다.

## 7. 표현을 중립적으로 바꾸기

| 피할 표현 | 면접에서 사용할 표현 |
|---|---|

| "연동 파트에서 자기 일이 아니라고 미뤘습니다." | "파트별 업무 범위가 달라 조치가 원활하게 이어지지 않았습니다." |

**원칙:** 실제 문제를 숨기거나 책임을 다른 곳으로 돌리지 않는다. 개인이나 부서를 비난하는 대신 **프로세스의 한계와 개선 방식**을 설명한다.

## 8. 기술 면접 대비 — 확인할 항목

- [ ] 실제 사용한 **업무 중심키**의 구성과 분해·매핑 방식 (세 값을 조합한 키의 정확한 형식)
- [ ] Kafka 메시지 재발행과 **DB PK 중복(DUP)** 오류 사이의 관계
- [ ] **MS949 / UTF-16** 적용 구간, 컬럼 길이 초과의 실제 원인 및 DB 길이 단위(BYTE/CHAR 등)
- [ ] GW 모니터링 사이트의 재검증 범위와 결과 해석
- [ ] **주간 70건→5건**의 정확한 집계 기준(신규 발생 건수인지, 남아 있는 미처리 건수인지 등)

## 9. 면접 직전 암기 포인트

**문제:** 다른 시기에 고도화된 시스템 간 데이터 구조 차이 + 정기 조치 체계 부족  
**행동:** 오류 분석 → 일일 집계 → 유형별 가이드 → 운영자·PL·PM 공유 → 재검증  
**결과:** 주간 오류 수준 **약 70건 → 5건(약 93%)**  
**나의 기여:** 개발자가 모든 데이터를 직접 수정한 것이 아니라 **조치가 실제로 이루어지고 검증되도록 운영 협업 체계를 개선**한 것
