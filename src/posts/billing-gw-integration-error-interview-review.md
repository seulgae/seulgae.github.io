| --- | --- | --- |
| 시스템 | 통신사 빌링 시스템의 Kafka 기반 GW 연동 구간 | 기존 블로그 기록 |
| 문제 | 고도화 시점이 다른 원부·이력 시스템과 응용 시스템의 업무 키·컬럼 구조가 맞지 않아 연동 오류가 반복·누적됨 | 실제 경험(기억) |

| 본인 역할 | 오류 분석·분류 → 일일 엑셀 취합 → 조치 가이드와 함께 운영자 20명·PL·PM에 공유 → 조치 후 재검증 | 실제 경험(기억). 일일 보고 체계는 직접 수립 |

| 성과 | **주간 연동 오류 약 70건 → 약 5건 (약 93% 감소)에 기여** | 당시 관찰한 어림값. 집계 기간·기준은 미확인 |

### 확정해서 말할 수 있는 문장

- 모니터링 도구는 있었지만 **정기적인 확인과 조치로 이어지는 관리 체계가 부족**했다.
- 내가 만든 것은 **일일 오류 분석·분류·보고와 재검증으로 이어지는 관리 방식**이다.
- 업무 데이터 수정은 **해당 업무 운영자**가, 발행 데이터 수정은 **발행 파트**가 했다.
- 주간 오류 수준이 **약 70건에서 5건 수준**으로 줄었고, 나는 그 감소에 **기여**했다.

## 2. 시스템 구조와 문제 배경

```text
원부·이력 파트 (가입 · 상품 · 단말)
       │  Kafka 토픽 발행
       ▼
   빌링 GW 연동 구간
       │  메시지 수신 · 데이터 연동
       ▼
응용 파트 (청구 · 과금 · 수미납 · 정산)
```

※ 이해를 돕기 위한 논리적 흐름이다. 실제 메시지 소비 순서와 컴포넌트 배치까지 확정한 그림은 아니다.

**구조가 어긋난 이유:** 응용 시스템이 먼저 고도화되고, 이후 원부·이력 시스템이 고도화되었다. 두 시스템은 업무 중심키와 데이터 구조가 달랐고, 원부가 발행한 데이터를 응용 시스템이 처리하는 과정에서 호환성 문제가 생겼다.

**오류가 쌓인 이유:** GW 모니터링 사이트에서 원부 DB와 응용 DB를 조회해 불일치를 확인할 수는 있었다. 하지만 그 정보를 담당 파트의 정기적인 조치로 연결하는 체계가 충분하지 않았다. 그래서 데이터 이상이 제기된 뒤에야 개별 건을 찾아 대응하는 일이 있었다.

### 주요 오류 유형

이번 복기에서 떠올린 유형은 세 가지다.

| 구분 | 당시 관찰한 현상 | 확인·조치 방향 |
| --- | --- | --- |
| 업무 중심키·컬럼 불일치 | 시스템별 식별키 구성이나 컬럼 형태가 맞지 않아 연동 실패 | 원부·응용 키 구성과 매핑, 컬럼 정의 비교 |
| PK 중복(DUP) | 이미 발행된 데이터가 수정·재발행되는 과정 등에서 기존 데이터와 키 충돌 | 대상 데이터와 처리 이력 확인, 필요 시 관련 파트 협업 |
| 문자열 길이 초과 | 인코딩·길이 기준이 다른 구간에서 컬럼 길이 초과 | 실제 데이터와 DB 컬럼의 길이 단위·인코딩 확인 |

이전 회고 글에는 다음 유형도 기록되어 있다.

| 이전 글에 기록한 유형 | 확인할 내용 |
| --- | --- |
| 발행 누락·원천 데이터 불일치 | 필요한 데이터가 발행되었는지, 발행 값이 실제 업무 데이터와 맞는지 |
| 이벤트 처리 순서 역전 | 현재 이벤트에 필요한 선행 데이터가 준비되어 있는지 |
| 신규 컬럼·매핑 누락 | 발행 데이터와 대상 테이블을 잇는 규칙이 반영되어 있는지 |
| 잔여 오류: 특수기호·필수값 누락 | 모델명의 특수기호, `NOT NULL` 컬럼에 대응하는 값이 `null`로 발행된 경우 → 발행 파트에 수정·재발행 요청 |

두 목록의 분류 기준은 완전히 같지 않다. 중심키·컬럼 불일치는 '신규 컬럼·매핑 누락'과 겹칠 수 있고, DUP는 이전 글에 따로 적지 않았다. 원본 보고 엑셀을 확인하기 전까지는 **"대표적으로 이런 유형이 있었다"** 정도로 말하고, 유형별 건수나 비율은 말하지 않는다.

## 3. 실제 수행한 일 — 오류 관리 흐름

```text
연동 실패 이력 · GW 사이트로 오류 확인
  → 원부·응용 DB 조회로 원인 분류
  → 일일 엑셀 취합 (유형 · 원인 · 조치 가이드)
  → 청구·과금 운영자 20명에게 메일 공유, PL·PM 보고·참조
  → 담당 운영자 수정 / 발행 파트 수정·재발행
  → GW 재검증 (불일치 0건이면 완료)
  → 다음 날 보고에서 완료 건 제외, 남은 건은 사유와 함께 유지
```

| 단계 | 한 일 |
| --- | --- |
| 1. 발견 | Kafka 연동 실패 이력과 GW 모니터링 사이트로 오류를 확인 |
| 2. 분석 | 사이트에서 원부·응용 DB를 쿼리로 조회·비교하고 오류 유형을 확인 |
| 3. 집계 | 오류 항목을 매일 엑셀에 취합하고 중심키 불일치·DUP·길이 초과 등으로 분류 |
| 4. 공유 | 현황·원인·조치 가이드를 메일 본문과 표로 정리해 **청구 운영자 12명, 과금 운영자 8명**(총 20명)에게 공유. PL·PM에게도 보고 또는 참조 |
| 5. 협의 | PL·PM에게 주간 회의나 정규 운영 작업 전에 미조치 항목을 확인하도록 건의. 담당 운영자 배분은 청구·과금 PM이 관리 |
| 6. 요청 | 발행 데이터 자체를 고쳐야 하는 건(특수기호, 필수값 `null` 등)은 발행 파트에 직접 메일로 수정·재발행 요청 |
| 7. 재검증 | 조치 후 **GW 사이트의 재검증 기능**으로 불일치 여부 확인 |
| 8. 완료 반영 | 불일치가 **0건**이면 완료로 판단하고 다음 날 미조치 보고에서 제외 |

### 왜 데이터를 직접 고치지 않았나

기술적으로 넣을 수 있는 값과 **업무상 올바른 값은 다르다.** 청구·과금 데이터는 운영자가 실제 업무에 쓰는 데이터라서, 값의 의미와 수정 영향은 담당자가 판단해야 한다고 봤다. 연동 파트에서 임의로 값을 채우면 연동은 성공해도 업무 데이터가 틀릴 수 있다.

### 직접 기술적으로 개선한 부분과 구분하기

이 문서의 성과는 **관리 방식 개선**이다. 별도로 문자열 바이트 길이 초과에 대해 Java 바이트 길이 보정과 GW 메타데이터 변환 규칙을 적용한 경험이 있다([바이트 길이 보정 글](/blog/gw-encoding-byte-length-validation)). 그 글의 인코딩 오류 감소 수치는 주간 70→5건과 **다른 지표**이므로 섞지 않는다.

## 4. 성과 수치와 설명 범위

| 항목 | 내용 |
| --- | --- |
| 개선 전 → 후 | 주간 오류 수준 약 70건 → 약 5건 |
| 계산 | `(70 - 5) / 70 × 100 ≈ 92.86%` → 약 93% |
| 수치 성격 | 당시 운영 중 관찰한 대략적인 평균 수준. 주별 변동 있음 |
| 아직 확인할 점 | 집계 기간, 신규 발생 기준인지 미처리 잔량 기준인지, 원본 집계 자료 |

> 일부 날에는 10건 이상, 긴급 장애 때는 기억상 100만 건 규모의 대량 오류가 발생한 사례도 있었다. 이 **예외적인 대량 오류**와 **평상시 주간 약 70→5건**을 섞지 않는다. 질문받지 않으면 100만 건 사례는 덧붙이지 않는다.

**말하는 기준:** "제가 93%를 줄였습니다"가 아니라 "일일 보고 체계를 만들고 담당 파트의 조치·재검증을 연결해 **약 93% 감소에 기여**했습니다"라고 말한다. 메일 보고만의 효과를 따로 측정한 수치가 아니다.

## 5. 면접 답변

### 약 1분 답변

> 당시 빌링 GW 시스템은 원부와 응용 시스템이 서로 다른 시기에 고도화되면서 업무 중심키와 데이터 구조가 맞지 않아 연동 오류가 반복 발생했습니다.
>
> 모니터링 시스템은 있었지만, 담당 파트의 정기적인 확인과 조치로 이어지지 않아 오류가 누적되는 상황이었습니다.
>
> 저는 매일 오류를 집계하고 원인별로 분류해 조치 가이드와 함께 각 파트 운영자에게 공유했습니다. PL·PM에게도 협조를 요청해 주간 회의나 정규 작업 전에 오류를 확인하도록 했습니다.
>
> 담당 파트가 조치한 뒤에는 GW 모니터링 사이트에서 정합성을 재검증하고, 완료 여부를 다음 날 보고에 반영했습니다.
>
> 이 과정을 이어 가면서 주간 연동 오류 수준을 약 70건에서 5건으로 낮추는 데 기여했습니다.

### 20초 압축 답변

> 연동 오류를 확인할 도구는 있었지만, 조치로 이어지는 관리 체계가 부족했습니다. 그래서 매일 오류를 유형별로 정리해 담당자와 PL·PM에게 공유하고, 조치 후에는 GW 사이트에서 재검증했습니다. 그 결과 주간 오류 수준을 약 70건에서 5건으로 낮추는 데 기여했습니다.

## 6. 예상 꼬리 질문

### 원인과 분석

**Q1. 연동 오류의 근본 원인은 무엇이었나요?**
응용 시스템과 원부·이력 시스템의 고도화 시점이 달라 업무 중심키와 컬럼 구조가 맞지 않았습니다. 그 결과 키 매핑 불일치, DB PK 중복, 문자열 길이 초과 같은 오류가 생겼습니다.

**Q2. 오류를 어떻게 분석했나요?**
Kafka 연동 실패 이력과 Python 기반 GW 모니터링 사이트를 썼습니다. 사이트에서 원부 DB와 응용 DB를 조회해 차이를 확인하고, 중심키 불일치·PK 중복·길이 초과 등으로 분류했습니다.

**Q3. 모니터링 시스템이 있었는데 왜 별도 보고 체계가 필요했나요?**
확인 도구는 있었지만 발생 항목이 담당 파트의 정기적인 확인과 후속 조치까지 이어지지 않았습니다. 매일 오류를 취합하고 원인·조치 방법을 함께 공유해 누락을 줄이려 했습니다.

### 역할과 협업

**Q4. 오류를 직접 수정한 건가요?**
제가 주로 한 일은 분석·분류, 조치 가이드 공유, 담당 파트 협업, 재검증이었습니다. 청구·과금 데이터 수정은 담당 운영자가 했고, 발행 데이터 문제는 발행 파트에 확인과 재발행을 요청했습니다.

**Q5. 왜 데이터를 직접 수정하지 않고 담당자에게 요청했나요?**
값을 넣는 것은 기술적으로 가능했지만, 그 값이 업무상 올바른지는 데이터를 쓰는 운영자가 판단해야 한다고 생각했습니다. 제가 확인할 수 있는 원인과 데이터를 정리해 드리고, 수정 판단은 담당 파트가 하도록 연결했습니다.

**Q6. 바로 해결하기 어려운 오류는 어떻게 관리했나요?**
이상하거나 특이한 데이터처럼 바로 처리하기 어려운 건도 있었습니다. 이런 건은 남은 이유와 확인할 내용을 함께 적어 다음 날 보고에도 유지했습니다. 미처리 목록에서 사라지지 않게 하려는 것이었습니다.

**Q7. 오류를 빨리 처리해야 했던 이유가 있었나요?**
연동 데이터는 청구 파트의 요금 생성과 과금 작업으로 이어졌습니다. 오류가 쌓이면 뒤 작업에 영향을 줄 수 있어서 월초·월중·월말 운영 작업 전에 미처리 건을 줄이려 했습니다.

### 검증과 성과

**Q8. 조치 완료 여부는 어떻게 검증했나요?**
담당 파트가 조치한 뒤 GW 사이트의 재검증 기능을 썼습니다. 원부와 응용 데이터의 불일치가 0건이면 완료로 판단하고 다음 날 미조치 보고에서 제외했습니다.

**Q9. 메일 공유만으로 오류가 93%나 줄 수 있나요?**
메일 자체보다 **정기 확인, 실제 조치, 조치 후 재검증을 연결한 것**이 중요했습니다. PL·PM의 협조로 담당자들이 작업 전에 확인하게 됐고, 수정·재발행을 재검증하면서 누적 오류가 줄었습니다.

**Q10. 93%는 어떻게 계산한 수치인가요?**
당시 일일 집계와 운영 현황으로 관찰한 주간 오류 수준을 비교했습니다. 약 70건에서 약 5건이라 계산상 약 93%입니다. 주별 편차가 있었고, 정확한 비교 기간과 집계 기준은 원본 확인이 필요합니다.

### 기술과 회고

**Q11. 직접 기술적으로 개선한 것도 있나요?**
문자열 바이트 길이 초과 오류에는 대상 컬럼 기준으로 Java에서 바이트 길이를 보정하고, GW 메타데이터 변환 규칙에 연결해 같은 유형에 적용되게 했습니다. 다만 70건→5건은 관리 체계와 협업의 결과이고, 인코딩 보정은 별도 개선으로 구분합니다.

**Q12. 지금 다시 한다면 무엇을 보완하겠습니까?**
엑셀·메일 중심의 공유에 미처리 사유와 마지막 확인 내역을 함께 남기겠습니다. 업무 판단 대기·원천 수정 대기·재발행 대기처럼 상태를 나누면 같은 내용을 매일 다시 확인하는 부담이 줄어듭니다. 오류 건수뿐 아니라 미처리 기간과 재발 건도 지표로 남기겠습니다.

**Q13. 이 경험이 지원 직무와 어떻게 연결되나요?**
문제를 분석하는 데서 끝내지 않고, 누가 무엇을 해야 하는지 정리해 전달하고 조치 결과까지 재검증한 경험입니다. 여러 담당자가 얽힌 운영 문제를 해결 가능한 단위로 나누는 방식은 운영·유지보수·기술 지원 업무 어디에나 적용할 수 있다고 생각합니다.
*(지원 회사에 맞춘 답은 해당 회사 준비 글에 따로 둔다. 예: [엠앤와이즈 TS팀 면접 준비](/blog/interview-mnwise-ts-prep))*

**Q14. 이 경험으로 무엇을 배웠나요?**
오류를 찾는 것만큼, 담당자가 실제로 조치할 수 있게 원인과 방향을 전달하고 결과까지 확인하는 과정이 중요하다고 배웠습니다. 운영 안정화는 분석과 협업, 후속 확인이 함께 있어야 가능했습니다.

## 8. 이론 보충 — 기술 질문 대비

> 아래는 면접 준비 중 공부한 일반 원리와 학습용 예시다. 당시 GW의 실제 설정·코드가 아니다.

### 8-1. Kafka 기본 용어

| 용어 | 한 줄 설명 |
| --- | --- |
| 토픽(Topic) | 메시지를 주제별로 모아 두는 이름 붙은 통로 |
| 파티션(Partition) | 토픽을 나눈 단위. **같은 파티션 안에서만 순서가 보장**된다 |
| 메시지 키(Key) | 어느 파티션으로 갈지 정하는 값. 같은 키는 보통 같은 파티션으로 간다 |
| 오프셋(Offset) | 파티션 안에서 메시지의 위치 번호. 컨슈머는 어디까지 읽었는지 오프셋으로 기록한다 |
| 컨슈머 그룹 | 같은 그룹의 컨슈머들이 파티션을 나눠 읽는다 |

**면접 포인트:** "이벤트 처리 순서 역전"은 관련 메시지가 다른 키·파티션으로 나뉘면 생길 수 있다. 같은 고객의 이벤트 순서가 중요하다면 같은 키를 쓰는 것이 일반적인 방법이다. 당시 실제 키 설계는 **미확인**이다.

### 8-2. 전달 보장과 중복(DUP)

| 보장 수준 | 의미 | 생길 수 있는 문제 |
| --- | --- | --- |
| At most once | 최대 한 번. 처리 전에 오프셋을 커밋 | 실패하면 메시지 유실 |
| At least once | 최소 한 번. 처리 후 오프셋을 커밋 | 커밋 전에 죽으면 **같은 메시지를 다시 받음 → 중복** |
| Exactly once | 정확히 한 번 | 트랜잭션 설정 등 조건이 필요하고, 외부 DB까지 자동 보장되지는 않음 |

일반적인 운영에서는 at least once를 택하고, **받는 쪽이 같은 메시지를 두 번 받아도 결과가 같게(멱등하게)** 만든다. 당시 GW의 오프셋 커밋 방식은 **미확인**이므로, 질문을 받으면 일반 원리로만 답한다.

```sql
-- 학습용 예시: 같은 키가 이미 있으면 갱신, 없으면 삽입 (Oracle MERGE)
MERGE INTO billing_target t
USING (SELECT :svc_no AS svc_no, :prod_cd AS prod_cd, :chg_dt AS chg_dt FROM dual) s
   ON (t.svc_no = s.svc_no AND t.chg_dt = s.chg_dt)
 WHEN MATCHED THEN
      UPDATE SET t.prod_cd = s.prod_cd
 WHEN NOT MATCHED THEN
      INSERT (svc_no, prod_cd, chg_dt) VALUES (s.svc_no, s.prod_cd, s.chg_dt);
```

단순 `INSERT`는 재수신 시 PK 중복 오류가 난다. 반면 위처럼 키 기준으로 합치면 다시 받아도 결과가 같다. 다만 **"덮어써도 업무상 맞는가"** 는 업무 규칙으로 따로 판단해야 한다. 그래서 당시에도 데이터 수정은 담당 운영자가 판단했다.

### 8-3. 문자열 길이 초과 — 글자 수와 바이트 수

```java
// 학습용 예시: 같은 문자열도 인코딩에 따라 바이트 수가 다르다
String name = "갤럭시";
name.length();                                       // 3 (글자 수)
name.getBytes(Charset.forName("MS949")).length;      // 6 (한글 1자 = 2바이트)
name.getBytes(StandardCharsets.UTF_8).length;        // 9 (한글 1자 = 3바이트)
```

DB 컬럼이 **바이트 단위**(예: Oracle `VARCHAR2(10 BYTE)`)라면, 원천에서 글자 수로 검증한 값도 대상 DB에서는 길이 초과가 될 수 있다. 실제 GW의 인코딩 구간과 컬럼 단위는 **미확인**이다.

```java
// 학습용 예시: 바이트 기준으로 자르되 한글이 반으로 잘리지 않게 한다
static String cutByBytes(String s, int maxBytes, Charset cs) {
    StringBuilder sb = new StringBuilder();
    int used = 0;
    for (int i = 0; i < s.length(); ) {
        int cp = s.codePointAt(i);
        String ch = new String(Character.toChars(cp));
        int len = ch.getBytes(cs).length;
        if (used + len > maxBytes) break;
        sb.append(ch);
        used += len;
        i += Character.charCount(cp);
    }
    return sb.toString();
}
```

자르는 것이 업무상 허용되는지는 별개 문제다. 실제 보정 규칙은 [바이트 길이 보정 글](/blog/gw-encoding-byte-length-validation)을 기준으로 말한다.

### 8-4. 대사(Reconciliation) 쿼리의 기본 모양

GW 사이트의 재검증은 결국 **원천과 대상을 키로 비교해 차이를 찾는 일**이다.

```sql
-- 학습용 예시: 원천에는 있는데 대상에는 없는 키
SELECT svc_no, chg_dt FROM source_table
MINUS
SELECT svc_no, chg_dt FROM target_table;
```

반대 방향도 확인하고, 키가 같아도 값이 다른 건은 `JOIN` 후 컬럼을 비교한다. 양방향 0건이 "불일치 0건"의 일반적인 의미다.
