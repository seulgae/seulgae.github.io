> **이 글의 범위:** (주)애버커스 빌링시스템팀에서 LG U+ 빌링·GW 연계를 유지보수하며 연동 오류를 관리한 경험을 정리했다. **내가 한 일**, **구조상 원인**, **기술 원리**를 나눠 적고, 당시 자료로 확인하지 못한 내용은 **확인 필요**로 남겼다.

## 1. 한눈에 보기

| 구분 | 내용 |
| --- | --- |
| 구조 | 원천(이력) 파트가 Kafka 토픽을 발행하고 응용 파트가 구독한다. GW는 그 사이에서 도메인 데이터를 변환해 반영하는 계층이다 |
| 출발점 | 인계 시점에 연동 오류 테이블에 **1,000건 이상**이 쌓여 있었다 |
| 문제 정의 | 오류는 화면에 있었지만, **누가 무엇을 확인해야 하는지 보이지 않았다** |
| 한 일 | 누적 오류 정리, 실패 유형·키워드·해결 가이드를 담은 메일 보고 체계 구축, 대량 오류 시 원인 확인 후 분할 처리 |
| 결과 | 대규모 이관이 없는 **평소 주간 기준**, 오류가 약 70건 안팎(어림값)에서 5건 수준으로 감소 (약 93%) |
| 하지 않은 일 | 운영 데이터 직접 수정, Kafka 전체 구조 설계, exactly-once 구현 |

## 2. 연동 구조와 GW가 생긴 이유

고객 데이터를 관리하는 **원천(이력) 파트**가 있고, 그 데이터로 요금 등을 처리하는 **응용 파트**가 있었다. 응용 파트의 고도화가 먼저 진행되고 원천 파트의 고도화가 뒤따르면서, 두 파트의 데이터를 맞추기 위해 **연동(GW) 파트**가 생겼다.

```text
원천(이력) 파트 ── Kafka 토픽 발행 ──▶ GW (도메인 데이터 변환·반영) ──▶ 응용 파트
                                          │
                                          └─ 실패 이벤트 → 연동 오류 테이블 → GW 모니터링 화면
```

여기서 GW는 요청을 라우팅하는 API Gateway가 아니다. **두 시스템의 데이터 구조 차이를 메우는 변환 계층**이다.

### 오류가 나는 이유

두 파트는 따로 고도화되었기 때문에 데이터 구조가 서로 달랐다. 확정해서 말할 수 있는 오류 유형은 두 가지다.

| 유형 | 원인 |
| --- | --- |
| 컬럼 사이즈 불일치 | 원천과 응용의 DB 인코딩이 달라, 같은 문자열도 차지하는 크기가 달랐다 |
| PK 중복 | 업무 중심 키가 달라, 다른 컬럼 값을 조합해 키로 쓰다가 중복이 났다 |

포트폴리오 기록에는 발행 누락, 이벤트 순서 역전, 신규 컬럼 매핑 누락도 원인 후보로 남아 있다. 다만 이 다섯 가지로 오류를 확정 분류했다고 말하지는 않는다.

## 3. 문제 정의 — 오류가 아니라 가시성의 문제

운영자가 GW 모니터링 화면에서 버튼으로 데이터를 맞춘 뒤, 같은 화면에서 해당 이벤트를 **조치 완료 처리**해야 오류 테이블이 정리되는 구조였다.

이 구조에는 두 가지 빈틈이 있었다.

1. **알려 주는 장치가 없었다.** 오류는 화면에 쌓이지만 화면에 들어가 봐야만 알 수 있었다.
2. **원인이 구분되지 않았다.** 시스템 문제인지 원천 데이터 문제인지 나눠 보이지 않아, 재검증 버튼을 누르는 방식에 머물렀다.

그 결과 오류 테이블에는 **데이터는 맞췄지만 완료 처리가 안 된 건**과 **아직 조치가 필요한 건**이 섞여 있었다. 그래서 문제를 "오류가 많다"가 아니라 **"누가 무엇을 확인해야 하는지 보이지 않는다"** 로 정의했다.

## 4. 한 일

### 4-1. 누적 오류 정리

- 메일 이력을 확인해 **이미 조치된 건은 이벤트 단위로 완료 처리**했다.
- 조치가 필요한 건은 운영자와 메일·연락으로 확인했다.
- 이 정리는 이전 담당자와 함께 진행했다.

### 4-2. 일일 보고 체계

건별로 찾아가 묻는 방식은 오래 이어가기 어려웠다. 반면 연락을 주고받으면 처리가 연결된다는 점은 확인할 수 있었다. 그래서 그 연결을 **정해진 형식과 주기**로 바꿨다.

| 항목 | 내용 |
| --- | --- |
| 담는 내용 | 실패 유형, 키워드, 해결 방법(가이드)을 엑셀로 정리 |
| 받는 사람 | 데이터를 담당하는 파트. PL·PM은 참조로 넣어 처리 상황을 함께 볼 수 있게 했다 |
| 회수 | 파트별 답변을 받아 종합했다 |
| 주기 | 오류 잔량이 하루 10건 안팎으로 줄어 **하루 안에 처리할 수 있게 된 뒤부터 매일** |

### 4-3. 데이터는 직접 고치지 않았다

운영 데이터는 내가 고치지 않고, **데이터를 가장 잘 아는 담당 파트가 고치도록** 알림과 가이드를 제공했다. 나는 그 데이터의 업무 맥락을 모르기 때문이다. 내 역할은 **원인을 분류하고, 담당자에게 연결하고, 처리 결과를 종합하는 것**이었다.

## 5. 대량 오류 사례 — 이관 때 10만 건

평소 주간 오류와 별개로, 원천 파트가 새 서비스 테이블로 데이터를 이관하면서 **한 번에 10만 건까지** 오류가 난 적이 있다.

```text
원천 파트 이관 → 변경 데이터가 한꺼번에, 평소와 다른 형식으로 유입 → 대량 오류
  → 정기 운영 작업 전에 원천 파트에 연락: 원인 확인, 이벤트 형식 특이사항 확인, 재발행 요청
  → 2만 건씩 나눠 재발행 받기
  → 나눠 받을 때마다 모니터링 화면의 일괄 조치 → 재검증으로 오류 감소 확인
```

**왜 나눴나:** 10만 건을 한 번에 처리하면 트랜잭션이 길어지고, 그만큼 락이 오래 잡혀 다른 작업이 대기하거나 타임아웃이 날 수 있다. 이를 **예방하려고** 나눴다. 실제로 락 대기를 겪었는지, 어떤 종류의 락이었는지는 확인하지 못했다.

**판단 기준:** 소량은 버튼 일괄 조치로 처리하고, 대량은 **원인을 먼저 확인한 뒤** 나눠서 처리했다.

## 6. 결과와 수치를 말할 때의 단서

| 수치 | 기준과 단서 |
| --- | --- |
| 약 70건 → 5건 수준 | 대규모 이관이 없는 **평소 주간** 기준. 70건은 정확한 평균이 아닌 **어림값**이다 |
| 약 93% | 70 → 5로 계산한 값: `(70 - 5) / 70 ≈ 93%` |
| 남은 5건 수준 | GW 쪽에서 고칠 수 없어 원천 파트에 메일로 **재발행을 요청해야 하는 건** |
| 10만 건 | 이관 시기의 **별도 사례**. 평소 주간 수치와 섞지 않는다 |
| 1,000건 이상 | 인계 시점에 오류 테이블에 쌓여 있던 건수 |

성과는 **"감소에 기여했다"** 로 말한다. 오류를 실제로 고친 것은 각 담당 파트이고, 나는 그 처리가 이어지는 체계를 만들었다.

## 7. 기술 원리 정리

아래는 경험을 설명할 때 필요한 **일반 원리**다. 당시 내가 구현한 내용과는 구분한다.

### 인코딩과 컬럼 사이즈

DB 컬럼 길이가 바이트 기준이면, 같은 한글도 인코딩에 따라 크기가 다르다. 일반적으로 EUC-KR·MS949 계열은 한글 한 글자에 2바이트, UTF-8은 3바이트를 쓴다. 그래서 한쪽에서는 들어가던 값이 다른 쪽에서는 컬럼 크기를 넘을 수 있다. 원천과 응용 시스템의 실제 인코딩과 컬럼 정의는 **확인 필요**다.

### 락과 트랜잭션 분할

- 락은 과부하를 막는 장치가 아니다. **동시에 같은 데이터를 바꿀 때 데이터가 꼬이지 않게 하는 장치**다.
- 트랜잭션이 길면 락이 오래 잡혀 다른 작업이 기다리거나 타임아웃이 날 수 있다. 그래서 대량 작업은 나눠서 커밋한다.
- 병렬 처리는 락 문제를 없애지 않는다. 병렬로 돌린다면 **서로 겹치지 않는 범위를 세션마다 맡겨야** 한다.

### Kafka 연동에서 알아 둘 것

- 발행 쪽(Producer)과 구독 쪽(Consumer)이 분리되어 있어, 구독 쪽이 실패해도 발행 쪽은 모른다. 그래서 실패를 따로 모아 보는 오류 테이블과 모니터링 화면이 필요했다.
- 재발행을 받으면 같은 데이터가 다시 들어올 수 있다. 구독 쪽 반영이 같은 데이터를 두 번 받아도 결과가 같게(멱등하게) 처리되는지가 중요하다. 당시 GW의 멱등 처리 방식은 **확인 필요**다.

## 8. 이어지는 질문 대비

답변은 외우는 문장이 아니라 **확인된 것 / 모르는 것 / 보완할 것**을 나눠 말하는 틀로 준비한다.

| 질문 | 확인된 것 | 모르는 것 | 보완할 것 |
| --- | --- | --- | --- |
| GW는 무엇인가요? | 원천·응용 사이에서 도메인 데이터를 변환해 반영하는 계층. API Gateway가 아님 | — | 데이터 흐름을 그림으로 설명할 수 있게 정리 |
| 93%의 근거는? | 평소 주간 약 70건 안팎(어림값) → 5건 수준 | 정확한 집계 기준과 기간 | 수치를 말할 때 기준을 먼저 붙이기 |
| 직접 데이터를 고쳤나요? | 고치지 않았다. 담당 파트가 고치도록 알림·가이드 제공 | — | 역할 경계를 짧게 말하기 |
| 남은 5건은 왜 남았나요? | GW에서 고칠 수 없어 원천 파트에 재발행을 요청해야 하는 건 | — | — |
| 10만 건은 어떻게 처리했나요? | 원인 확인, 재발행 요청, 2만 건씩 분할, 일괄 조치 후 재검증 | 2만 건 단위를 누가 정했는지, 순차·병렬 여부, 실제 락 종류 | 예방 목적으로 나눴다고 정확히 말하기 |
| 왜 매일 보고했나요? | 잔량이 하루 10건 안팎이 되어 하루 안에 처리할 수 있게 된 뒤부터 매일 | — | — |
| 다시 한다면? | — | — | 알림 자동화, 원인 유형별 자동 분류 (지금의 제안이며 당시 구현 아님) |

## 9. 지원 직무와 연결 — 엠앤와이즈 TS팀

TS팀 공고의 주요 업무는 자사 솔루션의 고객사 대응 개발과 고객사 문제 해결이다. 이 경험은 **두 시스템 사이에서 생긴 문제를 확인하고, 담당자에게 연결하고, 처리 결과를 재검증한 일**이라 그 지점과 맞닿는다.

> TS 업무도 고객사 시스템과 솔루션 사이에서 생긴 문제를 확인하고, 원인을 설명하고, 담당자가 조치할 수 있게 연결하는 일이 많다고 생각합니다. 저는 오류를 분석하는 데서 끝내지 않고 누가 무엇을 해야 하는지 정리해 전달하고, 처리 후 결과까지 재검증했습니다. 이 방식을 고객사 기술 지원에도 적용할 수 있다고 생각합니다.

**말할 때 주의할 점:** Kafka 전체 구조를 단독 설계하거나 exactly-once를 구현한 경험이 아니다. 엠앤와이즈 솔루션의 내부 구조는 확인되지 않았으므로, 솔루션 구조를 안다고 말하지 않는다.

## 10. 확인 필요 항목

- [ ] 주간 약 70건의 정확한 집계 기준과 기간
- [ ] 이관 사례에서 2만 건 단위를 누가 정했는지, 순차 처리였는지 병렬 처리였는지
- [ ] 실제로 걸린 락의 종류(테이블·행)와 락 대기를 겪었는지
- [ ] 원천·응용 DB의 실제 인코딩과 컬럼 정의
- [ ] GW 반영 로직의 중복 데이터 처리 방식

> 그래서 저는 연동 오류를 일 단위로 집계하고, 원인과 담당 파트별로 분류하여 공유하는 체계를 마련했습니다.
>
> 이후 담당 파트와 협업하여 반복적으로 발생하는 오류를 우선적으로 개선하고, 조치가 완료된 건은 GW 모니터링 시스템을 통해 데이터 정합성을 다시 확인했습니다.
>
> 그 결과 주간 약 70건 수준이었던 연동 오류를 5건 수준으로 줄여 약 93% 개선할 수 있었습니다.

#### 답변 검증과 보완 근거

| 구분 | 판단 |
| --- | --- |
| [실무 경험] | 누적 오류 정리, 담당 파트별 일일 집계·가이드·메일 보고, 답변 종합과 모니터링 재검증 |
| [실무 경험] | 약 70건 → 5건은 평소 주간 오류 수준의 어림값. 대규모 이관 10만 건·인수 시 누적 1,000건과 다른 기준 |
| [검증 완료] | `(70 - 5) / 70 × 100 ≈ 92.86%`이므로 준비 답변의 약 93%는 반올림 표현으로 유지 |
| [확인 필요] | 비교 기간, 신규 발생 건수인지 미해결 잔량인지에 대한 원본 집계 정의, 중복 이벤트 집계 방식 |
| 역할 보완 | 조치는 담당 파트와 함께 진행했다. 운영 데이터를 모두 직접 수정하거나 오류 감소를 혼자 달성했다고 확대하지 않음 |

집계 단위는 이벤트·대상 행·실패 시도에 따라 달라진다. 다시 자료를 모은다면 기간·대상 시스템·이벤트 식별자·재시도 포함 여부와 완료 판정 기준을 함께 기록한다. **이 기준을 당시 모두 구현했다는 뜻은 아니다.** 보고가 개선됐다는 사실과 순수 신규 장애 발생률이 같은 비율로 줄었다는 주장은 분리한다.

#### 오류 분류를 이해하는 SQL — 학습용, 미실행

다음 이름과 컬럼은 가상 예제다. 당시 사용한 집계 SQL이나 실제 내부 테이블을 재현한 것이 아니다. `open_flag`는 이 예제에서만 미해결 표시를 가정한다.

```sql
SELECT owner_part, error_type, COUNT(*) AS open_events
FROM example_gw_error
WHERE open_flag = 'Y'
GROUP BY owner_part, error_type;
```

이 결과는 미해결 잔량 분류이지 주간 신규 발생 건수가 아니다. 주간 추이를 계산하려면 실제 발생 시각·기간 조건과 이벤트 중복 기준을 별도로 정해야 한다. 생성하지 않은 집계 결과를 성과 증거로 제시하지 않는다.

#### 최종 면접 답변

> 당시 평소 주간 연동 오류가 약 70건에서 5건 수준으로 줄어드는 데 기여했습니다. 저는 누적 오류를 정리하고, 실패 유형과 담당 파트·조치 가이드를 일일 메일로 공유하는 체계를 만들었습니다. 데이터 수정은 담당 파트가 했고, 저는 답변을 종합하고 GW 모니터링에서 처리 결과를 다시 확인했습니다. 약 93%는 이 전후 수치로 계산한 값이고, 대규모 이관 때의 오류와는 구분합니다. 정확한 집계 기간은 추가 확인이 필요합니다.

#### 예상 꼬리 질문과 답변

- **직접 DB 데이터를 고쳤나요?** “데이터 조치는 담당 파트가 했고, 저는 오류 유형과 가이드를 전달하고 결과를 종합·재검증했습니다.”
- **93%는 어떤 기준인가요?** “평소 주간 약 70건과 5건을 비교한 어림값입니다. 정확한 기간·집계 정의는 추가 확인이 필요합니다.”
- **보고만으로 오류가 줄었나요?** “보고가 담당자의 조치로 연결되도록 한 것이 제 기여입니다. 실제 조치는 협업 결과이고 원인별 기여도를 따로 측정한 것은 아닙니다.”
- **데이터 정합성은 어떻게 확인했나요?** “담당 파트의 조치 결과를 받아 GW 모니터링에서 재검증했습니다. 사용한 화면의 상세 판정 SQL과 전체 검증 범위는 원본 자료가 필요합니다.”

### Q2. 데이터 연동이 실패하는 원인은 무엇이었나요?

#### 현재 준비한 답변 — 원문 보존

> 네, 당시 발생했던 문제는 데이터 유출이 아니라 시스템 간 데이터 불일치로 인한 연동 오류였습니다.
>
> 원천 시스템에서 Kafka 토픽으로 데이터를 발행하면 응용 시스템에서 해당 데이터를 구독하는 구조였습니다.
>
> 그런데 각 시스템이 서로 다른 시기에 고도화되면서 업무 식별키인 PK가 일치하지 않거나 컬럼 길이와 데이터 규격이 달라 정상적으로 반영되지 않는 문제가 있었습니다.
>
> 또한 오류가 발생했을 때 담당 파트에서 정기적으로 확인하고 조치하는 체계가 부족해 미처리 오류가 누적되는 상황이었습니다.
>
> 그래서 오류를 일 단위로 집계하고 원인별로 분류한 뒤 담당 파트에 조치 가이드를 공유했습니다.
>
> 조치가 완료되면 GW 모니터링 시스템을 통해 데이터 정합성을 다시 확인했습니다.

#### 답변 검증과 용어 정리

**[실무 경험]** 기존 복기에서 구체적으로 남은 원인은 PK 중복과 컬럼 사이즈·인코딩 불일치다. 발행 누락·순서 역전·신규 매핑 누락은 다른 글에 기록돼 있지만, 당시 로그가 없어 이번 두 사례와 같은 수준으로 확정하지 않는다. 위 원문의 “PK가 일치하지 않는다”는 표현은 서로 다른 키 체계를 대응시키는 문제와 실제 PK 제약 위반을 분리해 다듬었다.

**[검증 완료: 일반 원리]** PK는 한 테이블의 행을 유일하게 식별하고 NULL을 허용하지 않는 제약이다. 업무 식별키는 시스템 사이에서 어떤 대상을 같은 것으로 볼지 정하는 도메인 의미다. 업무 키를 PK로 사용할 수도 있지만 둘이 언제나 같지는 않다. 일반 계약은 [PostgreSQL 제약 문서](https://www.postgresql.org/docs/17/ddl-constraints.html)를 참고했으며 당시 DB 제품을 PostgreSQL이라고 바꾼 것은 아니다.

**[사후 학습]** 컬럼 길이 문제는 실제 문자셋·문자/바이트 단위·대상 컬럼 정의를 대조해야 한다. 예를 들어 PostgreSQL 17의 varchar(n)은 문자 수 제한이다. 모든 DB의 varchar가 바이트 제한이라고 답하면 틀린다. [문자 타입 문서](https://www.postgresql.org/docs/17/datatype-character.html)를 반례로 삼는다. 당시 DB 문자셋·DDL·예외 문자열은 확인 필요이며 존재하지 않는 원본 로그를 만들지 않는다.

```text
입력 이벤트·업무 키 확인 → 원천/대상 키 매핑·DDL 대조
  → 원인과 담당 파트 분류 → 해당 파트 조치
  → GW 모니터링 재검증 → 완료 처리
```

[실무 경험] 위 흐름의 분류·연결·결과 확인을 맡았다. [확인 필요] 실제 Consumer 예외 처리·offset 정책·원본 이벤트별 장애 로그는 별도 자료가 필요하다. Kafka 수신 성공과 대상 DB 제약을 만족한 반영 성공은 같은 상태가 아니다.

#### 최종 면접 답변

> 데이터 유출 문제가 아니라 원천과 응용 시스템 사이의 데이터 불일치였습니다. 기존 경험 기록에서 구체적으로 설명할 수 있는 사례는 키를 맞추는 과정의 PK 중복과 컬럼 사이즈·인코딩 차이입니다. PK는 각 테이블의 행을 식별하는 제약이고, 업무 식별키는 시스템 사이에서 같은 대상을 대응시키는 의미라 그대로 같다고 볼 수는 없습니다. 저는 오류와 키·매핑을 확인해 담당 파트에 조치를 요청하고 결과를 재검증했습니다. 당시 DDL과 원본 로그가 없어 정확한 규격이나 모든 실패 유형까지 확정하지는 않겠습니다.

#### 예상 꼬리 질문과 답변

- **PK가 다르면 무조건 오류인가요?** “아닙니다. 시스템별 PK가 달라도 올바른 매핑이 있으면 됩니다. 매핑 의미와 실제 유일성 위반을 나눠 확인하겠습니다.”
- **컬럼 길이가 같아도 실패할 수 있나요?** “문자·바이트 단위와 인코딩·실제 값이 다르면 가능합니다. 당시 정확한 DDL은 확인 필요합니다.”
- **문자열을 잘라 넣으면 되나요?** “잘라내기가 업무적으로 허용되는지부터 봐야 합니다. 식별값 손상이나 멀티바이트 경계 문제가 있어 일괄 해법으로 쓰지 않겠습니다.”
- **Consumer가 실패하면 자동 재처리됐나요?** “구체 설정은 확인하지 못했습니다. 당시 경험은 오류를 모니터링하고 담당 파트와 조치·재검증한 범위로 답하겠습니다.”
