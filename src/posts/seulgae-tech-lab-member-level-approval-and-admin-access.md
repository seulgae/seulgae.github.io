관리자실 접근과 운영 기능에 같은 권한 기준이 필요했다. PR #60·#61에서 회원 등급과 신청 절차를 만들고 #64에서 임시 관리자 ID 예외를 제거한 흐름을 살펴봤다.

## 신청 중복을 DB에서 막는다

V10은 회원 등급과 등급 신청을 추가했다. 일반 사용자·운영자·관리자를 구분하고, 검토 중인 신청은 회원당 하나로 제한한다. 실제 마이그레이션의 부분 유니크 인덱스다.

```sql
CREATE UNIQUE INDEX level_requests_one_pending_idx ON lab.level_requests (member_id) WHERE status = 'PENDING';
```

화면에서 버튼을 한 번만 누르게 하는 것과 별개로 DB 제약이 경쟁 요청을 다룬다. 처리 완료된 과거 신청까지 하나로 제한하지 않도록 조건을 붙였다.

## 승인과 등급 변경을 함께 묶는다

승인 SQL은 `PENDING`인 행만 상태를 바꾸고 대상 회원과 신청 등급을 반환한다. 반환된 결과가 있을 때만 회원 등급을 갱신하며, 서비스의 트랜잭션으로 묶는다. 동시에 두 관리자가 처리하더라도 같은 대기 신청을 두 번 결정하지 않게 한 설계다.

처음에는 기존 관리자 계정이 잠기는 일을 피하려고 설정 ID 예외를 함께 두었다. 이후 관리자 계정을 새 등급으로 옮기고 예외를 제거해 관리자 판단을 등급 3으로 모았다. 순서가 뒤집히면 관리자가 없는 상태가 될 수 있다. 화면 문 잠금은 사용성 보조이며 관리자 API는 서버에서 다시 권한을 검사한다.

로그는 #61 당시 백엔드 96개·프런트 133개 테스트와 타입 검사 통과를 기록한다. 당시 로그인 기능의 운영 화면은 별도 확인이 필요하다고 남겼다. 이 글에서 운영 승인을 다시 실행하지는 않았다.
