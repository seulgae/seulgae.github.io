> **이 글의 역할:** 성과 경험 면접에서 쓰는 네 가지 경험을 **한 화면에서 비교**하고, 경험을 가로지르는 질문("AI는 어떻게 썼나요?", "수치는 어떻게 쟀나요?")에 일관되게 답하기 위한 허브다. 경험별 상세 내용은 각 복기 글에 있다.

## 1. 네 가지 경험 한눈에 보기

| 경험 | 상황 | 내가 한 일 | 성과 | 상세 글 |
| --- | --- | --- | --- | --- |
| **빌링 GW 오류 관리** | 시스템 간 구조 차이로 연동 오류가 누적 | 일일 집계·분류·공유 체계를 만들고 조치 후 재검증 | 주간 오류 약 70건 → 5건 (약 93%)에 **기여** | [빌링 GW 복기](/blog/billing-gw-integration-error-interview-review) |
| **NURI2 알림톡 배치** | 심사 지연으로 신청자 문의 증가 | 지연 대상 안내 발송 배치와 이력 조회 화면 개발 | 민원 문의 44건 → 31건 (약 30%) | [NURI2 복기](/blog/nuri2-message-batch-interview-review) |
| **CUBRID SQL 튜닝** | 목록 조회 화면 여러 개가 수십 초~1분 이상 | 실행계획 확인, 인덱스·SQL 적용, 결과 대조, 운영 확인 | 접수 목록 SQL 53초 → 1초 미만 | [SQL 복기](/blog/sql-performance-tuning-interview-review) |
| **CodeRay 보안 조치** | 정적 분석 검출 358건 | 유형별 분류·조치, 두 단계 기능 검증, 4회 재점검 | 검출 358건 → 4건 | [CodeRay 복기](/blog/coderay-security-remediation-interview-review) |

**앞의 세 개는 전세사기 피해자 지원관리시스템**, 빌링 GW는 통신사 빌링 시스템의 경험이다. 프로젝트별 전체 맥락은 [면접 정리 1](/blog/interview-jeonse-support-system), [면접 정리 3](/blog/interview-lgu-billing-gw)에 있다.

## 2. 네 가지 수치의 성격 — 섞지 않기

| 수치 | 무엇을 센 것인가 | 근거 수준 | 말하는 법 |
| --- | --- | --- | --- |
| 70건 → 5건 (약 93%) | 주간 연동 오류 수준 | 운영 중 관찰한 **어림값** | "약 93% 감소에 **기여**했습니다" |
| 44건 → 31건 (약 30%) | 민원 문의 건수 | **기억**에 근거한 전후 비교 | "당시 집계 기준 약 30% 줄었습니다" |
| 53초 → 1초 미만 | 대표 SQL의 실행 시간 | 블로그에 **기록**된 값 | 퍼센트보다 "53초에서 1초 미만"으로 |
| 358건 → 4건 | 정적 분석 도구의 검출 건수 | 점검 결과 **기록** | "검출 건수 감소"라고 범위를 붙여서 |

**자주 섞이는 수치**

- **"약 98%"** 는 CloudXper 프로젝트의 API 응답 시간 지표다. CUBRID 사례에 붙이지 않는다.
- **"75초"** 는 CloudXper의 예전 기록과 같은 값이라, 확인 전에는 CUBRID 사례의 수치로 말하지 않는다.
- **웹 취약점 16건·SQL Injection 14건**은 다른 점검의 수치라 358건에 더하지 않는다.
- 감소율을 계산해서 말할 때는 **계산식을 함께** 말한다. 예: `(44 - 31) / 44 ≈ 29.5%`

## 4. 여러 경험에 걸친 공통 질문

### Q. AI 도구는 어떻게 활용했나요?

> 분석 속도를 높이는 보조 도구로 썼고, 제안은 **검증할 가설**로 다뤘습니다. SQL 튜닝에서는 실행계획을 함께 검토해 인덱스 개선안을 받았고, 보안 조치에서는 유형별로 세션을 나눠 코드 분석과 조치안 검토에 썼습니다. 두 경우 모두 개발환경 적용, 결과 데이터 대조, 화면 재테스트를 거친 뒤에 반영 여부를 제가 판단했습니다.

**피할 말:** "AI가 다 해 줬다", "AI 덕분에 몇 % 빨라졌다" (AI만의 효과를 측정한 수치는 없다)

### Q. 성과 수치는 어떻게 측정했나요?

> 경험마다 측정 방식이 달랐습니다. SQL은 DB 도구에서 같은 쿼리의 실행 시간을 비교했고, 보안은 정적 분석 도구의 회차별 검출 건수를 비교했습니다. 오류 건수와 민원 건수는 운영 중 집계한 전후 수준이라 정밀한 실험 결과는 아닙니다. 그래서 수치를 말할 때 무엇을 센 것인지 함께 말씀드리려고 합니다.

### Q. 가장 어려웠던 경험은 무엇인가요?

> 빌링 GW 오류 관리입니다. 기술적인 원인 분석보다, 여러 파트가 각자 맡은 일만 보는 상황에서 조치가 실제로 이어지게 만드는 것이 어려웠습니다. 매일 현황과 조치 가이드를 공유하고, PL·PM의 협조를 얻고, 조치 후 재검증까지 반복하면서 누적 오류를 줄였습니다.

### Q. 실패하거나 아쉬웠던 경험은 있나요?

> 정적 SQL 전환 작업에서 코드 목록을 전수라고 믿고 진행했다가 테이블 하나를 놓친 적이 있습니다. 운영 이력과 비교해 차이를 찾고, 데이터를 보정한 뒤 다시 대사했습니다. 그 뒤로는 목록을 믿기 전에 **실제 운영 데이터와 먼저 비교**하는 습관을 갖게 됐습니다.

### Q. 네 경험의 공통점은 무엇인가요?

> 모두 **원인을 분류하고, 바꾼 뒤에는 결과가 맞는지 확인했다**는 점입니다. 오류는 유형별로 나눠 재검증했고, 튜닝은 결과 데이터를 대조했고, 보안 조치는 기능과 데이터가 그대로인지 확인했고, 알림 배치는 적재와 발송 결과를 분리해 확인할 수 있게 만들었습니다.

### Q. 혼자 한 일과 다른 사람이 한 일을 어떻게 구분하나요?

| 경험 | 내가 한 일 | 다른 사람·도구가 한 일 |
| --- | --- | --- |
| 빌링 GW | 분석·분류·보고 체계·재검증 | 데이터 수정(운영자), 재발행(발행 파트), 모니터링 사이트(기존 도구) |
| NURI2 | 대상 관리·적재·이력 화면 | 실제 발송·결과 기록(NURI2 솔루션) |
| CUBRID SQL | 문제 발견·적용·결과 대조·운영 확인 | 개선안 분석 보조(AI) |
| CodeRay | 분류 기준·변경 범위·검증·반영 판단 | 검출(CodeRay), 분석·구현 보조(Claude) |

## 5. 모든 경험에 적용하는 말하기 원칙

1. **실제 한 일 / 솔루션·도구가 한 일 / 나중에 공부한 것**을 섞지 않는다.
2. 수치에는 **무엇을 센 것인지**를 붙인다.
3. 기억나지 않는 것은 "확인이 필요합니다"라고 말하고 **추측하지 않는다**.
4. 사람이나 부서를 탓하지 않고 **프로세스의 한계**로 설명한다.
5. "지금 다시 한다면"은 **당시 구현과 구분**해서 말한다.

답변 구조는 **상황(S) → 과제(T) → 행동(A) → 결과(R)** 순서를 기본으로 하고, 결과 뒤에 **배운 점**을 한 문장 붙인다.
