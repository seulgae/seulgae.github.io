가상머신에서 물리 홈 서버로 옮기자 기존 운영 스크립트가 전제하던 앱과 공유 서비스가 없었다. 업데이트 도구가 첫 설치도 처리하려면 ‘이전 버전 없음’을 정상 상태로 표현해야 했다. PR #17의 `808595a`는 기존 검증을 없애기보다 최초 배포의 상태 전이를 추가한 변경이다.

## 없는 공유 서비스와 필수 DB를 구별하기

예전 서버에 있던 다른 앱이나 캐시가 새 서버에 없다고 배포를 막을 이유는 없다. 반면 PostgreSQL과 DB 네트워크는 새 앱의 필수 조건이다. 존재하는 공유 컨테이너만 전후 비교하되 DB는 반드시 있어야 하도록 나눴다.

사전 점검은 Docker·Compose, DB 네트워크, 비밀값 파일의 존재와 읽기 권한, 해석된 Compose 설정과 스키마를 확인한다. 단순 파일 검사와 실제 컨테이너에 들어갈 설정 검사를 함께 수행한다. 공개 글에는 실제 파일 위치와 DB 계정을 넣지 않았다.

## 앱이 없다는 사실을 오류로 만들지 않기

도입 당시 `deploy/ops.py`의 bootstrap 시작 부분이다.

```python
    current = read(STATE / 'current.json')
    if current:
        return validate(current, local=True)
    data = application_containers()
    if not data:
        return None
```

이전 성공 상태도 앱 컨테이너도 없으면 None을 반환한다. 다만 앱 일부만 있거나 출처가 모호한 설치를 같은 상태로 취급하지는 않는다. 최초 배포 성공 때 current를 만들고 이후 업데이트부터 previous를 남긴다. 존재하지 않는 이전 릴리스를 가짜로 채우지 않았다.

## 최초 실패에는 롤백할 이미지가 없다

업데이트 실패는 이전 앱을 다시 실행하면 되지만 첫 설치 실패는 새로 만든 앱을 정리해야 한다. 같은 파일의 복구 분기다.

```python
              if current is None:
                  clean_initial(candidate, before)
              else:
                  activate(current)
```

정리 전에 Compose 소유권과 후보 이미지가 맞는지 확인한다. 앱을 지우는 작업이 공유 DB까지 포함해서는 안 된다. 정리와 전후 검증이 실패하면 진행 중 거래 기록을 남겨 사람이 명시적으로 복구하게 하고, 끝없이 자동 재시도하지 않는다.

배포가 중단된 순간도 고려했다. 상태 저장 직후 프로세스가 끝날 수 있으므로 ‘current가 있으니 모두 성공’이라고 판단하지 않고 transaction 기록과 실행 중 컨테이너를 대조한다.

## 앱 시작을 DB 초기화와 분리하기

이미 적용된 스키마를 첫 배포라는 이유로 다시 초기화하지 않는다. 당시 `compose.yml`의 설정이다.

```yaml
      SPRING_SQL_INIT_MODE: never
      SPRING_FLYWAY_ENABLED: "false"
```

운영 스키마 검증은 유지하면서 앱 기동 시 SQL 초기화와 Flyway 자동 실행을 끈다. 이미지 전환의 롤백과 DB 복원은 다른 절차다. 이후 스키마 확장 우선 방식도 이 분리 위에 얹혔다.

## 코드 검증과 실제 서버 이전을 나눠 보기

PR에는 Ubuntu 운영 테스트 37개, 셸 구문·Compose 해석, 프런트·백엔드와 이미지 빌드 검증이 기록돼 있다. Windows에서 못 돌린 Linux 전용 검증은 CI 기록과 구별했다. 자동 배포가 옛 서버로 향하지 않도록 당시 활성화 상태를 확인하고 비활성화한 절차도 남아 있다. 이는 현재 배포 설정이 계속 같다는 뜻은 아니다.

이 PR 작업에서는 서버 SSH와 수동 배포, 운영 DB 변경을 하지 않았다. 이번 글에서도 새 서버의 실제 최초 설치 성공 여부는 **확인하지 못함**이다.

## 배운 점

첫 설치와 업데이트는 이전 상태의 존재 여부부터 달랐다.
공유 인프라 보호는 필요한 서비스와 이미 존재하는 서비스를 구분해야 했다.
앱 복구와 DB 복원을 분리해야 첫 배포 실패도 제한된 범위에서 정리할 수 있었다.
