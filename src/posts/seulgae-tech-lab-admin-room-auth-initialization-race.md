서버에서는 관리자라고 확인됐는데 화면의 관리자실 문은 열리지 않았다. PR #67은 권한 자체보다 **인증 상태와 게임 클라이언트가 준비되는 순서**를 살펴본 사례다.

## 서버와 화면의 판단을 나눠 확인하다

개발 로그에 따르면 인증 응답은 관리자 상태를 반환했고 관리자 API도 정상 응답했다. 반면 게임 화면은 관리자 아님으로 판단했다. 서버 권한과 화면 상태가 어긋난 지점을 좁힐 수 있었다.

기존 effect는 인증 상태를 게임 클라이언트에 전달했는데, 인증 확인이 클라이언트 생성보다 먼저 끝나면 전달할 대상이 없었다. 이후 의존 값이 변하지 않으면 effect가 다시 실행되지 않아 기본값이 남았다.

## 필요할 때 현재 상태를 읽는다

현재 `GameCanvas`는 클라이언트를 만들 때 `isAdmin: () => authStore.get().admin`을 전달한다. 문 진입 판단 시점에 현재 상태를 읽기 때문에 최초 전달 타이밍에만 의존하지 않는다. 서버의 관리자 API 검사는 별도로 유지된다. 화면에서 문을 열 수 있다는 판단이 서버 권한을 대신하지는 않는다.

PR과 개발 로그는 프런트 테스트·타입 검사·빌드 통과를 기록한다. 운영에서 새로고침 없이 실제로 문이 열리는지는 당시 별도 확인이 필요했다. 비동기 객체 사이에 상태를 복사할 때는 초기 전달이 빠질 가능성과 원본 상태를 다시 읽을 시점을 함께 설계해야 했다.
