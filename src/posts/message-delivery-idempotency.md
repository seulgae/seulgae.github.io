# 메시지 전달 보장과 멱등성은 어떻게 다른가

## 1. 학습 배경

NURI2의 미발송 재처리와 Kafka 연동 경험에서 “다시 실행해도 되는가”를 설명할 원리를 복습한다. 업무 전체의 exactly-once를 구현한 경험으로 말하지 않는다. 아래 고유키·상태 설계는 학습용이다.

## 2. 핵심 개념

At-most-once는 중복을 피하는 대신 유실 가능성을, at-least-once는 재전달로 유실을 줄이는 대신 중복 가능성을 고려한다. Exactly-once는 반드시 보장 범위를 명시해야 한다. 메시지 저장·소비 offset·외부 DB 갱신·실제 문자 발송은 서로 다른 효과다.

멱등성은 같은 의미의 요청을 반복해도 의도한 결과가 중복 적용되지 않는 성질이다. 수신 횟수가 한 번이어야 한다는 뜻과 다르다.

## 3. 동작 원리

```text
업무 처리 성공 → offset·처리 결과 기록 전 장애
  → 재시작·재전달 → 같은 업무가 다시 실행될 가능성
```

Kafka 생산자의 멱등성은 재전송 중복을 Kafka에 기록하는 범위에서 줄이는 기능이다. 외부 DB나 발송사의 효과까지 자동으로 한 번만 적용하지 않는다. 생산 설정의 전제는 [Producer 문서](https://kafka.apache.org/41/configuration/producer-configs/)로 확인한다.

**학습용 DB 처리:** `(수신자, 업무종류, 업무기준일)` 같은 업무 키에 고유 제약을 두고, 처리 이력과 DB 변경을 같은 트랜잭션으로 기록하는 방식을 검토한다. 먼저 존재를 조회하고 나중에 INSERT하는 두 단계만으로는 동시 중복을 막을 수 없다. 실제 중복 기준은 업무 규칙에 따라 달라진다.

## 4. 실무 활용

발송사가 요청을 수락했는데 응답이 유실되면 단순 재요청은 중복 발송 위험이 있다. 안정적인 요청 식별자·외부 멱등성 지원·결과 조회가 가능한지 확인한다. 외부가 이를 지원하지 않으면 결과 미확인을 별도 상태로 관리하고 대사·수동 판단을 설계해야 한다. 로컬 고유 제약만으로 외부 효과의 정확히 한 번 실행을 보장했다고 말하지 않는다.

## 5. 주의사항 및 오개념

DB 반영과 처리 완료 표시를 따로 커밋하면 중간 실패 구간이 생긴다. 여러 저장소를 묶는 보장에는 추가 설계가 필요하다. Kafka 트랜잭션도 Kafka 내부의 기록과 offset 연계를 중심으로 이해하며 외부 시스템과의 원자성을 별도 확인한다. [Kafka 설계 문서](https://kafka.apache.org/41/design/design/)의 전달 의미를 참고한다.

## 7. 핵심 요약

무엇이 한 번이어야 하는지 정하고 업무 키·원자성·외부 효과를 따로 점검한다. 중복 확인용 메모리 Set은 지속적인 업무 보장의 대체가 아니다.
