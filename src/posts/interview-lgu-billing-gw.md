## Case 1. 차세대 전환에 따른 Kafka 도메인 GW 아키텍처와 데이터 정합성(DI) 수호

- **원문**: [쪼개진 원천 테이블과 달라진 PK 사이 — Kafka 서비스 도메인 GW에서 데이터 정합성 지키기](/blog/kafka-gw-data-integrity)

### 1. [문제 정의 및 배경]
- **원천 테이블 분할과 PK(UUID) 체계 변경**: 발행(Pub) 측 상위 시스템이 차세대로 전환되면서 기존 원천 테이블이 여러 테이블로 쪼개지고 PK가 기존 업무키에서 **UUID**로 변경됐다. 반면 과금·청구·정산 같은 하위 구독(Sub) 파트의 DB 테이블들은 기존 업무키 기준으로 설계돼 있어, 발행 페이로드를 그대로 적재할 수 없었다.
- **이벤트 순서 역전과 이기종 DB 오류**: 분산 이벤트 특성상 신규 생성(`INS`)보다 변경(`UPD`) 이벤트가 먼저 도착해 키 해석이 실패하거나, 신규 컬럼 누락 및 Oracle↔MySQL 간 인코딩 바이트 차이로 인해 적재가 실패하는 연동 오류가 **주간 약 70건**씩 발생하고 있었다.

### 2. [기술적 의사결정 및 대안 비교]
- **하위 구독 시스템 개별 수정 vs 중간 도메인 GW + 메타데이터 테이블 구동**:
  - 과금·청구·정산 파트가 각자 차세대 UUID와 쪼개진 테이블 형상을 직접 해석하게 만들면 전사 하위 시스템의 쿼리와 스키마를 모두 뜯어고쳐야 한다.
  - 대신 중간에 **서비스 도메인 GW**를 두어 형상 변환을 전담시키고, 변환 규칙(토픽·이벤트 필드·원천/대상 컬럼 매핑·UPDATE용 join 조건 플래그)을 코드 하드코딩이 아닌 **3종의 메타데이터 테이블(`gw_topic_mgmt`, `gw_event_mgmt`, `gw_src_trgt_mapg`)**로 관리하도록 설계했다.
- **UUID ↔ 기존 업무키 해석을 위한 Redis 매핑 저장소 활용**:
  - 변경(`UPD`) 이벤트가 새 UUID만 들고 왔을 때 구독 DB의 기존 업무키 행을 업데이트하려면 빠른 키 변환이 필요하다.
  - 신규 생성(`INS`) 이벤트 처리 시점에 `UUID ↔ 기존 업무키` 매핑을 **Redis**에 저장하고, 이후 변경 이벤트 수신 시 Redis에서 기존 업무키를 찾아 대상 테이블의 WHERE(join) 조건을 완성하도록 구성했다(여기서 Redis는 메시지 브로커가 아니라 **업무키 매핑 Lookup 저장소**로 동작한다).

### 3. [해결 과정 및 트러블슈팅 (Fail-Recovery)]
- **`AbstractGwService` 기반 변환 파이프라인 운영**:
  - 진입점 `Dispatcher`가 메시지 헤더로 사업 구분(MNO/MVNO)을 분기하고, payload 구조에 따라 단일 DTO는 `process()`, 레벨 2 리스트 포함 구조는 `processWithList()`를 실행했다.
  - 원천과 대상이 1:1이면 `OneToOneService`, 1:N이면 `OneToManyService` 구현체가 원천 해석(`stepInSrc`)과 대상 반영(`stepInTrgt`)을 수행하며 `eventWorkCd`에 따라 `INS / UPD / MER / DEL` DML을 실행했다.
- **[Fail-Recovery] 이벤트 순서 역전 대응과 일일 대사(Reconciliation)·보정 표준화**:
  - 순서 역전으로 `INS` 매핑이 Redis에 생성되기 전에 `UPD` 이벤트가 먼저 도착하면 키 해석에 실패한다. 이를 즉시 버리지 않고 **재처리 대기 경로**로 분리 보관했다가 업무키 매핑이 생성된 뒤 재처리되도록 운영했다.
  - **WhaTap 히트맵**에서 slow/fail 쿼리와 Kafka 연동 오류 내역을 일일 단위로 추출·집계하고, 원천-구독 데이터 대사 결과를 4가지 원인(**① 발행 누락 ② 이벤트 순서 역전 ③ 변환·신규 컬럼 매핑 오류 ④ 수기 데이터 변경**)으로 분류했다.
  - 특히 오류 발생 자체보다 **각 파트 운영자가 인지하고 조치하기까지 걸리는 리드타임**이 더 큰 문제였기 때문에, `불일치 키 추출 → 보정 DML 작성(일회성은 엑셀 수식 기반 DML 생성, 반복 유형은 보정 스크립트 정비) → 대상 SELECT 사전 검증 → 반영 → 재대사`로 이어지는 대응 시나리오를 매뉴얼화해 공유 체계를 정립했다.
- **[Encoding] Oracle ↔ MySQL 인코딩 바이트 차이(`SUBSTRB`) 해결**:
  - Oracle과 MySQL 간 캐릭터셋 바이트 계산 차이(한글 2바이트 vs 3바이트 등)로 인해 글자 수 기준 처리 시 발생하던 컬럼 길이 초과 오류를 Java 바이트 변환 로직(`SUBSTRB` 대응)과 Subscriber 검증 모듈 공통화로 근본 해결했다.

### 4. [정량적/정성적 성과 및 배운 점]
- **성과**:
  - WhaTap 모니터링·대사·보정 시나리오 표준화로 **주간 Kafka 연동 오류 70건 → 5건 미만 (약 93% 감소)**.
  - 이기종 DB 바이트 처리 개선 및 연동 검증 공통 모듈화로 **인코딩 오류 95% 감소, 신규 연동 실패율 5% 미만 유지**.
- **배운 점**:
  - 분산 이벤트 파이프라인에서는 "오류가 0건인 완벽한 상태"를 가정하기보다, 순서 역전이나 스키마 변경으로 정합성이 어긋났을 때 **얼마나 빨리 대사(Reconciliation)로 감지하고 동일한 표준 절차로 안전하게 보정할 수 있는가**가 시스템 신뢰성을 결정한다.

### 5. [면접관 예상 꼬리 질문 (3가지)]
1. **Q. 아키텍처에 Kafka와 Redis가 둘 다 있는데, 두 저장소의 역할은 어떻게 달랐나요?**
   - **답변 포인트**: Kafka는 차세대 발행 시스템에서 발생한 도메인·테이블 이벤트를 구독 측 GW로 전달하는 **Pub/Sub 메시지 스트리밍 통로**이고, Redis는 메시지 큐가 아니라 차세대의 **새 `UUID`와 구독 파트의 `기존 업무키`를 매핑해 둔 Key-Value Lookup 저장소**입니다. `INS` 이벤트 때 Redis에 매핑을 적재하고, 이후 UUID만 담겨 오는 `UPD` 이벤트 때 Redis를 조회해 대상 DB의 기존 PK를 찾아내는 용도로 책임을 분리했습니다.
2. **Q. 신규 토픽이나 payload 필드가 추가될 때 메타데이터 등록만으로 끝났나요, 아니면 배포도 필요했나요?**
   - **답변 포인트**: 기존 DTO 필드 범위 안에서 테이블·컬럼 매핑만 조정하는 경우라면 3종 메타데이터 테이블(`gw_topic_mgmt`, `gw_event_mgmt`, `gw_src_trgt_mapg`) 등록만으로 반영됩니다. 하지만 payload 자체에 신규 필드가 추가된 경우에는 메타데이터 등록과 함께 **공통 DTO 모듈을 수정해 사내 Nexus에 배포하고, 각 구독 파트의 `pom.xml` 의존성 버전을 올려 배포하는 작업**까지 한 세트로 진행해야 정합성이 깨지지 않았습니다.
3. **Q. 엑셀로 보정 DML을 만들어 불일치를 맞췄다고 했는데, 운영 DB에 수동 DML을 반영할 때 실수를 막기 위해 어떤 안전장치를 두었나요?**
   - **답변 포인트**: 보정 DML을 만들어서 바로 실행하지 않고 반드시 4단계 검증을 거쳤습니다. ① 대사 결과에서 `mismatch` 난 키만 추출해 원천 데이터를 조회하고, ② 반영 전 대상 DB에 `SELECT`를 먼저 날려 현재 상태와 변경될 값을 눈으로 대조한 뒤, ③ 건수가 많을 때는 블록 단위로 나눠 반영하고, ④ 반영 직후 대사 쿼리를 다시 돌려 불일치 건수가 정확히 0으로 떨어졌는지 재대사까지 확인한 뒤에야 조치를 완료했습니다.

## Case 2. 상담 청구 조회 Oracle 슬로우 쿼리 튜닝 (묵시적 형변환과 실행계획)

- **원문**: [인덱스가 있는데 왜 안 타지 — 실행계획으로 좁혀간 슬로우 쿼리 튜닝기](/blog/oracle-hint-subquery-fullscan)

### 1. [문제 정의 및 배경]
상담 화면에서 특정 월의 청구 목록과 각 청구 건의 '최근 납부일'을 함께 조회하는 쿼리가 있었다. 데이터가 몰린 고객사를 조회하면 응답이 **수십 초**까지 늘어져 실시간 상담 업무에 지장을 주었다.

### 2. [기술적 의사결정 및 원인 진단]
- **Trusted Orange 실행계획(Plan) 분석**:
  - 쿼리 본문(`bill` 테이블)은 `IX_BILL_YM_SVC` 인덱스를 정상적으로 타는데, 최근 납부일(`MAX(p.pay_dt)`)을 구하는 스칼라 서브쿼리의 `payment` 테이블이 **`TABLE ACCESS (FULL)`**로 돌고 있었다. 청구 목록이 5천 건이면 `payment` 풀스캔이 5천 번 반복되는 구조였다.
- **인덱스가 있는데 왜 안 타는가? — Predicate에서 찾은 '묵시적 형변환'**:
  - `payment` 테이블에는 이미 `bill_no` 인덱스가 존재했다. 그런데도 풀스캔이 나는 이유를 Orange 플랜 하단의 **Predicate Information**에서 찾았다.
  - `bill.bill_no`는 `NUMBER` 타입이고 `payment.bill_no`는 `VARCHAR2(20)` 타입이어서, Oracle 옵티마이저가 우선순위에 따라 인덱스 컬럼 쪽에 **`TO_NUMBER("P"."BILL_NO") = :B1` 묵시적 형변환**을 씌우고 있었다.
  - 인덱스 컬럼이 함수(`TO_NUMBER`)로 가공되면서 인덱스가 무력화됐을 뿐 아니라, 만약 `payment.bill_no`에 숫자가 아닌 문자가 한 건이라도 섞여 들어오면 `ORA-01722 (invalid number)` 런타임 장애가 터질 시한폭탄 상태였다.

### 3. [해결 과정 및 트러블슈팅]
- **1단계 (형변환 방향 교정 + 인덱스 힌트 고정)**:
  - 운영 중인 두 테이블의 컬럼 타입을 즉시 변경할 수는 없었다. 대신 양쪽 값의 표기 규칙(선행 `'0'` 유무 등)이 일치하는지 실제 데이터로 먼저 검증한 뒤, 인덱스 컬럼(`p.bill_no`)은 그대로 두고 반대편 본문 값을 **`TO_CHAR(a.bill_no)`**로 변환했다.
  - 통계 변화에도 경로가 흔들리지 않도록 `/*+ INDEX(p IX_PAYMENT_BILLNO) */` 힌트를 명시해 `TABLE ACCESS (FULL)`을 `INDEX (RANGE SCAN)`으로 복구했다.
- **2단계 (대량 목록 조회의 구조 변경 — 스칼라 서브쿼리 → LEFT JOIN + Hash Join)**:
  - 인덱스를 태워도 "본문 행 수만큼 서브쿼리가 반복 실행된다"는 구조는 남는다. 조회 건수가 많은 화면은 스칼라 서브쿼리를 걷어내고 `LEFT JOIN (SELECT bill_no, MAX(pay_dt) ... GROUP BY bill_no) p` 인라인 뷰와 `/*+ LEADING(a) USE_HASH(p) */` 해시 조인으로 재작성해 한 번의 집합 연산으로 끝나게 만들었다.
- **[과장 없는 기여도와 학습 맥락]**:
  - 당시 이 힌트들과 옵티마이저 원리를 처음부터 완벽히 알고 짠 것이 아니다. 시스템 내 다른 쿼리들과 **DBA가 남겨둔 과거 튜닝 보고서**를 읽으며 왜 `LEADING`, `USE_NL`/`USE_HASH`, `INDEX`를 썼는지 플랜과 대조해 역으로 배웠다. 또한 단일 쿼리를 빨리 돌리겠다고 온라인 화면 쿼리에 무심코 `PARALLEL` 힌트를 넣으면 동시 호출 시 DB CPU를 고갈시킨다는 운영 한계도 이때 배웠다.

## Case 3. 수작업 엑셀 대장 다운로드 기능화와 `XSSF` vs `SXSSF` 선택 기준

- **원문**: [XSSFWorkbook vs SXSSFWorkbook — 수작업 엑셀 업무를 기능으로 만들며 정리한 선택 기준](/blog/sxssf-vs-xssf-excel-download)

### 1. [문제 정의 및 의사결정]
운영자가 매번 DB에 쿼리를 날려 수작업으로 가공하던 추출 대장·통계 엑셀을 화면 다운로드 기능으로 구현해야 했다. Apache POI의 두 구현체(`XSSFWorkbook` vs `SXSSFWorkbook`) 중 무조건 하나만 쓰는 대신 **건수와 양식 복잡도에 따른 선택 기준**을 세웠다.
- **`XSSFWorkbook` (수천 건 이하 · 복잡한 서식/셀 병합)**: 전체 행을 JVM 메모리에 들고 있어 이미 쓴 이전 행(`getRow`)을 다시 읽어 위아래 셀 값을 비교·병합하거나 템플릿을 수정하기에 적합하다. 단, 수만 건 이상에서는 XML 객체 오버헤드로 Heap OOM 위험이 크다.
- **`SXSSFWorkbook` (수만 건 이상 대량 추출 대장)**: 지정한 `windowSize`(예: 500~1,000행)만 메모리에 남기고 이전 행은 디스크 임시 파일로 즉시 기록(Flush)해 대량 건수에서도 메모리가 일정하게 유지된다.

### 2. [트러블슈팅 및 엣지 케이스]
- **플러시된 이전 행 접근(`null`) 주의**: `SXSSF`에서 윈도우 밖으로 밀려나 디스크에 기록된 행은 `sheet.getRow()` 호출 시 `null`이 반환된다. 따라서 이전 행 참조가 필요한 작업은 윈도우 크기 안에서 끝내거나 단순 목록 추출에만 사용했다.
- **`autoSizeColumn` 깨짐과 고정 폭 적용**: `SXSSF`에서 `autoSizeColumn()`을 그냥 호출하면 현재 메모리에 남아 있는 최근 몇백 행의 글자 길이만 기준으로 폭을 계산해 앞쪽 긴 텍스트가 잘린다. 대량 시트는 컬럼별 고정 폭(`setColumnWidth`)을 지정해 해결했다.
- **임시 파일 정리(`wb.dispose()`)**: `SXSSF`는 디스크에 압축 전 임시 XML 파일을 만들므로, `wb.close()`와 별개로 `finally`에서 반드시 **`wb.dispose()`**를 호출해 서버 `/tmp` 디스크에 임시 파일이 쌓이지 않게 처리했다.

## 기본기를 다지기 위한 사이드 프로젝트 아이디어 (이 프로젝트 기반)

### Idea 1. Kafka 이벤트 순서 역전 방어 & Non-blocking Retry + DLQ 파이프라인
- **목적**: 실무 GW에서 겪었던 *"생성(`INS`)보다 변경(`UPD`) 이벤트가 먼저 도착하는 순서 역전"*을 Spring Kafka 표준 아키텍처로 직접 구현하기.
- **구현 내용**: 일부러 `UPD(UUID-1)`를 먼저 발행하고 3초 뒤 `INS(UUID-1, 업무키-100)`를 발행하는 시나리오에서, `@RetryableTopic`(지수 백오프 토픽 재시도)과 Dead Letter Topic(DLQ), 자동 대사 배치를 결합해 데이터 유실 없이 최종 정합성이 100% 맞춰지는 과정을 구현.

### Idea 2. 옵티마이저 함정 재현기 — 묵시적 형변환과 스칼라 서브쿼리 vs 해시 조인
- **목적**: DBA 보고서와 기존 소스를 보며 배웠던 내용을 **내가 직접 설계한 스키마와 실행계획 비교 실험**으로 체화하기.
- **구현 내용**: `bill(bill_no INT)` 10만 건과 `payment(bill_no VARCHAR)` 100만 건을 구성해 ① 타입 불일치로 인한 인덱스 무력화 재현 ② `CAST`/`TO_CHAR` 방향 교정 ③ 결과 건수(10건 vs 5만 건)에 따른 스칼라 서브쿼리(NL)와 인라인 뷰 Hash Join의 손익분기점 그래프 도출.

### Idea 3. `-Xmx256m` 환경 30만 건 엑셀 다운로드 OOM 재현 & Heap 프로파일링 실험실
- **목적**: `XSSF`와 `SXSSF`의 메모리 차이를 **JVM 힙 그래프(VisualVM / JFR)**로 직접 증명하기.
- **구현 내용**: 힙을 256MB로 제한한 서버에서 30만 건 다운로드 시 `XSSF`가 OOM으로 죽는 지점과, `SXSSF(windowSize=500)`가 일정한 톱니바퀴(Sawtooth) 힙 그래프를 그리며 완주하는 모습을 캡처하고 `wb.dispose()` 호출 여부에 따른 임시 파일 삭제를 테스트 코드로 검증.
