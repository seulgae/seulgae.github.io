운영 행정망 화면 중에 접수 목록을 조회하는 화면이 있었다. 대상 데이터는
약 **7만 건**이었고, 조회에 **53초**가 걸려 운영자가 목록을 확인하는 데 불편이 있었다.

데이터 규모에 비해 조회가 느리다고 판단해 **실행계획에서 데이터를 읽는 방식과 정렬 비용을 확인**했다. DB는 CUBRID였고, 진단은 큐브리드 매니저(CUBRID Manager)의 쿼리 플랜에서 시작했다.

**아래 SQL·테이블명·컬럼명·인덱스 정의와 실행계획은 당시 튜닝의 원리를 설명하기 위해 재구성한 예제다. 실제 운영 SQL이나 실행계획 원본은 아니다.** 실제 개선 결과인 53초 → 1초 미만과 예제의 구체적인 구조는 구분한다.

## 진단 — 읽는 범위와 정렬 비용 확인

조회 조건과 정렬을 함께 고려하는 목록 쿼리를 다음과 같이 단순화했다.

```sql
SELECT rcpt_no, rcpt_status, apply_nm, area_cd, reg_dt
  FROM rcpt_list
 WHERE del_yn = 'N'
   AND area_cd = ?
   AND rcpt_status = ?
   AND reg_dt BETWEEN ? AND ?
 ORDER BY reg_dt DESC, rcpt_no DESC
```

확인할 부분은 **필터링 전에 읽는 데이터 범위와 별도 정렬의 발생 여부**였다. 전체 조회 후 정렬하는 흐름을 설명용 플랜으로 나타내면 다음과 같다.

```text
Query plan:
  temp(order by)                  ← 별도 정렬
    sscan                         ← rcpt_list 순차 스캔
      class: rcpt_list
      filter: del_yn='N' and area_cd=? and rcpt_status=? and reg_dt between ...
```

CUBRID 플랜에서 `sscan`은 테이블을 처음부터 끝까지 읽는 순차 스캔이고,
`iscan`이 인덱스 스캔이다. 위 예제는 전체 행을 읽어 조건에 맞는 데이터를 거른 뒤 정렬하는 구조다. 인덱스 설계에서는 **필요한 범위만 읽게 하고 별도 정렬도 줄일 수 있는지**를 함께 살폈다.

## 인덱스 설계 — 컬럼을 어떤 순서로 태울 것인가

"인덱스를 건다"는 결정보다 **어떤 컬럼을 어떤 순서로 거는가**가 본론이다.
후보 컬럼은 WHERE의 4개(del_yn, area_cd, rcpt_status, reg_dt)와 ORDER BY의
2개(reg_dt, rcpt_no)다. 예제의 인덱스 순서는 다음 기준으로 설명할 수 있다.

**1) 등치(=) 조건을 앞에, 범위 조건을 뒤에.**
복합 인덱스는 선두 컬럼부터 순서대로 좁혀 들어간다. `area_cd = ?`,
`rcpt_status = ?` 같은 등치 조건은 인덱스 앞쪽에 있어야 탐색 범위를 점으로
좁히고, `reg_dt BETWEEN`은 연속 구간을 읽게 한다. 뒤 컬럼은 탐색 구간 축소에 제약이 있지만 인덱스 키 필터나 정렬 등에 활용될 수 있다. 예제에서는 reg_dt를 등치 조건들 뒤에 배치했다.

**2) 값의 종류 수와 조건을 만족하는 행의 비율을 구분한다.**
`del_yn`은 'Y'/'N' 두 값만 가지며, 예제에서는 대부분이 'N'인 분포를 가정한다. 이런 컬럼을
단독 선두 조건으로 조회하면 많은 행을 읽을 수 있다. 다만 복합 인덱스는 뒤의 등치 조건까지 함께 활용하므로 저카디널리티 선두가 항상 나쁜 것은 아니다. 예제에서는 del_yn을 뒤쪽에 포함해 인덱스 키에서 필터링하는 구성을 보여준다. 실제 설계에서는 포함 여부에 따른 필터 효과와 인덱스 크기를 비교해야 한다. 예제 SELECT에는 인덱스에 없는 `apply_nm`이 있으므로 전체 쿼리를 커버링 인덱스로 처리했다고 부를 수 없다.

**3) ORDER BY까지 인덱스로 해결할 수 있는지 본다.**
정렬 컬럼(reg_dt DESC, rcpt_no DESC)이 인덱스 순서와 이어지면 DB는 정렬
작업 없이 **인덱스를 읽는 순서 그대로** 결과를 내놓는다. 플랜의
`temp(order by)` 노드를 지우는 방법이다. 등치 조건 뒤에 reg_dt를 두고,
그 뒤에 rcpt_no를 붙여 조회 범위를 줄이면서 요구한 정렬 순서도 활용하도록 구성했다. 다만 인덱스가 존재한다고 정렬 생략이 보장되는 것은 아니며 실행계획에서 실제 적용을 확인해야 한다.
정렬 방향도 함께 본다. 아래 예제는 DESC 키로 정의했으므로 그 순서대로 읽을 수 있다. ASC 키를 역순으로 읽는 방식과는 구분해야 한다. 실제 스캔 방향은 계획에서 확인한다.

이 기준을 적용한 설명용 인덱스는 다음과 같다.

```sql
CREATE INDEX ix_rcpt_list_01
    ON rcpt_list (area_cd, rcpt_status, reg_dt DESC, rcpt_no DESC, del_yn);
```

```text
등치(area_cd, rcpt_status) → 범위+정렬(reg_dt) → 정렬 보조(rcpt_no) → 필터(del_yn)
```

## 함께 살펴볼 조건절 — 인덱스 설계와 구분한 보충 예제

다음은 인덱스를 설계할 때 함께 검토할 수 있는 조건절 패턴이다. 이 두 가지를 실제로 변경해 53초를 단축했다는 의미는 아니다.

```sql
-- (1) 컬럼 가공으로 일반 인덱스의 범위 탐색이 어려워질 수 있다
WHERE TO_CHAR(reg_dt, 'YYYYMMDD') = ?

-- 컬럼은 그대로 두고 파라미터 쪽을 범위로 가공한다
WHERE reg_dt >= ? AND reg_dt < ?   -- 해당 일자 00:00 ~ 다음날 00:00
```

```sql
-- (2) 선행 와일드카드는 일반 인덱스의 범위 탐색에 불리하다
WHERE apply_nm LIKE '%' || ? || '%'

-- 전방 일치로 바꿀 때는 검색 의미가 달라지므로 업무 요구 확인이 필요하다
WHERE apply_nm LIKE ? || '%'
```

이름 검색 예제의 `apply_nm`은 앞서 만든 복합 인덱스에 포함되지 않는다. 전방 일치로 바꾼다고 그 인덱스로 이름 검색을 해결할 수 있는 것은 아니며, 별도의 접근 경로와 검색 요구를 검토해야 한다.

통계 정보도 실행계획 선택에 영향을 준다. `UPDATE STATISTICS ON rcpt_list;`는 통계를 갱신하는 예시 명령이며, 이 글에서 실제 개선의 별도 기여도를 측정한 작업으로 제시하지 않는다.

일반 원리와 기능 범위는 [CUBRID 인덱스·실행계획 문서](https://www.cubrid.org/manual/en/10.1/sql/tuning.html)를 참고했다. 문서는 일반 원리의 참고 자료이며 당시 운영 버전의 증빙은 아니다. 함수 기반 인덱스나 최적화 예외도 있으므로 위 조건절 패턴이 모든 환경에서 인덱스를 완전히 무력화한다고 일반화하지 않는다.

## 결과

인덱스 활용과 별도 정렬 생략을 적용한 구조는 다음과 같이 단순화할 수 있다.

```text
Query plan:
  iscan                           ← 인덱스 스캔으로 접근
    class: rcpt_list
    index: ix_rcpt_list_01
```

실제 작업에서는 실행계획 분석과 인덱스 적용으로 조회 시간을 **53초 → 1초 미만**으로 개선했다. 이후 월간 운영 점검에서 이 화면의 Slow Query
특이사항은 0건으로 유지됐다.

## 배운 점

- **튜닝은 플랜을 여는 데서 시작한다.** "느리다"는 증상만으로 인덱스를
  추측해서 걸면 안 걸리는 인덱스만 늘어난다. 비용이 큰 작업이 읽기인지 정렬인지부터 확인하면 개선할 지점을 좁힐 수 있다.
- **인덱스 설계는 컬럼 나열이 아니라 순서 결정이다.** 등치 → 범위 → 정렬의
  배치와 데이터 분포, 정렬 방향에 따라 활용 범위가 달라진다. 실제 실행계획과 응답 시간으로 설계를 확인해야 한다.
- **인덱스는 공짜가 아니다.** INSERT/UPDATE마다 인덱스도 갱신된다. 조회뿐 아니라 쓰기 비용과 인덱스 크기도 함께 고려해야 한다.
- **조건절 습관이 인덱스를 살리고 죽인다.** 컬럼 가공과 선행 와일드카드는
  일반 인덱스의 효율적인 범위 탐색을 방해할 수 있다. 인덱스 설계와 쿼리 작성 규칙은 세트로
  다녀야 한다.
