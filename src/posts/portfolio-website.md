포트폴리오를 수정하다 보면 기능보다 내용이 먼저 복잡해진다. 소개를 다듬고 프로젝트를 합치고 기술 태그를 줄이는 동안, 같은 경험이 홈·이력서·블로그·구성도에 조금씩 다른 모습으로 남았다. 화면에서 빠진 요소의 스타일도 소스에는 남아 있었다.

그래서 이번에는 새 기능을 만드는 대신, **현재 사이트가 무엇을 읽어 화면을 만들고 어떤 내용을 공개하는지**부터 다시 확인했다. 검토 기준은 2026년 11월 5일의 로컬 코드다. 이 글은 사이트 제작·정리 과정의 기록이며, 과거 업무 프로젝트의 운영 성과를 사이트 자체의 성능으로 설명하지 않는다.

## 서버 없이 콘텐츠를 운영하는 구조

이 사이트는 React와 Vite로 만든 정적 웹사이트다. GitHub Pages가 HTML·CSS·JavaScript·이미지를 제공하고, 브라우저에서 React Router가 화면을 선택한다. 별도의 API 서버나 데이터베이스는 없다.

화면은 목적에 따라 나눴다. 홈은 소개·핵심 역량·프로젝트·이력과 자격을 순서대로 보여준다. 블로그는 글 탐색과 읽기에 맞춘 별도 레이아웃을 사용한다. 출력용 이력서는 같은 경력 데이터를 짧게 정리해 보여준다. 헤더의 서명과 푸터는 공통 컴포넌트를 사용해 두 공간의 연결감을 유지했다.

```text
src/data/              → 홈 포스터 · 출력용 이력서
src/posts/*.md         → 글 목록 · 검색 · 상세 본문
src/data/구성도 데이터 → 프로젝트 아키텍처 팝업
                    Vite build
                         ↓
               build/ 정적 파일 → GitHub Pages
```

여기에 Spring이나 DB를 붙일 필요는 없었다. 사이트가 소개하는 백엔드 경험과 사이트를 운영하는 기술은 역할이 다르다. 작성자가 파일을 수정하고 배포하는 현재 방식에서는 Markdown이 필요한 콘텐츠 저장소 역할을 한다.

## 글 하나를 추가할 때 등록 코드를 만들지 않기

글은 `src/posts/영문-kebab-case.md`에 저장한다. `src/lib/posts.js`가 아래 방식으로 파일을 읽는다.

```js
const modules = import.meta.glob("../posts/*.md", {
  query: "?raw",
  import: "default",
  eager: true,
});
```

파일명에서 확장자를 뺀 문자열이 slug다. 이 글의 파일은 `portfolio-website.md`이므로 주소는 `/blog/portfolio-website`가 된다. 새 글마다 라우터나 목록 데이터를 수정할 필요가 없다.

메타데이터는 `title`, `date`, `tags`, `summary`를 한 줄씩 작성한다. 현재 파서는 완전한 YAML 파서가 아니라 각 줄의 첫 콜론을 기준으로 나누는 작은 함수다. 따라서 태그는 쉼표로 구분하고 여러 줄 YAML 값은 쓰지 않는다. 목록은 날짜 역순으로 정렬하며 제목·요약·본문 검색, 카테고리·태그 필터와 페이지 이동을 제공한다.

본문은 기존 `react-markdown`과 `remark-gfm`으로 렌더링한다. 이 글을 추가하면서 등록 시스템이나 렌더러를 새로 만들지 않았다. 내부 검토 기록은 루트 문서에 두고, 블로그에는 기술적 선택과 배운 점을 정리했다. `src/posts` 안의 모든 Markdown이 공개 글로 수집되기 때문이다.

## 같은 데이터를 쓰는 것과 같은 의미를 전달하는 것은 다르다

[이전 구조 정리](/blog/portfolio-refactoring)에서는 복제된 경력 내용을 `src/data`로 모았다. 현재 홈과 이력서는 `getCareerGroups()`로 같은 회사·프로젝트 데이터를 읽고, 성과 요약도 같은 `result` 필드를 사용한다.

이 방식은 같은 성과를 두 군데서 따로 수정하는 실수를 줄인다. 하지만 데이터 공유만으로 설명까지 자동으로 맞아지는 것은 아니었다. 블로그 본문과 구성도는 별도 파일이고, 같은 회사에서 수행한 여러 업무를 화면 카드 하나로 묶으면 기술 버전이나 시스템 경계가 흐려질 수 있다.

| 구분 | 정리 기준 |
| --- | --- |
| 소개 | 문제를 다루는 방식과 앞으로 맡고 싶은 개발 업무 |
| 핵심 역량 | 실제 수행 가능한 업무와 사용 기술 |
| 프로젝트 | 대상 시스템, 본인 행동, 결과 |
| 기술 글·구성도 | 선택 이유, 담당 영역, 구현의 한계와 후속안 |

경력 기간도 같은 원칙으로 봤다. 회사 재직 기간 안의 고도화 프로젝트를 별도의 경력으로 더하지 않았다. 표면적으로 숫자를 맞추는 것보다 무엇을 집계했는지 구분하는 일이 먼저였다.

성과도 마찬가지다. [병렬 조회 개선](/blog/mybatis-builder-parallel-refactoring)의 약 480,000ms에서 10,000ms 이내라는 정정된 결과는 당시 DB 조회 대기 시간을 겹친 경험이다. 이를 SQL 호출 수를 줄인 성과로 바꾸면 숫자는 같아도 설명은 달라진다. [권한 캐시](/blog/redis-permission-cache-ttl) 역시 화면 전환·로딩의 체감 개선을 API나 Redis 명령의 정량 측정값과 혼동하지 않아야 한다.

이번 검수에서는 기존 글이나 저자가 확인한 수치를 임의로 바꾸지 않았다. 같은 팀의 업무를 합친 카드와 개별 시스템 설명 사이의 차이는 후속 정리 대상으로 남겼다. 운영 코드와 원본 측정 로그가 없는 상태에서 새로운 검증 결과를 만들 수도 없었다.

## 파일이 남아 있다는 이유만으로 삭제하지 않기

정리를 시작할 때는 폴더 크기가 먼저 눈에 들어왔다. 하지만 저장소 크기, 배포 파일 크기, 첫 화면에서 내려받는 크기는 서로 다르다.

`src/old`는 이전 화면을 참고하기 위해 보관한 소스다. 현재 진입점의 import 연결과 분리되어 있으므로 이 폴더를 지운다고 같은 양의 초기 JavaScript가 줄어드는 것은 아니다. 의도적으로 남긴 주석도 보존했다.

반면 `public` 파일은 앱에서 참조하지 않아도 빌드 디렉터리에 복사된다. 파일명 검색에 잡히지 않는다고 모두 미사용인 것도 아니다. 구성도 로고는 다음과 같이 데이터의 이름으로 경로를 만든다.

```jsx
<img src={`/tech-logos/${logo}.svg`} alt="" loading="lazy" />
```

이 경우에는 데이터의 노드·도구·클라우드 제공자를 따라가야 한다. 이번에 확인한 SVG 18개는 모두 사용 중이었다. 전체 파일 이름만 검색했다면 잘못된 삭제 후보를 만들 수 있었다. public 복사 방식은 [Vite 정적 리소스 문서](https://vite.dev/guide/assets.html#the-public-directory)에서도 확인했다.

잔여 스타일은 파일 단위보다 선택자 단위로 봤다. 이전 헤더, KPI 카드, 푸터의 클래스는 남아 있지만 같은 CSS 파일 안의 현재 스타일은 계속 사용한다. 반응형·인쇄·동적 클래스를 대조하지 않고 파일 전체를 지우는 방식은 피했다. 미연결 샘플 manifest와 과거 커밋 목록 생성 명령도 발견했지만, 이번에는 삭제하지 않고 영향과 함께 정리했다.

## 로딩 최적화는 필요한 화면의 경계에서

현재 앱은 블로그 레이아웃·목록·본문, 이력서, 아키텍처 팝업을 `lazy`로 분리한다. 이 분리는 이전 정리에서 적용된 상태이며 이번 검수의 새 성과로 계산하지 않았다.

```jsx
const BlogLayout = lazy(() => import("./pages/BlogLayout"));
const ResumePage = lazy(() => import("./pages/ResumePage"));
```

교육·수상·자격 썸네일도 지연 로딩을 사용한다. 다만 원본 이미지를 작은 화면에 보여주는 구조라 화면용 축소본을 따로 만드는 여지는 남아 있다.

블로그의 eager Markdown 수집에는 이유가 있다. 현재 검색은 제목과 요약뿐 아니라 본문도 읽는다. 글이 늘었다는 이유로 eager 옵션만 제거하면 기존 검색을 그대로 유지할 수 없다. 본문을 따로 읽게 바꾸려면 검색 색인과 목록 메타데이터의 생성 방식까지 함께 정해야 한다. 지금은 기존 동작을 유지하고, 새 글을 포함한 빌드 크기와 기능을 확인하는 쪽을 택했다.

파일 용량이나 빌드 성공을 실제 모바일 속도로 바꾸어 말하지도 않았다. 네트워크 조건과 기기에서 측정하지 않은 LCP·CLS·INP 개선율은 이 글의 성과가 아니다.

## 로컬에서 열리는 주소가 배포에서도 같은 응답을 주지는 않는다

개발 환경에서는 Vite가 `/blog/글이름` 요청을 앱으로 연결한다. GitHub Pages에는 그 경로의 실제 HTML 파일이 없으므로 최초 응답은 다르다.

현재 사이트는 `404.html`에서 원래 경로를 sessionStorage에 저장하고 루트로 이동한 뒤, `index.html`에서 주소를 복원한다. 배포된 기존 글을 직접 열어 보니 브라우저에서는 본문으로 돌아왔지만, HTTP 요청의 최초 상태는 404였다.

```text
직접 방문 /blog/글이름
  → GitHub Pages 404.html
  → 원래 경로 저장 후 /
  → 주소 복원
  → React Router가 글 렌더링
```

사용자가 글을 읽을 수 있는 것과 검색·공유 수집기가 해당 주소를 정상 문서로 읽는 것은 별개의 문제다. 현재 글별 변경은 `document.title` 중심이고 Open Graph 정보는 공통 HTML에 있다. 글별 공유 카드와 최초 HTTP 상태를 개선하려면 정적 HTML을 출력하는 방식을 따로 검토해야 한다. 이번에는 호스팅이나 라우터를 바꾸지 않았다. [GitHub Pages의 사용자 정의 404 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-custom-404-page-for-your-github-pages-site)

## 작은 입력 오류도 사이트 전체에 영향을 줄 수 있다

일반 메뉴 이동은 정상이어도 직접 주소 입력은 다른 경로다. `/#%`로 접속했을 때 해시를 해석하던 `decodeURIComponent`가 예외를 던져 홈 전체가 비는 문제를 재현했다.

섹션 스크롤과 라우트 변경 처리에서 같은 해시를 읽고 있었기 때문에 한 곳만 고치면 충분하지 않았다. 공통 함수에서 잘못된 인코딩을 빈 대상으로 처리하고 두 호출부가 사용하도록 바꿨다.

```js
export function getHashTarget(hash = "") {
  try {
    return decodeURIComponent(hash.replace(/^#/, ""));
  } catch {
    return "";
  }
}
```

정상 앵커 이동은 유지하면서 잘못된 해시로도 홈을 표시하는 회귀 테스트를 추가했다. 새 기능이 없어도 방문자가 입력할 수 있는 경계에서 작은 안정성 개선이 가능했다.

## 확인한 결과와 남긴 과제

이번에는 파일 참조·메타데이터·내부 링크 검사, 기존 테스트와 프로덕션 빌드, 브라우저 화면 확인을 나눠 진행했다. 새 글도 기존 목록과 상세 경로로 확인했다. 자세한 검증 범위는 글 끝의 기록에 남겼다.

모바일 폭에서 소개와 역량 카드는 한 열로 배치되고, 성과 링크는 해당 카드로 이동했다. 구성도는 내부 가로 스크롤과 확대 기능을 제공한다. 반면 구성도 팝업에서 Shift+Tab을 누르면 키보드 초점이 배경으로 빠지는 문제는 남아 있다. 모달은 열리는 것만으로 완성되지 않으며 초점 유지와 복귀를 함께 확인해야 한다. [WAI-ARIA 모달 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

공개 정보도 텍스트에만 있는 것은 아니었다. 연락처를 정리해도 증빙 이미지에는 별도의 식별 정보가 남을 수 있다. 공개용 이미지의 범위를 다시 정하는 일과 원본 보존을 구분해야 했다. 이번 검수에서는 이미지를 수정하거나 삭제하지 않았다.

의존성 점검 결과 역시 실행 위치를 나눠 읽었다. 개발·테스트 도구의 경고가 모두 정적 사이트 방문자에게 같은 방식으로 적용되는 것은 아니다. 반대로 정적 사이트라는 이유로 브라우저 라이브러리의 공지를 무시할 수도 없다. 패키지 업데이트는 영향 확인과 회귀 검증을 묶은 후속 작업으로 남겼다.

## 배운 점

포트폴리오의 완성도는 화면을 더 꾸미는 것만으로 올라가지 않았다. 같은 경험이 여러 화면에서 같은 의미로 전달되는지, 공개할 파일이 실제로 어디까지 배포되는지, 정상 메뉴 외의 주소에서도 읽을 수 있는지 확인하는 일이 필요했다.

공통 데이터와 작은 컴포넌트는 수정 비용을 줄여 주지만, 시스템 경계와 경험의 범위까지 대신 판단하지는 않는다. 과거 구현과 지금 제안하는 개선을 구분하고, 검증한 사실만 결과로 남기는 습관이 사이트 유지보수에도 그대로 적용됐다.

### 검증 기록 — 2026-11-05
