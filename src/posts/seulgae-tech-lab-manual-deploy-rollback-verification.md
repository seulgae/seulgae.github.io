앞 챕터에서 인자 없는 배포 스크립트와 운영 명령을 구현했다. 이번에는 게시된 검증 이미지를 서버에 실제 적용했다. 앱 이미지 복원이 DB 복원으로 이어지지 않는지도 확인하고, 기존 공유 컨테이너를 건드리지 않았는지 작업 전후를 비교했다.

## 병합과 이미지 게시를 나눠 확인했다

PR #3의 최신 head CI가 성공한 뒤 병합했다. 병합 커밋은 `ec2598716fe2b6ed3c48911864813338aa91b612`이다. main CI는 프론트엔드, Java 17 백엔드, 운영 테스트를 통과한 다음 GHCR 이미지와 배포 manifest를 게시했다.

기존 운영 안내에는 연구 기록 API가 없다는 설명과 과거 Funnel 경로가 남아 있었다. 이미 구현된 기능과 사용자가 바꾼 운영 상태를 반영하는 문서 수정은 PR #4로 분리했다. 이 PR도 CI 성공 후 병합했고 최종 main은 `61243e1cd0d6278c88c8a258d63c8bee8960275b`이 됐다.

| 확인 대상 | 실제 결과 |
| --- | --- |
| PR #3 최신 CI | 성공 |
| 첫 main 이미지·manifest 게시 | 실행 43704975569 성공 |
| PR #4 문서 CI | 성공 |
| 최종 main 이미지·manifest 게시 | 실행 43705453858 성공 |
| 운영 스크립트 검증 | 셸 문법 검사와 단위 테스트 12개 통과 |

[배포 로직 PR #3](https://github.com/seulgae/seulgae-tech-lab/pull/3), [운영 문서 PR #4](https://github.com/seulgae/seulgae-tech-lab/pull/4), [최종 main CI](https://github.com/seulgae/seulgae-tech-lab/actions/runs/43705453858)에서 확인한 이력이다.

## 준비되지 않은 상태에서는 배포가 멈췄다

서버 소스를 main으로 동기화한 뒤 프로젝트 루트에서 다음 명령을 실행했다.

```bash
./deploy.sh
```

첫 시도 당시에는 CI가 진행 중이었다. 성공 이력에 게시된 manifest가 없으므로 배포 가능한 릴리스가 없다는 오류로 종료했다. 기존 앱을 바꾸지 않았다.

게시가 완료된 뒤 다시 실행했을 때는 다른 사전 조건에서 중단됐다. 운영 DB는 아직 스키마 0이었고 새 앱은 스키마 1을 요구했다.

```text
ERROR: DB schema 0 outside compatible range 1..1; no DB changes performed
```

이 결과는 배포 실패 후에야 DB 문제를 발견한 상황과 다르다. 스키마 호환성 검사에서 컨테이너 갱신 전에 중단한 결과이다. 일반 배포 명령이 임의로 DB 마이그레이션을 실행하지 않는 것도 확인했다.

## 백업 후 기존 V1만 별도로 적용했다

현재 연구 기록 앱에 필요한 V1은 이미 main에서 검증된 마이그레이션이었다. 운영에서는 다음 별도 명령으로 처음 적용했다.

```bash
python3 deploy/migrate-prod.py
```

`deploy/migrate-prod.py`는 CI 성공 manifest와 main 커밋을 대조한 뒤 운영 DB를 custom 형식으로 백업했다. `pg_restore --list`로 그 백업 목록을 읽을 수 있는지 확인한 다음, 검증 커밋에서 꺼낸 소스의 V1을 전용 migrator로 실행했다.

아래는 실제 구현에서 Maven 실행 부분만 발췌한 내용이다. DB 연결과 비밀번호 파일을 준비하는 앞부분은 생략했다.

```bash
exec mvn -B -f /work/pom.xml -Dflyway.target=1 flyway:migrate flyway:validate
```

Flyway 로그에서 빈 스키마에 V1 한 개를 적용했고 validate가 성공한 것을 확인했다. 스키마 이력도 version 1, success true였다. **백업 목록을 읽은 것은 확인했지만 실제 DB 복원은 실행하지 않았다.** 운영 DB를 초기화하거나 테스트 데이터를 넣지도 않았다.

마이그레이션 뒤 읽기 전용 조회 결과는 다음과 같았다. 실제 계정명과 접속 값은 생략했다.

| 검사 | 결과 |
| --- | --- |
| 운영 연구 기록 수 | 0건 |
| 개발 앱 계정의 운영 DB CONNECT | false |
| 운영 앱 계정의 스키마 CREATE | false |
| 운영 앱 계정의 Flyway 이력 SELECT | false |

이 검사는 PostgreSQL의 권한 메타데이터와 테이블 수를 조회한 결과이다. 개발 계정으로 운영 DB 로그인을 다시 시도한 검증과는 구분했다.

## 이미지 digest로 첫 배포를 완료했다

이후 같은 `deploy.sh`를 다시 실행했다. 공개 GHCR 패키지에서 두 이미지를 Pull하고 OCI revision 라벨을 검사한 뒤 연구소 앱만 갱신했다. 컨테이너 health, 웹 HTML, 상태 API와 연구 기록 읽기 API가 통과했고 `SUCCESS deploy`가 출력됐다.

처음 적용한 앱은 `ec25987` 버전이었다. 서버의 Docker 인증 구성에 저장된 레지스트리 자격증명이 없는 상태에서 Pull이 성공했으므로 공개 이미지 사용도 실제 확인했다. GitHub 패키지 화면에서도 두 패키지의 Public 표시를 확인했다. 이 작업에서 공개 상태를 변경한 것으로 기록하지는 않았다.

앱 로그에서는 Java 17.0.21로 Spring Boot가 실행된 것을 확인했다. 프론트엔드 시작 로그에는 읽기 전용 설정 파일을 수정할 수 없다는 nginx 진입 스크립트 안내가 있었다. 의도한 read-only 설정을 유지한 상태에서 nginx가 시작됐고 health와 HTTP 응답이 통과했다. 이를 해결하려고 컨테이너의 쓰기 제한을 풀지는 않았다.

## 운영 명령과 수동 롤백을 실제 실행했다

다음 명령은 모두 서버의 연구소 프로젝트 루트에서 실행했다. 아래 표는 실행 책임과 확인 결과를 정리한 것이며 공유 서비스 관리 명령이 아니다.

| 명령 | 실제 확인 결과 |
| --- | --- |
| ./deploy.sh | CI 성공 릴리스 자동 선정, 이미지 Pull과 앱 갱신 성공 |
| ./start.sh | 이미 실행 중인 앱 확인 및 중지 후 다시 시작 성공 |
| ./stop.sh | 연구소 앱 두 개만 중지 성공 |
| ./restart.sh | 앱 재시작 후 health와 API 정상 |
| ./status.sh | SHA·실행 ID·digest·스키마·health 조회 성공 |
| ./logs.sh | 두 앱 로그 조회 성공, 백엔드 개별 조회도 확인 |
| ./rollback.sh | 기록된 초기 정상 이미지 복원 성공 |

시작·중지·재시작 검증은 첫 배포한 `ec25987` 앱에서 수행했다. 수동 롤백은 첫 배포 직전의 `c4b8156` 초기 이미지 ID를 복원하는 방식이었다. 그 초기 버전에는 연구 기록 API가 없으므로 복원 검증은 웹 HTML과 상태 API에 한정했다.

롤백 후에도 운영 스키마는 1이었다. DB와 Flyway 이력을 되돌리지 않고 앱만 복원한 결과이다. 이어서 `deploy.sh`를 실행하자 그동안 성공한 최신 main CI의 `61243e1`을 자동 선택해 배포했다. 운영자가 SHA를 입력하지 않았다.

최종 상태는 다음과 같았다.

- 현재 앱 SHA는 `61243e1cd0d6278c88c8a258d63c8bee8960275b`이다.
- 연결된 CI 실행 ID는 `43705453858`이다.
- 두 이미지는 태그 대신 digest로 기록돼 있다.
- 운영 스키마는 1이며 진행 중 복구 기록은 남아 있지 않았다.
- 같은 배포 명령을 한 번 더 실행하면 이미 최신 검증 버전이라는 안내로 종료했다.

운영 장애를 인위적으로 발생시키는 테스트는 하지 않았다. 실패 후 자동 복원과 복원 실패 시 중단은 모의 단위 테스트로 검증했고, 실제 서버에서는 정상 명령에 의한 수동 롤백을 검증했다.

## 공유 서비스와 공개 접속을 따로 확인했다

사용자가 중지한 기존 InvenCore 앱을 기준 상태에 반영했다. 과거의 정상 실행 기준 파일은 보존하고 이번 작업 시작 상태를 별도로 저장했다. 작업 후 비교에서 기존 컨테이너 6개의 ID·시작 시각·재시작 횟수·상태와 읽을 수 있는 설정 파일 9개의 해시가 일치했다.

공유 PostgreSQL, Kafka, Redis는 계속 정상 실행 중이었다. InvenCore 앱은 중지 상태를 유지했다. 사용자가 변경한 Funnel 설정은 수정하지 않았다. 기존 DB 데이터나 볼륨도 변경 대상으로 삼지 않았다.

공개 HTTPS 경로에서는 상태 API가 UP이고 연구 기록 목록이 `items=[]`, `hasMore=false`로 응답했다. OPTIONS 결과는 GET, HEAD, OPTIONS였다. 운영 쓰기 API가 기본 비활성인 구성과 일치하는 결과이며, 실제 POST로 운영 데이터를 생성하는 실험은 하지 않았다.

브라우저 검증은 도구와 사용자 확인을 나눴다. 도구로 Chrome의 게임 화면 렌더링과 경고·오류 로그가 없는 것을 확인했다. 캔버스 키 입력 자동화는 실패했으므로, 방향키 이동과 컴퓨터 근처 E 키 패널 열림은 사용자의 실제 조작 성공 확인을 별도로 받았다. 이를 자동화 테스트가 입력까지 통과한 것으로 표현하지 않았다.

최종 자원 조회는 가용 메모리 약 6.3GiB, 루트 디스크 여유 약 12GiB였다. 이미지와 빌드 도구가 추가된 뒤의 순간 측정값이며 부하 시험 결과는 아니다.

## 자동 배포는 자격증명 등록 뒤에 검증한다

전용 SSH 키는 서버 내부망 접속에서 인증됐고, 임의 셸 명령을 요청해도 고정된 연구소 배포 명령이 실행되는 것을 확인했다. 기존 개인 접속 키는 CI에 사용하지 않았다.

반면 Windows에서 서버 FQDN으로 SSH 접속을 시도한 검증은 시간 초과였다. 당시 DNS 조회는 공개 진입 주소를 반환했다. 이 결과로 GitHub 실행기의 Tailscale 접속 성공을 판단하지 않았다. GitHub에서 CI용 인증키로 tailnet에 참가한 이후의 SSH 경로는 별도 실제 검증이 필요하다.

GitHub에는 다음 Secrets 등록이 남았다. 값과 개인키 내용은 글에 포함하지 않았다.

- TAILSCALE_AUTHKEY
- DEPLOY_SSH_PRIVATE_KEY
- DEPLOY_SSH_KNOWN_HOSTS

자동 배포 활성화 변수는 아직 켜지 않았다. 최종 앱 버전의 자동 배포 workflow는 실행 43705607329에서 skipped 상태임을 확인했다. 수동 배포가 성공했다고 자동 배포까지 완료한 것으로 기록하지 않았다.

운영자의 실제 접속 명령, 디렉터리, 로그와 장애 대응, Secrets 등록 방법은 `docs/operations.md`에 정리했다. 다음 작업은 Secrets와 필요한 변수 등록 후 자동 배포를 활성화하고, GitHub 실행 결과와 서버 배포 이력이 연결되는지 확인하는 것이다.

이번 검증에서는 앱 버전, 스키마 버전, CI 성공, 수동 운영, 사용자 조작을 따로 확인하는 것이 중요했다. 하나가 성공했다고 나머지까지 완료한 것은 아니었다. 블로그 두 챕터는 파일로 저장했으며 블로그 저장소의 커밋·푸시·배포는 수행하지 않았다.
