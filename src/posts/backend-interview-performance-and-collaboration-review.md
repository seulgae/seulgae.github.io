과거 백엔드 면접에서 실무 경험을 설명하면서 결과는 이야기했지만, **어느 구간을 바꿨고 왜 효과가 있었는지** 충분히 설명하지 못한 순간이 있었다. 이 글은 당시 답변을 바탕으로 질문을 복기하고, 이후 공부한 내용을 정리한 기록이다. 정확한 면접 날짜는 확인되지 않아 작성일을 기준으로 남긴다.

면접에서 말한 내용은 기억을 정리한 요약이며, 학습 내용과 연습 답변은 당시 발언이 아니다. 확인하지 못한 구현 세부사항은 추정하지 않는다.

## 경력과 프로젝트를 짧게 설명하기

### 경력을 소개해 주세요

**당시 답변 요약:** Java와 Spring 기반 API·배치, 청구 시스템과 Kafka 기반 GW 운영 경험을 설명하면서 개발 환경도 함께 언급했다.

돌아보니 기술 이름을 나열하느라 내가 맡은 역할이 늦게 나왔다. 다음에는 **주력 업무 → 직접 담당한 역할 → 대표 사례** 순서로 짧게 말하고, 기술 구성은 추가 질문에서 설명하고 싶다.

> Java 기반 API와 배치 개발, 데이터 연동 운영을 경험했습니다. 청구 업무에서 API와 권한 기능을 개발했고, GW 운영에서는 연동 오류를 분석해 담당 파트와 처리 현황을 공유했습니다.

### 기억에 남는 프로젝트와 기여는 무엇인가요?

**당시 답변 요약:** 엑셀 중심의 업무를 플랫폼으로 전환하는 프로젝트에서 상품 가입·청구 API, 권한 기능, 비동기 처리와 개발 표준화에 참여했다고 설명했다.

여러 역할을 한꺼번에 말하면 내가 직접 맡은 범위가 흐려질 수 있다. 다음에는 한 기능을 골라 **업무상 필요했던 이유, 직접 수행한 작업, 검증과 한계**를 설명한다.

## 조회 성능을 개선한 위치를 설명하기

### `parallelStream`을 어떻게 적용했나요?

**당시 답변 요약:** 데이터가 늘면서 느려진 조회 로직에 Java `parallelStream()`을 적용해 응답 시간을 줄인 경험을 이야기했다. 추가 질문에는 DB 병렬 처리와 Java 병렬 처리를 섞어 설명했다.

별도로 정정한 성과 기록은 **약 480,000ms에서 10,000ms 이내**다. DB 전체 테스트 데이터가 100만 건인 환경에서 API 호출부터 응답 완료까지 측정한 당시 병렬화 결과다. 면접에서의 수치와 혼동하지 않도록 이후 확인한 기록을 기준으로 정리한다.

**사후 학습:** 병렬 스트림은 Java 스트림의 요소 처리를 병렬로 수행하는 방식이다. 이를 사용했다고 해서 하나의 SQL이나 JOIN이 DB 내부에서 자동으로 병렬 실행되는 것은 아니다. 여러 DB 호출을 동시에 수행했는지, 조회 결과를 받은 뒤 가공했는지는 실제 코드로 확인해야 한다. DB 호출이 포함된다면 커넥션 풀과 DB 부하, 공유 상태와 트랜잭션 경계도 살펴야 한다.

다음 면접 전에는 다음을 확인하고 싶다.

- 병렬 스트림에 전달한 컬렉션의 각 요소와 람다 내부의 작업
- 해당 작업 안에서 DB를 다시 호출했는지, 결과를 가공했는지
- 측정 조건과 응답 시간의 구간별 차이
- 동시성에 따른 부하, 예외 처리와 스레드 안전성

**연습 답변 방향:** 당시 적용한 병렬화와 측정 결과를 설명한 다음, 정확한 처리 단위와 부작용은 원본 코드 확인 범위 안에서 답한다. 지금 다시 개선한다면 SQL 실행계획과 서비스 구간별 시간을 확인하고 조회량 축소나 집합 조회도 검토하겠다. 이는 당시 성과의 원인이 아니라 이후 생각한 개선 방향이다.

## GW 운영과 Kafka 신규 구축의 차이

### 연동 오류를 어떻게 관리했나요?

**당시 답변 요약:** 원천과 응용 시스템 사이의 데이터 구조·업무 키 차이로 발생하는 오류를 설명했다. GW 오류 정보를 확인해 일일 집계하고 담당 파트에 공유한 경험을 말했다.

인계 당시 누적된 미처리 오류를 해소하기 위해 **일일 메일 보고 체계를 직접 수립**했고, 파트별 처리를 종합·공유해 운영자 확인과 PM 검토를 지원했다. 주간 오류는 약 70건에서 5건으로 감소했다. 각 응용 데이터의 수정은 담당 파트의 역할과 구분해 설명해야 한다. 이상 데이터처럼 즉시 해결하기 어려운 건도 있었다.

### 기존 시스템을 운영했다면 새로 구축할 수도 있나요?

기존 GW의 연계 로직과 메타데이터를 이해한 경험은 출발점이 되지만, 신규 시스템의 설계와 구축 경험까지 의미하지는 않는다. 새로 맡는다면 처리량과 순서 요구사항, 토픽과 파티션, 재처리·중복 처리, 관측과 보안을 확인하고 경험이 부족한 부분은 검증해야 한다.

**사후 학습:** Kafka의 오프셋은 컨슈머가 파티션별 처리 위치를 관리하고 재시작할 때 활용하는 정보다. 오프셋이 있다는 사실만으로 업무 처리 성공이나 유실 방지가 자동으로 보장되지는 않는다. 처리와 커밋의 순서, 실패 후 재처리, 중복에 대한 대응을 함께 설계해야 한다.

## Redis 권한 캐시와 변경 반영

### 왜 Redis에 권한 정보를 저장했나요?

**당시 답변 요약:** 권한 정보를 빠르게 조회하기 위해 Redis에 보관했고 TTL을 약 12시간으로 설정했다고 설명했다. 화면이 빠르게 표시되는 것을 관찰했다고 답했다.

**사후 학습:** 권한 정보를 DB에 저장하면 안 된다는 일반 규칙은 없다. 권한 정책의 원본을 DB나 인증·인가 시스템에서 관리하고 Redis를 캐시로 사용할 수 있다. 캐시의 TTL은 로그인 세션의 유효 시간과 반드시 같지 않다.

다음에는 실제로 저장한 값과 키, TTL을 선택한 이유, 권한 변경 시 캐시 무효화 방법을 확인해 설명해야 한다. 캐시 미스나 Redis 장애 시 권한을 어떻게 판단할지도 별도 설계가 필요하다. 당시 화면 체감과 측정 자료는 구분한다.

## MyBatis·JPA와 CI/CD 경험의 범위

### MyBatis와 JPA는 어떻게 다른가요?

**당시 답변 요약:** MyBatis를 주로 사용했고 JPA는 일부 소스를 읽은 경험이 있으나 실무 사용은 제한적이라고 설명했다.

**사후 학습:** JPA는 Java 객체와 관계형 데이터의 매핑을 위한 명세이며 Hibernate는 구현체 중 하나다. MyBatis는 개발자가 작성한 SQL과 객체 사이의 매핑을 지원한다. JPA의 N+1 문제는 연관 데이터를 접근하는 과정 등에서 최초 조회 외 추가 SQL이 반복되는 현상이다. 해결책은 fetch join, 엔티티 그래프, 배치 조회 등을 상황에 맞게 검토한다. MyBatis에서도 반복 조회를 작성하면 유사한 문제가 생길 수 있다.

### CI/CD에서 직접 한 일은 어디까지인가요?

**당시 답변 요약:** Git 커밋과 Jenkins 빌드까지 직접 경험했고, 운영 서버 배포는 별도 담당자가 수행했다고 구분했다.

**사후 학습:** CI는 변경 사항을 자주 통합하며 빌드와 테스트로 확인하는 방식이다. CD는 변경을 배포 가능한 상태로 전달하는 지속적 전달과 실제 운영까지 자동 배포하는 지속적 배포로 나눌 수 있다. 면접에서는 전체 흐름을 이해해 설명하되 **직접 수행한 단계와 팀이 수행한 단계**를 구분한다.

## 의견이 다를 때와 모르는 일을 맡았을 때

### 동료와 의견이 달랐던 경험은?

**당시 답변 요약:** 코드 스타일과 서비스 표준화 방향을 두고 동료와 의견 차이가 있었고, 이후 다시 대화하고 회의를 통해 방향을 공유한 사례를 말했다.

이 경험은 의견 충돌을 숨기기보다 상대의 관점과 합의 과정을 설명하는 연습이 필요하다는 점을 알려줬다. 당시 누가 어떤 대안을 받아들였는지 확인되지 않은 부분까지 만들어 내지 않고, 실제 기억하는 논의와 결과를 중심으로 말한다.

### 사수에게 질문하거나 새로운 기술을 배울 때는?

**당시 답변 요약:** 스스로 시도한 내용과 막힌 지점을 정리해 질문하고, 마감에 영향을 주기 전에 도움을 요청한다고 설명했다. 새로운 기술과 인프라 업무도 배우겠다는 의사를 밝혔다.

앞으로도 학습 의지를 말할 때는 **이미 수행한 일과 앞으로 배울 계획**을 구분하겠다. 질문할 때는 확인한 사실, 시도한 방법, 필요한 판단을 함께 전달하고, 해결 후에는 결과를 공유한다.

## 다시 연습할 질문

1. 성능 개선에서 실제 병렬화한 작업은 무엇이고 DB 호출은 어디에 있었는가?
2. Kafka 컨슈머의 처리와 오프셋 커밋 사이에서 실패하면 어떤 일이 생기는가?
3. 권한이 변경되었을 때 이전 캐시가 남지 않도록 어떻게 관리할 수 있는가?
4. JPA의 N+1은 어떤 상황에서 발생하고 어떻게 확인할 수 있는가?
5. Jenkins 빌드와 운영 배포 중 내가 직접 수행한 단계는 어디까지인가?
6. 동료와 의견이 달랐을 때 서로의 근거와 합의 과정을 어떻게 설명할 것인가?

경험을 설명할 때는 **상황 → 직접 한 일 → 검증 → 결과와 한계** 순서로 말하는 연습을 하려 한다. 원리와 구현 위치가 불확실한 부분은 코드를 확인한 뒤 보완한다.
