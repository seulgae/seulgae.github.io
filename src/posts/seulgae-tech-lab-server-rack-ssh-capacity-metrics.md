연구소 서버실의 랙을 열었을 때 실제 서버의 상태도 확인할 수 있으면 어떨까. 이전에 [SSH 기반 서버 점검을 만들며 정리한 경험](/blog/jsch-to-mina-sshd)을 바탕으로, 이번에는 호스트 지표와 애플리케이션 JVM 지표를 네 개의 랙에 나눠 보여 주는 기능을 살펴봤다.

이 글은 개발 로그와 PR #84, 해당 브랜치의 코드를 바탕으로 작성했다. **PR #84와 #85는 main에 병합됐으며, 이후 개발 로그와 PR #89에 운영 수집 성공이 기록됐다.**

## 호스트와 JVM은 서로 다른 곳에서 읽는다

랙 네 개는 CPU, 메모리, JVM 힙, 가동시간을 각각 담당한다. 호스트 CPU·메모리·가동시간은 SSH로 가져오고, 현재 애플리케이션의 힙·GC·스레드 등은 JVM의 MXBean에서 읽는다. 컨테이너 안 JVM의 상태와 호스트 전체의 상태는 같은 값이 아니므로 출처를 구분한다.

서버는 기본 30초 간격으로 호스트 수집을 시도하고, 성공한 CPU·메모리 값은 최근 30개만 메모리에 보관한다. 대략 15분 분량이지만 수집 실패나 실행 시간에 따라 간격은 달라질 수 있다. DB에 장기 이력을 저장하지 않는 선택이다. 수집 실패 시 마지막 성공값은 남기고 상태와 마지막 수집 시각을 함께 표시한다. 오래된 값을 현재 상태로 오해하지 않도록 이 구분이 중요하다.

SSH 설정이 없을 때는 호스트 측정값이 없음을 표시하면서 JVM 값은 계속 볼 수 있다. 첫 수집 전이라도 미설정이면 대기 상태 대신 `NOT_CONFIGURED`를 반환하도록 보완했다.

## SSH 명령은 한 번 실행하고 결과를 검증한다

Apache MINA SSHD의 EXEC 채널을 사용해 CPU 코어, 부하 평균, `vmstat`, 메모리와 가동시간을 한 번에 조회한다. 연결·인증·채널 열기와 종료 대기에 각각 시간 제한을 두고, 표준 출력과 오류 출력을 분리한다. 시간 초과와 0이 아닌 종료 코드도 확인한다. 기존 실무 글에서 다룬 비동기 단계별 대기와 자원 정리 원리를 이 프로젝트의 수집 경로에 다시 적용한 것이다.

`vmstat 1 2`의 첫 결과는 부팅 이후 평균이므로 두 번째 결과를 사용한다. 출력에는 구역 이름을 붙이고 CPU 열은 머리글로 찾아 파싱한다. 메모리 사용률은 전체에서 가용 메모리를 뺀 값의 비율이다. 단순히 사용 중인 바이트만 보는 것과 기준이 다르다.

## 접속 권한과 공개 응답을 좁힌다

접속은 키 인증을 사용하고 `known_hosts`에 없는 호스트 키를 거부한다. 운영 설정 문서에는 수집 전용 키가 지정된 프로브만 실행하도록 제한하는 방안이 적혀 있다. 이것은 운영에서 해당 제한을 **실제로 설정했을 때** 적용되는 조건이며, PR만으로 운영 설정이 완료된 것은 아니다.

공개 API는 집계 지표와 짧은 실패 분류를 반환하고 호스트명·IP·계정·명령 출력과 오류 원문은 응답에서 제외한다. 다만 집계 지표 자체도 공개 정보이므로 무엇을 공개할지는 별도의 판단이 필요하다.

## 운영 연결을 위한 준비 순서

다음은 설정의 흐름을 설명하는 **일반화한 예시**다. 실제 서버 경로와 계정은 환경마다 다르므로 저장소 운영 문서를 기준으로 확인한다. 이 명령을 실행하거나 운영 수집을 검증한 것은 아니다.

1. 수집 전용 디렉터리를 준비하고 별도 키를 생성한다. `<키_경로>`는 실제 운영 환경에 맞게 바꾼다.

   ```sh
   mkdir -p <키_디렉터리>
   ssh-keygen -t ed25519 -N '' -C capacity-probe -f <키_경로>
   ```

2. 프로브 스크립트에 실행 권한을 주고, 수집 계정의 `authorized_keys`에 공개키를 `restrict,command="<프로브_절대경로>"` 옵션과 함께 등록한다. 강제 명령과 키는 **한 줄**이어야 한다. 이 설정이 실제로 등록돼야 해당 키의 사용 범위가 제한된다.
3. 컨테이너가 사용할 호스트 이름으로 `known_hosts`를 준비한다. `ssh-keyscan`으로 얻은 키는 수집 결과일 뿐 신뢰성 검증이 아니므로, 신뢰할 수 있는 경로로 확인한 호스트 키 지문과 대조한다.

   ```sh
   ssh-keyscan <SSH_접속_호스트> > <known_hosts_경로>
   ssh-keygen -lf <known_hosts_경로>
   ```

4. 백엔드 컨테이너의 사용자 ID를 확인해 키 파일을 읽을 수 있도록 소유권을 맞추고 개인키 권한을 `600`으로 제한한다. 경로와 소유자를 확인한 뒤 적용한다.

   ```sh
   docker exec <백엔드_컨테이너> id
   chmod 600 <키_경로>
   ```

5. Compose의 기존 backend `environment`와 `volumes`에 SSH 호스트·계정·키 경로·known_hosts 경로와 읽기 전용 마운트를 추가하고, 필요한 환경에서는 host-gateway 연결을 설정한다. 기존 항목을 덮어쓰지 않고 합쳐야 한다. 배포는 저장소의 Compose 파일을 기준으로 하므로 서버에서만 수정하면 다음 배포 때 사라질 수 있다.
6. 배포 후 랙에서 수집 상태와 마지막 수집 시각을 확인한다. 실패하면 설정 누락, 키 인증·호스트 키, 스크립트 실행 권한, 연결 시간 초과, 출력 파싱을 순서대로 확인한다.

후속 **PR #85는 main에 병합됐으며**, 저장소 Compose의 환경 변수·host-gateway·읽기 전용 마운트와 배포 설정 검사를 추가한다. PR에는 운영 키와 권한을 준비했다고 기록돼 있으나, 강제 명령 등록과 배포 후 수집 성공은 아직 확인할 항목으로 남아 있다. 실제 운영 설정이나 배포를 이번 글 작성 과정에서 검증하지 않았다.

## 호스트 키 종류가 달라 연결이 거절된 문제

운영 배포 후 랙에 `CONNECT`가 표시되고 로그에는 `Server key did not validate`가 남았다. 개발 로그와 PR #87에 따르면 `known_hosts`를 만들 때 Ed25519 호스트 키만 저장했는데, MINA SSHD 연결에서는 서버의 ECDSA 호스트 키가 선택되어 검증에 실패했다. 이는 사용자 인증에 쓰는 개인키 종류와 별개인 **서버 호스트 키 검증** 문제였다.

운영 문서는 특정 종류로 제한하지 않고 서버가 제공하는 호스트 키를 수집하도록 변경하고, 실패 코드표에도 이 사례를 추가했다. 위 예시 역시 `-t ed25519`를 제거했다. 수집한 각 호스트 키의 지문은 신뢰할 수 있는 경로로 확인해야 한다. 호스트 이름과 포트도 실제 SSH 접속 대상과 일치해야 한다.

이 내용은 **PR #87에서 반영한 문서 수정**이며, 이후 main 병합을 확인했다. 이후 호스트 키 문제는 해결되어 접속이 사용자 키 인증 단계까지 진행됐지만, 전체 수집이 성공한 것은 아니다.

## 호스트 키 다음에는 개인키를 읽지 못했다

호스트 키 검증 문제를 해결한 뒤에는 `Unsupported key type (ssh-ed25519)` 오류가 나타났다. 이번에는 서버의 호스트 키가 아니라 **클라이언트가 인증에 사용할 개인키를 읽는 단계**의 문제였다. Java 17에서 사용한 Apache MINA SSHD 2.16 구성에 Ed25519 개인키 처리를 위한 `net.i2p.crypto:eddsa` 의존성이 빠져 있었다.

PR #88은 해당 라이브러리 0.3.0을 추가하고, 운영과 같은 Ed25519 클라이언트 키로 테스트 SSH 서버에 인증하는 회귀 테스트를 추가했다. 기존 로컬 접속 테스트는 RSA 키만 사용했기 때문에 운영과 다른 키 형식에서 발생하는 문제를 확인하지 못했다.

PR 기록에 따르면 의존성을 제거했을 때 새 테스트가 실패하는 것도 확인했고, 백엔드 테스트는 **110개 통과, 5개 건너뜀**으로 보고됐다. 건너뛴 항목은 로컬 DB가 없어 실행하지 못한 테스트다. 이 결과는 PR 작성 당시의 검증 기록이며 이번 글 수정에서 재실행한 결과는 아니다.

이후 #86 → #87 → #88 순서로 main에 병합된 것을 확인했다. 기존 키와 `known_hosts`를 다시 만드는 작업은 이 수정에 필요하지 않다. 기존 버전이 실행되는 동안에는 같은 오류가 수집 주기마다 반복될 수 있다. 배포 후 로그와 4번 랙의 정상 수집 상태를 확인하기 전까지 운영 수집 성공으로 기록하지 않는다. API 응답이 없었던 시점의 원인이 배포 중 재시작인지는 확인되지 않았다.

## 마지막 원인은 공개키 등록 누락이었다

개발 로그와 PR #89에는 Ed25519 의존성을 배포한 뒤에도 인증 단계에서 연결이 종료된 사례가 기록돼 있다. 확인 결과 수집 전용 공개키가 서버의 `authorized_keys`에 등록되지 않았고, 강제 명령을 포함해 등록한 뒤 다음 수집에서 `OK`를 확인했다고 한다. 호스트 키 검증, 클라이언트 개인키 읽기, 서버의 공개키 등록은 각각 다른 단계였다.

PR #89에는 운영 API가 `OK`를 반환하고 4번 랙에서 정상 수집을 확인한 기록이 있다. 이는 해당 시점의 운영 기록이며, 이번 글 수정 과정에서 운영 서버를 다시 조회한 결과는 아니다.

## 확인한 범위와 남은 일

PR 기록에는 테스트 SSH 서버로 키 인증과 EXEC 출력, 호스트 키 거절과 비정상 종료를 확인한 내용이 있다. 백엔드 테스트 115개(건너뜀 5), 프런트 테스트 150개, 타입 검사와 빌드 통과도 기록돼 있다. 로컬 화면의 호스트 값은 예시 응답으로 확인했으며 실제 로컬 API는 미설정 상태와 JVM 값을 반환했다.

기능 PR #84는 Compose 설정을 포함하지 않았으며 후속 PR #85에서 이를 추가했다. 위 초기 검증 기록과 이후 PR #89의 운영 확인은 시점이 다르다.
