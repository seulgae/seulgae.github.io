# 정적 분석 결과를 실제 취약점으로 검증하는 과정

## 1. 학습 배경

CodeRay 검출 유형별 조치와 공통 원인 수정, 미사용 코드 확인 후 삭제, 조치하기 어려운 범위를 남긴 기존 기록이 있다. 이를 바탕으로 검증 과정을 복습한다. 사용한 제품의 버전·규칙·탐지 범위를 새로 추정하거나 모든 경고를 공격으로 재현했다고 말하지 않는다.

## 2. 핵심 개념

SAST는 소스 또는 컴파일된 코드를 분석해 취약할 수 있는 흐름·패턴을 찾는 정적 검사다. 실행 중인 앱이 없어도 조사할 수 있지만 환경·프레임워크 모델에 따라 오탐·미탐이 있다. [OWASP 정적 분석 설명](https://owasp.org/www-community/Source_Code_Analysis_Tools)을 기준으로 한다.

DAST는 실행 중인 앱에 요청을 보내 외부에서 관측되는 동작을 검사한다. 인증·권한·입력 경로와 실행 환경의 영향을 받는다. 둘은 서로 보완하며 한쪽의 통과가 전체 보안 증명은 아니다.

## 3. 동작 원리

```text
검출 위치 확인 → 입력 출처와 위험 사용 지점 추적
  → 중간 검증·인코딩·권한 확인 → 실제 호출·노출 여부 확인
  → 수정 → 같은 경로 재검사 + 정상 기능 회귀 검사
```

변수 이름이나 경고 한 줄보다 데이터가 어느 경계를 통과하는지 본다. 정적 경고가 있어도 실행 가능성과 보호 조건을 대조해야 한다. 반대로 테스트에서 한 번 재현되지 않았다는 이유만으로 오탐이라고 결론 내리지 않는다. [OWASP 테스트 가이드](https://owasp.org/www-project-web-security-testing-guide/)는 검사 범위를 조직하는 참고 자료다.

## 4. 실무 활용

기존 경험에서는 공통 유틸리티·입출력 경로를 수정하거나, 실제로 사용하지 않는 코드임을 확인한 뒤 삭제하는 판단이 중요했다. 다만 현재 기록만으로 모든 호출 경로가 증명됐다고 확대하지 않는다.

**학습용 검토 예제:** 파일 경로 관련 경고라면 외부 입력의 영향, 허용 디렉터리 안에 머무는지, 정규화·실제 파일 접근 경로와 링크 처리를 확인한다. 수정 후 정상 파일 이용과 경계 밖 접근 거부를 각각 검사한다. 이 예제가 특정 고객사에서 직접 수행한 검증이라는 뜻은 아니다.

## 5. 주의사항 및 오개념

경고 줄만 우회하거나 예외 처리를 추가해도 취약한 데이터 흐름이 남을 수 있다. 무조건 필터 하나로 모든 문맥을 해결하지 않는다. 오탐 제외에는 근거·적용 범위·재검토 조건을 남긴다. 제품 전용 규칙 번호와 실제 CWE 대응은 보고서를 확인한 경우에만 인용한다.

## 6. 기술 면접 예상 질문

| 질문·의도 | 핵심을 담은 구어체 답변 | 꼬리 질문 |
| --- | --- | --- |
| SAST와 DAST 차이는? 관측 범위 | “코드 흐름을 분석하는 것과 실행 앱의 응답을 검사하는 차이예요. 각자 보지 못하는 범위가 있어 함께 확인하는 게 좋아요.” | 인증 뒤 기능은 어떻게 검사하나? |
| 오탐은 어떻게 판단하나? 근거 | “입력에서 위험 사용 지점까지 실제 흐름과 보호 조건을 확인해요. 재현이 안 됐다는 이유만으로 제외하지 않겠습니다.” | 호출되지 않는 코드라면? |
| 수정 완료 기준은? 검증·회귀 | “문제 경로가 막혔는지 재검사하고 정상 기능이 유지되는지도 봅니다. 검사 도구 결과와 실제 확인 범위는 따로 보고해요.” | 공통 코드 수정의 영향은? |

## 7. 핵심 요약

검출·분석·수정·재검증의 증거를 연결한다. 경고 건수 감소와 공격 가능성 제거, 전체 서비스 안전을 같은 성과로 합치지 않는다.
