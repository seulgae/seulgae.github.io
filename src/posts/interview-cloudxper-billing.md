## Case 1. 100만 건 환경 대용량 조회 성능 개선과 `parallelStream`의 명암

- **원문**: [10분짜리 API를 30초 이내로 — 100만 건 대용량 조회 성능 개선과 병렬 스트림](/blog/mybatis-builder-parallel-refactoring)

### 1. [문제 정의 및 배경]
- **100만 건 규모에서 터진 10분 지연**: 청구 목록·가입 목록 등 마스터 데이터를 조회한 뒤 각 항목의 상세 내역을 묶어 내려주는 조회·집계 API가 있었다. 개발 단계의 **1만 건** 테스트 데이터에서는 지연이 드러나지 않았으나, 성능 검증을 위해 **100만 건 규모의 테스트 데이터**를 구성하자 같은 API 응답 시간이 **10분**까지 치솟아 사실상 타임아웃 상태가 됐다.
- **MyBatis `selectList` 순차 반복 호출로 인한 직렬 대기 누적**:
  - 부모 목록 1회 조회 후 `for`문을 돌며 하위 상세 `selectList` 쿼리를 건건이 순차 실행하는 구조가 청구·가입·집계 로직 전반에 반복되고 있었고, 대용량 조건에서 네트워크 왕복 및 DB I/O 대기 시간이 직렬로 누적됐다.

### 2. [기술적 의사결정 및 대안 비교]
- **낯선 DB 옵티마이저 힌트 시도 vs 통제 가능한 애플리케이션 병렬화**:
  - 이전 운영 경험이 Oracle 기반이어서 당시 MySQL의 실행계획과 옵티마이저 특성에 충분히 익숙하지 않았다. 제한된 일정 안에 10분짜리 지연을 해결해야 하는 상황에서, 익숙하지 않은 DB 힌트를 근거 없이 건드리기보다 **내가 동작 흐름을 명확히 통제할 수 있는 애플리케이션 계층 병렬 처리**를 먼저 선택했다.
- **`ServiceImpl` 단일화 후 병렬 스트림 적용**:
  - 소스 전역의 순차 조회·집계 루프에 Java `parallelStream`을 적용해 여러 DB 조회의 I/O 대기 시간을 병렬로 중첩시켰다.

### 3. [해결 과정 및 기술적 한계 복기 (Fail-Recovery & Reflection)]
- **병렬 스트림 적용 결과**:
  - `ServiceImpl`에서 상세 리스트 조회 및 집계 조립을 `parallelStream`으로 병렬 실행하도록 변경해, 동일한 100만 건 테스트 조건에서 응답 시간을 **약 10분 → 30초 이내(95% 단축)**로 줄였다.
- **[핵심 복기] 당시 해결의 기술적 한계와 지금 다시 푼다면**:
  - 작업을 마친 뒤 가장 크게 돌아본 점은 **`parallelStream`은 여러 DB 조회의 대기 시간(Latency)을 겹쳐 전체 응답 시간을 줄인 것일 뿐, 반복되는 총 SQL 실행 횟수 자체를 줄인 것이 아니다**라는 사실이다.
  - **남아 있던 구조적 위험 3가지**:
    1. **공용 스레드 풀 및 커넥션 풀 경합**: `parallelStream`은 JVM 전역의 `ForkJoinPool.commonPool()`을 공유하므로, 대량 조회 요청이 동시에 여러 건 들어오면 워커 스레드와 HikariCP DB 커넥션 풀을 급격히 점유해 다른 일반 API 요청까지 대기시킬 수 있다.
    2. **트랜잭션 경계 분리**: 스프링의 `@Transactional`은 `ThreadLocal` 기반이므로 `parallelStream`이 쪼갠 별도 워커 스레드에는 호출 스레드의 트랜잭션 컨텍스트가 전파되지 않는다.
    3. **실행계획 미확인**: 애플리케이션을 고치는 동시에 MySQL `EXPLAIN`으로 실제 SQL의 인덱스 접근 경로부터 함께 확인했어야 했다.
  - **지금 다시 설계한다면**: 루프 안에서 단건 `selectList`를 병렬로 호출하는 대신, 마스터 목록에서 ID 리스트를 추출해 **`WHERE billing_id IN (...)` 배치 쿼리로 하위 데이터를 단 1번(총 쿼리 2회)에 조회한 뒤 메모리에서 `Collectors.groupingBy`로 매핑**하는 집합 단위 조회 구조로 풀었을 것이다.

### 4. [정량적/정성적 성과 및 배운 점]
- **성과**: 동일 100만 건 테스트 데이터 기준 API 응답 시간 **95% 단축 (10분 → 30초 이내)**.
- **배운 점**: "성능 수치 개선이 곧 구조적 완성을 뜻하지는 않는다." 10분을 30초 이내로 줄인 성과와 별개로, 애플리케이션 병렬화가 DB I/O에서 갖는 한계를 정확히 직시하고 쿼리 횟수 자체를 줄이는 집합 사고로 넘어가는 계기가 됐다.

### 5. [면접관 예상 꼬리 질문 (2가지)]
1. **Q. `parallelStream`으로 10분을 30초 이내로 줄였다고 하셨는데, DB 조회에 `parallelStream`을 쓰면 커넥션 풀이나 스레드 풀에서 어떤 문제가 생길 수 있나요?**
   - **답변 포인트**: 당시에는 순차 DB 왕복 대기 시간을 병렬로 겹쳐 당장의 10분 타임아웃을 30초 이내로 줄였지만, 반복되는 SQL 실행 횟수는 그대로라는 한계가 있었습니다. 특히 `parallelStream`은 JVM 전역의 `ForkJoinPool.commonPool()`을 쓰기 때문에 동시 요청이 몰리면 공용 스레드와 HikariCP 커넥션을 한 요청이 독점해 다른 API들이 커넥션 획득 타임아웃에 빠질 수 있고, `ThreadLocal` 기반인 `@Transactional`도 워커 스레드로 전파되지 않습니다. 그래서 회고를 통해 이 한계를 명확히 정리했고, 근본 해법은 병렬 호출이 아니라 `WHERE billing_id IN (...)`으로 한 번에 조회한 뒤 메모리에서 `groupingBy`로 조립해 쿼리 수를 2회로 줄이는 것이라는 결론을 내렸습니다.
2. **Q. 만약 `WHERE IN (...)` 절로 바꿨을 때 부모 ID가 수만 건이면 `IN` 절 파라미터 제한이나 쿼리 크기 문제는 어떻게 해결할 수 있나요?**
   - **답변 포인트**: 먼저 화면 조회 API라면 한 번에 수만 건을 다 내려주기보다 페이지네이션(예: 페이지당 50~100건)을 적용해 `IN` 절에 들어가는 ID 개수를 페이지 크기로 제한하는 것이 우선입니다. 만약 전체 대량 추출처럼 수만 건을 반드시 한 번에 읽어야 하는 경우라면, ID 리스트를 1,000건 단위 청크(Chunk)로 잘라 Batch `IN` 조회를 수행하거나 검색 조건 자체를 서브쿼리/JOIN으로 넘겨 DB 옵티마이저가 집합 단위로 처리하게 설계합니다.

## Case 2. OAuth 인증·권한 조회 Redis 캐싱과 `TTL = 세션 만료 시간` 설계

- **원문**: [화면마다 권한을 DB에 묻던 시스템 — Redis 캐시와 "세션과 같은 TTL"](/blog/redis-permission-cache-ttl)

### 1. [문제 정의 및 배경]
같은 조회 화면이라도 사용자 권한에 따라 셀렉트 박스에 노출되는 코드 항목(자기 부서만 노출 vs 전체 노출 등)이 달랐다. 기존 구조는 화면이 열릴 때마다, 그리고 화면 안의 셀렉트 박스가 대여섯 개 그려질 때마다 `사용자-역할-권한-코드`를 잇는 무거운 조인 쿼리를 매번 DB에 날리고 있어 화면 전환 및 렌더링에 **최대 10초**가 걸렸다.

### 2. [기술적 의사결정 및 대안 비교]
- **캐시 도입 타당성 판단**:
  - 권한·허용 코드 데이터는 ① 모든 화면 렌더링마다 읽혀 **읽기 빈도가 압도적**이고, ② 관리자의 권한 변경은 하루에 몇 번 안 될 만큼 **변경이 희소**하며, ③ **한 로그인 세션 동안에는 일관성이 유지**되므로 캐시 도입 시 비용 대비 효과가 가장 큰 영역이었다.
- **로컬 캐시 vs Redis 분산 캐시**:
  - 다중 인스턴스 환경에서 로컬 캐시를 쓰면 관리자가 특정 사용자의 권한을 변경했을 때 서버 간 캐시 불일치가 발생할 수 있다. 권한은 보안과 직결되므로 단일 저장소에서 즉시 키를 무효화할 수 있는 **Redis**를 선택했다.
- **핵심 의사결정 — 왜 TTL을 '세션 만료 시간(30분)'과 일치시켰는가?**:
  - **TTL > 세션 타임아웃일 때**: 사용자가 로그아웃하고 관리자가 권한을 축소한 뒤 재로그인해도, Redis에 살아 있는 이전 캐시 때문에 **회수된 권한이 그대로 보이는 보안 사고**가 발생할 수 있다.
  - **TTL < 세션 타임아웃일 때**: 로그인해 업무를 보는 도중에 캐시가 먼저 증발해 다시 무거운 DB 조인이 실행된다.
  - **결론 (`TTL = 세션 타임아웃`)**: 캐시 수명을 세션 수명(30분)에 정렬함으로써 "한 세션 동안의 권한은 로그인 시점 기준으로 유지된다"는 시스템의 기존 암묵적 규칙을 명시적 캐시 정책으로 일치시켰다.

### 3. [해결 과정 및 트러블슈팅]
- **핀포인트 캐시 키 설계 (`userPermissions::{username}:{codeGroup}`)**:
  - `@Cacheable(value = "userPermissions", key = "#username + ':' + #codeGroup")`과 `GenericJackson2JsonRedisSerializer`, `entryTtl(Duration.ofMinutes(30))`을 설정했다.
- **경계 이벤트 무효화(Cache Eviction) 처리**:
  - TTL에만 의존하지 않고 두 가지 경계 이벤트를 명시적으로 처리했다.
  - **로그아웃 시**: 세션 무효화와 동시에 해당 사용자의 캐시 키를 즉시 삭제해 남은 TTL과 무관하게 캐시 수명을 종료시켰다.
  - **관리자의 권한 변경 시**: 전체 캐시를 날려(flush) 다른 사용자의 캐시 미스를 유발하는 대신, 변경 대상 사용자의 키만 정확히 타겟팅해 `@CacheEvict` 처리했다.

### 4. [정량적/정성적 성과 및 배운 점]
- **성과**: 로그인 후 첫 조회 이후 반복되던 권한 조인 쿼리가 **0건**이 됐고, DB 왕복이 Redis 메모리 조회(밀리초 미만)로 대체되면서 화면 전환 및 렌더링 응답 속도가 **10초 → 0.10초 이내**로 단축됐다.
- **배운 점**: 캐시 설계의 본질은 `@Cacheable` 어노테이션 한 줄을 붙이는 것이 아니라 **"캐시 수명(TTL)을 비즈니스상 어떤 수명 주기에 정렬할 것인가"**와 **"어떤 이벤트에서 누구의 키를 지울 것인가(Invalidation)"**를 정의하는 데 있다.

### 5. [면접관 예상 꼬리 질문 (3가지)]
1. **Q. 사용자가 29분 동안 활동해서 세션은 연장됐는데, 첫 조회 시점에 생성된 Redis 캐시는 30분이 지나 만료되면 어떻게 되나요?**
   - **답변 포인트**: 그 경우에는 30분 시점의 다음 화면 요청에서 Cache Miss가 1회 발생하고, `@Cacheable`에 의해 DB에서 최신 권한을 다시 조회해 30분 TTL로 재적재합니다. 보안상 낡은 권한이 남는 문제(TTL > 세션)는 로그아웃 시 즉시 Evict와 관리자 변경 시 Evict로 막았고, 활동 연장으로 인한 30분 단위의 1회 재조회는 DB 부하에 영향을 주지 않으면서 오히려 장기 세션의 권한 최신성을 보강해 주는 효과가 있습니다.
2. **Q. 만약 운영 중에 Redis 서버에 장애가 나거나 네트워크가 끊기면 모든 화면 진입이 막히지 않나요?**
   - **답변 포인트**: 맞습니다. 권한 조회가 모든 화면에 걸려 있기 때문에 Redis 장애가 곧 전체 서비스 장애(Single Point of Failure)로 번지면 안 됩니다. Spring Cache의 `CacheErrorHandler`를 구현해 Redis 조회/저장 중 타임아웃이나 연결 예외가 발생하면 예외를 던지는 대신 경고 로그만 남기고 원본 DB(MySQL)를 조회하도록 Fallback(Graceful Degradation) 구조를 갖추는 것이 안전합니다.
3. **Q. `GenericJackson2JsonRedisSerializer`를 사용했을 때의 장단점은 무엇인가요?**
   - **답변 포인트**: 자바 기본 직렬화(`JdkSerializationRedisSerializer`)와 달리 Redis CLI에서 데이터를 사람이 읽을 수 있는 JSON 형태로 바로 확인할 수 있어 디버깅이 쉽고 `Serializable` 구현 강제도 없습니다. 다만 JSON 안에 `@class` 타입 패키지 경로가 함께 저장되기 때문에, 향후 패키지 경로나 클래스명을 리팩토링하면 기존 캐시 역직렬화 시 `ClassNotFoundException`이 날 수 있다는 점을 유의해야 합니다.

## Case 3. 4인 백엔드 팀 코드 리팩토링과 PDF 컨벤션 표준화

- **원문**: [4인 백엔드 팀의 제각각이던 selectList 코드 — 사원급에서 PDF 컨벤션을 만들어 표준화하기까지](/blog/backend-code-convention-standardization)

### 1. [문제 정의 및 배경]
백엔드 4명 중 소속 정규직은 사원급이던 나 한 명이었고, 나머지 구성원은 외부 파견 프리랜서 개발자분들과 기존 레거시 운영 위주로 업무를 해오던 선임 인력이었다. 함께 중심을 잡던 팀장님은 PM 역할까지 대행하시느라 대외 일정 조율에 여력이 없었고, 프로젝트 종료 후에도 시스템을 운영해야 할 내부 인력으로서 백엔드 실무 단에서는 사실상 PL 성격의 기술 기준 수립 책임이 내게 분담되어 있었다. 당시 합의된 코드 컨벤션이 없어 단순한 단일 `selectList` 조회 API조차 컨트롤러의 `DAO` 직호출 여부, `List<자료형>`에 담기는 단일 만능 VO 공용 사용 여부, `new` + `setter` 나열 방식이 작성자마다 모두 달랐고, Swagger 명세 혼선과 중복 보일러플레이트 코드가 계속 누적됐다.

### 2. [해결 과정 — 레퍼런스 코드 검증 후 PDF 가이드 주도 공유]
- **먼저 동작하는 레퍼런스 코드 구현**: 연차가 높은 프리랜서·선임 동료분들께 구두로만 규칙을 요청하면 부담이 될 수 있어, 담당 도메인 API를 먼저 `Controller → Service → ServiceImpl → DAO` 계층과 기능별 `Request / Response DTO` 및 `Model` 분리, `@Builder` 패턴, `@Valid` 검증 구조로 리팩토링해 효과를 증명했다.
- **PDF 가이드 문서화 및 상호 보완을 통한 팀 표준 완성**: 신규 패턴이 낯선 동료도 바로 따라 쓸 수 있도록 패키지 구조, 네이밍, 단일 `selectList`·등록·수정 Before/After 템플릿을 **PDF 파일**로 정리해 팀 회의에서 공유했다. 이 과정에서 사원급이던 내게 부족했던 기술적 디테일이나 예외 케이스는 경험 많은 고년차 프리랜서 개발자분들께서 조언과 가이드를 보태주셔서 다 함께 완성도 높은 팀 표준을 만들어낼 수 있었다.

### 3. [성과 및 면접관 예상 꼬리 질문]
- **성과**: 4인 백엔드 코드 구조 일원화로 객체 생성 중복 제거 및 유지보수성·프론트엔드 협업 효율 향상, 외부/교차 인력 온보딩 및 적응 시간 단축(정량적 정적 분석 지표를 전후 좌표로 측정해 두지 못한 점은 이후 회고 과제로 복기).
- **Q. 연차가 높은 외부 프리랜서나 선임 개발자분들께 사원급으로서 새 컨벤션을 도입할 때 어떻게 설득하고 협업하셨나요?**
  - **답변 포인트**: "기존 방식이 틀렸다"고 접근하기보다 "배경이 다른 4명이 서로의 코드를 5분 안에 읽고 교차 수정할 수 있게 틀을 맞추자"는 협업 관점으로 접근했습니다. 먼저 실제 모듈을 `Request/Response DTO · Model · @Builder` 구조로 리팩토링해 `setter` 중복 제거와 Swagger 자동 명세화 효과를 결과물로 보여드리고 바로 복사해 쓸 수 있는 PDF 예제 가이드를 준비해 전환 장벽을 낮췄으며, 사원급인 제게 부족했던 실무 예외 처리나 기술적인 부분들은 고년차 프리랜서 분들께 적극적으로 자문을 구하고 가이드를 반영하면서 팀 전원 합작의 표준으로 정착시킬 수 있었습니다.

## 기본기를 다지기 위한 사이드 프로젝트 아이디어 (이 프로젝트 기반)

### Idea 1. 반복 조회 vs 집합 조회(`IN` 절) 벤치마크 & HikariCP 커넥션 풀 프로파일러
- **목적**: 블로그 회고에서 남긴 *"지금 다시 한다면 집합 조회로 풀었을 것이다"*를 실제 코드와 부하 테스트 수치로 증명하기.
- **구현 내용**: 대용량 데이터 환경에서 ① 순차 `selectList` 반복 호출 ② `parallelStream` 병렬 호출 ③ 커스텀 `ThreadPoolExecutor` + `CompletableFuture` ④ `WHERE billing_id IN (...)` + `Collectors.groupingBy` 4가지를 구현하고, 동시 요청 50명일 때 `parallelStream`의 커넥션 풀 경합 현상과 `IN` 절 집합 조회의 안정성을 수치로 비교.

### Idea 2. 탄력적(Resilient) 2-Tier 권한 캐시 & Cache Fallback 모듈
- **목적**: 단순 `@Cacheable`을 넘어 **L1/L2 캐시 동기화와 Redis 장애 시 자동 DB 우회(Fallback)**까지 갖춘 권한 모듈 구현.
- **구현 내용**: Caffeine(L1) + Redis(L2) 구조에 권한 변경 시 Redis Pub/Sub으로 전 서버 L1 캐시를 즉시 무효화하고, `CacheErrorHandler`를 통해 Redis 컨테이너를 강제 중지(`docker pause`)했을 때 에러 없이 MySQL 원본 조회로 자동 전환되는지 통합 테스트로 검증.

### Idea 3. `ArchUnit` 기반 아키텍처 컨벤션 자동 검증 테스트
- **목적**: 팀에 PDF 문서로 공유했던 계층 분리와 `Request/Response DTO · Model` 분리 규칙을 **CI 빌드 테스트 코드로 자동 강제**하기.
- **구현 내용**: JUnit + `ArchUnit`으로 *"Controller는 DAO를 직접 참조할 수 없다"*, *"Controller의 public 메서드는 DB 영속 계층의 `Model`을 외부로 직접 반환할 수 없고 오직 `DTO`만 반환해야 한다"* 규칙을 코드화해 위반 시 테스트가 실패하도록 구성.
