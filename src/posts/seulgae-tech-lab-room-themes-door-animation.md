연구소의 방은 서로 다른 일을 하는 공간인데도 비슷한 바닥과 가구로 보였다. PR #21의 `8c34fa9`에서는 로비의 대리석과 카펫, 개발 연구실의 네온, 서버실의 냉각 통로, 회의실의 원목 분위기를 나눴다. 중요한 제약은 이미 서버와 공유하는 가구 위치와 충돌 크기를 유지하는 것이었다.

## 테마를 바꿔도 세계의 규칙은 유지하기

그림을 예쁘게 바꾸면서 책상의 실제 충돌 영역까지 움직이면 서버와 화면이 서로 다른 공간을 보게 된다. 같은 크기의 텍스처로 외형을 교체하고 바닥 배치와 팔레트는 Phaser에 의존하지 않는 데이터로 분리했다.

현재 `frontend/src/game/rooms/roomThemes.ts`의 로비 바닥 규칙이다.

```ts
    if (roomId === 'lobby') {
      // 정문(아래 중앙)에서 안내 데스크까지 이어지는 레드 카펫과 체크 대리석
      if (column >= 11 && column <= 13 && row >= 7) return 2
      return (row + column) % 2
    }
```

`roomAssets.ts`는 정수 좌표의 `fillRect`로 텍스처를 만든다. 바닥 배열은 무엇을 놓을지, 에셋 생성기는 어떻게 그릴지를 맡는다. React 페이지에는 방의 색을 CSS 변수로 전달했다. 캔버스와 바깥 UI가 같은 분위기를 쓰면서도 서로의 렌더링 코드를 알 필요는 없었다.

## 이동 승인과 문 열림은 다른 시간선이다

네트워크 응답이 빠르면 문이 열리기도 전에 다음 방으로 바뀔 수 있다. 요청과 동시에 문을 열고, 승인을 받아도 최소 열림 시간을 채운 뒤 페이드하도록 했다. 현재 `frontend/src/game/rooms/DoorAnimator.ts`의 시간 계산이다.

```ts
  remainingOpenMs() { return Math.max(0, this.openUntil - this.scene.time.now) }
```

Scene은 이 남은 시간을 기다린다. 문짝은 경첩을 기준으로 `scaleX`를 줄이고 문틈에는 목적지의 조명색을 비춘다. 이동이 거절되면 문을 다시 닫는다. 승인 여부와 애니메이션 완료를 하나의 불리언으로 섞지 않는 것이 핵심이었다.

## 이벤트의 규칙은 화면 밖에서 검사하기

빌드 결과와 과열 경보는 실제 CI나 서버 장애를 반영하는 기능이 아니라 각 브라우저 안의 연출이다. 현재 `frontend/src/game/rooms/roomEventLogic.ts`의 경보 시작 규칙은 다음과 같다.

```ts
  trigger(now: number, rack: string) {
    if (this.state.active) return false
    this.state = { active: true, rack, startedAt: now }
    return true
  }
```

이미 켜진 경보를 중복 시작하지 않고 수동 냉각과 자동 종료를 상태 기계로 처리했다. RoomFx는 이 결과를 조명·문구로 표현한다. 이후 추가된 간식과 낚시 등은 이번 분위기 변경과 구분해서 읽어야 한다.

## 멈춤처럼 보이는 장면을 해석하기

기록에는 승인 직후 캡처한 화면이 이전 방이어서 이동 실패처럼 보인 일이 남아 있다. 실제로는 문 열림 280ms와 페이드 연출을 기다리는 구간이었다. 숨겨진 브라우저의 프레임 갱신이 멈추는 문제도 있어 시간 규칙은 순수 TypeScript 테스트로 확인했다.

문서에는 텍스처 크기 일치와 경보의 중복·해제 검증이 기록돼 있다. 이번 글에서는 재실행하지 않았고 운영에서의 시각적 결과는 **확인하지 못함**이다.

## 배운 점

외형 변경에서도 서버와 공유하는 좌표 계약을 먼저 지켜야 했다.
승인 완료와 연출 완료를 분리해야 짧은 응답에도 문이 자연스럽게 열렸다.
시간과 상태 규칙을 분리하면 화면이 멈춘 환경에서도 검증할 수 있었다.
