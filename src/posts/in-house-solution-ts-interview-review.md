2026년 11월 23일 자사 솔루션 TS 직무 1차 면접을 마친 뒤 질문과 답변을 정리했다. 면접에서 말한 내용은 기억을 바탕으로 요약했으며, 평가와 개선 답변, 사후 학습은 구분했다. 확인되지 않은 내용은 추가 확인이 필요하다.

## 1. 1차 면접 개요: 실제로 무엇을 평가했나

**큰 흐름:** 자기소개 → TS 업무 이해 및 SI·SM 경력 확인 → 고객 대응 적합성 → 학력·경력 및 이직 사유 → Java/DB/성능 개선 기술 검증 → AI 활용 → 프레임워크/Java 버전/OS 지식 → 역질문. 이후 순서는 녹음을 들으며 확인한다.

**핵심 발견:** 준비했던 'GW 연동 오류 93%'와 '알림톡 민원 30%'는 **자기소개에서 언급되었으나**, 면접에서는 그 구현을 깊게 묻지 않았다. 대신 **데이터 조회 성능 약 48배 개선, `parallelStream`, SQL 튜닝, 운영 중 성능 문제 대처, Java 버전과 Linux 배포판**을 상세히 물었다.

**TS팀에 관해 면접관이 설명한 내용([면접 복기]):**
- 고객사 약 **130곳**에 설치되어 운영 중인 자사 솔루션을 지원한다는 설명.
- 고객사 장애 대응, 기술지원, 정기점검, 유선·이메일·현장 방문 등 **고객 접점 커뮤니케이션**이 중요.
- 외근이 많은 직무라고 설명했다.
- 장기간 파견하는 SI 형태라기보다 고객사에 필요할 때 방문하는 방식.
- 고객사별 주 담당자를 두되, 문제 해결이 어렵다면 **파트장 및 파트 내 팀원**의 도움을 받을 수 있음.
- 기술지원·트러블슈팅이 중심이고 **신규 개발 비중은 상대적으로 적다**는 취지.
- 서울 밖 고객사 출장 가능; 자차 필수는 아니며 교통비 지원.
- '6개월 수습'에 대한 면접관의 설명은 **계약직 후 전환에 가까운 것으로 알고 있다는 비확정 답변**. **인사팀에 서면 확인 필요**.

> **직무 선택 관점 메모:** 이 직무는 Java 백엔드 신규 기능 개발 중심의 커리어를 원할 때와 솔루션 기술지원·장애 대응 역량을 쌓을 때 각각 장단점이 다르다. 실제 배정 고객, 개발 참여 범위, 야간/주말 장애, 출장 빈도 및 처우는 별도 확인해야 한다.

## 2. 실제 면접 질문·지원자 답변·피드백 (시간순)

### Q01. 자기소개해 주세요.

**[면접 복기 | 면접관]** 자기소개를 요청.

**[면접 복기 | 내 답변]** TS 지원 인사 → 원천·응용 간 데이터 불일치로 인한 연동 오류를 일일 집계·파트별 보고 체계로 **주간 약 93% 감소에 기여** → 전세사기 피해자 심사 지연 관련 알림톡 자동 발송으로 민원 문의 **약 30% 감소** → 자사 메시징 솔루션 사업에 도움이 되고 싶다고 설명.

**[평가]** 성과가 수치로 드러나고 직무 연결도 있다. 다만 마지막 지원 동기 문장을 더 간결하고 선명하게 끝낼 수 있다.

**[개선 답변 예시]**
> 안녕하세요. TS 직무에 지원한 ○○○입니다. 저는 통신사 시스템에서 연동 오류를 원인별로 분석하고, 담당 파트와 일일 보고·후속 검증 체계를 마련해 주간 오류를 약 93% 줄이는 데 기여했습니다. 공공 시스템에서는 메시징 솔루션을 활용한 알림톡 자동 발송 기능을 구현해 민원 문의를 약 30% 줄인 경험도 있습니다. 이러한 장애 분석과 협업 경험을 바탕으로 고객사 솔루션의 안정적인 운영에 기여하겠습니다. 감사합니다.

**[복습 질문]** '93%'가 전체 시스템 장애 감소인가, 특정 기준의 주간 연동 오류 건수인가? 수치를 설명할 때 지표 정의도 말할 수 있는가?

### Q02. 우리 팀 업무를 알고 지원했습니까?

**[녹음 확인 | 면접관]** 자기소개 다음으로 팀 업무를 알고 지원했는지 물었다. 이어 경력이 SI 위주인 것 같다고 이야기했고, TS는 솔루션 장애를 지원하며 외근이 많은 직무라고 설명했다.

**[녹음 확인 | 내 답변]** SI뿐 아니라 SM 업무도 병행했다고 답했다.

**[기존 기억 | 추가 확인 필요]** 과거 공고를 조사한 내용과 파견 근무 여부를 되물었던 시점은 녹음으로 더 확인한다.

**[내 추측]** 지원자가 TS 업무를 기존 개발·유지보수 업무와 비슷하게 이해하고 지원했는지 확인하려는 질문이었을 수 있다. 나 역시 처음에는 그렇게 생각했다. 면접관의 실제 의도나 다른 지원자들의 상황은 확인되지 않았다.

**[평가]** 지원 전 조사한 흔적은 있다. 다만 고정 파견/일회성 방문, 개발/지원 비중 등 핵심 업무 형태를 입사 전에 더 구체적으로 알아볼 필요가 있었다.

**[다음 면접의 대답]**
> TS는 고객사에 설치된 자사 솔루션의 장애 원인을 분석하고, 안정적으로 운영되도록 기술지원·점검을 수행하는 업무로 이해하고 있습니다. 과거 연동 오류를 분석하고 여러 운영 파트와 해결한 경험이 있어, 기술적 문제를 상대방이 이해할 수 있게 전달하는 역량을 활용할 수 있다고 생각합니다.

### Q03. 고객 접점 소통이 많은 업무인데 잘 맞습니까?

**[녹음 확인 | 내 답변]** 주된 경험 중 하나인 파트별 보고 체계는 약 **20명의 실무 담당자와 소통하며 만든 성과**이므로, 사람들과 소통하고 관계를 맺는 업무에도 적응하는 데 문제가 없을 것 같다고 답했다.

**[평가]** 좋았던 부분. 막연한 친화력 강조가 아니라 **역할·규모·성과**를 연결했다.

**[더 나은 답변]**
> 네. 고객 대응은 단순히 친절하게 설명하는 것뿐 아니라, 기술적 원인을 업무 담당자가 실행할 수 있는 조치로 바꾸는 과정이라고 생각합니다. 저는 GW 연동 오류를 분석해 약 20명의 운영 담당자에게 파트별 조치 내용을 안내하고, 처리 결과를 재확인하는 체계를 운영했습니다. 고객사 장애에서도 영향도를 먼저 확인하고 기술 분석·진행 상황 공유·해결 확인까지 책임 있게 대응하겠습니다.

### Q04. 사이버대학교에 진학한 이유가 있나요?

**[녹음 확인 | 내 답변]** 특성화고등학교를 졸업한 뒤 일찍 취업하는 것이 목표였고, 컴퓨터 AS 엔지니어로 취업해 유지보수 업무를 맡았다고 설명했다. 해당 경력은 이력서에 기재하지 않았으며, 학사 학위를 취득하기 위해 일을 하면서 사이버대학교를 병행했다고 답했다.

**[당시 생각을 돌아보며]** 정규 대학에 진학하지 않은 이유에 대한 질문에도 답하려고 배경부터 설명하다 보니 답변이 길어진 것 같다. 정규 대학을 선택하지 않은 이유를 면접관이 실제로 물었는지는 추가 확인이 필요하다.

**[평가]** 학업·경력 선택의 맥락이 자연스럽다. TS 직무에서는 초기 AS 경험도 **현장 고객 응대 역량**으로 연결할 수 있다.

**[개선 답변]**
> 특성화고등학교를 졸업한 뒤 기술 업무는 현장에서 직접 경험하며 더 빨리 배울 수 있다고 생각해 먼저 취업했습니다. 컴퓨터 AS 엔지니어로 유지보수 업무를 하면서 실무 경험을 쌓았고, 그 과정에서 전공 지식도 체계적으로 배울 필요성을 느꼈습니다. 그래서 일을 계속하면서 사이버대학교에 진학해 학사 학위를 취득했습니다.

### Q05. 이직이 잦고 재직 기간이 짧은 이유는? 협업에서 어떤 문제가 있었습니까?

**[면접 복기 | 내 답변]** 파트를 혼자 담당하는 경험이 많았고, 단독 문제 해결 능력은 얻었지만 동료와 함께 기술적 의사결정과 성장을 할 기회가 적었다. 팀원들과 프로젝트를 협업했던 약 4개월의 SI 경험은 성장 체감이 컸고, 앞으로는 협업 환경에서 일하고 싶다는 취지. 면접관은 '선임에게 질문했는데 잘 답변받지 못한 것인가' 등으로 구체화함.

**[평가]** 진솔함은 강점. 다만 **'혼자 맡는 업무가 싫다/누가 도와줘야 한다'**는 인상으로 해석되지 않도록 주의. TS도 고객별 담당자가 책임지고 해결하는 일이 많다.

**[개선 답변]**
> 이전 직장에서는 한 파트를 주도적으로 맡아 장애 분석과 업무 조율을 수행하면서 독립적인 문제 해결 능력을 키웠습니다. 다만 복잡한 이슈일수록 기술적인 관점을 공유하고 서로 검토하는 환경이 더 좋은 해결책을 만드는 데 도움이 된다는 점도 느꼈습니다. 앞으로는 맡은 고객사 문제에 책임감을 갖되, 필요할 때 동료와 효과적으로 협업하는 조직에서 더 성장하고 싶어 지원했습니다.

**[추가 복습]** '도움 요청'과 '책임 회피'의 차이를 구분해 말하기: **본인이 원인과 영향부터 파악 → 시도와 근거 정리 → 적절한 시점에 에스컬레이션 → 해결 여부 검증.**

### Q06. 주로 사용한 언어는?

**[면접 복기 | 내 답변]** Java가 주요 언어. 정보처리기사 준비 과정에서 C와 Python도 조금 접했다.

**[평가]** 무난. 주력 언어에서 실제 자신 있는 기술 영역까지 하나 덧붙이면 좋다.

**[개선 답변]**
> 주력 언어는 Java입니다. Spring 기반으로 업무 로직과 API를 개발했고, 데이터 접근에는 주로 MyBatis를 사용했습니다. Oracle, MySQL, CUBRID 환경에서 SQL을 작성하고 조회 성능을 개선한 경험이 있습니다. 또 Redis로 권한 조회 결과를 캐싱하고 Kafka 기반 연동 시스템의 오류를 분석·운영했습니다.

다른 언어에 관한 질문이 이어지면 C와 Python은 정보처리기사 준비 과정에서 기초적으로 접한 수준이라고 설명한다.

### Q07. 데이터 조회 응답시간 약 48배 개선은 어떻게 했습니까?

**[면접 복기 | 내 답변]** 기존 프로젝트 고도화 과정에서 10만 건 테스트에서는 지연이 크게 보이지 않았으나 100만 건 수준 데이터에서는 API 성능이 떨어짐. Oracle의 `PARALLEL` 힌트에 대한 인식을 바탕으로 DB 병렬화 방법을 떠올렸으나 당시 사용 DB에서 적용법을 잘 몰랐음. Java **`parallelStream`**을 검색해 Service/비즈니스 계층의 로직에 적용했으며, 데이터를 분할·병렬 처리하면 빨라진다고 설명. 면접관은 개선 전 AS-IS와 개선 후 TO-BE 구조가 각각 어떻게 되어 있었는지 물었다.

**[평가 — 가장 큰 기술 리스크]**
- **DB 쿼리 자체를 병렬 수행한 것인지**, **쿼리 결과를 받은 후 Java 메모리에서 후처리만 병렬화한 것인지** 설명이 섞여 있다.
- `parallelStream()`은 **원칙적으로 Java Stream 요소의 연산을 병렬화**한다. 자동으로 DB 쿼리를 여러 개의 병렬 쿼리로 바꿔주는 기능이 아니다.
- `parallelStream` 내부에서 DB 쿼리를 실행했다면 **스레드 안전성, DB 커넥션 풀, 트랜잭션 경계, DB 부하**를 확인해야 하며, 무조건 개선된다고 할 수 없다.
- 원본 로직과 병렬화한 정확한 단위는 추가 확인이 필요하다. **없는 구조를 만들어 답하면 안 된다.**

**[저자 확인 | 측정 방법]** 필터에 처리 시간을 측정하는 로직을 작성하고, Swagger에서 API를 호출해 JSON 응답과 측정 시간을 확인하며 개선 전후 속도를 비교했다. 필터가 측정한 구간의 정확한 시작·종료 위치와 응답에 측정 시간이 표시된 방식은 원본 코드로 확인한다.

**[공부: 구분해야 할 구조]**

```text
A. DB 병렬 쿼리  : 하나의 SQL을 DB 엔진이 내부적으로 병렬 실행
B. SQL 여러 번   : 서비스가 여러 SQL을 분할 호출 (제한된 동시성 필요)
C. Java 후처리   : SQL 결과를 수신한 뒤 CPU 작업을 parallelStream()으로 병렬 실행
```

**[관련 글 기반 복기 | AS-IS와 TO-BE]**

| 구분 | 처리 흐름 | 응답 지연과의 관계 |
| --- | --- | --- |
| AS-IS | MyBatis로 가입·청구 목록을 조회한 뒤 각 항목의 상세 정보를 `selectList`로 순차 조회하고 결과를 조립했다. | 앞선 상세 조회가 끝난 뒤 다음 조회를 시작해 DB I/O 대기 시간이 누적됐다. |
| TO-BE | 서비스 계층에서 목록 항목을 `parallelStream()`으로 처리하며 각 항목의 상세 조회와 결과 조립을 수행했다. | 여러 조회의 대기 시간이 겹쳐 전체 응답 시간이 줄었다. 건별 SQL 호출 횟수 자체는 그대로였다. |

위 구조는 [병렬 조회 개선 회고](/blog/mybatis-builder-parallel-refactoring)의 설명과 예시 코드를 바탕으로 했다. 예시는 이해를 돕는 구조이므로 실제 병렬화 단위와 세션 처리는 원본 코드로 확인한다.

**[개선 답변 예시]**

> 기존에는 가입이나 청구 목록을 조회한 뒤 각 항목의 상세 정보를 순차적으로 조회해 결과를 조립했습니다. 앞선 조회가 끝나야 다음 조회를 시작하다 보니 데이터 규모가 커졌을 때 DB 응답을 기다리는 시간이 계속 누적되는 병목이 있었습니다.
>
> 이 대기 시간을 줄이기 위해 각 항목의 상세 조회와 결과 조립을 여러 작업이 동시에 진행할 수 있는 구조로 바꿨습니다. 서비스 계층에서 Java `parallelStream`을 사용해 항목별 작업을 병렬 처리했습니다. 필터에 작성한 처리 시간 측정 로직과 Swagger 호출로 전후를 비교한 결과, DB 전체 테스트 데이터가 100만 건인 환경에서 API 응답 시간이 약 480,000ms에서 10,000ms 이내로 줄었습니다.
>
> 이 방법은 SQL 호출 횟수를 줄인 것은 아니므로, 다시 개선한다면 연관 데이터를 집합으로 조회하는 방안과 실행 계획을 함께 검토하겠습니다. 병렬 조회 시 DB 커넥션과 부하, 트랜잭션 범위도 확인해야 합니다.

**[확인 필요 — 집에서 원본 코드로 검증]**
1. DB에서 먼저 모든 데이터를 읽었는가, 아니면 각 스트림 요소가 DB를 조회했는가?
2. `parallelStream()`에 전달한 리스트의 각 요소는 무엇인가? (고객, 날짜, 키, 요청, 결과 데이터 등)
3. 병렬화된 작업이 CPU 연산인지, I/O(쿼리/API 호출)인지?
4. 트랜잭션과 JDBC/MyBatis 세션은 스레드마다 어떻게 관리되었는가?
5. 필터의 측정 시작·종료 지점과 JSON 응답에서 측정 시간을 확인한 방식, 동시 요청 수와 반복 측정 조건은?

### Q08. 다른 성능 개선 방법은 검토했습니까?

**[면접 복기 | 내 답변]** 일정이 촉박했고, 여러 사람에게 질문한 뒤 가장 부담이 적게 적용할 수 있다고 판단한 방식을 선택.

**[평가]** 의사결정의 맥락은 있으나 '다른 대안'을 구체적으로 비교하지 못했다.

**[공부: 일반적인 대안 — 당시 검토했다고 주장하면 안 됨]**
- `EXPLAIN`/실행 계획으로 병목 지점 식별.
- 불필요한 데이터 조회 축소, 조건절 개선, 필요한 컬럼만 선택, 페이지네이션.
- 인덱스 적합성 점검, 쿼리 재작성, N+1 문제 여부 확인.
- 애플리케이션 병목이면 데이터 구조/알고리즘 최적화, 캐시 적합성 검토.
- 병렬화는 **측정 후** 선택하고 과도한 동시성을 피함.

**[대안 정리 — 추가 질문에 답할 때]**

| 접근 방법 | 확인하거나 바꿀 내용 | 사례와의 관계 |
| --- | --- | --- |
| DB 실행 계획·인덱스 | MySQL 실행 계획에서 접근 경로를 확인하고 조회 조건과 인덱스의 적합성을 살핀다. | 당시 Oracle 병렬 힌트를 떠올렸지만 MySQL에서 적용 방법을 잘 몰랐다. MySQL 실행 계획을 분석·비교했는지는 확인되지 않았다. |
| 집합 단위 조회 | 목록의 키를 모아 상세 데이터를 함께 조회한 뒤 키별로 조립해 반복 호출을 줄인다. 데이터 크기에 따라 나눠 조회할 수 있다. | 기존 회고에서 나중에 제시한 개선안이다. 당시 실제로 적용하거나 성능 비교한 기록은 없다. |
| 조회 범위 조정 | 필요한 컬럼과 조건, 페이지 단위를 검토해 읽고 반환할 데이터 양을 줄인다. | 이후 검토할 수 있는 대안이다. 업무상 전체 결과가 필요한지 먼저 확인한다. |
| 애플리케이션 병렬 처리 | 항목별 상세 조회와 조립을 동시에 수행해 대기 시간을 겹친다. | 당시 팀원들과 공유한 뒤 적용한 방식이다. 호출 횟수는 유지되므로 커넥션 풀, DB 부하와 트랜잭션 범위를 살펴야 한다. |

**[추가 질문에 대한 답변 예시]**

> 당시에는 이전에 경험했던 Oracle의 병렬 처리도 떠올렸지만, 프로젝트에서 사용한 MySQL의 적용 방법은 충분히 알지 못했습니다. 그래서 제가 적용할 수 있는 Java 병렬 처리 방안을 재택근무 중인 팀원들과 공유하고 긍정적인 의견을 받아 적용했습니다. 지금 다시 살펴보면 반복되는 상세 조회를 묶어 SQL 호출 횟수 자체를 줄이는 방법과 실행 계획·인덱스 점검도 검토하겠습니다. 실제 데이터 양과 결과가 동일한지 확인하면서 응답 시간과 DB 부하를 비교해 선택하겠습니다.

**[개선 답변 예시 1 — 적용한 방법을 중심으로]**

> 성능 개선 방법에는 SQL 실행 계획과 인덱스를 살펴보거나, 반복 조회를 묶어 호출 횟수를 줄이는 방법, 애플리케이션에서 독립적인 작업을 병렬화하는 방법이 있습니다. 당시에는 MySQL의 튜닝 방법에 익숙하지 않았고 Java에서 적용할 수 있는 방법을 찾아 `parallelStream`을 사용했습니다. 필터에 처리 시간 측정 로직을 작성하고 Swagger에서 API를 호출해 JSON 응답과 측정 시간을 비교했습니다. DB 전체 테스트 데이터가 100만 건인 환경에서 API 응답 완료까지 약 480,000ms에서 10,000ms 이내로 개선됐습니다. 지금은 병렬화와 함께 반복 조회 자체를 줄일 수 있는지도 확인하겠습니다.

**[개선 답변 예시 2 — 원인과 선택을 함께 설명]**

> 가입·청구 목록을 조회한 뒤 항목별 상세 정보를 반복해서 조회하는 구조에서 데이터 규모가 커지자 응답이 지연됐습니다. 조회 성능을 개선하려면 실행 계획과 인덱스를 점검하거나 상세 조회를 묶는 방법, 독립적인 조회 작업을 병렬 처리하는 방법을 생각할 수 있습니다. 저는 당시 Java의 `parallelStream`을 적용해 응답을 개선했습니다. 이후에는 DB 호출 횟수와 부하까지 함께 측정해 더 적합한 구조인지 판단하겠습니다.

**[개선 답변 예시 3 — TS 직무에서 장애 대응 관점으로]**

> 우선 API와 DB의 처리 시간을 확인해 지연 구간을 좁히겠습니다. SQL 병목이라면 실행 계획과 인덱스를 확인하고, 반복 조회가 많다면 필요한 데이터만 조회하거나 연관 데이터를 묶어 가져오는 방안을 검토하겠습니다. 과거에는 Java `parallelStream`으로 연관 조회를 병렬 처리해 응답 시간을 줄인 경험이 있습니다. 병렬 처리 시에는 DB 커넥션과 부하도 살펴보겠습니다.

**[표현할 때 구분할 점]** 위의 SQL·인덱스·집합 조회는 설명을 위한 대안과 이후 검토 방향이다. 당시 실제로 각 대안을 비교·검증했는지는 확인되지 않았다. 원래 글에는 반복 상세 조회와 병렬 처리 구조가 기록되어 있지만, 면접에서 정확한 병렬화 단위를 설명하기 전에 원본 코드도 확인한다. 100만 건은 DB 전체 테스트 데이터 규모이며 API 한 번에 반환한 건수가 아니다. 당시 동시 요청 수와 반복 측정 조건도 확인이 필요하다.

### Q09. 슬로우 쿼리·인덱스 튜닝은 어떻게 했습니까?

**[면접 복기 | 내 답변]** CUBRID Manager에서 쿼리 실행 계획을 확인해 Full Scan 및 인덱스 미사용 구간을 살펴봤고, AI 도구로 도움을 받아 인덱스 추가 또는 조건 정리 등을 적용했다고 설명. DBA 전문가는 아니라는 점도 언급.

**[평가]** 도구와 접근 경로는 설명했으나 **어떤 조건·인덱스가 왜 효과가 있었는지** 근거가 부족했다.

**[공부: 실행 계획 핵심]**
- **Table/Full Scan**: 테이블 범위 전체를 읽는 방식. 데이터 크기·선택도·테이블 크기에 따라 오히려 적절할 수도 있다.
- **Index Scan**: 인덱스로 후보 행을 탐색. 항상 Full Scan보다 빠르지는 않다.
- **선택도**: 조건으로 걸러지는 행의 비율. 복합 인덱스의 선두 컬럼 및 조건 패턴이 중요.
- **검증**: 실행 계획 변화뿐 아니라 실제 응답시간, 읽은 행 수, 부하 등을 가능한 동일한 조건에서 비교.

**[실전 설명 구조]**
> 문제가 된 SQL의 실행 계획을 확인했더니 [구체적 테이블/조건]에서 [병목]이 확인됐습니다. 그래서 [인덱스 또는 SQL 변경]을 적용했고, 변경 후 실행 계획과 처리 시간을 비교해 효과를 확인했습니다. AI 도구는 가설을 찾는 보조 수단으로 사용했고 최종 적용 여부는 제가 검증했습니다.

### Q10. 튜닝을 해도 느리면? 운영 서비스라면 어떻게 대응?

**[녹음 확인 | 내 답변]** 개선 후에도 원하는 성과가 나오지 않으면 테이블을 쪼개 데이터를 분산해 처리하는 방법을 이야기했다. 면접관이 운영 상황에서는 어떻게 할지 다시 묻자, 상급자를 찾아가 물어보겠다고 답했다.

**[평가]** 테이블 분할은 데이터 규모와 접근 패턴에 따라 검토할 수 있는 대안이다. 운영 환경에서는 현재 병목과 분할 방식, 데이터 이관·호환성·서비스 영향 등을 먼저 확인해야 한다. 상급자에게 도움을 요청하는 것도 적절하며, 요청 전에 영향도와 측정 결과, 이미 시도한 조치를 정리해 전달하면 본인의 대응 과정이 더 분명해진다.

**[공부: 운영 장애 대응의 기본 흐름]**
1. 영향 범위 파악: 어떤 고객/기능/시간대, 오류율·지연시간, 최근 배포/데이터 증가.
2. 안전 확보: 롤백 가능한지, 임시 우회 가능한지, 리소스 고갈 위험이 있는지.
3. 증거 수집: 앱 로그·APM·DB 실행 계획·락/커넥션·CPU/메모리.
4. 원인별 대응: SQL/인덱스/애플리케이션 로직/동시성/인프라를 구분.
5. 관련자 공유·에스컬레이션: 이미 확인한 사실, 재현 조건, 영향도, 시도한 조치와 위험을 묶어서 전달.
6. 조치 후 회귀 확인 및 재발 방지 기록.

**[다음 면접 답변]**
> 먼저 목표 응답 시간과 실제 측정 조건을 확인하고, DB 조회와 애플리케이션 처리 중 어느 구간에 시간이 남아 있는지 다시 측정하겠습니다. 병렬 처리 후에도 상세 조회가 반복된다면 연관 데이터를 묶어 조회해 호출 횟수를 줄이는 방안을 검토하겠습니다. 실행 계획과 인덱스도 확인하고, 병렬 요청이 커넥션 풀이나 DB에 부하를 주는지도 살펴보겠습니다.
>
> 운영 중인 서비스라면 고객 영향도를 먼저 확인하고, 필요하면 안정적으로 적용할 수 있는 임시 조치도 검토하겠습니다. 원인을 바로 찾기 어렵다면 측정 결과와 시도한 내용을 정리해 DBA나 팀원과 함께 분석하겠습니다. 변경 후에는 조회 결과가 기존과 같은지 확인하고 응답 시간과 DB 부하를 다시 비교하겠습니다.

### Q11. AI를 사용하면 해결할 수 있지 않나요?

- AI의 제안 = 가설/초안. 사실·정합성 확인은 개발자 책임.
- 빌드/정적 분석/단위·통합 테스트/실제 로그·실행 계획·성능 수치로 검증.
- 민감 정보, 고객 데이터, 비밀번호 등은 허용된 보안 정책에 맞게 처리.
- RAG는 **검색 증강 생성**이고, 'LLM을 학습시켰다(파인튜닝했다)'와는 다르다. 직접 구축한 범위만 말해야 함.

**[개선 답변]**
> 네, AI를 활용해 병목의 원인과 가능한 해결 방안을 찾아볼 수 있습니다. 제가 잘 모르는 분야라면 AI의 답변을 검토할 근거부터 확인하겠습니다. 예를 들어 제안한 SQL과 인덱스의 동작을 공식 문서와 실행 계획으로 살펴보고, 테스트 환경에서 기존 결과와 일치하는지, 응답 시간과 DB 부하는 어떻게 달라지는지 비교하겠습니다. 판단이 어려운 부분은 팀원이나 DBA와 논의한 뒤 운영 반영 여부를 결정하겠습니다.

**[녹음 확인 | 추가 질문]** 쿼리나 소스 코드를 직접 작성하는지도 물었다.

**[녹음 확인 | 내 답변]** 나만의 온톨로지·RAG·LLM을 구축하고, 틀을 기반으로 코딩한다는 취지로 답했다.

**[복기]** 질문에는 직접 작성하는 범위를 먼저 답하고, AI를 어떤 단계에서 활용하며 결과를 어떻게 검토하는지 설명한다. Markdown으로 자료와 개념을 정리한 경험과 검색 시스템이나 모델을 직접 구축한 경험은 실제 수행 범위를 확인해 표현한다.

**[개선 답변 예시 — 직접 작성하는 경우]**
> 네. 요구사항에 맞춰 SQL과 코드를 직접 작성하고 수정합니다. AI는 기존에 정리한 자료를 바탕으로 구현 방향이나 코드 초안을 검토할 때 활용합니다. 제안된 내용은 제가 흐름과 결과를 확인하고 테스트한 뒤 적용합니다.

**[면접 복기 | 내 답변]** 전자정부프레임워크와 통신사 쪽 별도 프레임워크, Spring Boot 기반 환경 등 경험을 이야기함. **통신사 프레임워크의 정확한 이름은 이름은 추가 확인 필요**.

**[평가]** 사용 경험을 말했으나 Spring/Boot, 내장 톰캣, DI 등 동작 원리까지 짧게 부연할 수 있으면 더 좋다.

- Bean: Spring IoC 컨테이너가 생성·등록·관리하는 객체.

### Q13. Java 1.8과 Java 11의 차이는?

**[면접 복기 | 내 답변]** 버전별 특정 클래스 지원 여부 등 차이가 있었던 것으로 기억하지만, 자세히는 기억나지 않는다고 답함.

**[평가]** 주력 언어의 버전 차이를 설명할 준비가 부족했다. 면접 후 확인한 결과, **실무 프로젝트에서 사용한 버전은 모두 JDK 1.8**이었다. Java 11과 17은 면접 이후 학습한 내용이다.

**[공부: Java 8·11·17의 차이]**

Java 1.8과 Java 8은 같은 버전을 가리킨다. 아래는 각 버전에서 사용할 수 있는 대표 기능을 비교한 것이다. Java 11과 17의 항목에는 이전 버전에서 도입되어 해당 버전에서도 사용 가능한 기능이 포함된다.

| 버전 | 대표 기능과 변화 | 실무에서 생각할 점 |
|---|---|---|
| Java 8 | 람다, Stream API, `Optional`, `java.time` 날짜·시간 API | 컬렉션 처리와 날짜 계산을 간결하게 작성할 수 있다. Stream 병렬 처리는 작업 특성과 공유 상태를 고려해야 한다. |
| Java 11 | Java 9의 모듈 시스템과 컬렉션 팩터리, Java 10의 지역 변수 타입 추론 `var`, Java 11의 표준 HTTP Client와 `String.isBlank()` 등 | JDK 8에서 이동할 때 JAXB 등 JDK에서 빠진 구성 요소와 라이브러리 호환성을 확인한다. |
| Java 17 | `switch` 표현식, 텍스트 블록, `record`, `instanceof` 패턴 매칭, `sealed` 클래스 사용 가능 | 간결한 데이터 표현과 타입 제한이 가능하다. `record` 등은 17 이전에 정식 도입됐으며, 17에서 새로 도입된 기능은 아니다. |

Java 8·11·17은 모두 LTS 버전으로 널리 사용된다. 다만 실제 지원 기간과 업데이트 제공 조건은 JDK 배포판과 공급사 정책에 따라 다르다.

**[말하기 연습]**
> 실무에서는 모든 프로젝트에서 Java 1.8을 사용했습니다. Java 8에서는 람다와 Stream, 새로운 날짜·시간 API가 대표적입니다. 이후 Java 11까지 모듈 시스템과 `var`, 표준 HTTP Client 등이 추가됐고, Java 17에서는 `record`, 텍스트 블록, `sealed` 클래스 같은 기능도 사용할 수 있습니다. 11과 17은 실무 사용 경험이 아니라 면접 이후 공부한 내용입니다.

> 버전 업그레이드 시에는 기능 차이 외에도 프레임워크·라이브러리 지원 버전, 제거된 API와 실제 애플리케이션 테스트를 확인해야 한다.

### Q14. CentOS와 Ubuntu의 차이는?

**[면접 복기 | 내 답변]** 디렉터리 구조나 배포 주체가 다를 수 있고, CentOS가 실무 호환성 면에서 유리하다고 들었다고 설명.

**[평가]** 정확도가 낮음. Linux **배포판 계열과 패키지 관리**를 먼저 말해야 한다. CentOS가 일반적으로 Ubuntu보다 '호환성이 무조건 좋다'는 식으로 말하면 부정확하다.

**[저자 확인 | 사용 경험]** CentOS, Fedora, Ubuntu 환경을 모두 경험했다. 프로젝트 기록에는 통신사 연동 시스템의 CentOS, 전세사기 피해자 지원 시스템의 Fedora, 클라우드 빌링 플랫폼의 Ubuntu가 각각 개발 환경으로 정리돼 있다. 배포판별로 직접 수행한 명령과 관리 범위는 추가 확인한다.

**[공부 | 배포판 비교]**

| 구분 | CentOS | Fedora | Ubuntu |
| --- | --- | --- | --- |
| 계열 | Red Hat 계열 | Red Hat 계열 | Debian 계열 |
| 패키지 형식 | RPM | RPM | DEB |
| 패키지 관리 | 버전에 따라 `yum` 또는 `dnf` | `dnf` | `apt` |
| 설치 명령 예시 | `sudo dnf install nginx` | `sudo dnf install nginx` | `sudo apt install nginx` |
| 특징 | 기존 CentOS Linux는 RHEL 기반 재구축 배포판이며 CentOS Stream은 RHEL 개발에 앞서 변경 사항을 반영한다. | Fedora 프로젝트가 개발하는 배포판으로 새로운 기술을 비교적 빠르게 반영한다. | Debian을 기반으로 하며 일반 릴리스와 장기 지원(LTS) 릴리스가 있다. |

명령어는 대표적인 예시이며 실제 CentOS의 버전과 저장소 설정을 확인해야 한다. [CentOS Linux와 Stream의 차이](https://www.centos.org/cl-vs-cs/), [CentOS Stream 소개](https://www.centos.org/centos-stream/), [Ubuntu 패키지 관리](https://ubuntu.com/server/docs/how-to/software/package-management/)

**[말하기 연습]**

> CentOS, Fedora, Ubuntu 환경을 모두 경험했습니다. CentOS와 Fedora는 Red Hat 계열로 RPM 패키지를 사용하고, Ubuntu는 Debian 계열로 DEB 패키지를 사용합니다. 패키지를 설치할 때 CentOS와 Fedora에서는 버전에 따라 yum이나 dnf를 사용하고 Ubuntu에서는 apt를 사용합니다. 또 CentOS는 기존 CentOS Linux와 CentOS Stream의 관계가 다르기 때문에 실제 서버의 배포판과 버전, 지원 기간을 확인하겠습니다.

**[꼬리 질문 대비]**

- `rpm`·`dpkg`는 패키지의 설치 상태 등을 관리하는 도구이고, `dnf`·`apt`는 저장소에서 패키지와 의존성을 찾아 설치·갱신하는 도구다.
- 세 배포판 모두 Linux 커널을 사용하며 `ssh`, `systemctl` 같은 도구도 활용할 수 있다. 실제 설정과 사용 가능 여부는 설치된 구성에 따라 확인한다.
- 배포판 이름만으로 특정 명령을 직접 수행한 경험까지 단정하지 않는다.

## 4. 오늘 면접에서 부족했던 부분 — 우선순위 학습 로드맵

### 최우선 A: Java `parallelStream`과 DB 성능 개선을 정확히 분리

**학습 목표:** `parallelStream()`을 썼다는 설명을 넘어, *무엇을 병렬화했고 왜 빨라졌는지* 재현 가능한 근거를 말하기.

**핵심 개념**

```java
// 예제는 개념 설명용. 실제 사용자 프로젝트 코드가 아님.
List<Long> inputs = List.of(1L, 2L, 3L);
List<Long> results = inputs.parallelStream()
    .map(x -> expensiveCpuCalculation(x))
    .toList();
```

- `parallelStream()`은 **스트림에 적용된 요소별 연산을 병렬 처리**하는 API다.
- 내부적으로 일반적으로 공용 `ForkJoinPool`을 사용하며, 순서 보장·공유 상태·스레드 안전성·작업 크기에 주의해야 한다.
- `ArrayList` 조회 결과를 `parallelStream`으로 후처리하는 것과 **여러 SQL을 병렬 호출**하는 것은 다르다.
- 네트워크 I/O나 DB 커넥션이 병목이면 스레드를 늘려도 더 느려질 수 있다.

**복기 실습:** 실제 서비스 메서드에서 `parallelStream()`이 호출되는 **앞뒤 20~30줄**을 찾아서 다음을 기록한다.

```text
실제 입력 자료형:
스트림 각 요소의 의미:
map/filter/forEach 내부 연산:
내부에서 DB 접근 여부:
트랜잭션 및 스레드 안전성:
전후 시간/테스트 조건 (기록: 약 480,000ms → 10,000ms 이내, DB 전체 테스트 데이터 100만 건, API 호출부터 응답 완료까지):
개선 효과가 있었던 이유:
```

### 우선순위 B: SQL 튜닝의 기술적 근거

**학습 목표:** 'Full Scan이라 인덱스 추가'에서 끝나지 않고 **어느 조건이 왜 비효율적이고 어떤 수정이 효과를 냈는지** 말하기.


**30초 말하기 템플릿**
> 운영 환경에서는 먼저 장애 영향도를 확인하고 관련 로그·지표를 수집하겠습니다. SQL 실행 계획과 애플리케이션 처리 시간을 나눠 병목을 좁히겠습니다. 위험한 변경은 검증 없이 적용하지 않고, 필요하면 수집한 정보를 바탕으로 관련 담당자와 협의하겠습니다. 조치 후에는 정상화 여부와 재발 가능성을 확인하겠습니다.

## 7. 이번 면접을 다음 면접 준비에 반영하는 방법

### 실전 답변 5단계

> **상황(문제가 뭐였는가) → 원인(왜 발생했나) → 직접 조치(내가 무엇을 했나) → 검증(어떻게 확인했나) → 성과(숫자와 한계)**

**예: GW 경험을 40~60초로 말할 때**
> 원천·응용 시스템의 고도화 시점과 데이터 구조가 달라 PK 중복, 컬럼 길이 초과, 매핑 누락 같은 연동 오류가 반복됐습니다. 저는 GW 오류 메시지와 메타데이터를 바탕으로 유형과 원인을 분석하고, 일일 집계·파트별 조치 가이드를 담당 운영자들에게 공유했습니다. 담당 파트에서 조치한 뒤에는 GW 모니터링으로 재확인하는 과정을 지속했고, 그 결과 주간 연동 오류가 약 70건에서 5건으로 줄어드는 데 기여했습니다.

**면접관이 '직접 코딩한 것은?'이라고 물으면:**
> 컬럼 길이 불일치 사례에서는 MS949와 UTF-8의 바이트 길이 차이를 고려해, 업무 담당자와 데이터 잘림의 영향도를 협의한 후 연동 구간의 Java 문자열 매핑 로직을 수정했습니다. 원천 데이터는 보존하고 대상 시스템으로 연동할 때만 길이를 조정했습니다. 실제 구현의 문자/바이트 기준은 원본 코드 확인 후 정확히 설명하겠습니다.

**중요한 표현 원칙**
- 본인이 직접 한 코딩·분석과 다른 파트가 조치한 데이터 수정을 구분한다.
- `parallelStream`으로 'DB 쿼리가 자동 병렬화되었다'고 단정하지 않는다.
- '업무상 상세 데이터의 길이 제한을 허용했다'고 설명하지, '데이터 유실은 문제없다'고 일반화하지 않는다.
- 모르는 기술은 범위를 명시하고, 무엇을 확인하겠다고 말한다.
