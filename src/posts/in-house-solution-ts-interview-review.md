2026년 11월 23일 자사 솔루션 TS 직무 1차 면접을 마친 뒤 질문과 답변을 정리했다. 면접에서 말한 내용은 기억을 바탕으로 요약했으며, 평가와 개선 답변, 사후 학습은 구분했다. 확인되지 않은 내용은 추가 확인이 필요하다.

## 1. 1차 면접 개요: 실제로 무엇을 평가했나

**큰 흐름:** 자기소개 → TS 업무 이해·고객 대응 적합성 → 학력·경력 및 이직 사유 → Java/DB/성능 개선 기술 검증 → AI 활용 → 프레임워크/Java 버전/OS 지식 → 역질문.

**핵심 발견:** 준비했던 'GW 연동 오류 93%'와 '알림톡 민원 30%'는 **자기소개에서 언급되었으나**, 면접에서는 그 구현을 깊게 묻지 않았다. 대신 **데이터 조회 성능 약 48배 개선, `parallelStream`, SQL 튜닝, 운영 중 성능 문제 대처, Java 버전과 Linux 배포판**을 상세히 물었다.

**TS팀에 관해 면접관이 설명한 내용([면접 복기]):**
- 고객사 약 **130곳**에 설치되어 운영 중인 자사 솔루션을 지원한다는 설명.
- 고객사 장애 대응, 기술지원, 정기점검, 유선·이메일·현장 방문 등 **고객 접점 커뮤니케이션**이 중요.
- 장기간 파견하는 SI 형태라기보다 고객사에 필요할 때 방문하는 방식.
- 고객사별 주 담당자를 두되, 문제 해결이 어렵다면 **파트장 및 파트 내 팀원**의 도움을 받을 수 있음.
- 기술지원·트러블슈팅이 중심이고 **신규 개발 비중은 상대적으로 적다**는 취지.
- 서울 밖 고객사 출장 가능; 자차 필수는 아니며 교통비 지원.
- '6개월 수습'에 대한 면접관의 설명은 **계약직 후 전환에 가까운 것으로 알고 있다는 비확정 답변**. **인사팀에 서면 확인 필요**.

> **직무 선택 관점 메모:** 이 직무는 Java 백엔드 신규 기능 개발 중심의 커리어를 원할 때와 솔루션 기술지원·장애 대응 역량을 쌓을 때 각각 장단점이 다르다. 실제 배정 고객, 개발 참여 범위, 야간/주말 장애, 출장 빈도 및 처우는 별도 확인해야 한다.

## 2. 실제 면접 질문·지원자 답변·피드백 (시간순)

### Q01. 자기소개해 주세요.

**[복습 질문]** '93%'가 전체 시스템 장애 감소인가, 특정 기준의 주간 연동 오류 건수인가? 수치를 설명할 때 지표 정의도 말할 수 있는가?

### Q03. 고객 접점 소통이 많은 업무인데 잘 맞습니까?

**[면접 복기 | 내 답변]** GW 운영 당시 약 **20명**의 담당자들과 협의해 오류를 줄였고, 실무 담당자와 조율한 경험이 있어 적응할 수 있다고 설명.

**[평가]** 좋았던 부분. 막연한 친화력 강조가 아니라 **역할·규모·성과**를 연결했다.

**[더 나은 답변]**
> 네. 고객 대응은 단순히 친절하게 설명하는 것뿐 아니라, 기술적 원인을 업무 담당자가 실행할 수 있는 조치로 바꾸는 과정이라고 생각합니다. 저는 GW 연동 오류를 분석해 약 20명의 운영 담당자에게 파트별 조치 내용을 안내하고, 처리 결과를 재확인하는 체계를 운영했습니다. 고객사 장애에서도 영향도를 먼저 확인하고 기술 분석·진행 상황 공유·해결 확인까지 책임 있게 대응하겠습니다.

### Q04. 사이버대학교에 진학한 이유는? 이전 하드웨어 업무는?

**[면접 복기 | 내 답변]** 특성화고 졸업 후 일찍 취업해 컴퓨터 하드웨어 AS, 조립, 프린터 교체 등 고객지원 업무를 경험. 이후 학위 필요성과 컴퓨터 분야에 대한 관심으로 일을 병행하며 사이버대학에 진학. 이력서에는 개발과 직접 관련이 적어 초기 하드웨어 경력을 적지 않았다고 설명.

**[평가]** 학업·경력 선택의 맥락이 자연스럽다. TS 직무에서는 초기 AS 경험도 **현장 고객 응대 역량**으로 연결할 수 있다.

**[개선 답변]**
> 특성화고 졸업 후 컴퓨터 AS 엔지니어로 일하면서 고객 불편을 직접 듣고 문제를 해결했습니다. 이후 실무 경험을 쌓는 동시에 전공 지식을 체계적으로 배우고자 일을 병행하며 학위를 취득했습니다. 초기 하드웨어 지원 경험은 개발과 직접 연관성이 낮아 이력서에서는 비중을 줄였지만, 고객의 문제를 직접 듣고 해결하는 TS 업무와는 맞닿아 있다고 생각합니다.

### Q05. 이직이 잦고 재직 기간이 짧은 이유는? 협업에서 어떤 문제가 있었습니까?

**[면접 복기 | 내 답변]** 파트를 혼자 담당하는 경험이 많았고, 단독 문제 해결 능력은 얻었지만 동료와 함께 기술적 의사결정과 성장을 할 기회가 적었다. 팀원들과 프로젝트를 협업했던 약 4개월의 SI 경험은 성장 체감이 컸고, 앞으로는 협업 환경에서 일하고 싶다는 취지. 면접관은 '선임에게 질문했는데 잘 답변받지 못한 것인가' 등으로 구체화함.

**[평가]** 진솔함은 강점. 다만 **'혼자 맡는 업무가 싫다/누가 도와줘야 한다'**는 인상으로 해석되지 않도록 주의. TS도 고객별 담당자가 책임지고 해결하는 일이 많다.

**[개선 답변]**
> 이전 직장에서는 한 파트를 주도적으로 맡아 장애 분석과 업무 조율을 수행하면서 독립적인 문제 해결 능력을 키웠습니다. 다만 복잡한 이슈일수록 기술적인 관점을 공유하고 서로 검토하는 환경이 더 좋은 해결책을 만드는 데 도움이 된다는 점도 느꼈습니다. 앞으로는 맡은 고객사 문제에 책임감을 갖되, 필요할 때 동료와 효과적으로 협업하는 조직에서 더 성장하고 싶어 지원했습니다.

**[추가 복습]** '도움 요청'과 '책임 회피'의 차이를 구분해 말하기: **본인이 원인과 영향부터 파악 → 시도와 근거 정리 → 적절한 시점에 에스컬레이션 → 해결 여부 검증.**

### Q07. 데이터 조회 응답시간 약 48배 개선은 어떻게 했습니까?

**[면접 복기 | 내 답변]** 기존 프로젝트 고도화 과정에서 10만 건 테스트에서는 지연이 크게 보이지 않았으나 100만 건 수준 데이터에서는 API 성능이 떨어짐. Oracle의 `PARALLEL` 힌트에 대한 인식을 바탕으로 DB 병렬화 방법을 떠올렸으나 당시 사용 DB에서 적용법을 잘 몰랐음. Java **`parallelStream`**을 검색해 Service/비즈니스 계층의 로직에 적용했으며, 데이터를 분할·병렬 처리하면 빨라진다고 설명. 면접관은 '정확히 어떻게?'를 재차 질문함.

**[평가 — 가장 큰 기술 리스크]**
- **DB 쿼리 자체를 병렬 수행한 것인지**, **쿼리 결과를 받은 후 Java 메모리에서 후처리만 병렬화한 것인지** 설명이 섞여 있다.
- `parallelStream()`은 **원칙적으로 Java Stream 요소의 연산을 병렬화**한다. 자동으로 DB 쿼리를 여러 개의 병렬 쿼리로 바꿔주는 기능이 아니다.
- `parallelStream` 내부에서 DB 쿼리를 실행했다면 **스레드 안전성, DB 커넥션 풀, 트랜잭션 경계, DB 부하**를 확인해야 하며, 무조건 개선된다고 할 수 없다.
- 원본 로직과 병렬화한 정확한 단위, 측정 도구는 추가 확인이 필요하다. **없는 구조를 만들어 답하면 안 된다.**

**[공부: 구분해야 할 구조]**

```text
A. DB 병렬 쿼리  : 하나의 SQL을 DB 엔진이 내부적으로 병렬 실행
B. SQL 여러 번   : 서비스가 여러 SQL을 분할 호출 (제한된 동시성 필요)
C. Java 후처리   : SQL 결과를 수신한 뒤 CPU 작업을 parallelStream()으로 병렬 실행
```

**[다음 면접 답변 뼈대 — 실제 코드 확인 후 채우기]**
> 당시 데이터가 약 [10만→100만] 건으로 늘면서 [구체적 API]의 응답 시간이 크게 증가했습니다. 먼저 [시간이 오래 걸린 구간]을 확인했고, 해당 구간에서 [실제로 병렬화한 작업]을 Java `parallelStream()`으로 처리했습니다. 적용 전후 같은 조건에서 [측정값]을 비교해 개선을 확인했습니다. 다만 `parallelStream`이 DB SQL 자체를 병렬 실행시키는 것은 아니며, 제가 병렬화한 것은 정확히 [작업 유형]입니다.

**[확인 필요 — 집에서 원본 코드로 검증]**
1. DB에서 먼저 모든 데이터를 읽었는가, 아니면 각 스트림 요소가 DB를 조회했는가?
2. `parallelStream()`에 전달한 리스트의 각 요소는 무엇인가? (고객, 날짜, 키, 요청, 결과 데이터 등)
3. 병렬화된 작업이 CPU 연산인지, I/O(쿼리/API 호출)인지?
4. 트랜잭션과 JDBC/MyBatis 세션은 스레드마다 어떻게 관리되었는가?
5. 실제 측정 시간·데이터 크기·부하 테스트 조건은?

### Q08. 다른 성능 개선 방법은 검토했습니까?

**[면접 복기 | 내 답변]** 일정이 촉박했고, 여러 사람에게 질문한 뒤 가장 부담이 적게 적용할 수 있다고 판단한 방식을 선택.

**[평가]** 의사결정의 맥락은 있으나 '다른 대안'을 구체적으로 비교하지 못했다.

**[공부: 일반적인 대안 — 당시 검토했다고 주장하면 안 됨]**
- `EXPLAIN`/실행 계획으로 병목 지점 식별.
- 불필요한 데이터 조회 축소, 조건절 개선, 필요한 컬럼만 선택, 페이지네이션.
- 인덱스 적합성 점검, 쿼리 재작성, N+1 문제 여부 확인.
- 애플리케이션 병목이면 데이터 구조/알고리즘 최적화, 캐시 적합성 검토.
- 병렬화는 **측정 후** 선택하고 과도한 동시성을 피함.

**[연습용 답변]**
> 당시에는 일정 제약 때문에 적용 가능한 방안 중 병렬 처리를 선택했습니다. 다시 같은 문제를 맡는다면 먼저 SQL 실행 계획과 API의 구간별 처리 시간을 측정해 병목이 DB인지 서비스 로직인지 분리하고, 불필요한 조회나 인덱스·쿼리 문제를 먼저 검토하겠습니다. 그다음 병렬화가 실제로 유리한 구간인지 판단하겠습니다.

### Q09. 슬로우 쿼리·인덱스 튜닝은 어떻게 했습니까?

**[면접 복기 | 내 답변]** CUBRID Manager에서 쿼리 실행 계획을 확인해 Full Scan 및 인덱스 미사용 구간을 살펴봤고, AI 도구로 도움을 받아 인덱스 추가 또는 조건 정리 등을 적용했다고 설명. DBA 전문가는 아니라는 점도 언급.

**[평가]** 도구와 접근 경로는 설명했으나 **어떤 조건·인덱스가 왜 효과가 있었는지** 근거가 부족했다.

**[공부: 실행 계획 핵심]**
- **Table/Full Scan**: 테이블 범위 전체를 읽는 방식. 데이터 크기·선택도·테이블 크기에 따라 오히려 적절할 수도 있다.
- **Index Scan**: 인덱스로 후보 행을 탐색. 항상 Full Scan보다 빠르지는 않다.
- **선택도**: 조건으로 걸러지는 행의 비율. 복합 인덱스의 선두 컬럼 및 조건 패턴이 중요.
- **검증**: 실행 계획 변화뿐 아니라 실제 응답시간, 읽은 행 수, 부하 등을 가능한 동일한 조건에서 비교.

**[실전 설명 구조]**
> 문제가 된 SQL의 실행 계획을 확인했더니 [구체적 테이블/조건]에서 [병목]이 확인됐습니다. 그래서 [인덱스 또는 SQL 변경]을 적용했고, 변경 후 실행 계획과 처리 시간을 비교해 효과를 확인했습니다. AI 도구는 가설을 찾는 보조 수단으로 사용했고 최종 적용 여부는 제가 검증했습니다.

### Q10. 튜닝을 해도 느리면? 운영 서비스라면 어떻게 대응?

**[면접 복기 | 내 답변]** 경험한 범위에서는 튜닝 후 속도가 개선됐으나, 여전히 느리다면 데이터를 분할해 조회/분산 처리하는 방안을 생각. 운영 상황에서 답이 나오지 않으면 상급자에게 도움을 요청하겠다고 응답.

**[평가]** 모르는 것을 인정한 점은 좋지만, **운영 우선순위와 에스컬레이션 기준**을 설명하지 못했다.

**[공부: 운영 장애 대응의 기본 흐름]**
1. 영향 범위 파악: 어떤 고객/기능/시간대, 오류율·지연시간, 최근 배포/데이터 증가.
2. 안전 확보: 롤백 가능한지, 임시 우회 가능한지, 리소스 고갈 위험이 있는지.
3. 증거 수집: 앱 로그·APM·DB 실행 계획·락/커넥션·CPU/메모리.
4. 원인별 대응: SQL/인덱스/애플리케이션 로직/동시성/인프라를 구분.
5. 관련자 공유·에스컬레이션: 이미 확인한 사실, 재현 조건, 영향도, 시도한 조치와 위험을 묶어서 전달.
6. 조치 후 회귀 확인 및 재발 방지 기록.

**[다음 면접 답변]**
> 운영 중이라면 우선 고객 영향도와 지연이 발생한 범위를 파악하겠습니다. 로그와 DB 지표를 통해 병목이 SQL인지 애플리케이션인지 확인하고, 안정성이 검증된 조치부터 적용하겠습니다. 즉시 해결이 어렵거나 위험도가 높다면 확인한 근거와 대안을 정리해 상급자·DBA와 함께 결정하고, 조치 후에는 정상 복구를 검증하겠습니다.

### Q11. AI로 개발하나요? AI 결과를 어떻게 검증합니까?

**[면접 복기 | 내 답변]** AI 사용 경험이 많다고 설명. 모르는 분야에서 AI가 제시한 코드가 적합한지 **검증해야 하는 부담**을 느꼈다고 언급. 개인적으로 LLM과 지식 저장소, 온톨로지/RAG와 유사한 검색 환경을 만들어 활용하는 시도도 이야기.

**[평가]** AI 결과 검증의 필요성을 이해한 점은 강점. 다만 무엇을 어떻게 검증하는지 **테스트·지표·코드 리뷰** 과정이 부족하다.

**[공부: AI 활용 답변의 핵심]**
- AI의 제안 = 가설/초안. 사실·정합성 확인은 개발자 책임.
- 빌드/정적 분석/단위·통합 테스트/실제 로그·실행 계획·성능 수치로 검증.
- 민감 정보, 고객 데이터, 비밀번호 등은 허용된 보안 정책에 맞게 처리.
- RAG는 **검색 증강 생성**이고, 'LLM을 학습시켰다(파인튜닝했다)'와는 다르다. 직접 구축한 범위만 말해야 함.

**[개선 답변]**
> AI는 분석 아이디어나 코드 초안을 얻는 데 사용합니다. 다만 그대로 반영하지는 않고, 제가 요구사항과 코드 흐름을 확인하고 테스트·로그·성능 지표로 검증한 후 적용합니다. 최근에는 개인 학습 내용을 검색 가능한 형태로 정리하는 실험도 하고 있습니다.

### Q12. 어떤 프레임워크를 사용했습니까?

**[평가]** 사용 경험을 말했으나 Spring/Boot, 내장 톰캣, DI 등 동작 원리까지 짧게 부연할 수 있으면 더 좋다.

### Q13. Java 1.8과 Java 11의 차이는?

**[면접 복기 | 내 답변]** 버전별 특정 클래스 지원 여부 등 차이가 있었던 것으로 기억하지만, 자세히는 기억나지 않는다고 답함.

**[평가]** 주력 언어의 버전 차이를 설명할 준비가 부족했다. 면접 후 확인한 결과, **실무 프로젝트에서 사용한 버전은 모두 JDK 1.8**이었다. Java 11과 17은 면접 이후 학습한 내용이다.

**[공부: Java 8·11·17의 차이]**

Java 1.8과 Java 8은 같은 버전을 가리킨다. 아래는 각 버전에서 사용할 수 있는 대표 기능을 비교한 것이다. Java 11과 17의 항목에는 이전 버전에서 도입되어 해당 버전에서도 사용 가능한 기능이 포함된다.

| 버전 | 대표 기능과 변화 | 실무에서 생각할 점 |
|---|---|---|
| Java 8 | 람다, Stream API, `Optional`, `java.time` 날짜·시간 API | 컬렉션 처리와 날짜 계산을 간결하게 작성할 수 있다. Stream 병렬 처리는 작업 특성과 공유 상태를 고려해야 한다. |
| Java 11 | Java 9의 모듈 시스템과 컬렉션 팩터리, Java 10의 지역 변수 타입 추론 `var`, Java 11의 표준 HTTP Client와 `String.isBlank()` 등 | JDK 8에서 이동할 때 JAXB 등 JDK에서 빠진 구성 요소와 라이브러리 호환성을 확인한다. |
| Java 17 | `switch` 표현식, 텍스트 블록, `record`, `instanceof` 패턴 매칭, `sealed` 클래스 사용 가능 | 간결한 데이터 표현과 타입 제한이 가능하다. `record` 등은 17 이전에 정식 도입됐으며, 17에서 새로 도입된 기능은 아니다. |

Java 8·11·17은 모두 LTS 버전으로 널리 사용된다. 다만 실제 지원 기간과 업데이트 제공 조건은 JDK 배포판과 공급사 정책에 따라 다르다.

**[말하기 연습]**
> 실무에서는 모든 프로젝트에서 Java 1.8을 사용했습니다. Java 8에서는 람다와 Stream, 새로운 날짜·시간 API가 대표적입니다. 이후 Java 11까지 모듈 시스템과 `var`, 표준 HTTP Client 등이 추가됐고, Java 17에서는 `record`, 텍스트 블록, `sealed` 클래스 같은 기능도 사용할 수 있습니다. 11과 17은 실무 사용 경험이 아니라 면접 이후 공부한 내용입니다.

> 버전 업그레이드 시에는 기능 차이 외에도 프레임워크·라이브러리 지원 버전, 제거된 API와 실제 애플리케이션 테스트를 확인해야 한다.

### Q14. CentOS와 Ubuntu의 차이는?

**[면접 복기 | 내 답변]** 디렉터리 구조나 배포 주체가 다를 수 있고, CentOS가 실무 호환성 면에서 유리하다고 들었다고 설명.

**[평가]** 정확도가 낮음. Linux **배포판 계열과 패키지 관리**를 먼저 말해야 한다. CentOS가 일반적으로 Ubuntu보다 '호환성이 무조건 좋다'는 식으로 말하면 부정확하다.

**[공부]**

| 구분 | CentOS 계열 | Ubuntu |
|---|---|---|
| 계열 | RHEL 계열 | Debian 계열 |
| 패키지 | RPM | DEB |
| 패키지 관리자 | `yum` 또는 `dnf`(버전별) | `apt` |
| 예시 | `dnf install nginx` | `apt install nginx` |
| 주의 | 기존 CentOS Linux와 CentOS Stream은 구분 필요 | LTS 버전의 지원 정책과 일반 릴리스가 다름 |

**[말하기 연습]**
> 두 운영체제 모두 Linux 배포판이지만 CentOS는 RHEL 계열, Ubuntu는 Debian 계열입니다. 대표적으로 패키지 관리 방식이 달라 CentOS 계열은 RPM과 yum/dnf를, Ubuntu는 DEB와 apt를 사용합니다. 실무에서 배포·운영할 때는 패키지 설치 방식과 버전별 지원 정책을 확인하겠습니다.

## 4. 오늘 면접에서 부족했던 부분 — 우선순위 학습 로드맵

### 최우선 A: Java `parallelStream`과 DB 성능 개선을 정확히 분리

**학습 목표:** `parallelStream()`을 썼다는 설명을 넘어, *무엇을 병렬화했고 왜 빨라졌는지* 재현 가능한 근거를 말하기.

**핵심 개념**

```java
// 예제는 개념 설명용. 실제 사용자 프로젝트 코드가 아님.
List<Long> inputs = List.of(1L, 2L, 3L);
List<Long> results = inputs.parallelStream()
    .map(x -> expensiveCpuCalculation(x))
    .toList();
```

- `parallelStream()`은 **스트림에 적용된 요소별 연산을 병렬 처리**하는 API다.
- 내부적으로 일반적으로 공용 `ForkJoinPool`을 사용하며, 순서 보장·공유 상태·스레드 안전성·작업 크기에 주의해야 한다.
- `ArrayList` 조회 결과를 `parallelStream`으로 후처리하는 것과 **여러 SQL을 병렬 호출**하는 것은 다르다.
- 네트워크 I/O나 DB 커넥션이 병목이면 스레드를 늘려도 더 느려질 수 있다.

**복기 실습:** 실제 서비스 메서드에서 `parallelStream()`이 호출되는 **앞뒤 20~30줄**을 찾아서 다음을 기록한다.

```text
실제 입력 자료형:
스트림 각 요소의 의미:
map/filter/forEach 내부 연산:
내부에서 DB 접근 여부:
트랜잭션 및 스레드 안전성:
전후 시간/테스트 조건 (기록: 약 480,000ms → 10,000ms 이내, DB 전체 테스트 데이터 100만 건, API 호출부터 응답 완료까지):
개선 효과가 있었던 이유:
```

### 우선순위 B: SQL 튜닝의 기술적 근거

**학습 목표:** 'Full Scan이라 인덱스 추가'에서 끝나지 않고 **어느 조건이 왜 비효율적이고 어떤 수정이 효과를 냈는지** 말하기.

**복기 실습:** 실제로 튜닝한 쿼리 하나에 대해 다음을 적기.

```text
문제 화면/API:
지연 시간(전/후):
대상 테이블 데이터 규모:
실행 계획(전):
변경 SQL/인덱스:
실행 계획(후):
검증 방식 및 부작용:
```

### 우선순위 C: 운영 장애 해결의 우선순위

**학습 목표:** '상급자에게 물어본다' 앞에 **영향 파악과 근거 수집**을 붙여서 책임감 있게 답하기.

**30초 말하기 템플릿**
> 운영 환경에서는 먼저 장애 영향도를 확인하고 관련 로그·지표를 수집하겠습니다. SQL 실행 계획과 애플리케이션 처리 시간을 나눠 병목을 좁히겠습니다. 위험한 변경은 검증 없이 적용하지 않고, 필요하면 수집한 정보를 바탕으로 관련 담당자와 협의하겠습니다. 조치 후에는 정상화 여부와 재발 가능성을 확인하겠습니다.

### 우선순위 D: 주력 기술의 기본기

**꼭 설명할 수 있을 정도로 복습**
- Java 8·11·17의 변화와 `Stream`의 지연 연산/병렬 스트림 주의점.
- CentOS/RHEL 계열과 Ubuntu/Debian 계열의 패키지 관리 차이.
- Spring IoC, Bean, DI, Spring Boot와 Spring Framework 차이.
- REST API·JDBC/MyBatis·트랜잭션의 기본 동작.

### 우선순위 E: 이직 사유와 TS 업무 수용성

**학습 목표:** '혼자 일하기 어려웠다' 대신 **독립적 책임 + 필요한 협업**을 함께 설명하기. 신규 기능 개발 비중이 낮고 대면 지원 비중이 높은 직무를 정말 원하는지도 스스로 판단하기.

## 5. 면접관의 추가 질문을 재현한 실전 연습 카드

> **연습 규칙:** 답변을 먼저 말하고, 막히면 정답을 확인한다. 한 번에 하나씩 연습한다.

1. **48배 성능 개선**: 어떤 코드가 느렸고, `parallelStream`이 DB 조회와 어떤 관계였나요?
2. **대안 탐색**: 병렬 처리 외에 SQL 튜닝이나 조회량 축소는 왜 선택하지 않았나요?
3. **운영 상황**: 배포 이후 조회가 30초씩 걸리면, 고객·개발·DBA 중 누구에게 무엇을 먼저 전달하나요?
4. **SQL**: 실행 계획에서 인덱스를 사용하지 않는다고 해서 무조건 인덱스를 추가해도 되나요?
5. **AI**: AI가 만든 SQL 튜닝 코드는 어떤 테스트를 통과해야 운영에 반영하나요?
6. **Java**: Java 8과 Java 11의 차이를 두 가지 말해보세요. Java 17에서 사용할 수 있는 언어 기능에는 무엇이 있나요?
7. **Linux**: 운영 서버에 Nginx를 설치할 때 CentOS와 Ubuntu의 명령어·패키지가 어떻게 다른가요?
8. **TS 적합성**: 고객사가 장애로 항의하는 중인데 즉시 해결이 어렵다면 어떻게 대응할 건가요?
9. **이직 이유**: 이번 TS 업무도 고객별로 혼자 맡는 일이 많을 텐데 괜찮겠습니까?
10. **고객 협업**: GW 오류 해결에서 본인과 담당 파트 운영자의 역할은 각각 무엇이었습니까?

## 6. 성과별 '내가 한 일'과 '확인할 일' 구분

| 성과 | 면접에서 언급한 내용 | 다음 연습 전에 검증할 항목 |
|---|---|---|
| GW 주간 연동 오류 약 93% 감소 | 일일 집계·파트별 보고 체계, 20명 내외 운영자 협업 | 70→5건의 지표 정의·기간, 메타데이터/오류 테이블 분석, 직접 개발한 매핑 로직과 운영 개선의 기여 구분 |
| 알림톡 자동 발송·민원 문의 약 30% 감소 | 메시징 솔루션 활용 자동 발송 | 전송 요청 DATA 적재와 실제 발송 성공(LOG) 구분, 민원 감소 집계 근거 |
| 조회 응답 약 48배 개선 | 데이터량 증가 후 Service 계층 `parallelStream` 적용 | 실제 병렬화 단위, DB 사용 위치와 측정 조건 |
| CUBRID SQL 개선 | 실행 계획·인덱스 확인, AI를 활용해 수정 | 쿼리·인덱스 변경 내역, 전후 실행 계획과 응답시간 |

> **중요:** 위 표의 오른쪽은 **현재 확인되지 않은 사항**이다. '확인할 일'을 마치 이미 했던 일처럼 말하지 않는다.

## 7. 이번 면접을 다음 면접 준비에 반영하는 방법

### 실전 답변 5단계

> **상황(문제가 뭐였는가) → 원인(왜 발생했나) → 직접 조치(내가 무엇을 했나) → 검증(어떻게 확인했나) → 성과(숫자와 한계)**

**예: GW 경험을 40~60초로 말할 때**
> 원천·응용 시스템의 고도화 시점과 데이터 구조가 달라 PK 중복, 컬럼 길이 초과, 매핑 누락 같은 연동 오류가 반복됐습니다. 저는 GW 오류 메시지와 메타데이터를 바탕으로 유형과 원인을 분석하고, 일일 집계·파트별 조치 가이드를 담당 운영자들에게 공유했습니다. 담당 파트에서 조치한 뒤에는 GW 모니터링으로 재확인하는 과정을 지속했고, 그 결과 주간 연동 오류가 약 70건에서 5건으로 줄어드는 데 기여했습니다.

**면접관이 '직접 코딩한 것은?'이라고 물으면:**
> 컬럼 길이 불일치 사례에서는 MS949와 UTF-8의 바이트 길이 차이를 고려해, 업무 담당자와 데이터 잘림의 영향도를 협의한 후 연동 구간의 Java 문자열 매핑 로직을 수정했습니다. 원천 데이터는 보존하고 대상 시스템으로 연동할 때만 길이를 조정했습니다. 실제 구현의 문자/바이트 기준은 원본 코드 확인 후 정확히 설명하겠습니다.

**중요한 표현 원칙**
- 본인이 직접 한 코딩·분석과 다른 파트가 조치한 데이터 수정을 구분한다.
- `parallelStream`으로 'DB 쿼리가 자동 병렬화되었다'고 단정하지 않는다.
- '업무상 상세 데이터의 길이 제한을 허용했다'고 설명하지, '데이터 유실은 문제없다'고 일반화하지 않는다.
- 모르는 기술은 범위를 명시하고, 무엇을 확인하겠다고 말한다.
